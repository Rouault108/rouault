# 検索機能仕様書

> [!WARNING]
> 本文書は移行過程の旧仕様整理です。現行の正本は [`docs/search-specification.md`](../search-specification.md) であり、shared `search-core` 導入後は本書より新仕様書と現行実装を優先してください。

## 1. 文書の目的

本書は、Rouault における検索機能の振る舞い、入出力契約、状態遷移、URL 契約、検索結果生成規則、およびフォールバック戦略を整理し、実装・保守・改修時の基準とするための仕様書です。

本書は現行実装と関連文書を基に再構成したものであり、特に以下を対象とします。

- グローバル検索ダイアログ
- `/search` 検索結果ページ
- `/tags/<tag>/` タグ起点の検索ページ
- 検索クエリ前処理
- Pagefind 検索アダプタ
- 補助検索カタログ
- URL 状態の正規化と同期
- 遷移処理

---

## 2. 用語

### 2.1 検索ダイアログ

ヘッダー等から起動する即時移動用の検索 UI。少数の候補を高速に提示し、選択したノートへ直ちに遷移させることを目的とします。

### 2.2 検索結果ページ

`/search` に配置される検索 UI。検索結果を一覧比較しながら、タグ絞り込みおよび並び順変更を行うことを目的とします。

### 2.3 タグページ

`/tags/<tag>/` に配置される、特定タグを初期選択した検索結果ページの派生形です。

### 2.4 補助検索カタログ

`/search-catalog.json` として配信される軽量検索用データです。Pagefind の本文検索だけでは拾いにくい `path`、`slug` 由来語、補助キーワードを補完します。

### 2.5 genre / tag

検索 UI 上では `genre` をユーザー向けに「タグ」として扱います。本仕様書でも UI 表現としては「タグ」を用いますが、内部データ源は `genre` です。

### 2.6 検索アダプタ

`pagefindSearchAdapter` を指します。Pagefind の有無や失敗を吸収し、共通の検索結果構造を返す責務を持ちます。

---

## 3. 機能の全体像

検索機能は、共通のクエリ前処理を基盤として、二つの利用文脈に分かれます。

1. **検索ダイアログ**
   - 目的は「素早く候補を探して移動すること」です。
   - Pagefind の検索結果と補助検索カタログの検索結果をマージして表示します。
   - タグフィルターや並び順切り替えは持ちません。

2. **検索結果ページ**
   - 目的は「一覧比較しながら絞り込み、読む対象を決めること」です。
   - キーワード、タグ、並び順を組み合わせて検索します。
   - URL と状態を同期し、戻る / 進む操作に追随します。

3. **タグページ**
   - 目的は「特定タグを入口に検索結果ページを再利用すること」です。
   - 初期状態のみ異なり、検索機能の本体は検索結果ページに準拠します。

---

## 4. 対象画面と責務

## 4.1 グローバル検索ダイアログ

### 目的

- ユーザーが現在の閲覧文脈を大きく崩さずに目的のノートへ移動できること。
- 少量の入力で適切な候補を即座に提示すること。

### 起動方法

- `open-search-dialog` カスタムイベント
- `Cmd+K` または `Ctrl+K`

### 起動抑止条件

- フォーカス対象が `input`、`textarea`、または `contenteditable` な要素である場合、ショートカット起動してはなりません。

### 選択時の振る舞い

- 候補選択時は `ui-search-dialog-selected` に含まれる URL を用いて遷移します。
- 遷移は `navigateToUrl()` を経由して行います。

### 検索ソース

- Pagefind
- 補助検索カタログ

### 表示対象

- タイトル
- URL / path
- 必要に応じたキーワード

### 非対象

- タグ選択 UI
- 並び順切り替え UI
- 結果本文の詳細比較

---

## 4.2 検索結果ページ

### 目的

- 検索結果を一覧として比較可能にすること。
- キーワードとタグの AND 条件で絞り込めること。
- URL を状態表現として使い、再訪・共有・ブラウザ履歴に耐えること。

### 構成要素

- 検索入力フィールド
- 件数表示
- 並び順セレクト
- タグフィルターパネル
- 結果一覧
- ローディング表示
- エラー表示
- 空状態表示

### 結果カード表示項目

- path
- title
- date（存在する場合）
- excerptHtml または description

### 遷移

- 通常クリック時は SPA ナビゲーションを優先します。
- 修飾キー付きクリック、非左クリック、既定抑止済みイベントは通常リンク動作を妨げません。

---

## 4.3 タグページ

### 目的

- タグ起点で検索結果ページを再利用すること。

### 契約

- 単一タグを初期選択した状態で検索結果ページ相当の UI を表示します。
- 初期状態以外の振る舞いは検索結果ページと同一でなければなりません。

---

## 5. データソース仕様

## 5.1 Pagefind インデックス

### 役割

- 本文全文検索の主検索源です。
- title、description、date、genre をメタデータ / フィルター / ソートキーとして扱います。

### 前提

- Pagefind モジュールは `/pagefind/pagefind.js` から読み込まれます。
- モジュールロード後に `basePath: '/pagefind/'` が設定されます。

### 利用機能

- `search(term, { filters, sort })`
- `filters()`

### 期待される検索結果構造

各結果から少なくとも以下を再構成できること。

- `url`
- `title`
- `description`
- `date`
- `excerptHtml`

### フィルター契約

- タグフィルターは `genre` キーに対して適用します。
- 複数タグ選択時は `genre` フィルターに複数値を渡します。

### ソート契約

- `date-desc` 選択時のみ `date: 'desc'` を指定します。
- `relevance` では明示的な sort 指定を行いません。

---

## 5.2 補助検索カタログ

### 役割

- グローバル検索ダイアログにおける Recall を補強します。
- Pagefind 不在時または Pagefind 失敗時の検索フォールバックにも利用します。

### 配信形式

`/search-catalog.json`

### 項目契約

各項目は以下の構造を持ちます。

- `title: string` 必須
- `url: string` 必須
- `path: string` 必須
- `description?: string`
- `date?: string`
- `keywords?: string[]`
- `genres?: string[]`

### 正規化契約

- 空文字は削除対象です。
- `title`、`url`、`path` のいずれかが空である項目は採用してはなりません。
- `url` と `path` には検索結果 URL 正規化を適用します。
- `keywords` と `genres` は空要素除去済み文字列配列として扱います。

---

## 6. クエリ前処理仕様

## 6.1 目的

日本語検索、および空白なし検索語に対するマッチング性能を安定化させることを目的とします。

## 6.2 正規化

検索クエリは `normalizeSearchQuery()` により以下を満たさなければなりません。

- 連続空白を 1 個の半角空白に畳み込む
- 前後空白を除去する

## 6.3 トークン化

`Intl.Segmenter('ja', { granularity: 'word' })` が利用可能な場合、語単位で分割します。

### トークン化規則

- 空トークンは除外する
- `isWordLike === false` のセグメントは除外する
- 大文字小文字を区別しない重複除去を行う
- 表示保持用の `rawQuery` と、検索投入用の `segmentedQuery` を分離する

### フォールバック

`Intl.Segmenter` が利用できない場合、正規化済みクエリを空白分割した結果をトークンとして扱います。

## 6.4 生成物

`prepareSearchQuery()` は次を返します。

- `rawQuery`: UI 上の正規化済みクエリ
- `segmentedQuery`: Pagefind へ渡す分かち書き済みクエリ
- `tokens`: 重複除去済みトークン列

---

## 7. URL 仕様

## 7.1 URL 状態構造

検索結果ページの URL 状態は以下で表現します。

- `q`: 検索クエリ
- `tag`: 0 個以上のタグ
- `sort`: 並び順

## 7.2 並び順

許可される値は次の二つです。

- `relevance`（既定）
- `date-desc`

未定義値は `relevance` に正規化しなければなりません。

## 7.3 タグ

- 空白のみのタグは除外しなければなりません。
- 同一タグの重複は除去しなければなりません。
- タグの順序は選択順を維持します。

## 7.4 URL 生成

`buildSearchHref()` は次の規則に従います。

- クエリが空なら `q` を付与しない
- タグごとに `tag` を追加する
- `sort` が既定値 `relevance` の場合は `sort` を付与しない
- 条件が空なら `/search` を返す

### 例

- `/search`
- `/search?q=foo`
- `/search?tag=math`
- `/search?q=foo&tag=math&sort=date-desc`

## 7.5 タグ URL

`buildTagHref(tag)` は `/tags/<tag>/` を返します。タグ値は URL エンコードしなければなりません。

---

## 8. 検索結果ページの状態遷移

## 8.1 初期化

初期表示時は次を行います。

1. 現在 URL から `q`、`tag`、`sort` を読む
2. 内部状態へ反映する
3. 検索を実行する
4. 履歴の `popstate` を監視する

## 8.2 入力更新

検索入力更新時は以下の順序で処理します。

1. 入力値を内部状態へ反映する
2. `history.replaceState()` で URL を更新する
3. 150 ms の debounce で検索を再実行する

## 8.3 タグ更新

タグ追加・削除時は以下の順序で処理します。

1. タグ配列を正規化する
2. `history.pushState()` で URL を更新する
3. 直ちに検索を再実行する

## 8.4 並び順更新

並び順変更時は以下の順序で処理します。

1. 値を `relevance | date-desc` に正規化する
2. `history.pushState()` で URL を更新する
3. 直ちに検索を再実行する

## 8.5 履歴復元

`popstate` 発生時は URL から状態を再読込し、再検索しなければなりません。

## 8.6 同時実行制御

- 検索要求ごとに request token を採番します。
- 遅れて返った旧リクエストの結果は破棄しなければなりません。

---

## 9. 検索結果ページの検索仕様

## 9.1 入力条件

検索アダプタは以下を入力として受けます。

- `query: string`
- `selectedGenres: readonly string[]`
- `sortMode: 'relevance' | 'date-desc'`

## 9.2 検索条件

- キーワードとタグは AND 条件として扱います。
- タグは `genre` フィルターに対応します。

## 9.3 空クエリ時の扱い

- クエリ空かつタグ未選択の場合、検索アダプタは結果 0 件を返してよいものとします。
- このとき UI は「キーワードまたはタグで絞り込めます」の空状態を表示します。

## 9.4 結果構造

各検索結果は以下の構造とします。

- `title: string`
- `url: string`
- `path: string`
- `excerptHtml: string`
- `description: string`
- `date: string`

## 9.5 件数

- `total` は検索全体の件数です。
- `genreCounts` は現在条件下でのタグ別件数です。
- `allGenreCounts` は検索語に対して利用可能なタグ別件数であり、フィルターパネルの選択肢表示に使います。

## 9.6 フィルターパネル

### 表示規則

- 選択中タグは常に先頭側で視認できるようにしなければなりません。
- 未選択タグは件数降順、同件数時タグ名昇順で並べます。
- 件数 0 の未選択タグは無効状態にします。
- 選択済みタグは件数 0 でも表示を保持します。

### フィルター内検索

- タグ一覧の検索はタグ名に対する部分一致で行います。
- 大文字小文字は区別しません。

---

## 10. 検索ダイアログの検索仕様

## 10.1 目的

検索ダイアログは「候補提示から遷移までの速度」を最優先にし、本文全文検索と path / keyword ベース検索を統合して候補を返します。

## 10.2 検索フロー

1. `pagefindSearchAdapter.search(query, [], 'relevance')` を開始する
2. `getSearchCatalog()` を開始する
3. 両者を並列実行する
4. Pagefind 結果をダイアログ候補へ変換する
5. 補助カタログ結果をダイアログ候補へ変換する
6. URL 単位でマージする
7. 再ランキングして返す

## 10.3 Pagefind 結果の扱い

Pagefind 由来候補には `pagefindBacked: true` を付与します。

## 10.4 補助カタログ検索条件

補助カタログ検索は以下のいずれかを満たす項目を一致とみなします。

- `rawQuery` が `title`、`path`、`description`、`keywords` の部分文字列に一致する
- 全トークンが `title`、`path`、`description`、`keywords` のいずれかに含まれる
- いずれかのトークンが厳密語として一致する

## 10.5 path 由来語の生成

`path` は次の規則で検索語へ分解します。

- URL デコード可能ならデコード後文字列を使う
- `/ ? # & = . _ : -` で分割する
- さらに `-` で分割する
- 空要素を除去する
- 重複除去する

## 10.6 候補マージ

- マージ単位は URL です。
- 同一 URL の候補は統合します。
- 説明文は長い方を優先します。
- 日付は新しい方を優先します。
- キーワードは重複除去して統合します。
- `pagefindBacked` はどちらか一方でも true なら true とします。

## 10.7 再ランキング規則

ダイアログ候補は次の優先順位で昇順ソートします。

1. `title === rawQuery`
2. `title startsWith rawQuery`
3. 全トークンが title に含まれる
4. いずれかのトークンが厳密語として一致する
5. 全トークンが `title | path | description | keyword` のどれかに含まれる
6. `pagefindBacked === true`
7. `title` または `path` に `rawQuery` 部分一致
8. `description` または `keyword` に `rawQuery` 部分一致
9. その他

同順位時は以下で安定化します。

1. 日付降順
2. title 昇順（`localeCompare('ja')`）
3. path 昇順（`localeCompare('ja')`）

## 10.8 失敗時の扱い

- Pagefind が失敗しても補助カタログに結果があれば検索ダイアログは継続可能でなければなりません。
- Pagefind が失敗し、かつ補助カタログにも結果がない場合はエラーとして扱います。

---

## 11. 検索アダプタのフォールバック仕様

## 11.1 Pagefind 利用可の場合

- `segmentedQuery` を検索語として Pagefind に渡します。
- タグがある場合は `genre` フィルターを付与します。
- `date-desc` の場合のみ sort を付与します。
- `filters()` から利用可能タグ件数を取得します。

## 11.2 Pagefind 利用不可または検索失敗時

検索アダプタは補助検索カタログへフォールバックしなければなりません。

### フォールバック検索規則

- クエリが空でない場合は、補助カタログ検索結果を採用します。
- タグが選択されている場合は `genres` を用いて絞り込みます。
- `date-desc` または空クエリ時は日付降順で整列します。
- `relevance` かつクエリありの場合はダイアログ用のランク順を再利用します。

### フォールバック時のタグ件数

- `allGenreCounts` はクエリ一致集合から算出します。
- `genreCounts` はタグ絞り込み後集合から算出します。

---

## 12. 遷移仕様

## 12.1 優先順

`navigateToUrl(url)` は以下の順序で遷移を試みます。

1. `app-router` 要素を取得する
2. `app-router.navigate(path)` が存在すればそれを await する
3. 存在しなければ `window.location.assign(url)` を実行する

## 12.2 契約

- ルーターが存在する環境では SPA 遷移を優先します。
- ルーターが存在しない環境でもフルページ遷移で機能しなければなりません。

---

## 13. エラー / ローディング / 空状態仕様

## 13.1 ローディング

### 検索結果ページ

- 検索中はローディング表示を出します。
- 表示文言は「検索インデックスを照会しています...」とします。

### 検索ダイアログ

- 検索中は loading 状態を保持し、対応 UI を出します。

## 13.2 エラー

### 検索結果ページ

- 失敗時は結果を空にし、エラー状態を表示します。
- 既知の `Error` はその `message` を表示し、それ以外は汎用エラーメッセージを表示します。

### 検索ダイアログ

- Pagefind 失敗のみでは即エラーにせず、補助カタログ結果があれば成功扱いにします。

## 13.3 空状態

### 検索結果ページ

- クエリ空かつタグ未選択時は「検索待ち」の空状態を表示します。
- クエリまたはタグ条件があるのに結果が 0 件のときは「一致なし」の空状態を表示します。

---

## 14. アクセシビリティ要件

## 14.1 キーボード

- 検索ダイアログはキーボードショートカットで起動できなければなりません。
- フォーム入力中はショートカットが誤発火してはなりません。
- ダイアログ内候補はキーボードで選択可能でなければなりません。

## 14.2 ラベル

- 検索入力にはプログラム上のラベルが必要です。
- 視覚的にラベルを隠す場合でもアクセシブルネームを失ってはなりません。

## 14.3 ライブリージョン

- 検索ダイアログは結果件数や状態変化を支援技術へ伝達できることが望まれます。

## 14.4 フィルターパネル

- タグフィルターの開閉状態は支援技術から把握可能でなければなりません。
- 選択済みタグの削除操作はキーボードで実行可能でなければなりません。

---

## 15. 性能要件

## 15.1 ダイアログ

- 検索ソースは並列問い合わせとします。
- 同一セッション中の補助検索カタログ読込はキャッシュし、重複取得を避けます。
- 大量候補時も一覧操作性が大きく劣化しないことを目的に、軽量描画戦略を採ります。

## 15.2 検索結果ページ

- 文字入力ごとに即時検索せず、150 ms の debounce を適用します。
- 古い検索結果で新しい検索結果を上書きしないことを優先します。

---

## 16. 非機能上の制約

- 検索体験は JavaScript 前提です。
- 非 JavaScript 環境向けの完全検索フォールバックは本仕様の対象外です。
- タグフィルターの対象軸は `genre` のみです。
- 検索ダイアログと検索結果ページは同一目的ではなく、完全に同一結果集合であることを要求しません。

---

## 17. 既知の設計判断

## 17.1 ダイアログと結果ページの差異を許容する

検索ダイアログは Pagefind に加えて補助検索カタログを使うため、`path` や `keywords` 由来の候補が出る場合があります。一方で検索結果ページは Pagefind 主体であり、同一クエリでも完全一致の結果集合にはなりません。

これは **移動支援** と **比較閲覧** が異なる目的であるため、意図的に分離された設計とします。

## 17.2 URL は検索結果ページの正規状態表現とする

検索結果ページでは内部状態ではなく URL を基準に復元できることを重視します。そのため、入力中は `replaceState`、条件変更時は `pushState` を使い分けます。

## 17.3 Pagefind 障害時は機能全停止を避ける

検索アダプタおよび検索ダイアログは補助検索カタログによる縮退運転を行います。全文検索精度は低下し得ますが、最低限の検索機能は維持します。

## 19. 仕様上の未固定事項

以下は現行仕様としては読み取れるものの、将来的には明示的に固定した方がよい事項です。

### 19.1 検索ダイアログの最大表示件数

現仕様では候補件数上限を本書で固定していません。UX と性能の両面から、将来的には最大件数とページング / 仮想化戦略を明文化する余地があります。

### 19.2 タグ複数選択時の意味論

現行実装は `genre` フィルターへ複数値を渡しますが、Pagefind 側意味論を本書で厳密固定していません。タグの複数選択を OR とみなすか、将来的に AND を選べるようにするかは別途設計判断が必要です。

### 19.3 excerptHtml の信頼境界

現仕様では Pagefind の抜粋 HTML をそのまま描画します。サニタイズ境界をどこで保証するかは、セキュリティ仕様として別文書で固定する価値があります。

### 19.4 検索ダイアログの結果表示情報

現仕様では path と title を中心に扱いますが、description や date をどの条件で UI 表示するかは、視認性とノイズ制御の観点からより厳密に定義可能です。

## 20. 受け入れ基準

以下を満たすとき、検索機能は本仕様に適合しているとみなします。

1. `Cmd+K` / `Ctrl+K` で検索ダイアログを開けること。
2. 入力欄編集中は上記ショートカットが誤発火しないこと。
3. 検索ダイアログが Pagefind と補助検索カタログを統合して候補を返すこと。
4. 同一 URL 候補が重複表示されないこと。
5. 検索結果ページが `q`、`tag`、`sort` を URL と同期すること。
6. 入力更新時は `replaceState`、タグ / 並び順更新時は `pushState` を使うこと。
7. `popstate` で検索状態が復元されること。
8. Pagefind が利用不可でも、補助検索カタログにより縮退検索が行えること。
9. タグフィルターで選択済みタグが保持され、件数 0 の未選択タグは無効表示になること。
10. 通常クリックでは `navigateToUrl()` を通じて SPA 遷移を優先すること。

---

## 21. 変更時の原則

今後の改修では次を守ることを推奨します。

- 検索ダイアログは「移動の速さ」を優先し、結果ページの UI を持ち込まない
- 検索結果ページは「比較と絞り込み」を優先し、URL 共有可能性を損なわない
- 日本語クエリ前処理は両 UI で共通化し、検索品質の差分を無用に増やさない
- Pagefind 依存を強めても、最低限の縮退運転経路は維持する
- URL、タグ、ソートの正規化規則は一箇所に集約し、UI ごとに重複実装しない

---

## 22. 設計改善方針

本章は、現状設計に対する講評を踏まえ、今後の改修で採用すべき改善方針を具体的な仕様として定めるものです。

本章の目的は、検索機能を単なる実装集合ではなく、**一貫した検索体系**として再定義することにあります。

## 22.1 改善の基本方針

今後の検索機能は、次の 3 原則に従って設計しなければなりません。

1. **検索意味論を UI から分離し、検索コアへ集約すること**
2. **ダイアログと検索結果ページの差分を、UI 目的差に限定すること**
3. **縮退運転は維持しつつ、障害の可観測性を失わないこと**

---

## 22.2 検索コアの導入

### 22.2.1 新設責務

検索機能は、`search-core` 相当の責務境界を新設し、以下を一箇所へ集約しなければなりません。

- クエリ前処理
- 検索ソース統合
- 検索結果正規化
- ランキング
- タグ件数算出
- フォールバック判定
- 障害種別の分類

### 22.2.2 UI 層との分離

- 検索ダイアログは検索コアに対して「候補検索」を要求します。
- 検索結果ページは検索コアに対して「一覧検索」を要求します。
- 両者は共通の検索ソース、共通の一致判定、共通のランキング基盤を使わなければなりません。

### 22.2.3 許容される差分

ダイアログと検索結果ページの差分として許容されるのは、以下に限ります。

- 表示件数上限
- 省略表示の有無
- フィルター UI の有無
- 並び順切り替え UI の有無
- 遷移即時性を優先するか、一覧比較を優先するかという表示戦略

### 22.2.4 禁止事項

以下の差分を UI ごとに個別実装してはなりません。

- 一致判定規則の分岐
- 検索ソース統合規則の分岐
- URL 単位マージ規則の分岐
- タグ件数算出規則の分岐
- フォールバック時ランキング規則の分岐

---

## 22.3 検索モードの明確化

### 22.3.1 モード定義

検索コアは少なくとも次の 2 モードを持たなければなりません。

- `navigate`
  - 目的は「最短で目的ノートへ移動すること」です。
  - ダイアログが使用します。

- `explore`
  - 目的は「検索結果を比較・絞り込みすること」です。
  - 検索結果ページが使用します。

### 22.3.2 モード差の意味

- `navigate` は上位候補の精度と速度を優先します。
- `explore` は結果集合の一貫性、件数整合、タグ絞り込み整合を優先します。

### 22.3.3 モード差の実装制約

モード差は **重み付け** と **件数上限** に留めなければなりません。検索対象集合そのものがモードごとに大きく変化してはなりません。

---

## 22.4 検索ソース統合の再定義

### 22.4.1 検索ソースの役割分担

検索コアは、検索ソースを次のように位置付けなければなりません。

- **Pagefind**
  - 本文、title、description、date、genre に対する主検索源
- **補助検索カタログ**
  - path、slug、補助キーワード、Pagefind 非搭載情報に対する補完検索源

### 22.4.2 補助検索カタログの地位

補助検索カタログは単なる緊急フォールバックではなく、**主検索を補完する第二検索源**として扱わなければなりません。

ただし、補助検索カタログ由来の一致は、本文一致と同等の重みとして扱ってはなりません。

### 22.4.3 推奨スコア軸

検索結果スコアは少なくとも次の軸に分解して保持することを推奨します。

- `titleExactScore`
- `titlePrefixScore`
- `titleTokenCoverageScore`
- `bodyScore`
- `pathScore`
- `keywordScore`
- `freshnessScore`
- `sourceConfidenceScore`

### 22.4.4 sourceConfidence の原則

- 本文一致または Pagefind に裏付けられた結果は高い `sourceConfidence` を与えます。
- 補助検索カタログの `path` / `keyword` のみで成立した結果は低い `sourceConfidence` を与えます。
- 同一 URL で Pagefind と補助検索カタログの両方に一致した結果は、より高い `sourceConfidence` を与えます。

---

## 22.5 ランキング規則の構造化

### 22.5.1 現行ヒューリスティックの扱い

現行の優先順位ベースのランキングは、暫定互換ルールとして維持してよいものとします。

ただし、今後の実装では「早い者勝ちの条件分岐列」として拡張してはなりません。

### 22.5.2 構造化ランキング

ランキングは、少なくとも以下の段階で構成しなければなりません。

1. **候補生成**
2. **候補正規化**
3. **候補統合（URL 単位）**
4. **特徴量算出**
5. **スコア計算**
6. **安定化ソート**

### 22.5.3 安定化ソート規則

スコア同点時は、少なくとも以下の規則で順序を安定化しなければなりません。

1. `sourceConfidence` 降順
2. 日付降順
3. title 昇順
4. path 昇順

### 22.5.4 説明可能性

検索結果には、内部デバッグ用途として少なくとも次の理由情報を保持できる構造を持たせることを推奨します。

- どのソースに一致したか
- どのフィールドに一致したか
- どの token が一致したか
- なぜ上位に来たか

本情報は本番 UI に必須ではありませんが、開発時・検証時には観測可能であることが望まれます。

---

## 22.6 タグ意味論の固定

### 22.6.1 複数タグ選択の意味論

複数タグ選択時の意味論は、**既定で OR** として固定します。

すなわち、いずれかの選択タグを持つノートを一致とみなします。

### 22.6.2 理由

- 現行実装との連続性を保ちやすいこと
- タグを入口とする探索的検索に適していること
- 個人ノートの分類密度では AND が過度に結果を減らしやすいこと

### 22.6.3 将来拡張

将来的に AND を導入する場合は、URL 状態へ明示的な演算子を追加しなければなりません。

例:

- `tagMode=or`
- `tagMode=and`

暗黙の意味論変更はしてはなりません。

### 22.6.4 UI 契約

- 既定モードは OR とします。
- UI 上で複数タグを選択した場合、「いずれかのタグに一致」と解釈されることが利用者に分かる表現を持つことが望まれます。

---

## 22.7 情報モデルの正規化

### 22.7.1 URL / path / canonical の分離

検索結果データモデルは、少なくとも次の 3 概念を分離して保持することを推奨します。

- `url`
  - 遷移に用いる URL
- `pathLabel`
  - UI 表示用の短縮 path
- `canonicalUrl`
  - 正規化と重複判定に用いる URL

### 22.7.2 重複判定

- 候補統合の主キーは `canonicalUrl` としなければなりません。
- `url` と `pathLabel` は同一であることを前提にしてはなりません。

### 22.7.3 表示契約

- UI には原則として `pathLabel` を表示します。
- 遷移には常に `url` を用います。

---

## 22.8 フォールバックと障害可観測性

### 22.8.1 維持すべき性質

- Pagefind 障害時でも検索機能全体を停止させてはなりません。
- 補助検索カタログによる縮退運転を維持しなければなりません。

### 22.8.2 追加すべき観測点

検索コアは、少なくとも次の障害区分を内部的に識別できなければなりません。

- Pagefind ロード失敗
- Pagefind 検索失敗
- Pagefind フィルター件数取得失敗
- 補助検索カタログ取得失敗
- 補助検索カタログ正規化失敗
- すべての検索ソース失敗

### 22.8.3 UI 契約

- ユーザー向け UI は必要以上に内部障害詳細を露出しなくてよいものとします。
- ただし、縮退運転中であることを開発時に観測できる仕組みを持たなければなりません。

### 22.8.4 開発時観測手段

次のいずれか、または複数を備えることを推奨します。

- `console.warn` / `console.error`
- 開発モード専用のデバッグパネル
- 計測イベント
- テスト時に参照可能な内部ステータス

---

## 22.9 Pagefind ローダー改善方針

### 22.9.1 目的

Pagefind ローダーは、CSP、キャッシュ挙動、障害切り分け容易性の観点から、現在の Blob URL 依存実装を将来的に簡素化することを推奨します。

### 22.9.2 方針

- 標準的な `import('/pagefind/pagefind.js')` で成立する環境ではそれを優先します。
- Blob URL 化は互換性確保のための限定的手段として扱います。
- Blob URL 経路を維持する場合、採用理由と前提制約を文書化しなければなりません。

### 22.9.3 非機能要件

- CSP 制約下での動作可否を検証対象に含めること
- キャッシュ挙動を確認できること
- ロード失敗時のログに URL と失敗段階を含めること

---

## 22.10 結果説明性の向上

### 22.10.1 目的

検索結果が「なぜ出たのか」を最低限説明可能にし、ノイズ混入時の調査コストを下げることを目的とします。

### 22.10.2 内部契約

各候補は、内部的に少なくとも以下の一致理由を保持できることが望まれます。

- `matchedInTitle`
- `matchedInBody`
- `matchedInPath`
- `matchedInKeywords`
- `matchedTokens`
- `matchedSources`

### 22.10.3 UI 活用

本番 UI では必須ではありませんが、以下の活用余地があります。

- ダイアログでの補助ラベル表示
- 検索結果ページでの「タイトル一致」「本文一致」等の補足表示
- 開発時の検証オーバーレイ表示

---

## 22.11 段階的移行方針

### 22.11.1 第 1 段階

既存実装を大きく崩さず、次を先に行うことを推奨します。

- タグ意味論を OR として仕様固定する
