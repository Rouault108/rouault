# アクセシビリティ

## 概要

本書は、Rouault に適用するアクセシビリティ要求事項を定義するものです。

本書は、`index.md` に記載された設計原則および Foundations に定義された設計トークンを前提とし、次の事項を規定します。

- アクセシビリティに関する設計上の基本原則
- 実装時に満たすべき要求事項
- コンポーネント単位の運用基準
- 検証時に確認すべき項目

本書に定めのない値定義は Foundations を参照します。本書は値そのものではなく、値の使用条件、適用対象、および満たすべき品質基準を規定します。

## 適用範囲および前提

### 適用範囲

本書は、`src/` 配下の Rouault UI 全体に適用します。対象は Web Components および通常 DOM により構成される UI を含みます。

### 対象読者

本書の対象読者は、次のとおりです。

- 実装者
- 設計者
- レビュー担当者

### 前提文書

本書の適用にあたり、次の文書を前提とします。

- `index.md`
- Foundations
- 各コンポーネント仕様書

### 前提環境

対象環境は最新のエバーグリーンブラウザを基本とします。非対応機能が存在する環境においても、段階的機能強化により閲覧および基本操作は成立しなければなりません。

### 非対象

次のものは、本書の直接の適用対象外とします。

- マーケティングページ
- 外部埋め込み先独自 UI
- 実験用プロトタイプ

### 文書の位置付け

各文書の役割は次のとおりです。

| 文書                   | 役割                                                       |
| ---------------------- | ---------------------------------------------------------- |
| `index.md`             | デザインシステム全体に関する理念および横断原則を定義します |
| 本書                   | アクセシビリティに関する要求事項および運用基準を定義します |
| 各コンポーネント仕様書 | 個別 UI に関する契約、例外、および補足要件を定義します     |

## 基本原則

### 1. 明瞭性優先

可読性、発見可能性、操作可能性、および状態理解可能性を優先します。これらを満たさない設計は採用しません。

### 2. ネイティブ優先

HTML の本来の意味およびブラウザの標準挙動を優先的に利用します。ARIA はネイティブ意味論の代替としてではなく、補強としてのみ用います。

### 3. 単一感覚依存の禁止

情報伝達を色、位置、hover、またはアニメーションのいずれか単独に依存させてはなりません。

### 4. 高密度 UI における操作性維持

表示密度を高める場合であっても、ヒットエリア、フォーカス視認性、および構造理解性を損なってはなりません。

### 5. 段階的機能強化

JavaScript、`backdrop-filter`、View Transitions API 等の高度機能が利用できない場合であっても、閲覧および基本操作は成立しなければなりません。

## 準拠レベルおよび達成基準

Rouault は WCAG 2.1 Level AA を最低基準とします。加えて、運用上必要な範囲において WCAG 2.2 の一部基準を採用します。

| 基準     | レベル         | 方針                                               |
| -------- | -------------- | -------------------------------------------------- |
| WCAG 2.1 | AA             | 最低保証基準です                                   |
| WCAG 2.2 | AA の一部      | Target Size、Dragging Movements 等を優先採用します |
| 運用推奨 | AAA 相当の一部 | 主としてターゲットサイズ 44×44px を採用します      |

### 重点達成基準

| 項目                   | 要求                                                         |
| ---------------------- | ------------------------------------------------------------ |
| コントラスト比         | 通常テキストは 4.5:1 以上とします                            |
| フォーカス可視性       | `:focus-visible` をすべてのインタラクティブ要素に適用します  |
| キーボード操作         | 主要フローはキーボードのみで完結可能でなければなりません     |
| ターゲットサイズ       | 最低 24×24px、推奨 44×44px とします                          |
| テキスト拡大・間隔変更 | レイアウト破綻または情報欠落を生じさせてはなりません         |
| モーション軽減         | `prefers-reduced-motion` を尊重しなければなりません          |
| 通知                   | `aria-live` は用途別に適切に使い分けなければなりません       |
| Forced Colors          | 高コントラスト環境で構造および状態を維持しなければなりません |

## 実装要求事項

### セマンティクスおよび情報構造

#### 一般要求

- 意味のある要素には、意味のある HTML 要素を使用しなければなりません。
- 見出し要素は視覚表現ではなく文書構造に基づいて選定しなければなりません。
- 支援技術上の順序と視覚上の順序は、可能な限り一致させなければなりません。

#### 必須要件

| 項目         | 要求                                                                           |
| ------------ | ------------------------------------------------------------------------------ |
| ランドマーク | `header` `nav` `main` `aside` `footer` を適切に用いなければなりません          |
| 見出し構造   | 階層を不必要に飛ばしてはなりません                                             |
| ボタン       | クリック可能な UI を `div` で代用してはなりません                              |
| ラベル       | 入力要素には視覚ラベルまたは同等の名前計算を与えなければなりません             |
| 補助説明     | 補足およびエラーは `aria-describedby` により関連付けなければなりません         |
| 装飾要素     | 意味を持たないアイコンおよび装飾は `aria-hidden="true"` としなければなりません |

#### 設計上の補足

- 見た目のみを理由としてセマンティクスを破壊してはなりません。
- Shadow DOM を用いる場合であっても、アクセシブルネーム、状態、およびロールは外部から理解可能でなければなりません。
- 意味関係の維持を優先すべき場合、Light DOM を採用しても構いません。

### キーボード操作

#### 一般要求

Rouault における主要フローは、キーボードのみで完結可能でなければなりません。

#### 必須要件

| 項目           | 要求                                                                       |
| -------------- | -------------------------------------------------------------------------- |
| タブ順序       | DOM 順に従う自然な順序を維持しなければなりません                           |
| `tabindex`     | 原則として乱用してはなりません。複合ウィジェット内部に限定します           |
| Esc            | 閉じる、戻る、またはキャンセルとして一貫した挙動を提供しなければなりません |
| Enter / Space  | ボタン、タブ、トグル等において期待どおりに動作しなければなりません         |
| フォーカス復帰 | モーダルやメニューを閉じた後、トリガーへフォーカスを戻さなければなりません |

#### 複合ウィジェット

ロービングタブインデックスを採用できるのは、原則として次に限ります。

- `tablist`
- `listbox`
- `grid`
- 同等の複合ウィジェット

この場合の操作要件は次のとおりです。

| 操作            | 要求                                     |
| --------------- | ---------------------------------------- |
| Tab / Shift+Tab | ウィジェット全体への出入りに用います     |
| 矢印キー        | 項目間移動に用います                     |
| Home / End      | 可能な場合は先頭または末尾へ移動させます |
| Enter / Space   | 選択または確定に用います                 |

#### Focus Trap

| UI                 | 要求                                                 |
| ------------------ | ---------------------------------------------------- |
| Modal / Dialog     | フォーカストラップを実装しなければなりません         |
| Dropdown / Popover | 原則としてトラップしてはなりません                   |
| Bottom Sheet       | モーダルとして扱う場合はトラップしなければなりません |

フォーカストラップの要否は、当該 UI がユーザー操作を独占するか否かに基づいて判断します。

### フォーカス表示

#### 一般要求

フォーカス表示は常に視認可能でなければなりません。

#### 使用トークン

| トークン                    | 用途           |
| --------------------------- | -------------- |
| `--focus-ring-width`        | リング太さ     |
| `--focus-ring-offset`       | 要素からの距離 |
| `--focus-ring-radius`       | 角丸           |
| `--focus-ring-color-subtle` | 移動中の色     |
| `--focus-ring-color`        | 最終強調色     |

#### 必須要件

- すべてのインタラクティブ要素に `:focus-visible` を適用しなければなりません。
- `outline: none` を代替手段なしに用いてはなりません。
- フォーカスリングが切断されるレイアウトを採用してはなりません。
- `overflow: hidden` によりリングが欠ける場合、余白、`outline-offset`、またはラッパー構造を調整しなければなりません。
- Rouault 固有の `main#main-content` は router-document 契約で管理する論理フォーカス到達先であり、この節のインタラクティブ要素向け focus-visible 契約の例外です。

#### 実装例

```css
:focus-visible {
  outline: var(--focus-ring-width) solid var(--focus-ring-color);
  outline-offset: var(--focus-ring-offset);
  border-radius: var(--focus-ring-radius);
}
```

#### Reduced Motion 時の要件

`prefers-reduced-motion: reduce` 環境では、フォーカス演出に関する遅延または変化を省略し、即時に最終状態へ遷移させます。

### ターゲットサイズ

#### 一般要求

表示上の寸法が小さい場合であっても、操作対象のヒットエリアは十分な大きさを有しなければなりません。

#### 基準

| レベル   | サイズ  | 要求                                               |
| -------- | ------- | -------------------------------------------------- |
| 最低保証 | 24×24px | 最低限満たさなければなりません                     |
| 推奨     | 44×44px | 主要インタラクションでは採用することが望ましいです |

#### 使用トークン

| トークン              | 値   | 用途                       |
| --------------------- | ---- | -------------------------- |
| `--control-min-touch` | 44px | タッチターゲット最小推奨値 |

#### 実装例

```css
.icon-button {
  position: relative;
  width: 16px;
  height: 16px;
}

.icon-button::after {
  content: '';
  position: absolute;
  inset: 50% auto auto 50%;
  width: var(--control-min-touch);
  height: var(--control-min-touch);
  transform: translate(-50%, -50%);
}
```

#### 適用対象

- 閉じるボタン
- 小型アイコンボタン
- TOC のストリップトリガー
- インライン操作ボタン
- タッチ前提 UI 全般

### コントラストおよび色の運用

#### 一般要求

色は意味を補強する目的で用いても構いませんが、意味そのものを色のみに依存させてはなりません。

#### 必須要件

| 項目             | 要求                                                            |
| ---------------- | --------------------------------------------------------------- |
| 通常テキスト     | 背景に対し 4.5:1 以上のコントラスト比を確保しなければなりません |
| 補助テキスト     | 読解に必要なものは 4.5:1 以上を確保しなければなりません         |
| UI 状態表示      | 色以外にラベル、アイコン、境界等を併用しなければなりません      |
| プレースホルダー | ラベルの代替として用いてはなりません                            |

#### 運用要件

- 本文には、保証済みの Foreground / Background 組み合わせのみを使用します。
- `--fg-subtle` を通常本文に用いてはなりません。
- 選択状態およびエラー状態は、背景色のみで表現してはなりません。
- タッチ環境において hover のみに依存した発見可能性を設計してはなりません。

#### 状態表示の例

| 状態   | 最低限必要な手がかり                                     |
| ------ | -------------------------------------------------------- |
| 選択中 | 背景または下線に加え、境界またはインジケータを併用します |
| エラー | 色に加え、メッセージおよび `aria-invalid` を付与します   |
| 警告   | 色に加え、アイコンまたは文言を付与します                 |
| 無効   | 見た目の変化に加え、操作不能状態を伝達します             |

### 文字サイズおよびテキスト間隔

#### 最小文字サイズ運用

| サイズ    | 要求                                                     |
| --------- | -------------------------------------------------------- |
| 12px 未満 | 原則として使用してはなりません                           |
| 12px      | キャプションまたは補助情報に限定します                   |
| 11px      | 例外用途に限り使用しても構いませんが、補正を必須とします |

#### 12px 以下での補正要件

12px 以下の文字サイズを使用する場合、次のいずれかを適用しなければなりません。

1. Weight Boost: ウェイトを一段階上げます
2. Tracking Boost: 字間を広げます
3. High Contrast: `--fg-default` 相当へ格上げします

#### Text Spacing 要件

利用者が文字間隔等を上書きする場合であっても、内容欠落または重なりを生じさせてはなりません。

| 項目   | 基準        |
| ------ | ----------- |
| 行間   | 1.5 倍以上  |
| 段落間 | 2 倍以上    |
| 文字間 | 0.12em 以上 |
| 単語間 | 0.16em 以上 |

#### 設計上の注意

- 高さ固定のボタンまたはラベルにおいて、縦方向の文字切れを発生させてはなりません。
- `line-height: 1` を安易に使用してはなりません。
- 省略表示を採用する場合、意味喪失が許容される文脈であることを確認しなければなりません。

### モーション軽減

#### 一般要求

`prefers-reduced-motion: reduce` 環境では、装飾的アニメーションを停止し、状態理解に必要な変化のみを残さなければなりません。

#### 必須実装例

```css
@media (prefers-reduced-motion: reduce) {
  *,
  *::before,
  *::after {
    transition-duration: 0.01ms !important;
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
  }
}
```

#### 維持可能な変化

次のものは、実質瞬時であることを条件として維持しても構いません。

- フォーカス表示
- モーダルおよびドロップダウンの出現・消失
- トースト通知の出現
- 状態変化の理解に必要な最小限の切替

#### 禁止事項

- バウンス
- 振動
- 長時間の慣性表現
- 装飾目的のパララックス
- 読書中の視線を乱す背景アニメーション

### ライブリージョンおよび通知

#### 一般要求

動的更新は、視覚だけでなく音声においても理解可能でなければなりません。ただし、通知は必要最小限とし、読み上げの乱発を防止しなければなりません。

#### `aria-live` の使い分け

| 値          | 用途                             |
| ----------- | -------------------------------- |
| `off`       | 通知不要な変化                   |
| `polite`    | 重要であるが割り込み不要な通知   |
| `assertive` | 緊急性が高く即時通知を要する内容 |

#### 標準運用

| UI               | `aria-live`         | `role`                           |
| ---------------- | ------------------- | -------------------------------- |
| 成功トースト     | `polite`            | `status`                         |
| 情報トースト     | `polite`            | `status`                         |
| 警告トースト     | `assertive`         | `alert`                          |
| エラートースト   | `assertive`         | `alert`                          |
| ローディング表示 | `polite`            | `status`                         |
| 進捗通知         | 専用領域で `polite` | `progressbar` 本体に乱用しません |

#### 禁止事項

- 一般通知に `assertive` を乱用してはなりません。
- 連続更新をそのまま live region に流してはなりません。
- 表示されていない内容のみを支援技術へ過剰通知してはなりません。

### フォームおよびバリデーション

#### 一般要求

フォームは入力可能であるだけでなく、状態、エラー理由、および修正方法が理解可能でなければなりません。

#### 必須要件

| 項目     | 要求                                                         |
| -------- | ------------------------------------------------------------ |
| ラベル   | 各入力に名前を与えなければなりません                         |
| 必須項目 | 視覚表示と支援技術向け状態を一致させなければなりません       |
| エラー   | 該当フィールドと関連付けなければなりません                   |
| 無効状態 | 視覚的および意味論的の両方で伝達しなければなりません         |
| 説明文   | 必要時は `aria-describedby` により関連付けなければなりません |

#### エラー時の要求

- 入力要素に `aria-invalid="true"` を設定しなければなりません。
- エラーメッセージ要素の ID を `aria-describedby` に関連付けなければなりません。
- 必要に応じて `aria-live="polite"` を用いなければなりません。
- 色のみでエラーを伝達してはなりません。

#### 追加要件

- 視覚ラベルと読み上げラベルは、可能な限り一致させます。
- 必須項目である旨は、視覚的表示だけでなくアクセシブルネームまたは補足情報でも伝達します。

---

### ローディングおよび非同期状態

#### 一般要求

ローディング中は、処理中であることを理解可能としつつ、不要な視覚ノイズを増加させてはなりません。

#### スケルトン UI 要件

| 項目           | 要求                                                                                      |
| -------------- | ----------------------------------------------------------------------------------------- |
| スケルトン自身 | `aria-hidden="true"` としなければなりません                                               |
| 親コンテナ     | `aria-busy="true"` を設定しなければなりません                                             |
| 完了時         | `aria-busy="false"` に更新しなければなりません                                            |
| 必要時         | `aria-live="polite"` または補助テキストにより読み込み中である旨を伝達しなければなりません |

#### スピナー要件

- スピナー単独の視覚表現のみで終わらせてはなりません。
- 必要に応じて `role="status"` を付与しなければなりません。
- ボタン内スピナーにおいて、ラベル消失により意味が失われてはなりません。

#### 非同期表示閾値

短時間処理においてローディング表示を点滅させてはなりません。一定閾値を超える場合に限りローディング表示を行っても構いません。

---

### Forced Colors Mode 対応

#### 一般要求

Forced Colors Mode または高コントラスト環境において、背景色またはシャドウが失われることを前提に設計しなければなりません。

#### 必須要件

- システムカラーへのマッピングを用意しなければなりません。
- `box-shadow` のみに依存した境界表現を採用してはなりません。
- フォーカス表示は実線アウトラインにより保証しなければなりません。
- 選択状態は背景色のみで表現してはなりません。
- SVG アイコンは `currentColor` を用いることが望ましいです。

#### 実装例

```css
@media (forced-colors: active) {
  :focus-visible {
    outline: 3px solid CanvasText;
    box-shadow: none;
  }

  .card,
  .button {
    border: 1px solid CanvasText;
  }

  [aria-selected='true'],
  .active {
    outline: 2px solid CanvasText;
    outline-offset: -2px;
  }
}
```

#### 設計上の注意

- 透過ボーダーが無効化される可能性を考慮します。
- 情報構造をスペーシングのみに依存させてはなりません。
- `forced-color-adjust: none` は最後の手段としてのみ用います。

## コンポーネント別要求事項

### Dialog / Modal

- `role="dialog"` または `alertdialog` を付与しなければなりません。
- アクセシブルネームを与えなければなりません。
- フォーカストラップを実装しなければなりません。
- `Esc` により閉じることができなければなりません。
- 閉じた後、トリガーにフォーカスを戻さなければなりません。
- 背景スクロール抑止がキーボード操作を阻害してはなりません。

### Dropdown / Popover / Menu

- 不要なフォーカストラップを実装してはなりません。
- 開閉状態をトリガーと同期させなければなりません。
- 矢印キー移動を実装する場合、ロールと操作契約を一致させなければなりません。
- クリック外または `Esc` により閉じなければなりません。

### Tabs

- `tablist`、`tab`、`tabpanel` を正しく構成しなければなりません。
- 矢印キーによるタブ移動を提供しなければなりません。
- 現在選択タブに `aria-selected` を設定しなければなりません。
- 非表示パネルの扱いは一貫していなければなりません。
- URL 同期を行う場合、視覚状態とアクセシビリティ上の状態が矛盾してはなりません。

### Toast / Banner

- 情報および成功通知には `status` / `polite` を用います。
- 警告およびエラー通知には `alert` / `assertive` を用います。
- 自動消去する場合、読み取りに必要な時間を確保しなければなりません。
- 閉じる操作には明確なアクセシブルネームを与えなければなりません。

### Form Controls

- ラベル、説明、およびエラーの関連付けを保証しなければなりません。
- Disabled、Readonly、および `aria-disabled` を適切に使い分けなければなりません。
- プレースホルダーをラベルとして扱ってはなりません。

### Icon Button

- アクセシブルネームを与えなければなりません。
- 視覚サイズが小さい場合であっても、ヒットエリアを拡張しなければなりません。
- トグルである場合、押下状態を属性により伝達しなければなりません。

### Loading / Skeleton

- スケルトンは装飾として扱わなければなりません。
- 親要素に `aria-busy` を設定しなければなりません。
- 状態完了時の更新通知は必要最小限でなければなりません。

## 禁止事項

次の実装または設計を禁止します。

| 禁止事項                                      | 理由                                                 |
| --------------------------------------------- | ---------------------------------------------------- |
| `outline: none` のみを指定すること            | フォーカスが消失するためです                         |
| 色のみによる意味伝達                          | 色覚差および Forced Colors で破綻するためです        |
| `div` をボタン代替として用いること            | セマンティクスおよびキーボード挙動が欠落するためです |
| hover 前提の発見可能性                        | タッチ環境で成立しないためです                       |
| 24px 未満のヒットエリア                       | 操作困難となるためです                               |
| 12px 未満の本文相当テキスト                   | 可読性が不足するためです                             |
| `assertive` の乱用                            | スクリーンリーダー体験を損なうためです               |
| バウンスまたは振動アニメーション              | 認知負荷または前庭負荷が高いためです                 |
| 背景色のみで選択状態を表現すること            | Forced Colors で消失し得るためです                   |
| プレースホルダーをラベル代替とすること        | 入力後に意味が失われるためです                       |
| Shadow DOM 内で状態を外観のみに閉じ込めること | 支援技術へ伝達されないためです                       |

## 検証および品質保証

### 自動検証

| 手法         | 目的                                                          |
| ------------ | ------------------------------------------------------------- |
| axe-core     | WCAG 違反の自動検出を行います                                 |
| Playwright   | キーボード操作、表示崩れ、および状態変化を確認します          |
| トークン検証 | コントラスト比を保証します                                    |
| VRT          | フォーカスリング、Forced Colors、テーマ差異の回帰を検出します |

### 手動検証

| 手法               | 観点                                                 |
| ------------------ | ---------------------------------------------------- |
| キーボードのみ操作 | Tab 順序、Esc、矢印キー、フォーカス復帰を確認します  |
| スクリーンリーダー | 名前、役割、状態、および通知の妥当性を確認します     |
| Reduced Motion     | 動作停止と状態理解の両立を確認します                 |
| Forced Colors      | 境界、選択状態、およびフォーカスの可視性を確認します |
| Text Spacing       | 文字間隔変更時の破綻有無を確認します                 |
| ズーム / 拡大      | 200% 相当でも情報欠落がないことを確認します          |

### 重点確認項目

1. フォーカスリングが途切れていないこと
2. 閉じる操作後にフォーカスが喪失しないこと
3. エラー文言が読み上げ可能であること
4. 非同期更新が無通知で発生しないこと
5. 色が利用できない環境でも状態判別が可能であること
6. タッチ環境で hover 前提 UI が残存しないこと
