# Syntax Card

## 文書の目的

本書は、`ui-syntax-card` の公開契約、状態モデル、アクセシビリティ、視覚契約、および現行実装に残る未強制事項を整理するものです。

`ui-syntax-card` は、構文シグネチャと補足説明を分離し、API リファレンスや言語仕様書に近い読書体験を提供するコンポーネントです。単にコード片を囲う枠ではなく、**何を見出しとして提示するか**、**どのシグネチャをコピー対象とするか**、**詳細セクションが存在しない場合にどのように縮退するか**を公開契約として固定します。

本コンポーネントは `ui-syntax-section` と組み合わせて使うことを前提としており、構文の表面形と補足情報を同一カード上で秩序立てて提示します。Rouault における syntax card は、読み手が本文から API 記述へ一時的に移動しても集中を失わないことを重視します。したがって、本コンポーネントの契約は、**情報の切り分けの明快さ**と、**「没入して読む」ことのできるデザイン**の維持を両立する方向で定義します。

## 適用範囲

本書は、`ui-syntax-card` の次の事項を対象とします。

- 公開契約
- 状態モデル
- DOM / Accessibility
- Visual Contract
- 環境別の振る舞い

これらは上位レイヤまたは別コンポーネントの責務です。

## コンポーネントの定義

`ui-syntax-card` は、**単一の代表シグネチャと、その補足説明節群を提示する参照カード**です。

本コンポーネントの責務には、ヘッダーの描画、任意の種別タグの表示、見出しレベルの正規化、単一シグネチャの提示、コピー可能性の判定、詳細セクションの有無に応じたレイアウト切り替えを含みます。

一方で、どの言語識別子をどのスタイルへ対応付けるか、シグネチャのシンタックスハイライト、メンバー一覧の構造化、詳細テキストの意味内容の妥当性までは責務に含めません。

## 公開契約

`ui-syntax-card` は、`kind`、`name`、`lang`、`headingLevel` を公開入力として扱います。スロットは `signature` スロットと既定スロットを持ちます。既定スロットは任意ノードを受け取れるように見えますが、**公開契約上の正規入力は **``** のみ**です。

`kind` は任意入力です。空文字列の場合、種別タグは描画に参加しません。`name` はカード見出しの核であり、実運用では空文字列にしてはなりません（SHOULD NOT）。実装上は空文字列でも描画を継続しますが、空見出しを推奨契約とはしません。

`lang` は公開 property 名としては `lang` ですが、HTML 属性面では `data-lang` を用います。これは自然言語を表す HTML の `lang` 属性ではなく、**構文表示対象の言語識別子**です。値は前後空白を除去し、小文字化したうえでホストの `data-lang` 属性へ反映します。空文字列の場合、`data-lang` 属性は除去されます。

`data-lang` の値は **opaque token** として扱います。`ui-syntax-card` 自身は値集合を列挙管理せず、`ts` / `tsx` / `sql` などの妥当性検証や意味解釈も行いません。どの値をどの見た目やハイライトへ対応付けるかは、本コンポーネントの責務外です。したがって、利用者は `data-lang` の語彙を本コンポーネントの列挙契約として扱ってはなりません（MUST NOT）。

`headingLevel` は `2` から `6` までを正規値として受理します。範囲外値、小数、非整数は公開契約上の無効値であり、表示は `h4` へフォールバックします。

### 入力契約

| 名前             | 種別                                     | 必須   | 内容     | 契約                                                          |
| -------------- | -------------------------------------- | ---- | ------ | ----------------------------------------------------------- |
| `kind`         | property / attribute                   | いいえ  | 種別タグ   | 空文字列の場合は非表示です                                               |
| `name`         | property / attribute                   | 実質必須 | 見出し名   | ヘッダー見出しとコピー文脈の基準です                                          |
| `lang`         | property / attribute (`data-lang`)     | いいえ  | 言語識別子  | 前後空白を除去し、小文字化してホストへ反映します                                    |
| `headingLevel` | property / attribute (`heading-level`) | いいえ  | 見出しレベル | `2` / `3` / `4` / `5` / `6`。既定値は `4` で、範囲外は `4` へフォールバックします |

### スロット契約

| 名前          | 種別         | 位置づけ | 内容                                |
| ----------- | ---------- | ---- | --------------------------------- |
| `signature` | named slot | 正規入力 | 直接の子として単一の `<pre>` を受け取ります        |
| 既定スロット      | slot       | 正規入力 | `ui-syntax-section` を 1 件以上受け取ります |

`signature` スロットには、**直接の割り当て要素として単一の **`` を配置します。`<pre>` 内部に `<code>` を置く構成を標準とします。コピー値は `<code>` の `textContent` を優先し、`<code>` がない場合は `<pre>` 自身の `textContent` を使用します。

`signature` スロットに `<pre>` が 0 件、複数件、または空白のみのコードしか存在しない場合、コピー機能は無効化されます。これは単なる見た目の差ではなく、**カードが単一の代表シグネチャを持たない**とみなす契約です。

既定スロットの正規入力は `ui-syntax-section` のみです。`ui-syntax-section` 以外の要素を既定スロットへ配置しても、コンテンツ領域の存在判定には寄与しません。したがって、任意ノードを既定スロットへ直接置く構成には依存してはなりません（MUST NOT）。

### 派生状態契約

`ui-syntax-card` は、公開入力とは別に次の派生状態を内部で導出します。

| 状態                   | 意味        | 導出条件                                                |
| -------------------- | --------- | --------------------------------------------------- |
| `data-content-empty` | 詳細セクションなし | 既定スロットに `ui-syntax-section` が 0 件                   |
| copy enabled         | コピー可能     | `signature` スロットに有効な `<pre>` がちょうど 1 件あり、抽出コードが空でない |
| copy disabled        | コピー不可     | 上記以外                                                |

`data-content-empty` は公開入力ではなく、実装が導出するホスト属性です。利用者はこの属性を手動で与えて状態を制御してはなりません（MUST NOT）。

### 動的更新契約

`ui-syntax-card` は初期描画時だけでなく、公開入力またはスロット内容の変更後も派生状態を再評価します。

| 変更対象                 | 再評価される契約                 |
| -------------------- | ------------------------ |
| `name`               | コピー操作ラベル                 |
| `lang` / `data-lang` | 正規化済みホスト属性               |
| `signature` スロット     | コピー可否、コピー値、コピーラベル        |
| 既定スロット               | `data-content-empty` の有無 |

したがって、利用者は `ui-syntax-card` を静的な初期化専用コンポーネントとして扱う必要はありません。後から `name`、`lang`、`signature`、`ui-syntax-section` 群を差し替えた場合でも、契約上の状態は更新後の入力に追従します。

### 属性反映契約

| property       | attribute       | reflect | 備考                                   |
| -------------- | --------------- | ------- | ------------------------------------ |
| `kind`         | `kind`          | なし      | Lit の通常 property / attribute 変換に従います |
| `name`         | `name`          | なし      | Lit の通常 property / attribute 変換に従います |
| `lang`         | `data-lang`     | 実質あり    | 更新時に小文字化してホスト属性へ同期します                |
| `headingLevel` | `heading-level` | なし      | 範囲外値は描画時に `4` として解決します               |

とくに `lang` は通常の reflect 指定ではなく、更新時同期で `data-lang` へ反映されます。属性値の正規化は公開契約に含まれます。

## 状態モデル

`ui-syntax-card` の主要状態は、**シグネチャを持つか**、**詳細セクションを持つか**、**コピー可能か**、**見出しをどの階層で公開するか**によって読み分けます。

### 1. 基本状態

最小状態は、`name` を持ち、`signature` スロットに単一の `<pre>` を持ち、既定スロットに `ui-syntax-section` を持たない状態です。このときカードは、**シグネチャのみの参照カード**として振る舞います。

### 2. 種別タグ状態

`kind` が非空文字列である場合、ヘッダー左側に種別タグを描画します。`kind` は情報分類の補助であり、見出し本文の代替ではありません。`kind` を与えても `name` の責務は置き換わりません。

### 3. 見出しレベル状態

`headingLevel` は見出しの文書階層を制御します。`2` から `6` まではそのまま `h2` から `h6` へ対応付けます。範囲外値は `h4` へ縮退します。したがって、本コンポーネントは文書内での見出し階層を親文脈に合わせて調整できますが、**無効値をそのまま DOM へ反映することはしません**。

### 4. コピー状態

コピー状態は `signature` スロットの構成から導出します。

| 条件                       | 状態            |
| ------------------------ | ------------- |
| `<pre>` が 1 件あり、抽出コードが非空 | copy enabled  |
| `<pre>` が 0 件            | copy disabled |
| `<pre>` が複数件             | copy disabled |
| `<pre>` は 1 件だがコードが空白のみ  | copy disabled |

copy disabled 時は `ui-copy-button` に `disabled` が伝播し、`aria-disabled="true"` と `tabindex="-1"` を持ちます。利用者は、コピー可能性を外部から直接上書きしてはなりません（MUST NOT）。

### 5. コンテンツ状態

既定スロットに `ui-syntax-section` が 1 件以上ある場合、詳細コンテンツ領域を表示します。0 件の場合は `data-content-empty` を付与し、詳細コンテンツ領域を非表示にします。このときシグネチャ領域下端の区切り線も除去され、**カードがシグネチャ単体の終端形**になります。

### 6. コピー操作の可視状態

コピー操作は常時露出しません。ホバーまたは `focus-within` のときに可視化します。ただし、`hover: none` かつ `pointer: coarse` 環境では、タッチ操作前提のため常時半透明で表示します。これは discoverability とノイズ抑制の折衷です。

## DOM / Accessibility

ルートは `:host` です。Shadow DOM 内部には、ヘッダー、シグネチャ領域、コンテンツ領域を持ちます。

```text
<ui-syntax-card>
  #shadow-root
    <header class="header">
      [span.kind-tag]
      <h2-h6 class="name">...</h2-h6>
      <ui-copy-button class="copy-action"></ui-copy-button>
    </header>
    <div class="signature-area">
      <slot name="signature"></slot>
    </div>
    <div class="content-area">
      <slot></slot>
    </div>
</ui-syntax-card>
```

`ui-syntax-card` 自体は対話主体ではありません。対話要素はヘッダー内の `ui-copy-button` のみです。したがって、カード全体に button / region などの対話ロールを付与する設計には依存しません。

### Accessibility 契約

アクセシビリティ上の重要点は次のとおりです。

- 見出しは必ず `h2` から `h6` のいずれかで描画します。
- `headingLevel` が不正でも、見出し要素は `h4` として維持します。
- コピー不能状態では、コピー操作は `disabled`、`aria-disabled="true"`、`tabindex="-1"` となり、キーボード到達性を持ちません。
- `ui-syntax-section` は内部で `section[aria-labelledby]` を用い、ラベルとセクション本文を関連付けます。
- `kind` は補助ラベルであり、見出し構造そのものではありません。

`ui-syntax-section` の見出し要素は `p.section-title` です。これは文書アウトライン上の追加見出しではなく、**カード内部の補助ラベル**として扱います。したがって、詳細セクションの階層を文書全体の見出し構造へ参加させることを目的としません。

### `ui-syntax-section` 契約

`ui-syntax-section` は `ui-syntax-card` の既定スロットで使用することを前提とした補助コンポーネントです。

| 名前      | 種別                   | 必須 | 内容          | 契約                |
| ------- | -------------------- | -- | ----------- | ----------------- |
| `label` | property / attribute | はい | セクション見出しラベル | 空文字列は推奨しません       |
| 既定スロット  | slot                 | はい | セクション本文     | 任意の説明コンテンツを受け取ります |

`ui-syntax-section` は自前で一意な見出し ID を生成し、`section` に `aria-labelledby` を設定します。利用者はこの ID 生成規則に依存してはなりません（MUST NOT）。

`ui-syntax-section` の責務は、**ラベルと本文を 1 セクションとして束ねること**にあります。本文の詳細レイアウトまでは一律に保証しません。段落（`p`）は既定の内側余白を持ちますが、`dl`、`ul`、表、独自要素などは子要素側のレイアウト責務を前提とします。したがって、利用者は「どの要素を入れても同じ内側余白になる」ことを期待してはなりません（MUST NOT）。

## Visual Contract

`ui-syntax-card` の視覚契約は、構文情報を**ヘッダー / シグネチャ / 詳細**の 3 層に分離して読む秩序を作ることにあります。

### 情報順位

- `kind` は分類情報です。
- `name` はカードの主題です。
- `signature` は主題の表面形です。
- `ui-syntax-section` 群は補足情報です。

この順序は視覚的にも保たれます。ヘッダーは種別と名称をまとめ、シグネチャは罫線で区切られた独立領域に置き、詳細は余白を広く取り、縦方向に積みます。

### レイアウト

ルートは block 要素です。幅は `--ui-syntax-card-breakout-width`、インライン余白は `--ui-syntax-card-breakout-margin` で調整できます。これにより、本文カラムより広いブレークアウト表示も可能です。

ヘッダーは横並びの flex で構成し、コピー操作は右端へ寄せます。シグネチャ領域は横スクロールを許可し、長いコードでもカード幅を破壊しません。詳細領域は縦方向の flex で、セクション間に一貫したギャップを取ります。

### 視覚仕様

- ルートは境界線と小さな角丸を持つカードです。
- `kind` は小さな大文字風タグとして表示します。
- `name` はモノスペース系の見出しとして表示します。
- コピー操作は通常時に隠れ、必要なときのみ現れます。
- `data-content-empty` 時は詳細領域を消し、シグネチャ領域の下罫線も消します。

### 参照トークン

本コンポーネントは、主として次のトークンに依存します。

| 用途      | トークン                                              |
| ------- | ------------------------------------------------- |
| カード幅    | `--ui-syntax-card-breakout-width`                 |
| カード余白   | `--ui-syntax-card-breakout-margin`                |
| 境界線     | `--border-width` / `--border-default`             |
| 背景色     | `--bg-default`                                    |
| 既定文字色   | `--fg-default`                                    |
| 控えめ文字色  | `--fg-muted`                                      |
| 角丸      | `--radius-sm`                                     |
| 余白      | `--space-*`                                       |
| フォントサイズ | `--text-xs` / `--text-sm` / `--text-base`         |
| フォント    | `--font-mono` / `--font-semibold` / `--font-bold` |
| 行高      | `--line-height-normal` / `--line-height-relaxed`  |
| トランジション | `--duration-normal` / `--ease-out`                |
| 非活性不透明度 | `--opacity-disabled` / `--opacity-link-touch`     |

`ui-syntax-card` は `::part(...)` を公開していません。したがって、外部スタイル拡張は CSS Custom Properties とホスト単位の配置調整に限定します。内部 class 名や Shadow DOM 構造に依存してはなりません（MUST NOT）。

## 環境別の振る舞い

### Touch / Coarse Pointer

`hover: none` かつ `pointer: coarse` 環境では、コピー操作を常時利用可能状態で表示します。これは、ホバーに依存した discoverability を避けるためです。

### Forced Colors

`forced-colors: active` 環境では、カード境界線、ヘッダー下罫線、シグネチャ下罫線、種別タグ、コピー操作の可視境界を `CanvasText` ベースで補強します。`ui-syntax-section` 側でもセクションタイトル色を `CanvasText` へフォールバックします。

### Print

`@media print` では、カード背景を透明化し、コピー操作を非表示にします。印刷時もシグネチャと詳細テキスト自体は残します。したがって、本コンポーネントは**印刷時に意味を保持する静的資料**として扱います。

## 関連契約

### `ui-copy-button` 連携契約

`ui-syntax-card` はコピー操作の UI と実コピー処理を `ui-copy-button` に委譲します。`ui-syntax-card` 側の責務は、**何をコピー対象とするかを決めること**に限定されます。

| 条件           | `ui-copy-button` への反映                             |
| ------------ | ------------------------------------------------- |
| 有効なシグネチャ 1 件 | `value` に抽出コード、`label` に文脈付きコピーラベルを渡します           |
| `name` が空    | 一般的なコピーラベルへ縮退します                                  |
| `name` が非空   | `name` を含む文脈付きコピーラベルを生成します                        |
| コピー不能        | `disabled`、`aria-disabled="true"`、`tabindex="-1"` |

コピーラベルの具体的な文言は、アクセシビリティ要件とローカライズ方針に従って将来調整され得ます。ただし、``** がある場合に対象名を含む文脈付きラベルを生成すること**、および ``** が空の場合に一般ラベルへ縮退すること**は公開契約として維持します。

### `ui-syntax-section` 連携契約

`ui-syntax-card` は既定スロットに `ui-syntax-section` が存在するかどうかだけを見て、詳細領域の有無を決定します。さらに、`ui-syntax-section` の**入力順をそのまま表示順として保持**します。ラベル内容に基づく自動並べ替えや意味解釈は行いません。

したがって、「パラメータ」「戻り値」「プロパティ」などの推奨順序が必要な場合、その順序を決める責務は利用側にあります。`ui-syntax-card` は `ui-syntax-section` の数を制限しませんが、過剰な分割で読書リズムを崩してはなりません。1 セクション 1 主題を原則とします。

### シグネチャ抽出契約

コピー対象は `signature` スロットの**直接子である単一の **`` から抽出します。ネストされた `<pre>`、ラッパー要素の内側に置かれた `<pre>`、複数の `<pre>` を許容する契約にはしていません。

また、改行は `\n` に正規化します。CRLF と CR は LF へ変換します。したがって、コピー値の行末形式に原文の改行コード保持を期待してはなりません（MUST NOT）。

ここでの契約は、**コピー対象の特定**にのみ作用します。`signature` スロット内容の表示可否とコピー可否は同一ではありません。`<pre>` 構造が不正な場合でも、スロット内容自体が表示されることはあり得ますが、コピー対象としては採用しません。

## 境界条件

### 1. `kind` なし

`kind` が空文字列の場合、種別タグは描画されません。見出しとコピー操作のみがヘッダーに残ります。

### 2. `name` あり、セクションなし

シグネチャのみのカードとして成立します。`data-content-empty` が付与され、詳細領域は非表示になります。

### 3. `ui-syntax-section` が 1 件のみ

単一セクションカードとして成立します。たとえば、「戻り値」のみ、または「プロパティ」のみの構成を許容します。

### 4. `headingLevel` 無効値

`headingLevel="9"` などの無効値は `h4` へフォールバックします。無効値エラーや描画中断は行いません。

### 5. `data-lang` 更新

`lang` / `data-lang` は更新時に小文字化してホスト属性へ再同期されます。たとえば `TS` は `ts` へ正規化されます。空文字列にした場合、属性は除去されます。

### 6. `signature` に `<pre>` がない

コピーは無効になります。`signature` スロット内容自体は表示され得ますが、コピー対象としては扱いません。

### 7. `signature` に `<pre>` が複数ある

コピーは無効になります。複数候補から自動選択は行いません。

### 8. `signature` のコードが空白のみ

コピーは無効になります。空文字列コピーは行いません。

### 9. 既定スロットに `ui-syntax-section` 以外のみがある

`data-content-empty` が付与され、詳細領域は非表示になります。既定スロットの任意ノードが自動的に可視化されることには依存できません。

### 10. `signature` に有効な `<pre>` 1 件とその他ノードが混在する

現行実装では、コピー判定は `<pre>` 要素だけを数えるため、有効な `<pre>` が 1 件であればコピーは有効になり得ます。一方で、`signature` スロットに与えたその他ノード自体はスロット描画上は残り得ます。したがって、`signature` 領域に `<pre>` 以外を混在させる構成は正規入力ではありませんが、実装上は表示とコピー可否が分離したまま成立し得ます。

### 11. 既定スロットに `ui-syntax-section` とその他ノードが混在する

現行実装では、既定スロットに `ui-syntax-section` が 1 件でも存在すれば `data-content-empty` は付与されません。そのため、`ui-syntax-section` 以外のノードも同じ既定スロットに混在している場合、詳細領域は表示状態となり、それらのノードもスロット描画上は残り得ます。これは正規入力ではありませんが、実装上は自動排除されません。

### 12. 印刷時

コピー操作は非表示になりますが、カード本体は残ります。インタラクションだけを除去し、情報は保持します。

### 13. `kind` と `name` がともに空

実装上は描画が継続し得ますが、公開契約上の正規利用とはしません。少なくとも `name` のいずれかの意味核を与えることを前提とします。

### 14. `ui-syntax-section` の `label` が空

実装上は描画され得ますが、公開契約上は非推奨です。詳細セクションには、内容の主題を識別できるラベルを与えることを前提とします。

### 15. `signature` なしで詳細のみが存在する

実装上はカードとして成立し得ますが、公開契約上の正規形は**代表シグネチャを持つこと**です。詳細のみカードを常用してはなりません（SHOULD NOT）。

## 設計上の要点

`ui-syntax-card` の要点は、コードを見せることそのものではありません。**構文の代表形を 1 つに定め、その周囲の説明を節として整列させ、必要なときだけコピー操作を表に出すこと**にあります。

したがって、今後の変更でも次の 4 点は崩さない方がよいです。

1. 見出しは常に `h2` から `h6` のいずれかで出すこと。
2. コピー対象は単一シグネチャに限定し、曖昧な複数候補を自動解決しないこと。
3. 詳細領域の正規入力は `ui-syntax-section` に限定すること。
4. 印刷時はインタラクションのみを除去し、情報本体は残すこと。

## 契約が不明瞭な箇所と長期的な明確化方針

本節は、現行実装をそのまま是認するのではなく、`ui-syntax-card` を長期的に保守しやすい設計へ寄せる観点から、なお契約が曖昧な論点を整理するものです。目的は、不明瞭な挙動を列挙することではなく、**何を公開契約として固定し、何を別コンポーネントへ切り出すべきか**を明らかにすることにあります。

### 1. `ui-syntax-card` が表す概念単位

現行実装は、`signature` スロットから直接配置された単一の `<pre>` をコピー対象として採用し、それ以外の構成ではコピーを無効化します。この挙動は、`ui-syntax-card` が本質的には**単一の代表シグネチャを提示する単位**であることを示唆しています。しかし、契約書上はまだ「シグネチャを持たないカード」や「複数シグネチャを持つカード」との境界が完全には固定されていません。

長期的には、`ui-syntax-card` を**単一の公開シグネチャと、その補足説明節群を提示する参照カード**として定義し切るのがよいです。この定義に合わない要件、たとえば overload 群、複数言語の並列表記、比較表示は、別コンポーネントへ分離する方が設計がきれいです。

### 2. `signature` なしカードを正式に許容するか

現行実装では、`signature` がなくてもカード自体は描画され得ます。しかし、コンポーネント名と責務から考えると、これは縮退表示なのか正式な variant なのかが曖昧です。

長期的には二者択一にすべきです。すなわち、``** は代表シグネチャを必須とする**か、または**signature optional の variant を正式契約として追加する**かです。保守性を優先するなら前者を採り、説明のみのカードは別概念へ切り出す方がよいです。

### 3. 多重シグネチャの扱い

複数の `<pre>` を与えた場合、現行実装はコピーを無効化するのみで、表示上の意味づけは行いません。このため、overload や variant を `ui-syntax-card` 自体で表現すべきかは未整理です。

長期的には、`ui-syntax-card` は 1 シグネチャ 1 カードに固定し、複数シグネチャは `ui-syntax-signature-list` のような上位コンポーネントで束ねる方が責務分離として明快です。`ui-syntax-card` 自身に多重シグネチャ対応を持ち込まない方が、コピー契約と見出し契約を単純に保てます。

### 4. `name` の意味

`name` は見出し本文にもコピーラベルにも使われていますが、それが**表示名**なのか**識別子**なのかはまだ固定されていません。両者を同一フィールドで兼ねる設計は初期段階では簡潔ですが、長期的には人間向け表示と機械的識別を分けたくなる可能性があります。

長期的には、少なくとも `name` を**表示上の主題名**と定義して固定し、必要になった時点で `identifier` の追加を検討する方がよいです。現時点では `name` の責務を増やし過ぎない方が保守しやすいです。

### 5. `kind` の性格

`kind` は現行では自由文字列の補助ラベルとして扱われています。しかし、将来的にこれを情報設計上の分類子として使うのか、単なる視覚補助に留めるのかは未固定です。

長期的には、`kind` を**自由テキストの補助ラベル**として定義するのが拡張性に優れます。分類語彙として統制したい場合は、列挙、未知値時の扱い、ローカライズ規則まで含めて別途定義すべきであり、中間状態のままにしない方がよいです。

### 6. `lang` 命名の不整合

公開 property 名が `lang` である一方、その意味は自然言語ではなく構文言語です。これは Web Platform の `lang` と意味が異なり、API 設計としては直感に反します。

長期的には、公開名を `syntaxLang`、`codeLang`、`sourceLang` などへ改めることを検討する価値があります。互換性維持が必要な場合でも、`lang` を将来的な deprecated alias とし、新しい意味整合的な名前へ移行する設計の方がきれいです。

### 7. `data-lang` の役割

`data-lang` は正規化されてホスト属性へ同期されますが、コンポーネント自身はその値を意味解釈しません。したがって、これが presentation hook なのか将来の統合面なのかがまだ曖昧です。

長期的には、`data-lang` を**外部スタイリングや統合のための opaque hook**として明示し、`ui-syntax-card` 自体は値意味を解釈しない方針を固定するとよいです。中途半端に意味を持たせると責務が膨らみます。

### 8. 既定スロットの型付け

既定スロットは DOM 上は open slot に見えますが、実質的には `ui-syntax-section` 専用です。このため、構文上は何でも入れられるのに、契約上は一部しか有効でないというズレがあります。

長期的には、既定スロットを**typed slot**としてより強く明記し続けるか、あるいは `sections` 相当の名前付きスロットへ改める方が誤解が少ないです。とくに長期運用では、名前付きスロットの方が誤用を減らせます。

### 9. `ui-syntax-section` の意味論

`ui-syntax-section` は自由ラベルと本文を束ねるだけで、節種別の意味づけは持ちません。このため、「パラメータ」「戻り値」「例外」「備考」といった節の型をコンポーネント側で扱うのかどうかが曖昧です。

長期的には、`ui-syntax-section` を**自由ラベル節**として割り切るのが基本です。そのうえで、デザインシステム側に推奨ラベル語彙を定める方が、コンポーネント責務を増やさずに一貫性を確保できます。

### 10. セクション順の意味

現行実装は入力順をそのまま表示順として保持します。しかし、その順序が単に保持されるだけなのか、文書設計上の意味順とどう関係するのかはまだ弱いです。

長期的には、**表示順は入力順に従う**ことを固定契約とし、意味的な推奨順序は別途ガイドラインとして定めるのがよいです。順序づけ責務をコンポーネント自身に持たせない方が、構成自由度と責務分離の両方を保てます。

### 11. セクション本文の文法

現行では `p` のみが特別扱いされ、`dl`、`ul`、表、独自要素は子要素側責務です。これは柔軟ですが、節ごとの推奨文法は未固定です。

長期的には、`Parameters` や `Properties` は `dl` 系、`Returns` や `Notes` は `p` または `ul` 系、`Examples` はコードブロック系といった**推奨内容文法**をガイドラインとして示すとよいです。ただし、これは公開契約ではなく推奨設計に留める方が保守性は高いです。

### 12. `label` の非空性と重複

`ui-syntax-section` の `label` は空でも描画され得て、重複も禁止されていません。これは初期段階では自由度がありますが、長期運用では無題節や重複節が増えやすくなります。

長期的には、少なくとも\*\*`label` 非空\*\*は公開契約として昇格させる価値があります。重複禁止までを契約に含めるかは慎重でよいですが、同一カード内の意味節として識別できることは保証した方がよいです。

### 13. カード全体のアクセシビリティ上の役割

現行実装では、`ui-syntax-card` 自体は対話主体でも landmark でもなく、見出しとコピー操作だけを持つ視覚コンテナです。この方針は妥当ですが、なぜ card 全体を region にしないのかは、まだ契約上で十分に説明していません。

長期的には、`ui-syntax-card` は**視覚レイアウトコンテナであり、対話主体でも landmark でもない**と明記するのがよいです。補助節の見出しを文書アウトラインへ参加させないことも、この方針と合わせて説明すべきです。

### 14. `headingLevel` の責務境界

`headingLevel` はカード主題見出しのみを制御し、`ui-syntax-section` 側のラベル階層には影響しません。この境界は暗黙には成立していますが、まだ十分に強く固定されていません。

長期的には、`headingLevel` を**カード主題見出し専用の階層制御**として明確化し、節ラベルはアウトライン参加を目的としない補助ラベルであることを明記しておくのがよいです。

### 15. コピー仕様の厳密さ

現行実装は `<code>` の `textContent` を優先し、なければ `<pre>` の `textContent` を採用し、改行を LF に正規化します。ただし、末尾改行の保持、前後空白の扱い、可視表示とコピー値の乖離をどこまで許すかは、なお掘り下げ余地があります。

長期的には、コピー仕様を**テキスト抽出仕様**として独立に整理する方がよいです。とくに、何を空とみなすか、どのテキストを優先するか、可視表示との差分を許容するかは、信頼性に直結するため明文化する価値があります。

### 16. コピー操作の露出方針

現行では、コピー操作は hover / focus-within で可視化され、coarse pointer では常時半透明表示されます。この方針自体は合理的ですが、コピー不能時に control を残すのか、完全に隠すのかは設計哲学として未固定です。

長期的には、**読書ノイズを減らすことを優先するのか**、**操作 discoverability を優先するのか**を明示し、その方針に合わせて disabled affordance を統一すべきです。本プロジェクトの方向性からは、通常時は静かに保ち、必要なときのみ露出する方が整合的です。

### 17. ローカライズ境界

コピーラベルは内部生成されていますが、将来的に locale 切り替えや文言差し替えが必要になる可能性があります。現状では、文言が内部責務なのか、外部から override 可能にすべきかが未整理です。

長期的には、**内部デフォルトを持ちつつ、必要なら override 可能**という構成が扱いやすいです。公開契約としては、文言そのものよりも、どの情報を含むべきかを固定する方が保守性は高いです。

### 18. 開発時診断ポリシー

現行実装は、不正構成に対して安全側に縮退しますが、開発時警告は出しません。このため、契約違反が静かに見逃される余地があります。

長期的には、描画は継続しつつも、契約違反に対しては**開発時のみ警告を出す**方針を採る価値があります。実行時例外よりも、静かな診断の方がドキュメント UI には適しています。

### 19. 外部スタイリング拡張面

`ui-syntax-card` は `::part` を公開せず、CSS Custom Properties による調整を中心にしています。この方針はよいですが、どのカスタムプロパティが正式な公開面かは、なお明文化の余地があります。

長期的には、**公開 CSS Custom Properties の一覧を正式 API として固定**し、Shadow DOM 構造は非公開面として保つ方がよいです。見た目拡張の安定面を token に集約した方が保守しやすいです。

### 20. Reduced Motion

現行実装には `prefers-reduced-motion` に応じたコピー操作遷移の抑制はありません。これは単なる未実装事項であると同時に、横断アクセシビリティ契約へ昇格させるかどうかが未確定でもあります。

長期的には、Reduced Motion をコンポーネント単位ではなくデザインシステム全体の横断契約として定め、その一部として `ui-syntax-card` にも適用するのがよいです。

### 本節の扱い

本節に記載した事項は、すべてを直ちに実装へ反映すべきという意味ではありません。重要なのは、**曖昧なまま運用しないこと**です。正式契約へ昇格させる論点は、実装、Storybook、契約書の 3 点を同時に更新し、曖昧な状態のまま公開面へ残しません。

## 新規で追加を検討する価値がある機能

本節は、`ui-syntax-card` の責務を拡散させるのではなく、**単一の代表シグネチャと補足節を静かに提示する参照カード**という性格を保ったまま、追加を検討する価値がある機能を整理するものです。ここでいう「価値がある」とは、単に便利そうであるという意味ではなく、**契約の強化、誤用の減少、アクセシビリティ整合、限定的な拡張性**に寄与することを指します。

### 最優先で検討する価値がある機能

#### 1. 開発時診断機能

現行実装は、不正構成に対して安全側に縮退しますが、`name` 空、`label` 空、既定スロット誤用、`signature` の `<pre>` 不備に対する開発時警告は出しません。このため、契約違反が静かに見逃されやすい状態です。

長期的には、描画を継続しつつ、**開発時のみ警告を出す診断機能**を追加する価値があります。これにより、閲覧体験を壊さずに、執筆時の構造ミスを早期に修正できます。`ui-syntax-card` のようなドキュメント UI では、実行時例外よりも静かな診断の方が適しています。

#### 2. Reduced Motion 対応

現行実装には、コピー操作のフェード表示に対して `prefers-reduced-motion` を考慮する明示機能がありません。視覚ノイズは大きくないものの、アクセシビリティ整合の観点では未完です。

長期的には、`ui-syntax-card` 単体の都合としてではなく、**デザインシステム横断の Reduced Motion 契約の一部**として取り込む価値があります。具体的には、コピー操作の opacity transition を抑制し、Storybook 側でもその契約を検証できるようにするのがよいです。

#### 3. ヘッダー拡張アクション面

現行ヘッダー右端の操作は `ui-copy-button` に固定されています。この構成は単純でよい一方、将来的に permalink、仕様原典へのリンク、バージョン表示などを追加したくなった際の拡張面がありません。

長期的には、`actions` などの**限定的な named slot**を追加し、ヘッダー補助操作を差し込めるようにする価値があります。ただし、自由なツールバーへ拡張するのではなく、あくまでヘッダー右端の補助操作面として責務を狭く保つ方がよいです。既定値としては従来どおり `ui-copy-button` を維持し、必要なときのみ拡張できる設計が望ましいです。

### 次点で検討する価値がある機能

#### 4. 意味整合的な言語 API の追加

公開 property 名が `lang` である一方、その意味は自然言語ではなく構文言語です。この不整合は、長期的には API の直感性を損ねます。

長期的には、`syntaxLang`、`codeLang`、`sourceLang` などの**意味整合的な公開名**を追加する価値があります。互換性維持が必要な場合は、`lang` を当面の互換 alias としつつ、新しい名前へ移行する設計がよいです。これは見た目機能ではありませんが、公開契約の質を高める重要な拡張です。

#### 5. コピー値の明示 override 機能

現行実装は、`<code>` または `<pre>` の `textContent` からコピー値を抽出します。この規則は単純で安定していますが、将来的に「表示は装飾付き、コピーは素のコード」といった要件が出る可能性があります。

長期的には、`copyValue` などの**明示 override 面**を追加する価値があります。未指定時は現行の抽出規則を維持し、必要なときのみ表示値とコピー値を分離できる設計にすると、既存契約を壊さずに拡張できます。ただし、これは単一代表シグネチャという前提を崩さない範囲に限るべきです。

### 条件付きで検討する価値がある機能

#### 6. `identifier` と `name` の分離

現行では `name` が見出し本文とコピーラベルの両方に使われています。初期段階では簡潔ですが、将来的に表示名と機械的識別子を分けたくなる場面はあり得ます。

長期的には、permalink、外部参照、国際化見出しなどの要件が明確になった時点で、`identifier` を追加する価値があります。ただし、現時点で直ちに導入すると責務が増え過ぎるため、必要性が高まった段階で検討するのがよいです。

#### 7. セクション推奨プリセットまたは補助レイヤ

`ui-syntax-section` は自由ラベル節であり、現行の設計は柔軟です。一方で、「パラメータ」「戻り値」「プロパティ」など、よく使う節には実質的な慣習があります。

長期的には、`ui-syntax-card` 本体へ節種別ロジックを入れるのではなく、**周辺レイヤで推奨プリセットや linter を提供する**価値があります。たとえば、推奨ラベル語彙、推奨順序、推奨内容文法を補助する仕組みは、責務分離を保ったまま一貫性を高められます。

### 本体へ入れない方がよい機能

#### 1. 多重シグネチャ対応

overload や variant を `ui-syntax-card` 本体へ取り込むと、単一代表シグネチャという核が崩れます。必要であれば別コンポーネントで束ねる方がよく、本体に取り込む価値は高くありません。

#### 2. 詳細セクションの折りたたみ

折りたたみは一見便利ですが、`ui-syntax-card` の強みである「一望できる静かな参照カード」という性格を損ねやすいです。読書体験を優先する本プロジェクトでは、本体機能としては入れない方がよいです。

#### 3. `kind` の強い列挙化

`kind` は自由テキストの補助ラベルとして扱う方が拡張性に優れます。列挙固定を本体へ入れると、情報設計ルールまでコンポーネント責務に抱え込みやすくなります。

### 本節の扱い

本節に記載した機能候補は、すべてを実装すべきという意味ではありません。重要なのは、**責務を壊さずに伸ばせるか**を基準に選別することです。正式に採用する場合は、実装、Storybook、契約書を同時に更新し、「あると便利そう」という理由だけで本体責務を膨らませません。

## 現行実装で未対応または未強制の事項

本節は、現行の `syntax-card.ts`、`syntax-section.ts`、`syntax-card.stories.ts` を基準として、契約上は重要だが現時点では未強制、未拡張、または利用側規律に依存している事項を整理するものです。

### 1. `name` 非空の実行時強制

`name` はカード見出しの核ですが、現行実装は空文字列でも描画を継続します。空見出しに対する警告、例外、フォールバック文言はありません。したがって、**見出しの意味的妥当性は利用側規律に依存**しています。

### 2. 既定スロット入力の実行時警告

既定スロットの存在判定は `ui-syntax-section` の有無だけで行われますが、`ui-syntax-section` 以外の要素が入っている場合に警告は出しません。したがって、**不正入力が黙って非表示になる**可能性があります。

### 3. `signature` 構造違反の実行時警告

`signature` に `<pre>` がない、複数ある、空白のみである場合、コピーは安全側で無効化されます。しかし、違反内容の診断や警告は行いません。これは堅牢ではある一方で、**執筆時の構造ミスを早期に発見する仕組みは未実装**です。

### 4. `signature` スロット混在ノードの排除

現行実装は、`signature` スロットに割り当てられた要素のうち `<pre>` だけをコピー判定対象として数えます。そのため、有効な `<pre>` が 1 件であれば、`<pre>` 以外のノードが同じ `signature` スロットへ混在していてもコピーが有効なまま残り得ます。一方で、それらのノード自体を非表示にしたり警告したりする仕組みはありません。したがって、``** 領域における不正混在入力の排除や診断は未実装**です。

### 5. 既定スロット混在ノードの排除

既定スロットの存在判定は `ui-syntax-section` の有無だけで行われます。このため、`ui-syntax-section` が 1 件でもあれば `data-content-empty` は解除され、同じ既定スロットに混在した任意ノードもスロット描画上は残り得ます。現行実装は、これらを自動排除したり警告したりしません。したがって、**既定スロットにおける typed slot の実行時強制は未実装**です。

### 6. `signature` 内の `<code>` 直子強制

現行実装は `pre.querySelector('code')` によって最初の子孫 `<code>` を取得します。したがって、`<pre><code>...</code></pre>` を標準構造としつつも、`<code>` が直子であること自体は実行時に強制していません。開発時警告もありません。したがって、``** 直子構造の実行時強制は未実装**です。

### 7. `data-lang` の意味利用

`lang` / `data-lang` は正規化されてホスト属性へ反映されますが、その値に応じてカード自身が見た目や振る舞いを切り替えるわけではありません。したがって、**言語識別子は現時点では主に外部スタイリングや将来拡張のためのフック**です。

### 8. ヘッダーアクション拡張

ヘッダー右端の操作は現行では `ui-copy-button` に固定されています。複数アクション、補助リンク、バージョン表示などのヘッダー拡張面は公開されていません。

### 9. `ui-syntax-section` の見出し要素型固定

`ui-syntax-section` のラベルは `p` 要素で固定されており、文書階層に応じた見出しレベル調整は行いません。詳細セクションを文書アウトラインに参加させたい要件には未対応です。

### 10. Storybook の責務範囲

現行 Storybook はコピー可否、見出しフォールバック、空コンテンツ、`data-lang` 同期、印刷、forced-colors、セクション順保持を確認していますが、長大シグネチャ、極端に長い `name`、セクションラベル空文字、国際化文言切り替えに加えて、``** スロットへの混在ノード**、**既定スロットへの混在ノード**、``** 直子でない構造**などは明示的には検証していません。

### 11. Reduced Motion

現行実装には `prefers-reduced-motion` に応じてコピー操作のフェード遷移を抑制する明示契約はありません。現状は通常トランジションに委ねていますが、アクセシビリティ整合の観点では将来検討の余地があります。

### 12. 本節の扱い

本節に記載した事項は、現行公開契約として依存してよい拡張ではありません。これらを正式契約へ昇格させる場合は、実装、Storybook、契約書の 3 点を同時に更新し、未強制のまま公開面へ昇格させません.
