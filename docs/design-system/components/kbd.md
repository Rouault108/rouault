# Kbd

## 概要

本書は、`ui-kbd` の公開契約、入力解釈、アクセシビリティ、および視覚契約を整理するものです。

`ui-kbd` は、キーボードショートカットや入力指示を、ネイティブ `<kbd>` を基礎に表現するコンポーネントです。単にキー名を囲んで表示するのではなく、**単体キーと複合キーをどのように判定するか**、**どの入力源を優先するか**、**記号キーをどのように読み上げ可能にするか**、**高コントラスト環境や印刷時にどのように劣化させるか**を公開契約として固定します。

Rouault における kbd は、本文中の補助記法であり、本文そのものより強く主張してはなりません。したがって、本コンポーネントの契約は、**ショートカット表記の認識しやすさ**と、**「没入して読む」ことのできるデザイン**の維持を両立する方向で定義します。

---

## 適用範囲

本書は、`ui-kbd` の次の事項を対象とします。

- 公開契約
- 入力解釈契約
- 状態モデル
- DOM / Accessibility
- Visual Contract
- 環境別の振る舞い
- 関連契約
- 境界条件
- Storybook 契約
- 現行実装で未対応の事項

一方で、本書は次の事項を扱いません。

- 画面全体のショートカット設計
- 実際にどの操作へどのショートカットを割り当てるかというプロダクト判断
- `aria-keyshortcuts` の自動生成
- OS ごとのショートカット出し分けロジック
- キーボードイベント監視やショートカット起動そのもの
- Markdown パーサや本文記法側でのショートカット抽出

これらは上位レイヤまたは別契約の責務です。

## 公開契約

`ui-kbd` は、**キー列を視覚表記するための literal renderer** として定義します。長期的な公開契約としては、`ui-kbd` は**正準化済みトークン列**を受け取り、それを単体キーまたは複合キーとして描画します。

本書では、設計のきれいさと保守性を優先し、次を長期契約とします。

- **正準入力はトークン列です**
- **単体キー / 複合キーの意味論はトークン数で決まります**
- ``** は OS 判定、ショートカット意味論、ローカライズ責務を持ちません**
- **文字列表記やスロットは互換入力または補助入力であり、正準入力ではありません**

### 入力契約

| 名前       | 種別                   | 必須  | 内容            | 契約                                                |
| -------- | -------------------- | --- | ------------- | ------------------------------------------------- |
| `tokens` | property             | いいえ | 表示するキー列       | 正準入力です。`['Ctrl', 'K']`、`['⌘', 'K']` のようにキー単位で与えます |
| `keys`   | property / attribute | いいえ | 文字列による互換入力    | 補助入力です。`+` 区切り文字列を `tokens` へ正規化するためにのみ使います       |
| 既定スロット   | slot                 | いいえ | 読み上げ補助用の構造化入力 | 正準入力ではありません。単体キーの補助表現に限定します                       |

`tokens` が存在する場合、`tokens` を唯一の入力として扱います。`tokens` が未指定の場合に限り、`keys` を文字列正規化して `tokens` へ変換します。スロットは、`tokens` / `keys` のどちらも未指定で、かつ記号キーや読み上げ補助を明示したい場合の補助経路としてのみ扱います。

### 入力源の優先順位

入力源の優先順位は次のとおりです。

1. `tokens` property
2. `keys` property / attribute
3. 既定スロット
4. ホストのテキストノード

長期的には、3 と 4 は互換レイヤとして縮小し、利用者は `tokens` を優先します。

### 単体 / 複合の決定契約

単体キーか複合キーかは、**正規化後トークン数**だけで決定します。

- 1 トークンなら単体キーです
- 2 トークン以上なら複合キーです
- 0 トークンなら描画しません

この判定は意味論であり、見た目の都合で上書きしません。したがって、長期契約としては `variant` のような**意味論を書き換える公開入力を持ちません。**

### 文字列入力の互換契約

`keys` は正準入力ではなく、互換的な文字列入力です。文字列入力は `+` を区切り記号としてトークン化します。各トークンは前後空白を除去し、空トークンは除外します。

ただし、この文法は**literal plus を安全に表せない**ため、`+` 自体をキーとして表現したい場合には適しません。長期的には、`+` キー、`=` キー、テンキー記号などの厳密表現が必要な場面では `tokens` を使います。

### スロット契約

既定スロットは、**正準入力ではなく補助入力**です。許容する内容は、本文中に自然に収まる **phrasing content** 相当のインライン内容に限定します。主用途は次のとおりです。

- `.sr-only` と `aria-hidden="true"` を組み合わせた記号キー補助
- 単体キーに対する読み上げ補助の明示

`button`、`a`、`input` などの対話要素、ならびに段落・見出し・リストなどのブロック内容は受け付ける前提にしません。

長期契約としては、**複合キー全体をスロットで構築することに依存しません。** 複合キーは `tokens` または `keys` から生成します。スロットは、単体キーの補助的な表現に責務を絞ります。

### 属性反映契約

長期契約として reflect 対象は持ちません。`tokens` は property 入力であり、`keys` は互換用の property / attribute 入力です。

| property | attribute | reflect | 備考          |
| -------- | --------- | ------- | ----------- |
| `tokens` | なし        | なし      | 正準入力です      |
| `keys`   | `keys`    | なし      | 互換的な文字列入力です |

### 公開 part 契約

`ui-kbd` は、Shadow DOM 内部のスタイル拡張面として次の `part` を公開します。

| part 名      | 役割                |
| ----------- | ----------------- |
| `key`       | 単体キー、または複合キー内の各キー |
| `combo`     | 複合キー全体のまとまり       |
| `separator` | 複合キー間の区切り         |

単体キー描画では `part="key"` のみを持ちます。複合キー描画では外側に `part="combo"`、各キー片に `part="key"`、区切り記号に `part="separator"` を持ちます。

### 列挙外値・無効値の扱い

公開契約としては、`tokens` の各要素は非空文字列を受理します。空文字列、空白のみ文字列、`null` 相当値は正規化過程で除外します。

`keys` は互換入力として自由文字列を受理しますが、正規化結果が 0 トークンになった場合は描画しません。`keys` の解析失敗や列挙外キー名に対して例外は投げず、**開発時警告を許容しつつ、本番では最善努力で描画または省略する**方針とします。

### 責務範囲

責務範囲には、単体キーと複合キーの描き分け、キー列の視覚表記、既知キー名への読み上げ補助、ネイティブ `<kbd>` の出力、ならびにメディア条件下での劣化制御を含みます。

一方で、`aria-keyshortcuts` の生成、OS 判定、ショートカット起動処理、プラットフォーム別のキー置換、ローカライズ戦略、セパレータ体系の切り替えは責務に含めません。

## 入力解釈契約

`ui-kbd` は、**正準化済みキー列を描画するコンポーネント**です。文字列解釈や light DOM 解析は、正準入力へ寄せるための互換レイヤとしてのみ扱います。

### 正規化契約

最終的な描画判定は、内部の `normalizedTokens` に対して行います。`normalizedTokens` は次の手順で決定します。

1. `tokens` があれば、その配列から空要素を除去します
2. `tokens` がなければ、`keys` を `+` 区切りで分割し、前後空白を除去して空要素を除去します
3. `keys` もなければ、既定スロットを補助入力として扱います
4. スロットもなければ、ホストテキストを互換入力として扱います

### 空白正規化契約

空白の正規化は、入力源ごとに次のように扱います。

- `tokens` の各要素は、前後空白だけを除去します
- `keys` は全体を trim したうえで `+` 区切りに分割し、各トークンの前後空白だけを除去します
- ホストのテキストノード由来の文字列は、連続空白・改行・タブを 1 つの空白に畳み込み、その後で trim します
- スロット要素経由の入力は、利用者が明示した DOM 構造を優先するため、`ui-kbd` 側で文字列正規化を行いません

### 文字列文法の境界

`keys` は簡易文法です。`/`、`,`、`-`、`→` などを区切りとして解釈しません。また、literal plus を厳密に表現する責務も持ちません。厳密なキー表現が必要な場合、利用者は `tokens` を使います。

### 混在入力の扱い

要素ノードとテキストノードが混在する入力は、長期契約として推奨しません。互換的に受け入れる場合でも、それは**スロット補助入力**として扱い、文字列再解析には依存しません。

## 状態モデル

`ui-kbd` の主要状態は、見た目の差ではなく、**入力源がどこにあるか**、**単体キーか複合キーか**、**読み上げ補助が必要か**によって読み分けます。

### 基本状態

最小状態は、`keys="Esc"` かつ `variant="auto"` の状態です。この場合、単体キーとして描画します。

### 単体キー状態

単体キー状態では、Shadow DOM 内に `kbd.kbd-key` を 1 つ出力します。既知のキー名であれば、必要に応じて `aria-label` を付与します。

### 複合キー状態

複合キー状態では、Shadow DOM 内に `kbd.kbd-combo` を出力し、その内部に各キー片を `kbd.kbd-key` として並べます。キー間の区切りは `+` のテキストノードで表現します。複合キー全体には `white-space: nowrap` を適用し、途中改行を防ぎます。

### 記号キー補助状態

`⌘` は視覚記号だけでは読み上げが安定しないため、単体でも複合でも SR 専用テキストを内部に同梱します。視覚上は `⌘` のみを表示し、読み上げ上は `コマンド` として扱います。

### スロット優先状態

`keys` が空で、かつスロットに要素ノードが存在する場合、入力文字列は解析しません。`variant="combo"` なら外側に `kbd.kbd-combo` を出力し、スロット内容全体をそのまま配置します。`variant="key"` または `auto` で単体扱いになる場合は、単体キー用の `kbd.kbd-key` にスロットを配置します。

### 空入力状態

`keys` が空で、スロット要素も存在しない場合、空のキートップは描画せず、出力を省略します。これは空の `<kbd>` を視覚ノイズとして残さないための契約です。

## DOM / Accessibility

ルートは `:host` です。Shadow DOM 内に、単体キーまたは複合キーのための構造を出力します。

単体キー時の基本構造は次のとおりです。

```text
<ui-kbd>
  #shadow-root
    <kbd part="key">Esc</kbd>
</ui-kbd>
```

複合キー時の基本構造は次のとおりです。

```text
<ui-kbd>
  #shadow-root
    <span part="combo">
      <kbd part="key">Ctrl</kbd>
      <span part="separator" aria-hidden="true">+</span>
      <kbd part="key">K</kbd>
    </span>
</ui-kbd>
```

長期契約として、**複合キー全体の外枠は中立要素**とし、各キー片だけをネイティブ `<kbd>` として表現します。これは、複合キー全体を 1 つの keyboard input とみなすのではなく、**複数のキー入力の列**として意味論を揃えるためです。

`⌘` のような記号キーでは、内部に SR 専用テキストと視覚専用テキストを分離して持ちます。

```text
<kbd part="key">
  <span class="sr-only">コマンド</span>
  <span aria-hidden="true">⌘</span>
</kbd>
```

### Accessibility 契約

アクセシビリティ上の重要点は次のとおりです。

- 各キー片はネイティブ `<kbd>` を出力します。
- 複合キーの外枠は中立要素とし、余分な keyboard input 意味論を持ちません。
- `Ctrl`、`Esc`、`Shift`、`Enter`、`Tab`、`Space`、`⌘` など既知トークンには、日本語読み上げ補助を付与します。
- 記号キー `⌘` は `aria-label` のみには依存せず、SR 専用テキストと `aria-hidden="true"` の視覚記号を併用します。
- 複合キー全体の可読な読み上げ列が必要な場合、上位レイヤでアクセシブルネームを与えます。`ui-kbd` 自身は `aria-keyshortcuts` を生成しません。
- `ui-kbd` は非対話要素として扱います。フォーカス取得、クリック起動、キーボード操作主体、`role="button"` 付与、`tabindex` 付与を前提としません。
- `ui-kbd` は操作対象ではなく表記要素です。利用者は、操作意味論を上位のリンク・ボタン・メニュー項目などに載せます。

### 読み上げマッピング契約

読み上げ補助は、**可視トークン辞書**と**読み上げ辞書**を分離したうえで運用するのが長期契約として望ましいです。現時点で最低限保証する代表的なキー名は次のとおりです。

| 入力                               | 読み上げ     |
| -------------------------------- | -------- |
| `ctrl` / `control`               | `コントロール` |
| `esc` / `escape`                 | `エスケープ`  |
| `shift`                          | `シフト`    |
| `enter` / `return`               | `エンター`   |
| `tab`                            | `タブ`     |
| `space` / `spacebar`             | `スペース`   |
| `cmd` / `command` / `meta` / `⌘` | `コマンド`   |

大文字小文字は区別せずに解釈します。上表にない文字列は、そのまま可視文字列として描画し、追加の読み上げ補助は付与しません。

### 言語契約

Rouault では、読み上げ補助は日本語を基準とします。ただし、長期的な責務分離の観点では、ローカライズ戦略そのものは `ui-kbd` の責務に含めません。将来多言語対応が必要になった場合、上位レイヤまたは辞書注入経路で解決します。

## Visual Contract

`ui-kbd` の視覚契約は、キー表記を本文より一段だけ強く見せつつ、本文の流れを遮らないことにあります。

### 情報順位

- 単体キーは小さなキートップとして認識できることを優先します。
- 複合キーは 1 つのまとまりとして読めることを優先します。
- 連続ショートカットでも、途中改行により意味が崩れないことを優先します。
- 視覚強度は本文の主役を奪わない程度に抑えます。

### レイアウト

`:host` は `display: inline`、`vertical-align: baseline` とし、本文中に自然に差し込みます。単体キーは `inline-flex` で中央寄せし、最小寸法を持つキートップとして表示します。複合キーの外枠は `inline-flex` とし、各キー間に一定の間隔を設けます。区切り記号は独立した separator として扱います。

### 視覚仕様

- 単体キーは淡い背景、細い境界線、控えめな内側ハイライト、軽いシャドウを持ちます。
- 複合キー全体は透明背景とし、各キー片だけがキートップ表現を持ちます。
- 角丸、境界線、背景色、文字色、最小寸法はトークンで制御します。
- 小さい親フォント環境でも、キー表記自体は 12px 未満にならない下限を持ちます。

### 参照トークン

本コンポーネントは、主として次のトークンに依存します。

| 用途        | トークン                      |
| --------- | ------------------------- |
| フォント      | `--font-sans`             |
| 最小文字サイズ   | `--text-xs`               |
| 文字色       | `--fg-default`            |
| 控えめ背景     | `--bg-fill-muted`         |
| 控えめ境界線    | `--border-muted`          |
| 境界線幅      | `--border-width`          |
| 角丸        | `--radius-md`             |
| 間隔        | `--space-2` / `--space-3` |
| 行高        | `--line-height-none`      |
| 太さ        | `--font-medium`           |
| トラッキング    | `--tracking-normal`       |
| 強制カラー時背景  | `--bg-surface-2`          |
| 強制カラー時境界線 | `--border-default`        |

## 環境別の振る舞い

### Forced Colors

`forced-colors: active` 環境では、キートップの背景と境界線をシステム側で認識しやすい形に寄せ、box-shadow を除去します。`forced-color-adjust: auto` を維持し、独自の装飾より可読性を優先します。

### Print

`@media print` では、キートップ背景とシャドウを除去し、透明背景と明示的な境界線だけを残します。複合キー全体の `white-space: nowrap` は維持し、印刷時も `Ctrl + K` のようなまとまりを崩しません。

### Dark Mode

専用のメディアクエリは持ちませんが、色はトークン追従で吸収します。したがって、暗色テーマでは `--fg-default`、`--bg-fill-muted`、`--border-muted` などの差し替えに追従することを契約とします。

## 関連契約

### ショートカット表示契約

`ui-kbd` は、ショートカットの**視覚表記**を担当します。実際のショートカット意味論は、起動主体側の `aria-keyshortcuts` と対応付けます。

たとえば、検索ボタンに `aria-keyshortcuts="Control+K Meta+K"` を付与し、その可視ラベルとして `Ctrl + K` と `⌘ + K` を `ui-kbd` で併記する構成は正規です。このとき、`ui-kbd` 自身は `aria-keyshortcuts` を生成しません。

### OS 抽象契約

`ui-kbd` は **literal renderer** です。与えられたキー列をそのまま描画し、OS 判定やプラットフォーム別の自動置換は行いません。`Ctrl` と `⌘` のどちらを出すか、両方を併記するか、`aria-keyshortcuts` とどう整合させるかは上位レイヤの責務です。

### スタイル拡張契約

外部スタイル拡張面は、CSS Custom Properties と `::part(key)`、`::part(combo)`、`::part(separator)` に限定します。内部 class 名 `.sr-only` を含む内部実装には依存しません。

利用者は、各 `part` に対して色、境界線、角丸、余白、フォントなどの装飾を与えられます。一方で、次は **hard invariants** として扱います。

- 単体キーのキートップ性
- 複合キー外枠の `inline-flex`
- 複合キーの `nowrap`
- キートップの最小文字サイズ
- キートップの最小寸法

これらを壊す変更には依存しません。

### 入力正規化契約

複合キー文字列の正規化は `+` 区切り、前後空白除去、空トークン除去に限定します。キー名そのものの正規化は、読み上げ補助に必要な一部既知値に対してのみ行います。`Control` を `Ctrl` へ視覚変換する、`Meta` を `⌘` に置換する、といった表示上の強制変換は行いません。

### 読み上げ辞書契約

読み上げ辞書の最低保証集合は、本書の読み上げマッピング表に限定します。`Alt`、`Option`、`Delete`、`Backspace`、矢印キー、`Fn` などは、将来拡張対象ではあり得ますが、現時点では最低保証集合に含めません。

## 境界条件

### 1. 単体キー

`tokens=['Esc']` のように 1 トークンを与えた場合、単体キーとして描画します。

### 2. 複合キー

`tokens=['Ctrl', 'K']` のように 2 トークン以上を与えた場合、複合キーとして描画します。

### 3. 互換文字列入力

`keys="Ctrl + K"` のような入力は、互換的に `tokens=['Ctrl', 'K']` へ正規化されます。

### 4. literal plus

`+` 自体をキーとして厳密に表したい場合、`keys` 文法には依存しません。`tokens` を使います。

### 5. 記号キーの補助表現

単体の記号キーに対して `.sr-only` と `aria-hidden="true"` を併用する構成は正規です。この場合、`ui-kbd` は補助構造を壊さず保持します。

### 6. 要素ノードとテキストノードの混在

混在入力は長期契約として推奨しません。互換的に受け入れる場合でも、文字列再解析や自動複合判定には依存しません。

### 7. 不適切なスロット内容

既定スロットはインライン内容を前提とします。対話要素やブロック要素を与えた場合の見た目や意味論は公開契約外です。

### 8. 空入力

正規化後トークン数が 0 の場合、空の `<kbd>` は描画しません。

### 9. 小さい親フォント

親コンテナが 11px であっても、`ui-kbd` のキートップ自体は 12px 未満に縮みません。

### 10. 複合キーの折り返し

複合キーは `white-space: nowrap` と `inline-flex` を維持し、狭い幅でも途中改行しません。

## Storybook 契約

各 Story は見本ではなく、契約確認点として扱います。将来変更時には、次の契約を維持します。

| Story                        | 固定する契約                                                     |
| ---------------------------- | ---------------------------------------------------------- |
| `Default`                    | 単体キーでネイティブ `<kbd>` を出力し、既知キーに `aria-label` を付与すること         |
| `VariantStateMatrix`         | 単体キー / 複合キーの描き分け、`⌘` の SR 補助、長い複合キーのトークン数が成立すること           |

| `ComboNoWrapIntegrity`       | 複合キーが `inline-flex` と `white-space: nowrap` を維持すること        |
| `BoundaryCases`              | 互換文字列入力、literal plus の境界、スロット補助運用、混在入力を推奨契約外として扱う境界が成立すること |

## 補足

`ui-kbd` の要点は、キー名を装飾することではありません。**正準化済みキー列をネイティブ **``** により静かに可視化し、本文中で意味論を過剰に持ち込まず、既知キーの読み上げだけを最小限補助すること**にあります。

したがって、今後の変更でも次の 5 点は崩さない方がよいです。

1. 正準入力はトークン列に寄せること。
2. 単体キー / 複合キーの意味論はトークン数で決めること。
3. `ui-kbd` 自身は literal renderer に徹すること。
4. 各キー片にはネイティブ `<kbd>` を使い、複合キー外枠は中立要素に保つこと。
5. `⌘` を含む既知キーの読み上げ補助と複合キーの `nowrap` 契約を緩めないこと。

## 現行実装で未対応の事項

本節は、長期契約に対して、現行の `kbd.ts` および `kbd.stories.ts` がまだ満たしていない事項を記載します。

### 1. `tokens` を正準入力とする公開 API

現行実装は `tokens` property を公開しておらず、`keys` と light DOM 解析を主入力として扱います。長期契約に寄せるには、`tokens` を公開し、`keys` を互換入力へ落とす必要があります。

### 2. `variant` の整理

現行実装は `variant` により単体キー / 複合キーの描画モードを上書きできます。長期契約では、単体キー / 複合キーの意味論をトークン数だけで決めるため、`variant` は廃止または見た目専用 API へ再編する必要があります。

### 3. 複合キー外枠の意味論

現行実装は複合キー外枠にも `<kbd>` を使います。長期契約では、外枠は中立要素、各キー片のみ `<kbd>` とするため、DOM 構造の再設計が必要です。

### 4. `separator` part の公開

現行実装は区切り記号を独立した公開 part としては扱っていません。長期契約に寄せるには、separator を独立したスタイル拡張面として公開する必要があります。

### 5. スロット責務の縮小

現行実装は `keys` が空で要素子が存在する場合、複合キー相当の構造もスロットで丸ごと受け入れます。長期契約では、スロット責務を単体キーの補助表現へ絞るため、責務整理が必要です。

### 6. literal plus の厳密表現

現行実装の文字列文法では、`+` 自体のキーを安全に表現できません。長期契約に寄せるには、`tokens` ベースでの厳密表現へ移行する必要があります。

### 7. 読み上げ辞書の分離

現行実装は読み上げ辞書を内部定数として持ちます。長期契約では、可視トークン辞書と読み上げ辞書を分離し、将来拡張をしやすくする余地があります。

### 8. ローカライズ責務の切り出し

現行実装の読み上げ補助は日本語固定です。将来多言語対応が必要な場合、`ui-kbd` 外へ責務を切り出す設計が必要です。

### 9. 無効値に対する開発時警告

現行実装は列挙外 `variant` や意図不明な入力に対して明示的な警告を出しません。長期契約に寄せるには、開発時警告と本番時の最善努力描画を分ける方針整理が必要です。
