# Divider

## 概要

本書は、`ui-divider` の公開契約、状態モデル、アクセシビリティ、視覚契約、および関連する文書スコープ契約を整理するものです。

`ui-divider` は、本文やレイアウトの流れの中に区切りを導入するためのコンポーネントです。単に線を描画するのではなく、**ネイティブ `hr` の意味論を維持すること**、**適用スコープを限定して通常の `hr` へ副作用を広げないこと**、**読書リズムを乱さない静かな境界として振る舞うこと**を公開契約として固定します。

また、本コンポーネントは Shadow DOM に閉じた局所装飾ではなく、`.prose hr`、`ui-divider > hr`、`hr[data-divider-variant="layout"]` に対する文書スコープのスタイル契約も含みます。したがって、本書はコンポーネント実体の描画契約と、ドキュメントレベルのスコープ契約を併せて扱います。

Rouault における divider は、**話題の転換や構造の一区切りを静かに示し、読むことへの没入を壊さないこと**を目的とします。したがって、本コンポーネントの契約は、可視的な境界を与えつつも、本文や見出しより強く主張しない方向で定義します。

---

## 適用範囲

本書は、横方向の `ui-divider` と、それに関連する divider スコープの公開契約を対象とします。具体的には、次の事項を定義します。

- `ui-divider` の公開契約
- `variant` の状態モデル
- DOM / Accessibility 契約
- Visual Contract
- 環境別の振る舞い
- 関連する文書スコープ契約
- 境界条件
- Storybook における公開契約確認点

本書が扱う divider は、**横方向の区切り**に限ります。本文内の節区切りおよびレイアウト上の領域分節を対象とし、区切りの実体は常にネイティブ `<hr>` とします。

一方で、本書は次の事項を定義しません。

- 記事全体のどこに区切り線を置くべきかという編集判断
- 各ページ固有の余白設計全体
- 区切り前後の見出しや本文の情報設計
- 他コンポーネントとのレイアウト統括
- トークン定義そのもの
- 縦方向 separator の契約
- `section` / `layout` の視覚差分
- `section` / `layout` ごとの余白差分
- 装飾密度の段階化
- 文書スコープスタイル適用の明示的 bootstrap API

縦方向 separator が必要な場合は、本コンポーネントの拡張ではなく、別コンポーネントまたは別契約として扱います。

また、本書における `variant` は現時点では**意味分類**であり、視覚バリアントではありません。したがって、`section` / `layout` の差は、使用文脈の違いとして解釈されます。

上記の非対象事項は、将来の検討余地があること自体を否定するものではありません。ただし、現行の公開契約としては固定せず、利用者が依存してよい前提には含めません。

## 公開契約

`ui-divider` は、`variant` を唯一の公開入力として扱います。内部実体はネイティブ `<hr>` であり、利用者は `ui-divider` を区切り線の契約単位として扱います。

`variant` の既定値は `section` です。受理する値は `section` と `layout` のみです。列挙外値を与えた場合、描画時には `section` へフォールバックしなければなりません（MUST）。

`ui-divider` は、追加ロールや追加キーボード操作を持つインタラクティブ要素ではありません。内側 `hr` に `role` や `tabindex` を付与してはなりません（MUST NOT）。

### 入力契約

| 名前      | 種別                 | 必須   | 内容               | 契約                                          |
| --------- | -------------------- | ------ | ------------------ | --------------------------------------------- |
| `variant` | property / attribute | いいえ | 区切り線の用途種別 | `section` / `layout`。既定値は `section` です |

### 属性反映契約

`variant` は property / attribute の両面から操作できます。`reflect: true` を持ち、ホスト属性へ反映します。

| property  | attribute | reflect | 備考                                                |
| --------- | --------- | ------- | --------------------------------------------------- |
| `variant` | `variant` | あり    | 列挙外値は描画時に `section` へフォールバックします |

### 出力契約

`ui-divider` は、最終 DOM として `hr` を出力します。Shadow DOM は使用せず、ホスト直下に `hr` を描画します。

```text
<ui-divider variant="section">
  <hr data-divider-variant="section" />
</ui-divider>
```

`hr` には、解決済み `variant` を `data-divider-variant` として出力します。`section` と `layout` のいずれであっても、最終描画ノードは常に `hr` です。

`data-divider-variant` は出力契約の一部です。とくに `layout` 値は、文書スコープの divider スタイルへ参加するための識別子として扱います。したがって、属性名または値体系の変更は互換性に影響する変更として扱わなければなりません（MUST）。

### 属性転送契約

`ui-divider` は、ホスト属性を内側 `hr` へ自動転送しません。内側 `hr` に反映されるのは、コンポーネント実装が明示的に出力する属性のみです。

したがって、`class`、`style`、`title`、`data-*`、ARIA 属性、`role` などをホストへ付与しても、それらはホスト自身にのみ作用します。利用者は、ホスト属性によって内側 `hr` の意味論または描画が変化することを期待してはなりません（MUST NOT）。

### スロット契約

`ui-divider` は公開スロットを持ちません。子要素による内容差し替えには対応しません。

### 公開イベント / 公開メソッド

`ui-divider` は独自イベントを公開しません。公開メソッドも持ちません。利用者は区切り線を操作対象として扱ってはなりません（MUST NOT）。

### 非対応方針

`ui-divider` は、区切りを静かに導入するためのコンポーネントであり、次の機能は公開契約として採りません。

- ラベル付き divider
- 名前付き separator
- インタラクティブ境界
- 子要素埋め込みによる内容差し替え
- 見た目だけを目的とした `variant` の増殖

ラベルや名前が必要な場合は、見出し、テキスト、または別コンポーネントで表現します。`ui-divider` 自体に説明ラベル、操作性、装飾的な派生種別を持ち込んではなりません（MUST NOT）。

したがって、`ui-divider` は区切りそのものを表す最小契約に留まり、意味付けの追加や操作対象化によって責務を拡張しません。

### 列挙外値・無効値の扱い

`variant` の公開列挙値は `section` と `layout` のみです。HTML 属性として他の文字列を与えること自体は可能ですが、公開契約上の有効値ではありません。

列挙外値は描画時に `section` と同等に扱います。利用者は列挙外値固有の挙動に依存してはなりません（MUST NOT）。

### 責務範囲

責務範囲には、ネイティブ `hr` の描画、`data-divider-variant` の付与、ドキュメントスコープへの divider スタイル注入、および適用スコープの限定を含みます。

一方で、区切り前後の余白再配分、見出しとの組み合わせによる視線誘導、ページ固有の階層差の設計は責務に含めません。

## 状態モデル

`ui-divider` の主要状態は、操作状態ではなく、**どの用途種別として解釈されるか**、**スコープ内で描画されるか**、**コンポーネント実体を伴うかどうか**によって読み分けます。

### 1. 基本状態

最小状態は、`variant="section"` の `ui-divider` を描画した状態です。この状態ではホスト直下に `hr[data-divider-variant="section"]` を出力し、ドキュメントスコープの divider スタイルを受けます。

### 2. `section` 状態

`section` は既定状態です。`section` を使用するのは、**prose 文脈における本文内の区切り**に限ります。ここでいう prose 文脈とは、段落、見出し、引用、リスト、本文補助要素など、読む順序を持つ文章流れの内部を指します。

`section` を用いる代表例は次のとおりです。

- 話題転換
- 節と節のあいだの静かな区切り
- 本文ブロック群の切れ目
- 長文中で読書リズムを整えるための構造境界

一方で、コンテナ配置、カラム分割、補助ペイン分離、カード群の領域分割など、**文章流れそのものではなくレイアウト構造を区切る目的**には `section` を使用してはなりません（MUST NOT）。

現行実装では `section` 固有の視覚差分は持ちません。したがって、`section` の意味は見た目ではなく、**本文内区切りとして解釈されること**にあります。

### 3. `layout` 状態

`layout` は、**prose 外の構造境界**または**レイアウト上の領域分節**に使用する状態です。`layout` を使用するのは、文章流れの区切りではなく、領域・容器・補助面の区切りを示したい場合に限ります。

`layout` を用いる代表例は次のとおりです。

- 補助カラムと本文領域の境界
- カード群、パネル群、設定領域などの構造的区切り
- prose 外コンテナ内部でのブロック分節
- `ui-divider` を介さない `hr[data-divider-variant="layout"]` による補助的参加面

一方で、本文段落群、見出し間、引用前後など、**読書順序を持つ prose 文脈の区切り**には `layout` を使用してはなりません（MUST NOT）。

現行実装では `layout` も `section` と視覚差分を持ちません。したがって、`layout` の意味は見た目ではなく、**レイアウト境界として解釈されること**にあります。

### 4. 列挙外値フォールバック状態

`variant` の公開列挙値は `section` と `layout` のみです。列挙外値が与えられた場合、内部では `section` として解決しなければなりません（MUST）。

このフォールバックは、未知の意味分類を許容するための拡張点ではありません。利用者は列挙外値を独自用途として運用してはなりません（MUST NOT）。

### 5. ホスト属性付与状態

`ui-divider` のホストには `class`、`style`、`data-*` などの属性を付与できますが、これらは**ホスト自身に対する付加情報または外側調整**としてのみ扱います。内側 `hr` への意味論転送、状態拡張、視覚モード切替の契約には用いません。

とくに `role`、ARIA 属性、`tabindex` などをホストへ付与して、`ui-divider` のアクセシビリティ上の意味や操作性を変更する運用は公開契約外です。利用者はそのような運用に依存してはなりません（MUST NOT）。

したがって、ホスト属性の有無は、内側 `hr` の意味論、解決済み `variant`、および divider としての公開挙動を変更しません。

### 6. コンポーネント実体なし状態

`ui-divider` が 1 つも存在しない場合でも、ドキュメントスタイル注入が成立していれば `.prose hr` および `hr[data-divider-variant="layout"]` は divider 契約に従って描画されます。したがって、本コンポーネントは**インスタンス存在に依存しない文書スコープ契約**を持ちます。

### 7. 更新反映状態

`variant` が更新された場合、次回描画では内側 `hr` の `data-divider-variant` も解決済み値へ更新されます。したがって、`ui-divider` は初回描画時だけでなく、更新後も出力契約を維持しなければなりません（MUST）。

## DOM / Accessibility

ルートは `:host` です。`createRenderRoot()` はホスト自身を返し、Shadow DOM を使用しません。したがって、描画は light DOM に対して行われます。

```text
<ui-divider>
  <hr data-divider-variant="..." />
</ui-divider>
```

### Accessibility 契約

本コンポーネントのアクセシビリティ契約は、**ネイティブ `hr` の意味論を保ったまま区切りを表現すること**です。したがって、`ui-divider` は独自のウィジェット、操作対象、説明付きセパレーターとして振る舞いません。

アクセシビリティ上の固定条件は次のとおりです。

- 実体は常にネイティブ `<hr>` です。
- 内側 `hr` に追加の `role` を付与してはなりません（MUST NOT）。
- 内側 `hr` に `tabindex` を付与してはなりません（MUST NOT）。
- 内側 `hr` に操作性を与えるイベント契約を追加してはなりません（MUST NOT）。
- ホスト上の `role`、ARIA 属性、`tabindex` は内側 `hr` に転送してはなりません（MUST NOT）。

本コンポーネントは、ARIA による意味上書きや補助説明の追加によって価値を生む部品ではありません。意味は `hr` によって充足されるため、追加のアクセシビリティ意味付与を前提に設計してはなりません。

また、本コンポーネントは名前付き separator を提供しません。`aria-label`、`aria-labelledby`、追加 `role` などによって divider 自体へ独自の名前や説明を与える設計は採りません。名前や説明が必要な場合は、隣接する見出し・本文・別要素で表現します。

### ホスト属性の位置づけ

ホスト要素に属性を付与すること自体は可能です。ただし、それらは `ui-divider` の公開意味論を変更、補強、拡張する契約ではありません。

とくに次の運用は公開契約外です。

- `role` をホストへ付与して別の要素種別として扱うこと
- `aria-label` や `aria-labelledby` により名前付き separator のように扱うこと
- `tabindex` を付与してフォーカス対象にすること
- ホスト属性によって内側 `hr` の意味が変わると期待すること

`class`、`style`、`data-*` は、ホスト自身に対する外側調整としてのみ許容します。一方で、`role`、ARIA 属性、`tabindex` による意味変更・操作性変更は採りません。利用者は、ホスト属性を用いて `ui-divider` のアクセシビリティ契約を変更してはなりません（MUST NOT）。

## Visual Contract

本節は、divider の**適合判定に用いる視覚契約**を定義します。叙述的な設計意図ではなく、利用者が依存してよい出力条件を固定します。

### 視覚目的

divider の視覚目的は、本文または構造の区切りを示すことです。ただし、その役割は境界の強調ではなく、構造把握の補助にあります。したがって、divider は本文、見出し、主要操作要素より強く前景化してはなりません（MUST NOT）。

### 適用スコープ

divider スタイルの適用対象は次に限定します。

- `.prose hr`
- `ui-divider > hr`
- `hr[data-divider-variant="layout"]`

このスコープ外の通常 `hr` に divider スタイルを適用してはなりません（MUST NOT）。

### スタイル特異性契約

divider の文書スコープスタイルは、テーマ層およびページ層からの正当な上書きを妨げない低特異性で提供しなければなりません（MUST）。

特異性を不必要に引き上げる変更は、見た目が等価であっても互換性に影響する変更として扱います。利用者は、ページ固有調整を不能にする高特異性 selector を公開前提として期待してはなりません。

### 視覚仕様

divider スタイルは、少なくとも次の条件を満たさなければなりません（MUST）。

- `border: 0`
- 可視境界は `border-top` により表現すること
- `border-top-width: 1px`
- `margin: var(--space-12) 0`
- `width: 100%`

境界線の色および線種は、`--border-style-subtle` および `--border-default` に整合する範囲で解決しなければなりません（MUST）。色を固定値へ焼き付けて、トークン経由の環境追従を失ってはなりません（MUST NOT）。

### 視覚強度の契約

divider は次の条件を満たさなければなりません（MUST）。

- 本文テキストより視線誘導が強くならないこと
- 見出しの階層表現を代替しないこと
- 装飾線や強調線として解釈される強度を持たないこと
- 区切りの可視性を失わない範囲で、低コントラストかつ低密度であること

ここでいう視覚強度は、色、線幅、線種、余白量の合成結果として判断します。したがって、いずれか一要素だけでなく、総体として divider が前景化しないことを維持します。

### バリアントの視覚位置づけ

現行実装では、`section` と `layout` は視覚差分を持ちません。したがって、現時点の `variant` は**視覚バリアントではなく意味分類**です。

利用者は、`section` と `layout` の見た目の差に依存してはなりません（MUST NOT）。将来視覚差分を導入する場合でも、それは意味分類に従属する補助差分としてのみ導入します。見た目だけの都合で `variant` を増殖させてはなりません（MUST NOT）。

### 参照トークン

本コンポーネントは、主として次のトークンまたは意味的変数に依存します。

| 用途                         | トークン                |
| ---------------------------- | ----------------------- |
| 区切り線スタイル             | `--border-style-subtle` |
| 既定境界線色のフォールバック | `--border-default`      |
| 余白                         | `--space-12`            |
| forced-colors 時の境界線色   | `--border-ghost`        |

本コンポーネントは色モードごとの個別分岐を公開前提とせず、できる限りセマンティックトークン参照で環境差分へ追従します。

### スタイル拡張契約

本コンポーネントの見た目を調整する正式な経路は、まず**トークン参照の上書き**です。利用者は、`--border-style-subtle`、`--border-default`、`--space-12`、`--border-ghost` など、本書で参照を明示したトークンを通じて調整することを優先しなければなりません（SHOULD）。

divider スタイルは低特異性 selector で提供されますが、これはページ層・テーマ層からの正当な調整を可能にするためです。ただし、低特異性 selector の存在は、内部 selector 文字列や style tag ID そのものを正式な公開 API として保証することを意味しません。

推奨される調整は次のとおりです。

- セマンティックトークンの差し替え
- テーマ層・ページ層からの妥当な上書き
- divider の前景化を避けた範囲での色・余白の調整

一方で、次のような運用には依存してはなりません（MUST NOT）。

- 内部 helper 名を前提とした連携
- style tag ID を公開 API とみなした連携
- 内部 selector 文字列への強い依存
- `hr` の構造意味を壊す上書き
- 見た目だけの都合で `variant` の役割を上書きする調整

したがって、本コンポーネントのスタイル拡張面は、**トークンを中心とした意味的調整面**として扱い、内部実装詳細への直接依存は公開契約外とします。

## 環境別の振る舞い

### Reduced Motion

`ui-divider` 自体はモーションを持ちません。したがって、reduced motion 対応で個別停止すべきアニメーション契約は持ちません。

### Dark Mode

ダークモード専用の `prefers-color-scheme` 分岐は持ちません。境界線の見え方は、`--border-style-subtle` や `--border-default` などのトークン差し替えで吸収します。

### Forced Colors

`forced-colors: active` 環境では、divider スコープに対して `border-top-color: var(--border-ghost)` を適用します。`forced-color-adjust: auto` を維持し、強制カラー環境での可視性を確保します。

### Print

`@media print` では、divider スコープに対して `margin: var(--space-12) 0` を維持しつつ、`break-inside: avoid` および `page-break-inside: avoid` を適用します。これにより、区切り線周辺での不自然な分断を抑えます。

## 関連契約

### ドキュメントスタイル注入契約

`ui-divider` は、`ensureDividerDocumentStyles()` によりドキュメントへスタイルタグを注入します。注入先スタイルタグ ID は `ui-divider-document-styles` です。

この注入は idempotent でなければなりません（MUST）。同一ドキュメント内で複数インスタンスが存在しても、スタイルタグは 1 回だけ注入します。

一度注入したスタイルタグは、コンポーネントの切断時に自動削除しません。したがって、このスタイル契約は個々のインスタンス寿命ではなく、document 単位で保持されます。

### インスタンス非依存契約

`.prose hr` 契約を成立させるため、divider スタイルはコンポーネント実体の存在に依存しません。`ui-divider` が存在しない文脈でも、スタイル注入が完了していれば `.prose hr` と `hr[data-divider-variant="layout"]` は契約どおりに描画されます。

### モジュール評価契約

`ensureDividerDocumentStyles()` は接続時だけでなく、モジュール評価時にも実行されます。これにより、初期描画より前に `.prose hr` 契約を満たしやすくします。

したがって、`ui-divider` モジュールは import 自体に文書スコープスタイル注入の副作用を持ちます。この副作用は偶発的な実装詳細ではなく、`.prose hr` 契約を成立させるための公開上の前提です。

一方で、`document` が存在しない環境では何もしません。したがって、サーバー環境では安全に no-op でなければなりません（MUST）。

### 生 `hr` との関係

`hr[data-divider-variant="layout"]` は、`ui-divider` を経由しない生の `hr` でも divider スコープに参加できます。これは、layout 用境界をマークアップ上の都合で直接記述する場合のための契約です。

ただし、公開契約の主経路は `ui-divider` です。生の `hr[data-divider-variant="layout"]` は補助的な参加面として扱い、通常の利用では `ui-divider` を優先します。

一方で、生の通常 `hr` は divider スコープに自動参加しません。利用者は単なる `hr` に対して divider スタイルが適用されることを期待してはなりません（MUST NOT）。

### Document 境界契約

現行実装のスタイル注入先はグローバル `document` です。したがって、複数 document、iframe 内 document、adopt された別 document などをまたぐ利用は、現時点では公開サポート対象として固定しません。

将来 `ownerDocument` 基準へ拡張する場合は、スタイル注入先、重複判定単位、ライフサイクルを改めて定義します。

## 境界条件

### 1. 既定状態

`<ui-divider></ui-divider>` は、`<hr data-divider-variant="section">` を出力します。

### 2. `layout` 指定

`<ui-divider variant="layout"></ui-divider>` は、`<hr data-divider-variant="layout">` を出力します。

### 3. 列挙外値

`<ui-divider variant="unknown"></ui-divider>` のような列挙外値は、描画時に `section` へフォールバックします。

### 4. ホスト `aria-label`

ホストに `aria-label` を付与しても、内側 `hr` へは転送しません。

### 5. ホスト `role`

ホストに `role` を付与しても、内側 `hr` へは転送しません。

### 6. スタイルスコープ外の通常 `hr`

`.prose` 配下でもなく、`ui-divider > hr` でもなく、`data-divider-variant="layout"` も持たない通常 `hr` には divider スタイルを適用しません。

### 7. コンポーネント実体なし

`ui-divider` が存在しない状態でも、スタイル注入が完了していれば `.prose hr` および `hr[data-divider-variant="layout"]` は契約どおりに描画されます。

## 契約が不明瞭な箇所と明確化方針

本節は、現行の `divider.ts` および `divider.stories.ts` を踏まえつつ、**現行実装への追従ではなく、長期的な設計の明瞭性と保守性を優先して**、契約上なお曖昧である箇所を整理するものです。

### 1. コンポーネント契約と文書スコープ契約の境界

現行の `ui-divider` は、単体コンポーネントであると同時に、`.prose hr`、`ui-divider > hr`、`hr[data-divider-variant="layout"]` に対する文書スコープスタイル契約も担っています。この二重性は説明可能ではあるものの、責務境界としてはなお曖昧です。

長期的には、次のどちらかへ収束させる方がよいです。

- `ui-divider` を純粋な `hr` ラッパーとして定義し、文書スコープスタイル契約を別文書・別モジュールへ分離します。
- 本書の名称と章立てを改め、単体コンポーネント契約と文書スコープ契約を同格の第一級契約として明示します。

設計のきれいさを優先するなら、前者を推奨します。

### 2. 正規経路が複数ある点

現行契約では、`ui-divider`、`.prose hr`、`hr[data-divider-variant="layout"]` の 3 経路が divider 規約に参加できます。しかし、これらを同格の公開面として扱うのか、主従を付けるのかがなお曖昧です。

長期的には、公開契約の正規経路を 1 本に絞る方がよいです。原則として `ui-divider` を唯一の正規経路にし、`.prose hr` と raw `hr[data-divider-variant="layout"]` は上位文書契約または補助的参加面に落とす方が、公開面を整理しやすくなります。

### 3. `variant` の意味

現行の `variant` は視覚差分ではなく用途識別に使われていますが、名前としては視覚バリアントのようにも読めます。このため、意味分類なのか見た目分類なのかが契約上なお不鮮明です。

長期的には、`variant` を**意味分類**として固定する方がよいです。すなわち、`section` / `layout` はまず使用文脈の差を表し、視覚差分は必要な場合にのみ従属的に導入します。

### 4. `section` と `layout` の配置文脈

現行文書は `section` を本文の節区切り、`layout` をレイアウト境界として説明していますが、どの構造でどちらを使うかという配置文脈はまだ十分に厳密ではありません。

長期的には、少なくとも次の水準まで意味を固定する方がよいです。

- `section`: prose 文脈における話題転換、節区切り、本文内の静かな境界
- `layout`: prose 外の領域分節、補助カラム境界、コンテナ群の構造境界

### 5. `data-divider-variant` の公開性

`data-divider-variant` は出力契約に含めていますが、正式な連携フックとして維持するのか、`ui-divider` の内部詳細にとどめるのかはなお曖昧です。

長期的には、次のどちらかへ明確に寄せる方がよいです。

- raw `hr[data-divider-variant]` を正式サポートし、属性名と値体系を公開連携面として維持します。
- raw `hr` 連携を縮退させ、`data-divider-variant` を `ui-divider` の内部出力詳細として扱います。

公開面を絞るなら、後者が望ましいです。

### 6. export されている補助要素の扱い

`ensureDividerDocumentStyles()`、`DOCUMENT_STYLE_ID`、`DIVIDER_SCOPE_SELECTOR` などを export している場合、それらを公開 API とみなすか、Storybook やテストの都合による内部要素とみなすかを明確にする必要があります。

長期的には、これらを公開 API に含めない方がよいです。Storybook や検証用の補助 import は internal test helper 側へ寄せ、本体モジュールの公開面からは外す方が保守しやすくなります。

### 7. import 副作用の位置づけ

現行ではモジュール評価時にスタイル注入が走ります。これは便利ですが、`ui-divider` の import が即座に文書スタイルへ副作用を与える設計を恒久採用するのかは、なお判断余地があります。

長期的には、次のどちらかへ固定する方がよいです。

- import 副作用を正式仕様として保証します。
- 文書スタイル適用を明示的な bootstrap API に分離します。

設計の透明性を優先するなら、後者の方が明瞭です。

### 8. スタイル注入のライフサイクル

現行実装では、注入済みスタイルは document 単位で残り続けます。これは合理的ですが、インスタンス寿命との関係がまだ設計方針として十分に言語化されていません。

長期的には、divider スタイルは**document lifetime に属する常駐資産**であると固定する方がよいです。参照カウント制御や切断時自動削除は、この種の静的スタイルには不要です。

### 9. `document` と `ownerDocument` の基準

現行実装はグローバル `document` を前提としています。単一 document アプリケーションでは十分ですが、複数 document や iframe まで一般化するかは決め切れていません。

長期的には、Rouault のスコープを単一 document に固定するか、`ownerDocument` 基準へ昇格するかを明示する必要があります。一般性を重視するなら `ownerDocument` 基準の方がきれいですが、現行要件では単一 document 固定でも成立します。

### 10. ホスト属性の扱い

現行文書は host 属性が内側 `hr` に転送されないことを明記していますが、`role`、ARIA 属性、`class`、`style` をどの強さで許容・非推奨・禁止するかはまだ分化し切れていません。

長期的には、少なくとも次を固定する方がよいです。

- `role` や ARIA による意味変更は採りません。
- `class` / `style` は host 自身への調整に限って許容します。
- host 属性は `ui-divider` の意味論を拡張する契約ではありません。

### 11. light DOM の公開性

現行実装は light DOM を採用していますが、これは単なる実装詳細なのか、外部 CSS、検査、DOM 観測を可能にする公開性なのかを明確にした方がよいです。

長期的には、`ui-divider` は prose や外側 CSS との接続を重視するため、light DOM を事実上の公開前提として扱う方が自然です。ただし、保証するのは「内側に単一の `hr` を描画すること」までに留め、DOM 構造の過剰固定は避ける方がよいです。

### 12. 子要素の扱い

現行では公開スロットを持ちませんが、子要素を与えた場合の扱いを明文で禁止しているわけではありません。

長期的には、`ui-divider` は子ノードを受理しないコンポーネントとして明記する方がよいです。内容差し替えやラベル埋め込みを想定する余地を残さない方が責務を明確にできます。

### 13. スタイル拡張面

現行文書は参照トークンを示していますが、どのカスタムプロパティや selector 上書きを正式な調整面とみなすかはまだ厳密ではありません。

長期的には、スタイル拡張契約を独立節として設け、次を明確化する方がよいです。

- 正式に調整可能なトークン
- 正式な調整手段として許容する方法
- 非推奨または内部詳細に依存する上書き方法

### 14. `.prose hr` を divider が担う責務範囲

現行では `.prose hr` が divider スタイルへ自動参加しますが、これは divider 単体の責務というより、上位の prose / markdown 契約に近い側面があります。

長期的には、「`.prose hr` は上位文書契約により divider 扱いとみなされる」と参照関係で記述する方が、責務の所在を明確にできます。

### 15. 名前付き separator の非対応

現行設計は無名の `hr` を前提としており、名前付き separator やラベル付き区切りは対象としていません。ただし、その非対応方針はまだ本文で十分には強調していません。

長期的には、名前付き separator は `ui-divider` の責務外であることを明記する方がよいです。ラベルが必要な場合は、見出しや別コンポーネントで扱います。

### 16. Storybook 契約の範囲

現行 Storybook は有用ですが、内部 helper や selector 文字列まで契約確認の文脈に入ると、公開面が不用意に広がります。

長期的には、Storybook を次の 2 層に分けて考える方がよいです。

- 公開契約 Story: 利用者が依存してよい事実のみを検証します。
- 内部検証 Story / test: selector、style tag ID、internal helper などを検証します。

## 本文改訂案（長期方針）

本書を今後改訂する場合は、現行実装の説明を厚くするだけでなく、契約の重心を明確にする方向で再構成する方がよいです。長期方針としては、次の形を推奨します。

### 1. 契約書の分離

最も望ましいのは、契約書自体を次の 2 文書へ分けることです。

- `divider.md`: `ui-divider` 単体の公開契約
- `divider-document-styles.md`: `.prose hr` と raw `hr[data-divider-variant]` を含む文書スコープ契約

これにより、コンポーネント契約書に global style bootstrap の議論を混在させずに済みます。

### 2. `ui-divider` を唯一の正規経路に寄せる

長期的には、公開契約の主経路を `ui-divider` に一本化する方がよいです。`.prose hr` と raw `hr[data-divider-variant="layout"]` は、上位文書契約または補助的な escape hatch に位置付けます。

### 3. `variant` を意味分類として固定する

`variant` は視覚差分ではなく、使用文脈の分類として固定します。視覚差分は必要な場合に限り、意味分類へ従属させて導入します。

### 4. 文書スコープスタイルの適用を明示的にする

import 副作用を設計として保証し続けるよりも、文書スコープスタイルの適用は明示的な bootstrap API に切り出す方が透明です。たとえば `installDividerDocumentStyles(targetDocument)` のような明示 API に分離すると、責務境界が明確になります。

### 5. internal helper を公開面から外す

`ensureDividerDocumentStyles()`、selector 定数、style tag ID などは Storybook / test helper 側へ寄せ、本体モジュールの公開 export からは外す方がよいです。

### 6. スタイル拡張契約を独立節として追加する

本書には、次の内容を持つ独立節を追加する方がよいです。

- 公式に保証するトークン参照
- 低特異性 selector 提供の位置づけ
- 推奨される調整手段
- 内部 selector への直接依存を避けること

### 7. `.prose hr` の責務を上位文書へ逃がす

`.prose hr` が divider 扱いとなる理由は、divider 単体の都合ではなく prose / markdown の上位契約に属します。したがって、将来の本文改訂では「`.prose hr` は上位文書契約から参照される」という構造へ寄せる方がよいです。

### 8. 非対応方針をより強く明記する

次の事項は、将来も採らない方針としてより強く明示する方がよいです。

- ラベル付き divider
- 名前付き separator
- インタラクティブ境界
- 見た目だけの variant 増殖

## 補足

`ui-divider` の要点は、線を引くこと自体ではありません。**どの `hr` に divider 契約を適用するかを限定しながら、意味論と読書リズムを両立させること**にあります。

したがって、今後の変更でも次の 5 点は崩さない方がよいです。

1. 実体は常にネイティブ `<hr>` であること。
2. 適用スコープを限定し、通常の `hr` へ漏らさないこと。
3. 文書スコープ契約をコンポーネント実体の有無に依存させないこと。
4. import 副作用と document 単位のスタイル保持を偶発的な実装として扱わないこと。
5. `variant` を現時点では用途識別として扱い、過度な視覚差分を持ち込まないこと。
