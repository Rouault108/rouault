# Skip Link

## 概要

本書は、`ui-skip-link` の**長期的に安定させるべき契約**を定義するものです。

`ui-skip-link` は、キーボード利用者およびスクリーンリーダー利用者が、反復的なナビゲーションや補助 UI を飛び越えて、主コンテンツへ最短で到達するための単一導線コンポーネントです。契約上の中核は、**ページ先頭で捕まえられること**、**必要時のみ即時に可視化されること**、**起動後に主コンテンツへフォーカスが移ること**の 3 点です。

Rouault における skip link は、単なるアクセシビリティ部品ではなく、**読む行為へ復帰するための低ノイズな導線**です。したがって本契約書では、現行実装の細部よりも、設計の純度・保守性・再現性を優先して定義します。

---

## 設計方針

本コンポーネントの設計方針は次のとおりです。

- `ui-skip-link` は**単一 destination 専用**とする。
- 複数のスキップ先を束ねる責務は持たせない。
- 対話主体は**ネイティブ **``** 1 要素**に限定する。
- アクセシブル名の源泉は**可視ラベルのみ**とする。
- 起動後の事後条件は、**ターゲット要素がフォーカスを持ち、読書開始位置が画面内で視認可能になること**とする。
- ページ先頭配置はコンポーネント単体の責務ではなく、**ページ統合契約**として分離する。
- URL ハッシュ更新や履歴操作には依存せず、**コンポーネント自身が起動後状態を決定可能**であることを優先する。

複数 destination が必要な場合は、`ui-skip-link` を拡張せず、別コンポーネント `ui-skip-nav` のような上位導線コンポーネントへ責務を分離する方針とします。

## コンポーネント公開契約

### 契約の中心概念

`ui-skip-link` は、一般 URL を扱うリンクコンポーネントではありません。**同一文書内の読書開始位置を指す単一ターゲット導線**です。

長期契約上の本質的な入力は「どこへ移るか」と「何と表示するか」です。そのため、意味論としては `href` より `` の方が適切です。

### 公開 API 方針

長期契約では、公開入力の正規名を ``とします。現行実装との互換のために`href` が残る場合でも、これは**互換エイリアス**としてのみ扱います。

| 名前       | 種別                 | 必須   | 内容             | 契約                                                                                              |
| ---------- | -------------------- | ------ | ---------------- | ------------------------------------------------------------------------------------------------- |
| `targetId` | property / attribute | いいえ | ターゲット識別子 | `main-content` のような同一文書内要素 ID を受け付けます。`#` は含めません                         |
| `label`    | property / attribute | いいえ | 表示ラベル       | 可視ラベルとして描画されます。既定値は `メインコンテンツへスキップ` です                          |
| `href`     | property / attribute | いいえ | 互換入力         | 当面は `#main-content` のような入力を受け付けてもよいですが、長期契約上の正規入力とはみなしません |

既定値は次のとおりです。

- `targetId`: `main-content`
- `label`: `メインコンテンツへスキップ`

### 入力値制約

- `targetId` は同一 `document` 内で一意に解決できる ID でなければなりません（MUST）。
- `targetId` は空文字列であってはなりません（MUST NOT）。
- `targetId` は CSS セレクタとして解釈してはなりません（MUST NOT）。
- `label` は `trim()` 後に非空でなければなりません（MUST）。
- `label` 中の改行、タブ、連続空白は、長期契約上は単一空白へ正規化したうえで解釈します（MUST）。
- `label` は単一行テキストとして扱います。複数行表示を前提にしてはなりません（MUST NOT）。
- `label` には、移動先が利用者に分かる文言を用いるべきです（SHOULD）。

### 非対応入力

次の入力は公開契約に含めません。

- 外部 URL
- 相対 URL
- CSS セレクタ
- 別 document や別 iframe を指すターゲット
- 非一意なターゲット
- 空文字列または空白のみの `label`

### スロット契約

`ui-skip-link` は公開スロットを持ちません。表示内容は `label` によってのみ決定されます。内部アンカーの文言をスロットで差し替えることは認めません。

### 公開メソッド

| 名前              | 種別   | 契約                                                          |
| ----------------- | ------ | ------------------------------------------------------------- |
| `focus(options?)` | method | 内部の対話主体であるネイティブ `<a>` にフォーカスを委譲します |

`click()`、`blur()`、または独自の起動 API は公開しません。

### 属性反映契約

`targetId`、`label`、`href` は属性入力を受け付けてもよいですが、property 変更が host attribute へ反映されることは公開契約に含めません。

アクセシブル名は**内部アンカーの可視ラベル**により決定するものとし、host 側の `aria-label` 反映は長期契約に含めません。

### 公開しないもの

次のものは公開契約に含めません。

- 内部 DOM 構造の詳細
- 内部セレクタ名
- `clip-path`、transform、z-index の具体値
- ホスト要素の `tabindex` 実装詳細
- host 側の `aria-label`、`role`、`tabindex` の有無

## 起動契約および事後条件

### 起動契約

起動はネイティブ `<a>` に対する Enter または click により行います。長期契約では、起動処理は**コンポーネント管理型**とし、ネイティブハッシュ遷移へ委ねません。

起動時の処理順は次のとおりです。

1. 既定動作を抑止します。
2. `targetId` を用いて同一 `document` 内からターゲットを解決します。
3. 正規ターゲットが見つかった場合、その要素へ programmatic focus を行います。
4. ターゲットがビューポート外または視認困難な位置にある場合、`scrollIntoView({ block: 'start', inline: 'nearest', behavior: 'auto' })` と同等の結果を与えるスクロールを行います。
5. `stopPropagation()` は行いません。イベントは通常どおり上位へ伝播してよいものとします。

### 事後条件契約

本コンポーネントの起動後に保証すべき契約は、次の 2 点です。

- ターゲット要素がフォーカスを持つこと
- ターゲット要素、またはその読書開始位置がビューポート内で視認可能であること

観測可能な事後条件は次のように固定します。

- ターゲットが存在し、正規入力である場合、起動後にターゲット要素が `document.activeElement` と整合する状態になること
- 起動後、利用者が追加のスクロールなしに読書開始位置を認識できること

### 非保証事項

次のものは長期契約として保証しません。

- URL ハッシュの更新
- ブラウザ履歴への追加
- UA 依存のフラグメント遷移挙動
- Space キーによる起動

---

## 責務範囲

本コンポーネントの責務は次のとおりです。

- 単一の skip link を描画すること
- 非表示待機状態とフォーカス可視状態を提供すること
- 起動時にターゲットへフォーカス移動と必要最小限のスクロール調整を行うこと
- アクセシブル名を可視ラベルで提供すること
- 開発時に設定不備を検知し得ること

一方で、次の責務は含めません。

- 複数 destination の管理
- 起動後に見出しへ再移動すること
- フォーカスを元の位置へ戻すこと
- 追加アナウンスを行うこと
- ページ先頭配置を単体で保証すること
- ページ全体のフォーカス順を統制すること

## 状態モデル

### 基本状態

既定の `targetId` と `label` を持つ状態です。視覚的には退避していても、順次フォーカス参加対象であることを前提とします。

### 非表示待機状態

非フォーカス時、リンクは A11y ツリーから除去されずに視覚的に退避します。

この状態では次を満たさなければなりません。

- 視覚的に認知されないこと
- A11y ツリーには残ること
- ポインター操作の対象にならないこと

### フォーカス可視状態

リンクが `:focus-visible` になったとき、中央上部に即時表示されます。表示に探索コストを増やすアニメーションを含めてはなりません。

### 起動状態

リンク起動時、ターゲットが正しく解決できる場合は、その要素へフォーカス移動し、必要に応じて読書開始位置を視認可能にします。

### 設定不備警告状態

開発時には、ターゲット未存在、ターゲット非一意、またはターゲット構成不備を警告し得ます。これは描画停止ではなく、DX 支援です。

### 印刷時非表示状態

印刷時は常に非表示とします。

## DOM / Accessibility 契約

### 対話主体

対話主体は Shadow DOM 内の**単一のネイティブ **`` です。コンポーネント全体を擬似ボタン化したり、複数のフォーカス可能要素を持たせたりしてはなりません。

### ホスト契約

host は公開上の対話面ではありません。したがって、利用側は host に対して `role`、`aria-label`、`tabindex` を追加設定してはなりません（MUST NOT）。

### フォーカス契約

- 起動主体はネイティブ `<a>` とします。
- `focus()` はこの `<a>` へ委譲されなければなりません。
- ターゲットは programmatic focus を受け取れる必要があります。
- 標準構成として、ターゲットには `tabindex="-1"` を要求します。
- ターゲットは `hidden`、`inert`、`disabled` 相当、または読書開始位置として不適切な閉域にあってはなりません（MUST NOT）。

ここで重要なのは、`tabindex="-1"` そのものではなく、**起動後に主コンテンツへ確実にフォーカスが移ること**です。ただし、長期保守上の単純性を優先し、契約上の標準構成は `tabindex="-1"` とします。

### アクセシブル名契約

アクセシブル名は可視ラベルのみで決定します。host に別の名前源を重ねることは契約の本質ではありません。

### キー操作契約

- Enter による起動は保証します。
- Space による起動は保証しません。

### 非表示契約

非表示時も A11y ツリーから除外してはなりません。`display: none` や `visibility: hidden` のような完全除去は契約違反です。

## Visual Contract

`ui-skip-link` の視覚契約は、**通常時は静かで、必要時だけ強く見えること**です。

### 情報順位

- 通常時は読書面より前景化しません。
- フォーカス時のみ、一時的に最前面級の補助導線として現れます。
- 常時表示を前提にしてはなりません。

### レイアウト

- 表示位置は画面上部中央とします。
- 配置は固定配置を前提とします。
- ラベルは単一行とし、長文は省略表示を許容します。

### 視覚仕様

- 非フォーカス時は視覚的に退避します。
- 非フォーカス時は `pointer-events: none` と同等の結果を与えなければなりません。
- フォーカス時は即時に可視化します。
- 高コントラストで読めることを優先します。
- 出現に遅延的な transition を前提にしません。

### スタイル API

外部へ安定公開するスタイル面は、原則として `::part(link)` に限定します。

CSS Custom Properties はテーマ実装の便宜として利用し得ますが、**すべてのトークン名を長期安定 API とみなすわけではありません**。本コンポーネント単体では個別トークン名を固定せず、公開トークンは別途デザイントークン契約で管理します。

## ページ統合契約

本節は、コンポーネント単体ではなく、ページ側が満たすべき契約です。

### First Tab Stop

`ui-skip-link` は、ページ読み込み後の最初の Tab 操作で到達できる位置に統合しなければなりません。これはコンポーネントの内部責務ではなく、ページ統合責務です。

### 配置位置

ページ先頭、理想的には `<body>` 直下またはそれに準ずる最上位位置に配置します。先に到達可能なリンクやボタンが存在する構成は、skip link の価値を損ないます。

### 配置数

1 つの文書に対して、主コンテンツへ移る `ui-skip-link` は原則 1 個とします。複数の skip 導線が必要な場合は `ui-skip-nav` のような別責務へ分離します。

### ターゲット構成

ページ側は、主コンテンツ領域に一意なターゲット要素を用意しなければなりません。標準構成は次のとおりです。

```html
<main id="main-content" tabindex="-1">...</main>
```

### 文書構造との整合

skip link のターゲットは、実際に読み始めるべき主要領域を指さなければなりません。視覚上の目立つ要素ではなく、読書開始位置として妥当な要素を選ぶ必要があります。

## 境界条件

### 1. 既定構成

`<ui-skip-link></ui-skip-link>` は `main-content` を指す単一導線として成立しなければなりません。

### 2. カスタムターゲット

別の `targetId` を指定できますが、同一文書内に存在し、programmatic focus を受け取れ、読書開始位置として妥当な要素に限ります。

### 3. 長いラベル

長いラベルは単一行のまま省略表示を許容します。可視上は切り詰めても、意味が保持される文言設計を求めます。

### 4. 短すぎるラベル

極端に短いラベルは技術的には描画できても、契約上の良い入力とはみなしません。移動先が判別できる文言を要求します。

### 5. ターゲット未存在

ターゲットが存在しない場合、起動はできても skip 契約は成立しません。開発時警告の対象です。

### 6. ターゲットが `tabindex="-1"` を持たない場合

技術的にフォーカスできる場合があっても、標準契約には適合しません。

### 7. 互換入力 `href`

`href` が残る場合でも、`#<id>` の互換入力としてのみ扱います。一般リンクとしては解釈しません。

### 8. host の属性上書き

host に対して `tabindex`、`role`、`aria-label` 等を利用者が追加することは契約違反とみなします。

## 新規で追加を検討する価値がある機能

本節は、`ui-skip-link` の責務を壊さずに追加を検討する価値がある機能を整理するものです。判断基準は、機能量の多さではなく、**主コンテンツ到達の確実性を高めるか**、**契約をより明確にするか**、**別責務へ分離した方がきれいか**の 3 点とします。

### 優先度が高い機能

#### 1. 起動後の視認性を保証するスクロール制御

最優先で検討する価値があります。skip link の価値は、単にフォーカスを動かすことではなく、利用者が**追加操作なしで読書開始位置へ到達できること**にあります。

そのため、ターゲットがビューポート外または固定ヘッダーの下に潜る場合でも、起動後に読書開始位置が視認可能になるよう、必要最小限のスクロール制御を持つことには明確な価値があります。

長期契約上は、任意の派手なアニメーションや挙動選択を公開するのではなく、`behavior: auto` 相当の即時スクロールを既定挙動として持つ形が望ましいです。

#### 2. `targetId` 正規 API の導入

これは見た目上は機能追加ではなく API 整理ですが、実質的には利用者の誤用を減らし、契約と実装の意味論を一致させるための重要な改善です。

`href` は URL を連想させますが、本コンポーネントが扱うのは一般リンクではなく、同一文書内の読書開始位置です。したがって、`targetId` を正規入力とし、`href` は互換入力へ退かせることには高い価値があります。

#### 3. 入力正規化と開発時検証の強化

本コンポーネントは小さいため、入力正規化と開発時検証を少し強くするだけで運用品質が大きく上がります。

とくに次は追加価値が高い項目です。

- 接続時の初期検証
- `targetId` 未解決時の警告強化
- `label` の空値・空白値・改行値の警告
- ターゲットが `hidden`、`inert`、または読書開始位置として不適切な状態にある場合の警告
- `targetId` と `href` の併用時警告

### 条件付きで検討価値がある機能

#### 4. 固定ヘッダー環境への補助契約

固定ヘッダーを持つページでは、skip 後のターゲットがヘッダー下に隠れる問題が起こり得ます。この問題自体への対応価値は高いですが、解決手段をコンポーネント本体の公開 prop として持たせるかどうかは慎重であるべきです。

長期的には、まずページ統合契約としてターゲット側へ `scroll-margin-top` を与える方針を標準化し、それでも不足がある場合に限って補助 API を検討するのが妥当です。

#### 5. 開発専用の失敗観測手段

ターゲット未解決や契約不適合を、開発時により観測しやすくする手段には一定の価値があります。具体的には、診断イベント、デバッグフラグ、またはテスト補助のための観測ポイントが候補になります。

ただし、本体の責務を重くしやすいため、まずは `console.warn` の充実と Storybook / E2E の強化を優先し、それで不足する場合にのみ検討すべきです。

### 本体ではなく別責務で検討すべき機能

#### 6. 複数 skip destination を束ねる導線

`本文へ`、`検索へ`、`目次へ`、`注釈一覧へ` のように複数のスキップ先を束ねる要求には現実的な価値があります。

ただし、これは `ui-skip-link` 自身の責務へ含めるべきではありません。単一導線という純度を守るため、必要なら `ui-skip-nav` のような別コンポーネントとして定義すべきです。

### 追加しない方がよい機能

#### 7. `disabled`

skip link は存在するなら使えるべき導線です。`disabled` を導入すると、アクセシビリティ上の重要導線を任意に無効化できることになり、責務を壊します。

#### 8. 遅延的なアニメーションや装飾的演出

skip link は見つけさせないことが本質です。したがって、出現アニメーションや装飾演出を増やすことにはほとんど価値がありません。

#### 9. 一般リンクとしての拡張

外部 URL や任意ナビゲーションへ広げると、本コンポーネントは skip link ではなく汎用リンクに近づきます。これは責務の純度を損ない、採るべき方向ではありません。

### 結論

本体に追加を検討する価値が高いのは、次の 3 点です。

1. 起動後の視認性を保証するスクロール制御
2. `targetId` 正規 API の導入
3. 入力正規化と開発時検証の強化

さらに大きな価値があるのは、本体を多機能化することではなく、必要に応じて `ui-skip-nav` のような**別責務の導線コンポーネント**を設計することです。

## 補足

本コンポーネントの要点は、見えないリンクを描画することではありません。**ページ先頭で捕まえられ、主コンテンツへ戻るための最短経路を、静かな見た目で提供すること**です。

したがって、今後の変更でも次の原則は維持した方がよいです。

1. 対話主体は常にネイティブ `<a>` であること。
2. アクセシブル名は可視ラベル 1 つに寄せること。
3. 起動後の事後条件を「ターゲットへフォーカスし、読書開始位置が視認可能になること」で固定すること。
4. 複数 destination の責務を持ち込まないこと。
5. ページ先頭配置をページ統合契約として分離すること。
6. 一般 URL 概念を持ち込まず、ターゲット識別子として扱うこと。

## 現行実装との差分および移行課題

本節は、現行実装がこの長期契約にまだ完全一致していない点を整理するものです。

### 1. 公開入力名の移行

現行実装は `href` を用いていますが、長期契約では `targetId` を正規入力とします。互換エイリアスを経由した移行設計が必要です。

### 2. 起動処理の管理方式

現行実装はネイティブハッシュ遷移を完全には抑止していないため、長期契約が求めるコンポーネント管理型の起動順序へ移行する必要があります。

### 3. スクロール事後条件の固定

現行実装はフォーカス移動中心であり、読書開始位置の視認可能性までを明示的には固定していません。長期契約に合わせるには、必要最小限のスクロール契約を加える必要があります。

### 4. アクセシブル名の二重化

現行実装は host 側への `aria-label` 反映を含みますが、長期契約では可視ラベル単独を名前源とします。

### 5. `label` 正規化の実行時強制

契約上は `label` を正規化して単一行・非空として扱いますが、実装側でその制約を厳密に強制する整備が必要です。

加えて、現行 Storybook には極端に短い `label="移動"` を許容する境界例が含まれており、長期契約が要求する「移動先が判別できる文言」と整合していません。この点は Storybook 側の追随対象です。

### 6. host 属性の封止

長期契約では host を公開対話面とみなしません。host への `tabindex`、`role`、`aria-*` を利用者が触れない形へ整理する余地があります。

### 7. 非表示時のポインター契約

視覚的非表示に加え、`pointer-events: none` と同等の結果を保証する実装整理が必要です。

### 8. `targetId` の検証時機

長期契約では接続時および `targetId` 変更時の検証を標準とし、必要なら開発用再検証戦略を別途設ける余地があります。

現行実装は `href` が変更された場合にのみ `validateTargetConfiguration()` を実行するため、既定値のまま接続されたケース、ターゲット側が後から DOM へ追加されたケース、またはターゲット属性が後から変化したケースを自動再検証しません。

### 9. Storybook の追随

現行 Storybook は `href` 前提や iframe 制約下の確認を含みます。長期契約に合わせて、`targetId` 前提・事後条件前提の記述へ更新する必要があります。

加えて、現行 Storybook には次の未追随があります。

- docs と argTypes が依然として `href` を正規入力として説明していること
- `href` を「IDセレクタ」と表現しており、実装実態である `getElementById()` ベースの ID 解決と語義がずれていること
- `SkipNavigationFlow` が iframe 制約のため、実クリック時の既定動作抑止・フォーカス移動・スクロール事後条件を直接検証していないこと
- `HiddenByDefault` が視覚的非表示は検証していても、`pointer-events: none` 相当の非操作性までは検証していないこと
- `LabelBoundaries` が長期契約上は非正規入力に寄せたい短すぎるラベルを現在は例示していること

### 10. 不正入力の黙殺

現行実装は `href` が `#` で始まらない場合や、`#` のみで実質的に空ターゲットになる場合、例外や警告を出さずに静かに処理を打ち切ります。長期契約では `targetId` の正規入力を明確にする方針であるため、不正入力を黙殺するのではなく、少なくとも開発時には診断可能にする余地があります。

### 11. 警告対象の不足

現行実装の警告対象は、ターゲット未存在と `tabindex="-1"` 不足にほぼ限られます。長期契約で重要になる次の不適合は、まだ検知対象に含まれていません。

- ターゲットが `hidden` または `inert` 相当であること
- ターゲットが読書開始位置として不適切な閉域にあること
- `label` が空、空白のみ、または改行を含むこと
- `targetId` と `href` の競合入力

### 12. 非一意ターゲットの検出不能

長期契約ではターゲット ID の一意性を要求しますが、現行実装は `getElementById()` に依存しており、重複 ID がある不正文書を明示的には検出しません。文書側の不備として扱うにしても、契約と検証能力の差としては明記しておく方がよいです。

### 13. 開発時警告環境の判定方式

現行実装の警告は `process.env.NODE_ENV`、または `localhost` / `127.0.0.1` を用いたヒューリスティック判定に依存しています。したがって、実際には開発相当の環境でも警告が出ない場合があります。長期契約としては警告の存在だけでなく、どの環境で一貫して有効にするかも移行課題です。
