# Callout

## 1. 概要

本書は、`ui-callout` の長期的な公開契約を定義するものです。

`ui-callout` は、本文から一段だけ引いた**非対話の補助情報ブロック**です。通知システム、バナー、トースト、ダイアログの代替とは位置付けません。主目的は、本文の読書リズムを壊さずに、補足、助言、成立状態、注意喚起を静かに区切って提示することです。

したがって、本書では現行実装の細部よりも、設計の明瞭さ、意味の一貫性、保守性の高さを優先して契約を定義します。現行実装との差分は末尾に分離して記載します。

---

## 2. 適用範囲

本書は、`ui-callout` の次の事項を対象とします。

- 公開契約
- 状態モデル
- DOM / Accessibility
- Visual Contract
- 環境別の振る舞い
- 関連契約
- 境界条件
- 検証契約
- 追加を検討する価値が高い機能
- 現行実装との差分

本書は、次の事項を対象外とします。

- ページ全体でどの種類の callout をどの頻度で使うかという編集方針
- Markdown から `ui-callout` をどう生成するかというパーサ契約
- callout 内の個別コンテンツ記法の詳細
- Iconify アイコンセット自体の提供方針
- `banner`、`dialog`、`toast` など他種コンポーネントの責務

これらは上位レイヤまたは別契約の責務です。

## 3. 公開契約

`ui-callout` の長期公開 API は、`** / **`\*\* / **\*\* / \*\*** / \*\*\`\` を中心に定義します。本文は既定スロットから受け取ります。

この設計では、**意味種別**、**可視見出し**、**アクセシブル名**を分離します。これにより、HTML グローバル属性との衝突、ARIA 生属性への依存、意味と見た目の混線を避けます。

### 3.1 入力契約

| 名前           | 種別                                   | 必須   | 内容                         | 契約                                                                        |
| -------------- | -------------------------------------- | ------ | ---------------------------- | --------------------------------------------------------------------------- |
| `kind`         | property / attribute                   | いいえ | callout の意味種別           | `note` / `tip` / `success` / `warning` / `danger`。既定値は `note` とします |
| `heading`      | property / attribute                   | いいえ | 可視見出し                   | 前後空白を除去して評価します。空白のみは未指定として扱います                |
| `label`        | property / attribute                   | いいえ | 見出しなし時のアクセシブル名 | `heading` がない場合にのみ使用します。空白のみは未指定として扱います        |
| `icon`         | property / attribute                   | いいえ | 装飾アイコン上書き           | 空文字列の場合は `kind` ごとの既定アイコンを使用します                      |
| `headingLevel` | property / attribute (`heading-level`) | いいえ | 見出しレベル                 | `heading` があり、かつ整数 1〜6 の場合のみ有効とします                      |

### 3.2 意味種別契約

`kind` は見た目テーマではなく、**補助情報の意味種別**です。用途は次のとおりです。

| `kind`    | 意味                               | 想定用途                       |
| --------- | ---------------------------------- | ------------------------------ |
| `note`    | 中立的な補足                       | 前提、補記、余談               |
| `tip`     | 実践上の助言                       | ヒント、コツ、推奨操作         |
| `success` | 成立済みの良好状態                 | 完了、成功、達成               |
| `warning` | 非破壊の注意喚起                   | 制約、警告、留意点             |
| `danger`  | 重大な失敗や損失につながる注意喚起 | 破壊的結果、重大注意、高リスク |

`kind` は単なる色選択に使用しません。特に `danger` は装飾目的で使用しません。

### 3.3 既定アイコンと既定ラベル契約

`kind` ごとの既定アイコンおよび既定ラベルは次のとおりです。

| `kind`    | 既定アイコン            | 既定ラベル |
| --------- | ----------------------- | ---------- |
| `note`    | `lucide:info`           | `補足`     |
| `tip`     | `lucide:lightbulb`      | `ヒント`   |
| `success` | `lucide:check-circle`   | `成功`     |
| `warning` | `lucide:alert-triangle` | `警告`     |
| `danger`  | `lucide:alert-octagon`  | `危険`     |

既定ラベルはアクセシブル名の最終フォールバックです。より具体的な読み上げを必要とする場合は、`heading` または `label` を明示指定します。

### 3.4 アクセシブル名契約

アクセシブル名の決定順序は次のとおりです。

1. `heading` がある場合は `aria-labelledby` を用います
2. `heading` がなく、`label` が非空の場合は `aria-label` を用います
3. `heading` がなく、`label` が空または未指定の場合は `kind` ごとの既定ラベルを用います

`heading` がある状態では `label` に依存しません。`label` は見出しなし callout のための補助入力としてのみ扱います。

### 3.5 スロット契約

| 名前         | 種別 | 位置づけ | 内容                       |
| ------------ | ---- | -------- | -------------------------- |
| 既定スロット | slot | 正規入力 | callout 本文を受け取ります |

名前付きスロットは公開しません。見出し、ラベル、アイコンはスロットではなく公開入力で制御します。

### 3.6 内容モデル契約

既定スロットは、**本文を構成する非対話中心のフローコンテンツ**を正規入力とします。少なくとも次の内容を許容します。

- 段落
- リスト
- インラインリンク
- インラインコード
- コードブロック
- 短い引用

一方で、次のものは `ui-callout` の正規責務に含めません。

- フォーム要素
- 複数の主要アクション
- 折りたたみや展開を前提とする対話コンテナ
- 内部状態を持つ複合 UI

対話要素を内部に配置する設計は採りません。action 付き callout が必要な場合は別コンポーネントへ分離します。

### 3.7 ホスト属性契約

`ui-callout` は、ホストへ与えられた生の `aria-*` 属性を公開 API として採用しません。アクセシブル名は `label` 入力と `heading` 入力により構成します。

したがって、次のものは公開入力として扱いません。

- `aria-label`
- `aria-labelledby`
- `aria-describedby`
- `role`
- `data-*`

これらがホストに与えられていても、内部ルートへの自動転送や意味再解釈は保証しません。

### 3.8 属性反映契約

| property       | attribute       | reflect | 備考                                                 |
| -------------- | --------------- | ------- | ---------------------------------------------------- |
| `kind`         | `kind`          | あり    | 不正値は正規化後の正値を反映します                   |
| `heading`      | `heading`       | あり    | 空白のみは未指定として扱います                       |
| `label`        | `label`         | あり    | 空白のみは未指定として扱います                       |
| `icon`         | `icon`          | あり    | 空文字列は既定アイコンへ戻します                     |
| `headingLevel` | `heading-level` | あり    | 有効値でない場合は見出しセマンティクスに反映しません |

### 3.9 無効値契約

`kind` に列挙外値を与えた場合、コンポーネントは \`\`\*\* へ正規化\*\*します。正規状態は常に canonical value で表現し、ホスト属性にも正規化後の値を反映します。raw input と resolved state は二重に保持しません。

`headingLevel` に対して、非数、非有限値、小数、0 以下、7 以上を与えた場合は無効値として扱い、`role="heading"` および `aria-level` は出力しません。

空白のみの `heading` は未指定として扱います。空白のみの `label` も未指定として扱います。

### 3.10 公開メソッド / 公開イベント

`ui-callout` は独自の公開メソッドを持ちません。独自のカスタムイベントも公開しません。

これは「現時点では存在しない」という意味ではなく、`ui-callout` を**非対話の情報提示ブロック**として定義するためです。閉じる、展開する、切り替える、確定する、送信する、といった責務は持ちません。

### 3.11 責務範囲

責務範囲には、次を含みます。

- `kind` に応じた背景、アクセント、既定アイコン、既定ラベルの切り替え
- `heading` / `label` に基づくアクセシブル名の決定
- 任意の見出しセマンティクス付与
- 高コントラスト環境での境界視認性維持

責務範囲には、次を含めません。

- dismiss
- collapse / expand
- action 実行
- close button
- toast 的自動消滅
- 通知キュー管理

## 4. 状態モデル

`ui-callout` の状態は、主として `、`\*\* の有無\*\*、**見出しセマンティクスの有無**、**アクセシブル名の解決方法**で読み分けます。

### 4.1 基本状態

最小状態は、`kind="note"`、`heading=""`、`label=""`、`icon=""`、`headingLevel` 未指定の状態です。この場合、ルートは `note` 相当の見た目を持ち、アクセシブル名には `補足` を使用します。

### 4.2 `kind` 状態

`kind` は意味種別を決定します。

- `note` は中立的補足です
- `tip` は実践上の助言です
- `success` は成立済みの良好状態です
- `warning` は非破壊の注意喚起です
- `danger` は重大な失敗や損失につながる注意喚起です

`warning` と `danger` は色の違いだけで区別しません。利用文脈も明確に分けます。

### 4.3 `heading` 状態

`heading` が非空である場合、内部に見出し要素を描画します。`heading` が空、または空白のみである場合、見出し要素は描画しません。

### 4.4 見出しセマンティクス状態

`headingLevel` は単独では意味を持ちません。`heading` が存在し、かつ `headingLevel` が整数 1〜6 の場合に限り、見出し要素へ `role="heading"` と `aria-level` を付与します。

`ui-callout` はセクショニングコンテンツではありません。`headingLevel` は callout 自体を節にするためではなく、**先頭ラベルを見出しとして露出するための補助入力**です。

### 4.5 `label` 状態

`label` は、`heading` が存在しない場合にのみアクセシブル名へ反映します。`heading` が存在する場合、`label` はアクセシブル名決定に使用しません。

### 4.6 `icon` 状態

`icon` が非空である場合、その値を装飾アイコンとして使用します。`icon` が空文字列である場合は、`kind` ごとの既定アイコンを使用します。

アイコンは常に装飾要素です。意味決定は `kind`、`heading`、`label` のみで行います。

### 4.7 アクセシブル名状態

アクセシブル名は次のいずれかで確定します。

- `heading` による `aria-labelledby`
- `label` による `aria-label`
- `kind` ごとの既定ラベル

この決定順序は検証契約として固定します。

## 5. DOM / Accessibility

ルートは `:host` です。Shadow DOM 内部に単一の意味ブロックを持ち、その中に装飾アイコンと本文領域を配置します。

```text
<ui-callout>
  #shadow-root
    <aside part="container" data-kind="...">
      <iconify-icon part="icon" aria-hidden="true"></iconify-icon>
      <div class="content">
        [div part="heading"]
        <div part="body">
          <slot></slot>
        </div>
      </div>
    </aside>
</ui-callout>
```

### 5.1 ルート要素契約

ルート要素は `aside` とします。`ui-callout` は本質的に本文の外側に置かれる補助情報ブロックであり、通常の段落箱や単なる装飾コンテナとして扱いません。

### 5.2 アクセシビリティ契約

- ルート要素は `aside` とします
- `heading` あり状態では `aria-labelledby` により内部見出し要素を参照します
- `heading` なし状態では `aria-label` により callout 全体の名前を与えます
- `headingLevel` が有効な場合のみ見出し要素に `role="heading"` と `aria-level` を付与します
- アイコンは常に装飾要素であり、`aria-hidden="true"` とします
- 内部見出し id は公開安定 ID として扱いません

### 5.3 見出し契約

callout 内の見出しは、文書小節を形成するための section heading ではありません。callout 先頭の識別ラベルです。したがって、`ui-callout` は内部見出し階層の自動補正、見出しレベル昇降、アウトライン正規化を行いません。

スロット内部に追加見出しを置く構成は、正規入力として採りません。

### 5.4 内部 ID 契約

内部見出し要素へ付与される id は、`aria-labelledby` を成立させるための内部生成値です。外部安定値としては保証しません。

契約上保証するのは、`heading` あり状態で `aria-labelledby` が有効に結び付くことのみです。id の生成方式や具体値は内部実装に属します。

## 6. Visual Contract

`ui-callout` の視覚契約は、**控えめな背景差、左アクセントボーダー、装飾アイコン、見出し強調**によって、本文と補助情報の境界を静かに示すことにあります。

### 6.1 情報順位

- 背景色は本文面より一段だけ異なる弱い面とします
- 左アクセントボーダーは `kind` を示す主記号とします
- アイコンは補助記号とします
- 見出しは本文より強く、ページ見出しより弱く保ちます

callout は本文を遮る通知パネルではありません。強い面塗り、過剰なシャドウ、全面強境界線には依存しません。

### 6.2 レイアウト

ルートは `display: flex` とし、アイコンと内容を横並びにします。`align-items: flex-start` により先頭行基準で揃えます。内容領域は `min-width: 0` を持ち、長文や長いリンクでも過剰にはみ出しにくい構成とします。

### 6.3 見出しと本文

見出しは本文より一段強く表示します。本文と見出しは同系統の行間で整え、読書リズムを壊さない差にとどめます。

### 6.4 アイコン契約

アイコンは意味の唯一の担い手としません。`kind` とアクセシブル名が意味を担い、アイコンは視覚補助に限定します。

### 6.5 `kind` 別トークン

| `kind`    | 背景                  | アクセント     | アイコン色     |

| `note`    | `--bg-note-subtle`    | `--fg-muted`   | `--fg-muted`   |

## 7. 環境別の振る舞い

### 7.1 Dark Mode

`ui-callout` は `prefers-color-scheme` 分岐を内部に持ちません。ダークモード対応は、セマンティックトークンの差し替えによって成立します。

### 7.2 Forced Colors

`forced-colors: active` 環境では、境界視認性を最優先します。通常時の `kind` 差は縮退し得ます。最低限、次を維持します。

- callout の境界が背景から判別できること
- `danger` が他より強い注意として識別できること

完全な色差再現は契約しません。

### 7.3 Reduced Motion

本コンポーネントはアニメーション主体ではありません。Reduced Motion 専用契約は定義しません。

### 7.4 Print

印刷専用スタイルは必須契約に含めません。印刷時の背景再現可否はユーザーエージェントおよび印刷設定に依存します。

## 8. 関連契約

### 8.1 トークン供給契約

`ui-callout` は、セマンティックトークンが上位テーマ層から供給されることを前提とします。特に、背景、前景、アクセント、境界は必須トークンとします。

spacing、radius、font weight、icon size は推奨トークンとします。未供給時の縮退表示は許容しますが、同品質表示は保証しません。

### 8.2 スタイル拡張面契約

`ui-callout` の安定した styling surface は **トークン** と **最小限の part** です。公開する `part` は次の 4 つに限定します。

- `container`
- `icon`
- `heading`
- `body`

Shadow DOM 内部の class 名、DOM 階層、`data-kind` への直接依存は公開契約として扱いません。

### 8.3 アイコン解決契約

`icon` は `iconify-icon` の `icon` 属性へ渡します。アイコン名の意味解決は icon system 側の責務です。`ui-callout` 自身は、icon 名の妥当性検証、取得失敗時の代替描画、意味補完を保証しません。

アイコン解決失敗は視覚補助の低下として扱います。意味解決には影響しません。

### 8.4 多言語契約

`ui-callout` はコンポーネント単体でロケール切替を提供しません。既定ラベルはプロダクト既定語彙として扱います。多言語環境で別語彙を必要とする場合は、`heading` または `label` を明示指定します。

## 9. 境界条件

### 9.1 `heading` あり

`heading` が非空である場合、見出し要素を描画し、ルートは `aria-labelledby` を持ちます。`label` はアクセシブル名決定に使用しません。

### 9.2 `heading` なし

`heading` が未指定または空白のみである場合、見出し要素は描画しません。アクセシブル名は `label` または既定ラベルで決定します。

### 9.3 `headingLevel=1`

`heading` があり、`headingLevel="1"` の場合、見出し要素は `role="heading" aria-level="1"` を持ちます。

### 9.4 `headingLevel=0` / `7` / `2.5`

これらは無効値です。見出し要素は描画されても、`role` と `aria-level` は出力しません。

### 9.5 `headingLevel` 指定あり・`heading` なし

`heading` がない場合、`headingLevel` は無視します。

### 9.6 `icon` 上書き

`icon` が非空である場合、`kind` に関わらずその値を優先します。既定アイコンには戻りません。

### 9.7 空白 `heading`

`heading="   "` のような空白のみ入力は未指定として扱います。見出し要素は描画しません。

### 9.8 `label` 明示値

`heading` なし状態で `label` が非空なら、その値を既定ラベルより優先します。

### 9.9 空白 `label`

`label="   "` のような空白のみ入力は未指定として扱い、既定ラベルへ戻します。

### 9.10 不正 `kind`

`kind="unknown"` など列挙外値を与えた場合、コンポーネントは `kind="note"` へ正規化します。描画、アクセシブル名、既定アイコンはすべて `note` 相当になります。

## 10. 検証契約

Storybook やテストは、少なくとも次の観点を固定するものとします。

| 検証軸             | 確認内容                                                                    |
| ------------------ | --------------------------------------------------------------------------- |
| DOM 契約           | ルートが `aside` であり、公開 `part` が成立すること                         |
| Accessibility 契約 | `heading` / `label` / 既定ラベルの優先順位が正しく働くこと                  |
| Heading 契約       | `headingLevel` 有効時のみ `role="heading"` と `aria-level` が付与されること |
| `kind` 契約        | 5 種の意味種別が視覚とラベルで区別されること                                |
| 無効値正規化       | 列挙外 `kind` が `note` へ正規化されること                                  |
| アイコン契約       | `icon` 上書きと既定アイコンが成立すること                                   |
| Style 契約         | 境界、アクセント、背景差、forced-colors 時の縮退方針が維持されること        |
| Token 契約         | モード分岐の直書きではなく、トークン参照で配色が成立すること                |

## 11. 追加を検討する価値が高い機能

本節は、`ui-callout` の長期契約を崩さず、むしろ公開面を明確化する方向で追加を検討する価値が高い機能を定義するものです。

### 11.1 `label` 公開入力の追加

`label` は、`heading` を持たない callout のアクセシブル名を、コンポーネント固有 API として明示するための入力です。

この機能を追加する目的は、ホストの生 `aria-label` 属性への依存をやめ、公開契約をコンポーネント固有入力へ集約することにあります。これにより、意味決定の経路が明確になります。

`label` を追加する場合、次を契約とします。

- `heading` がある場合、アクセシブル名は `heading` により決定します
- `heading` がない場合、`label` が非空なら `label` により決定します
- `heading` も `label` もない場合、`kind` ごとの既定ラベルへ縮退します
- 生の `aria-label` は長期公開 API として採用しません

`label` は最優先で追加を検討する価値がある機能です。理由は、アクセシビリティ契約を最小の公開面で完結させられるためです。

### 11.2 `part` の最小公開

`ui-callout` は、内部 DOM 全体を公開拡張面としません。一方で、トークン差し替えだけでは不足する調整点に対応するため、最小限の `part` を公開します。

公開する `part` は次の 4 つに限定します。

- `container`
- `icon`
- `heading`
- `body`

この機能を追加する場合、次を契約とします。

- `part` は安定した styling surface として扱います
- Shadow DOM 内部の class 名、DOM 階層、`data-kind` は安定 surface として扱いません
- 新たな `part` の追加は慎重に行い、既存 `part` の意味は流用しません
- 外部調整は、まずトークン差し替えで行い、それで不足する場合にのみ `part` を使用します

`part` の最小公開は、クローズドな内部実装と外部調整可能性の均衡を取る機能として優先度が高いです。

### 11.3 移行期 alias 契約の追加

現行実装との差分を一挙に切り替えるのではなく、移行期には旧公開名を限定的に受け入れる alias 契約を追加する価値があります。

対象は次の 3 組です。

| 旧公開名     | 新公開名  |
| ------------ | --------- |
| `variant`    | `kind`    |
| `title`      | `heading` |
| `aria-label` | `label`   |

この機能を追加する場合、次を契約とします。

- 正規公開名は常に `kind` / `heading` / `label` とします
- 旧公開名は移行のためにのみ受理します
- 旧公開名と新公開名が同時に与えられた場合、新公開名を優先します
- 内部状態および最終反映属性は、新公開名に基づく canonical state へ正規化します
- alias は恒久公開面として扱いません

移行期 alias は、互換性のための便宜ではありますが、長期契約を汚さずに移行できるため、追加価値が高い機能です。

### 11.4 優先順位

最優先で追加を検討する価値がある機能の優先順位は次のとおりです。

1. `label` 公開入力
2. `part` の最小公開
3. 移行期 alias 契約

この順序は、アクセシビリティ契約の明確化、安定した拡張面の確保、移行容易性の順に重視したものです。

## 12. 補足

`ui-callout` の要点は、色付きの補足箱を描くことではありません。**本文から独立した補助情報であることを示しつつ、本文の読書体験を中断しないこと**にあります。

したがって、今後の変更でも次の 5 点を維持します。

1. `ui-callout` は非対話の補助情報ブロックとして扱います。
2. ルートは `aside` を維持します。
3. 意味種別、可視見出し、アクセシブル名を分離します。
4. アクセシブル名は `heading` / `label` / 既定ラベルの順で決定します。
5. スタイリングはトークンと最小限の `part` を中心に拡張します。

## 13. 現行実装との差分

本節は、長期契約と現行実装との差分を整理するものです。現行実装をただちに否定するものではありませんが、将来の整理対象を明示します。

### 13.1 `title` から `heading` への移行

現行実装は表示用見出し入力として `title` を使用します。長期契約では、HTML グローバル属性との衝突を避けるため、`heading` を正規公開名とします。

### 13.2 `aria-label` 直読みに代えて `label` を採用

現行実装はホストの `aria-label` を補助入力として読み取ります。長期契約では、生 ARIA 属性への依存を避けるため、`label` を正規公開入力とします。移行期には、旧入力としての `aria-label` を限定的 alias として受け入れてもよいですが、正規公開名としては扱いません。

### 13.3 `variant` から `kind` への移行

現行実装は `variant` を使用します。長期契約では、見た目差分の語感を避け、意味種別を表す `kind` を正規公開名とします。移行期には `variant` を alias として受け入れてもよいですが、正規公開名としては扱いません。

### 13.4 不正値の正規化反映

現行実装は列挙外値を内部的に縮退させても、ホスト属性へ raw input が残る場合があります。長期契約では、正規化後の canonical value をホスト属性へ反映します。

### 13.5 `danger` の既定ラベル

現行実装は `danger` の既定ラベルとして `注意` を使用します。長期契約では、意味強度を明確にするため `危険` を採用します。

### 13.6 `part` の公開

現行実装は `::part(...)` を公開していません。長期契約では、トークンだけで不足する調整点に対応するため、`container` / `icon` / `heading` / `body` を公開します。これは内部 DOM 全体を公開するのではなく、最小限の安定 surface を追加するものとします。

### 13.7 スロット内容制約の明確化

現行実装はスロット内容を広く受け入れます。長期契約では、非対話中心の本文フローコンテンツを正規入力とし、action 付き構成は別コンポーネントへ分離します。

### 13.8 移行期 alias 契約の未実装

長期契約では、移行期に限って `variant` / `title` / `aria-label` を旧公開名として受け入れつつ、`kind` / `heading` / `label` を正規公開名として優先する alias 契約を想定します。

現行実装は、この alias 契約をまだ持ちません。したがって、次の事項は未対応です。

- `variant` と `kind` の併存時に `kind` を優先すること
- `title` と `heading` の併存時に `heading` を優先すること
- `aria-label` と `label` の併存時に `label` を優先すること
- 旧公開名から新公開名への canonical state 正規化
- alias を移行専用入力として扱い、恒久公開面にしない運用

この差分は、単なる命名差ではなく、移行戦略そのものが未実装であることを意味します。
