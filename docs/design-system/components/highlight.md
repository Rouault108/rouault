# Highlight

## 概要

本書は、Rouault における highlight コンポーネントの**長期的な公開契約**を定義するものです。現行実装の都合を固定することではなく、**設計のきれいさ、責務分離、保守性**を優先して、どの契約を残し、どの契約を縮退または別文書へ分離するかを明確にします。

本コンポーネントの目的は、本文中の一部文字列を**意味的にマークされた箇所**として表現することです。強い装飾や対話機能を担うのではなく、**ネイティブ **``** を最終 DOM として出力し、本文読解の流れを壊さずに注意を添える**ことを第一目的とします。

また、本コンポーネントは本文フローと自然に統合されることを重視します。したがって、公開契約では次を優先します。

- 公開タグはできる限り 1 つへ絞ること
- タグ名ではなく property を意味源にすること
- 値と制御信号を分離すること
- component contract と document styling policy を分離すること
- 外部が依存してよい公開面を最小化すること

Rouault における highlight は、**「没入して読む」ことのできるデザイン**の一部として、検索ヒットや注目箇所を静かに示すために存在します。したがって、本書では**読書面の一貫性**と**長期保守性**を優先して契約を定義します。

## 適用範囲

本書は、highlight コンポーネントの次の事項を対象とします。

- 公開タグと公開入力
- コンテンツ入力契約
- 状態モデル
- DOM / Accessibility
- Visual Contract
- 環境別の振る舞い
- 関連契約
- 境界条件
- Storybook 契約
- 現行実装で未対応の事項

一方で、本書は次の事項を扱いません。

- 検索語の抽出アルゴリズム
- 検索ヒット集合の管理や `current-match` 切替ロジック
- 文書全体の検索 UI、検索移動、スクロール同期

- `.prose mark` を含む本文組版全体の見た目契約

- `current-match` 以外の追加バリアント設計
- 強いアニメーション表現

これらは上位レイヤまたは別契約の責務です。

## 設計判断

本書では、highlight を**検索結果中の文字列を本文内で示すための小さな inline semantic component**として定義します。汎用注目表現や注釈表現まで取り込まず、責務と語彙を意図的に狭く保ちます。

長期的な設計判断は次のとおりです。

- 公開タグは `ui-highlight` を唯一の正規タグとします。
- `ui-search-highlight` は長期契約上の正規タグに含めません。互換上残す場合でも、新規利用の基準にはしません。
- 本コンポーネントは**検索ハイライト専用**とし、`kind` のような意味分類入力は持ちません。
- `current` という汎用状態名は採らず、`current-match` という**検索文脈に限定された状態名**のみを採ります。
- `text` は子テキストを与えにくい場面のための**明示入力**として扱い、通常の宣言的入力はホスト直下のプレーンテキストを正規入力とします。
- `aria-current` の自動付与はコンポーネント責務に含めません。
- `.prose mark` の見た目契約とグローバル style 注入は本コンポーネントの責務に含めません。

この判断により、highlight は**検索ヒットの意味的マークアップ**に集中し、注釈機能、検索 UI、文書スタイル全体の policy を抱え込まない形へ整理します。

---

### 公開入力

`ui-highlight` は、`current-match` と `text` を公開入力として扱います。

| 名前            | 種別                 | 必須   | 内容                           | 契約                                                                 |
| --------------- | -------------------- | ------ | ------------------------------ | -------------------------------------------------------------------- |
| `currentMatch`  | property             | いいえ | 検索ヒット列の現在位置かどうか | boolean として扱います。既定値は `false` です                        |
| `current-match` | attribute            | いいえ | `currentMatch` の attribute 形 | boolean attribute として扱います                                     |
| `text`          | property / attribute | いいえ | 表示文字列                     | 子テキストを与えにくい場合の明示入力です。`null` のときのみ fallback を許可します |

### `current-match` 契約

`current-match` は、**検索ヒット列の中で現在位置にある要素**を表す状態です。

- `current-match=false` は通常の検索ヒットを表します。
- `current-match=true` は現在位置の検索ヒットを表します。
- `current-match` は意味状態であり、コンポーネント自身がアクセシビリティ属性へ自動変換することは公開契約に含めません。
- ただし、既定スタイルでは **`current-match=true` を `false` と識別可能にする最小限の視覚差分**を持たなければなりません。
- その差分は本文文字色の可読性を損なわず、強いアニメーションに依存してはなりません。

### `text` 契約

`text` は、子テキストを直接配置しにくい生成系コードやプログラム的描画のための**明示入力**です。

- `text` が非 `null` である場合、その値を表示に用います。
- `text` が `null` である場合に限り、初期子テキスト fallback を許可します。
- `text` が空文字列 `''` である場合、**空文字を明示した入力**として扱います。
- 解決後文字列が空である場合、本コンポーネントは**成功状態を形成しません**。

### 属性反映契約

`current-match` は reflect されます。`text` は attribute 入力を受理しますが、property から attribute への reflect は公開契約に含めません。

| property       | attribute       | reflect | 備考                                             |
| -------------- | --------------- | ------- | ------------------------------------------------ |
| `currentMatch` | `current-match` | あり    | boolean attribute として扱います                 |
| `text`         | `text`          | なし    | 明示入力です。正規の宣言的入力は子テキストです   |

## コンテンツ入力契約

### 入力優先順位

本コンポーネントは、次の順で表示文字列を解決します。

1. `text` が非 `null` である場合は、その値を使用します。
2. `text` が `null` である場合に限り、初期子テキストを使用します。
3. それでも解決後文字列が空である場合は、成功状態を形成しません。

### 正規入力

長期契約における**正規の宣言的入力**は、ホスト直下のプレーンテキストです。

```text
<ui-highlight>検索語</ui-highlight>
```

`text` は正規入力を置き換えるものではなく、子テキストを扱いにくい場面のための補助的入力です。

### 初期子テキスト fallback

初期子テキスト fallback は、`text === null` の場合に限り評価します。

fallback を許可する条件は次のとおりです。

- ホスト直下にプレーンテキストが存在すること
- そのテキストが初回接続時に読み取れること
- 接続後の子ノード変更に追従しないこと

### 子ノード文法

長期契約における正規入力文法は、**ホスト直下のプレーンテキストのみ**です。

- ホスト直下のプレーンテキストを正規入力として扱います。
- 直下 `<mark>` は長期契約上の正規入力に含めません。
- 任意の inline 要素子の `textContent` を吸収し続けることは公開契約に含めません。
- ネストされた `ui-highlight` を入力文法として認めません。

### テキスト正規化契約

文字列解決では、空白や改行を自動補完しません。初期子テキストを読む場合は、**元の文字列をできる限り保持し、前後の trim のみを行う**方針とします。

したがって、次を固定します。

- テキストノード間に区切り空白は自動挿入しません。
- 前後空白は除去します。
- 中間の空白や改行は入力由来のまま保持します。
- component 自身が文意を推測して文字列を再構成しません。

### 更新契約

初期子テキスト fallback は、**初回接続時に 1 回だけ**評価します。接続後は、初期子ノードを継続的な入力面として扱いません。

したがって、次を固定します。

- 接続後にホスト直下の子ノードを書き換えても、表示文字列は自動再解決しません。
- `MutationObserver` 等による Light DOM 監視は行いません。
- 接続後の表示更新は `text` の変更によってのみ行います。

## 状態モデル

`ui-highlight` の状態は、**現在ヒットかどうか**と、**表示文字列がどこから供給されたか**の 2 軸で読みます。

### 基本状態

最小状態は、`current-match=false`、非空文字列を 1 つ持つ状態です。この状態では、本文フローの中に静かな線状ハイライトとして描画されます。

### `current-match` 状態

`current-match=true` は、検索ヒット集合の中で現在位置にある要素を表します。

- `current-match=false` は非 current の検索ヒットです。
- `current-match=true` は current の検索ヒットです。
- `current-match` は意味状態ですが、既定スタイルでも**最小限の識別可能性**を持たなければなりません。
- その差分は、本文の読解を妨げない範囲に制限します。
- ARIA 属性への自動変換は別責務です。

### 文字列供給状態

表示文字列は、**明示入力**と**初期子テキスト fallback**のいずれかから供給されます。

- 明示入力: `text` による供給
- 正規の宣言的入力: ホスト直下のプレーンテキスト
- fallback 評価: 初回接続時のみ

この区別は、更新契約に直接関わります。

### 空文字状態

長期契約では、空文字 highlight を成功状態として扱いません。

- 解決後文字列が空である場合、最終 DOM に意味主体としての `<mark>` を形成しません。
- 実装は no-op としなければなりません。
- 開発時 warning を追加することは許容しますが、warning の有無は公開契約に含めません。

## DOM / Accessibility

### 最終 DOM 契約

意味表現の主体はホスト直下の `<mark>` です。最終 DOM は概ね次の形をとります。

```text
<ui-highlight current-match>
  <mark data-current-match="true">...</mark>
</ui-highlight>
```

または

```text
<ui-highlight>
  <mark data-current-match="false">...</mark>
</ui-highlight>
```

`mark` には次の属性を安定公開面として許可します。

| 属性                   | 契約                          |
| -------------------- | --------------------------- |
| `data-current-match` | `true` / `false` の文字列を出力します |

`kind`、`data-kind`、`annotation` に依存する出力は、長期公開契約に含めません。

### Accessibility 契約

アクセシビリティ上の重要点は次のとおりです。

- 意味主体はネイティブ `<mark>` です。
- `mark` は本文フローに留まり、ボタンやリンクのような対話主体になりません。
- `role`、`tabindex`、独自キーボード操作は公開契約に含めません。
- `aria-current` の自動付与は公開契約に含めません。
- 必要な ARIA 意味付けは上位レイヤが判断します。

highlight は**検索 UI そのものではなく、本文内の意味マークアップ**です。したがって、検索のアクセシビリティ policy 全体を内包しません。

### レイアウト / Selection 契約

本コンポーネントは、本文中の**インライン文脈**で使用することを前提とします。

したがって、次を固定します。

- ホストは本文フローに自然に挿入されるインライン要素として扱います。
- `mark` 自体は本文の `line-height`、`letter-spacing`、`white-space`、`text-wrap` を変更しません。
- ハイライトは選択可能テキストであり、コピー結果に不可視文字や補助記号を混入させません。
- 文字選択時も元の本文文字列を維持し、選択結果の意味内容を変えません。

## Visual Contract

`ui-highlight` の視覚契約は、背景塗りつぶしではなく、**本文色を維持したまま下方に控えめな強調を与えること**にあります。これは本文文字のコントラストを保ったまま、検索ヒットを静かに示すためです。

### 情報順位

- 本文文字色が主です。
- ハイライトは本文より前面に出ず、補助的に機能します。
- `current-match=false` と `current-match=true` は、既定状態でも識別可能でなければなりません。
- その差分は最小限にとどめ、読書面に不要な強調競合を持ち込みません。
- 色だけに依存せず、強制カラーおよび印刷では下線系の非色シグナルへ移行します。

### 視覚不変条件

通常モードでは、`mark` に対して少なくとも次を満たさなければなりません。

- `background` は本文塗りつぶしの主体にならないこと
- `color` は `inherit` を維持すること
- `padding` を持たないこと
- 複数行にまたがる場合でも行ごとの強調が途切れにくいこと
- 本文の `line-height`、`letter-spacing`、`white-space`、`text-wrap` を変更しないこと

具体的な CSS レシピ、色計算式、長さ値、角丸値は**実装詳細**であり、本契約の固定対象に含めません。

### `current-match` の見た目契約

`current-match=true` は、`false` に対して最小限の視覚差分を持たなければなりません。

ただし、次を守ります。

- 本文文字色の可読性を下げません。
- 常時アニメーションや強い発光を使いません。
- 強いバリアント化を行いません。
- 差分は既存の線状強調の範囲で与えます。

### 安定 styling hook

本コンポーネントの安定 styling hook は次に限定します。

- `ui-highlight > mark`
- `data-current-match`
- `--bg-highlight-subtle`
- 必要であれば `--bg-highlight-current`

`.prose mark` やグローバル selector は、本コンポーネントの安定公開面に含めません。

## 環境別の振る舞い

### Forced Colors

`forced-colors: active` 環境では、色面塗りを維持しません。`background` を透明にし、`text-decoration-line: underline` によって非色シグナルを維持します。`box-shadow` は除去します。

このとき、独自色を固定するのではなく、環境側の色制御を妨げないことを優先します。

### Print

`@media print` では、通常モードの線状ハイライトを維持しません。背景依存を避けるため、`background: transparent`、`color: currentColor`、`text-decoration-line: underline`、`box-shadow: none` へ切り替えます。

### Light / Dark Theme

本コンポーネントはセマンティックトークンに依存するため、Light / Dark いずれでも同一 CSS で動作します。テーマ差は `--bg-highlight-subtle` と上位文字色の差し替えで吸収します。

### Reduced Motion

本コンポーネント自身はアニメーションやトランジションに依存しません。したがって、`prefers-reduced-motion` に対する特別な分岐は不要です。

## 関連契約

### 文書スタイル契約との分離

`.prose mark` を含む本文全体のマークアップ見た目契約は、本コンポーネントの責務に含めません。これは prose / typography / foundations など別契約で定義します。

### style 提供責務との分離

グローバル style 注入機構は、本コンポーネントの公開契約に含めません。必要な style は、design system bootstrap、foundation layer、または別の style registrar が提供する設計を第一候補とします。

### 検索 UI 契約との分離

検索ヒット集合の管理、`current-match` の切替、スクロール同期、キーボード移動、ARIA policy 全体は上位レイヤの責務です。highlight はその結果を受けて意味マークアップを出力するだけです。

### 正規化後の真実

長期契約では、外から観測できる状態と内部で使う状態を一致させます。

- `current-match` は host 属性と内部 `data-*` の両方で同じ真偽値を表さなければなりません。
- 解決後文字列が空である場合、成功状態の `<mark>` を内部だけで形成してはなりません。
- 契約外入力を受け取った場合でも、host 側と内部側で異なる「真実」を持つ設計は採りません。

## 境界条件

## 境界条件

### 1. `text` のみを与える場合

`text` が非 `null` かつ解決後文字列が非空である場合、その値を `<mark>` に描画します。

### 2. `text` が `null` で初期子テキストがある場合

`text` が `null` の場合に限り、初回接続時のプレーンテキストを入力として採用できます。接続後は継続入力として扱いません。

### 3. 要素子を含む場合

任意要素子の `textContent` を吸収し続けることは公開契約に含めません。要素子を用いた入力は契約外です。

### 4. 直下 `<mark>` を含む場合

直下 `<mark>` は長期契約上の正規入力に含めません。互換のために受理する実装があっても、利用者は依存しません。

### 5. 解決後文字列が空である場合

長期契約では、空の highlight を意味ある成功状態として扱いません。実装は no-op とし、空の `<mark>` を正式な最終状態として出力してはなりません。

### 6. 接続後の子ノード変更

初回接続後にホスト直下の子ノードを書き換えても、表示文字列の自動再解決は行いません。再描画入力として保証されるのは `text` です。

### 7. ネストされた highlight

`ui-highlight` の内側に別の `ui-highlight` を入れる構成は公開契約外です。入れ子の統合、平坦化、意味優先順位付けは保証しません。

### 8. 隣接する複数 highlight

隣接する複数の highlight は独立要素として扱います。自動マージや連結表示への正規化は行いません。

## Storybook 契約

各 Story は見本ではなく、**契約確認点**として扱います。将来変更時には、少なくとも次を固定します。

| Story                              | 固定する契約                                                                                 |
| ---------------------------------- | -------------------------------------------------------------------------------------------- |
| `Default`                          | `ui-highlight` がネイティブ `<mark>` を出力し、不要な対話属性を持たないこと                  |
| `CurrentMatchMatrix`               | `current-match=false` / `true` の両状態が正しく出力されること                               |
| `CurrentMatchVisualContract`       | `current-match=true` が既定状態でも `false` と識別可能であること                             |
| `ExplicitTextContract`             | `text` を明示した場合、その値が最優先されること                                              |
| `FallbackTextContract`             | `text === null` のときのみ初期子テキスト fallback が働くこと                                 |
| `WhitespaceNormalizationContract`  | 初期子テキスト解決で前後 `trim()` のみを行い、空白を自動補完しないこと                       |
| `EmptyResolvedTextContract`        | 解決後文字列が空である場合に成功状態の `<mark>` を形成しないこと                             |
| `UpdateLifecycleContract`          | 初期子テキスト fallback が初回接続時 1 回のみであり、接続後の Light DOM 変更に追従しないこと |
| `BoundaryConditions`               | 要素子、直下 `<mark>`、ネスト、隣接 highlight の境界が明示されること                         |
| `MediaAndTokenContracts`           | `forced-colors` / `print` / トークン参照契約を保持すること                                   |
| `DarkModeTokenAndContrastContract` | Light / Dark 両方でセマンティックトークンを追従すること                                      |

## 補足

`ui-highlight` の要点は、強い装飾を与えることではありません。**本文の意味論を壊さず、自然言語の流れの中で注意点を静かに示すこと**にあります。

したがって、今後の変更でも次の 4 点は崩さない方がよいです。

1. 最終 DOM は常にネイティブ `<mark>` であること。
2. highlight 自身は小さな inline semantic component にとどまること。
3. `.prose mark` やグローバル style policy を抱え込まないこと。
4. 強制カラーおよび印刷で非色シグナルを失わないこと。

---

## 現行実装で未対応の事項

本節は、現行の `highlight.ts` および `highlight.stories.ts` を基準として、**本書が定義する長期契約に対して未実装、未強制、または未整合である事項**を整理するものです。

### 1. 公開タグの一本化

現行実装は `ui-highlight` と `ui-search-highlight` の 2 タグを公開しています。長期契約が求める `ui-highlight` への一本化は未対応です。

### 2. `origin` / `current` から `current-match` 中心設計への再設計

現行実装は `origin` と `current` を公開入力としています。本書が求める長期契約では、意味分類入力を持たず、検索文脈に限定した `current-match` と `text` を中心に公開面を構成します。したがって、`origin` の撤廃と `current` から `current-match` への状態名整理は未対応です。

### 3. `aria-current` の自動付与

現行実装は `current=true` のとき内部 `<mark>` へ `aria-current="true"` を自動付与します。本書が求める「ARIA policy は上位レイヤ責務」という分離は未対応です。

### 4. `text` の未指定と空文字の分離

現行実装では `text === ''` が fallback 解決トリガとしても機能します。したがって、値と制御信号の分離は未対応です。

### 5. 子ノード入力文法の狭義化

現行実装は、直下 text node、直下 `<mark>`、さらに `textContent` fallback により、要素子を広く吸収し得ます。本書が求める「プレーンテキスト中心の狭い文法」は未対応です。

### 6. 空文字 highlight の扱い

現行実装は空文字を許容し、空の `<mark>` を描画し得ます。本書が求める「空文字は no-op または warning 対象」という方針は未対応です。

### 7. グローバル style 注入の分離

現行実装はコンポーネント自身が文書へ style を注入します。本書が求める「component contract と document styling policy の分離」は未対応です。

### 8. `.prose mark` の責務分離

現行実装の style スコープには `.prose mark` が含まれます。本書が求める「本文組版契約との分離」は未対応です。

### 9. 正規化後状態の一貫性

現行実装では、host 側属性と内部 `data-*` の解決済み状態が一致しないケースを許し得ます。本書が求める「外から見える状態と内部状態の一致」は未対応です。

### 10. Storybook 契約の再編

現行 Storybook は `origin` / `current` / `aria-current` / style 注入 ID など現行実装前提の確認を含みます。本書が求める `current-match` / `text` と fallback の分離 / style policy 分離を前提とした Storybook 契約への再編は未対応です。

### 11. 複数 document 境界への非対応

現行実装の style 注入はグローバル `document` を直接参照しており、`ownerDocument` 単位での注入一意性を持ちません。したがって、iframe や別 window を含む複数 document 環境に対して、本書が前提とする責務分離や document 境界の明確化は未対応です。

### 12. 初回接続時の直下ノード強制除去

現行実装は初回接続時に `replaceChildren()` を無条件で実行し、Light DOM 直下の既存ノードを一括で除去します。これは重複表示防止としては合理的ですが、長期契約が求める「狭い互換入力だけを許可し、それ以外は契約外として扱う」方針に対して、**移行方針や警告方針が未整備**です。

とくに、コメントノード、装飾用 wrapper、直下 `<mark>`、任意 inline 要素子をどのように非推奨化・排除していくかは未対応です。

### 13. 内部 style helper / 定数 export の縮小

現行実装は `DOCUMENT_CSS`、`DOCUMENT_STYLE_ID`、`HIGHLIGHT_SCOPE_SELECTOR`、`HIGHLIGHT_RULE_TEMPLATE` を export しています。これは Storybook から参照しやすい反面、**本来は内部実装に属する style policy や生成詳細が公開面へ漏れている**状態です。

本書が求める「安定公開面の最小化」に対して、これらの内部 export をどこまで内部化し、どこまでテスト専用の補助面として残すかは未対応です。

### 14. Storybook と Visual Contract の角丸 / トークン不整合

現行実装の通常モード CSS は `border-radius: 0` を与えていますが、現行 Storybook は `--radius-sm` 由来の角丸が適用されることや CSS 文字列に `var(--radius-sm)` が含まれることを要求しています。したがって、**実装、Storybook、契約書の 3 点で角丸ポリシーとトークン依存が一致していません**。

これは単なる Story の書き漏れではなく、Visual Contract の基礎要素が未整合であることを意味します。

### 15. 本節の扱い

本節に記載した事項は、現行公開契約として利用者が依存してよいものではありません。これらを採用する場合は、実装、Storybook、契約書の 3 点を同時に更新し、未対応状態を残したまま公開契約へ昇格させません。

## 実装修正優先順位

本節は、長期契約に照らして**現行実装で優先的に修正すべき事項**を、設計上の重要度と依存関係に基づいて並べるものです。単に実装量の多少ではなく、**契約の歪みをどれだけ先に減らせるか**を基準に優先順位を付けます。

### 最優先

#### 1. 公開 API の一本化

最優先で着手すべきなのは、公開 API の意味源を 1 つへ揃えることです。

具体的には次を含みます。

- `ui-search-highlight` を正規公開タグから外し、`ui-highlight` に一本化すること
- `origin` を公開入力から外すこと
- `current` を廃止し、`current-match` へ置き換えること

この修正が最優先である理由は、現行設計の最大の歪みが**タグ名と属性の二重意味源**にあるためです。ここを残したまま他の修正を進めると、後段の契約整理が再び崩れます。

#### 2. `aria-current` の自動付与廃止

次に着手すべきなのは、highlight 本体から `aria-current` の自動付与を外すことです。

この修正は、**本文内意味マークアップ**と**検索 UI のアクセシビリティ policy** を切り分けるために必要です。highlight は `data-current-match` までを担い、ARIA の current state は上位レイヤが判断して付与する構造へ寄せます。

#### 3. `text` の値と fallback 制御の分離

`text === ''` を fallback 解決トリガとしても使っている設計は、早い段階で解消すべきです。

したがって、次を優先して実装します。

- `text` が未指定または `null` のときだけ fallback を許可すること
- `text === ''` は明示的空文字として扱うこと
- 値そのものと制御信号を別の意味として扱うこと

この修正により、表示値の意図が API 上で明瞭になります。

### 高優先

#### 4. グローバル style 注入の分離

公開 API の一本化が済んだ後は、component contract と document styling policy の分離へ進みます。

具体的には次を対象とします。

- コンポーネント自身が `document.head` へ style を注入する責務を外すこと
- 必要な style を foundation layer、bootstrap、または専用 registrar 側へ移すこと
- highlight 本体は `<mark>` の意味出力と最小限の styling hook の提供に集中すること

この修正は、責務分離の観点で非常に重要です。

#### 5. `.prose mark` 契約の分離

`.prose mark` を含む本文組版の見た目契約は、本コンポーネント契約から分離します。

これにより、次を明確化できます。

- `ui-highlight > mark` は component contract
- `.prose mark` は prose / typography / foundations contract

見た目が似ていても、責務層は同一ではありません。

#### 6. 子ノード入力文法の狭義化

次に、fallback 入力をプレーンテキスト中心の狭い文法へ寄せます。

具体的には次を行います。

- 直下プレーンテキストのみを互換入力として残すこと
- 直下 `<mark>` fallback を廃止または互換扱いへ降格すること
- 任意要素子の `textContent` 吸収をやめること

これにより、何が正式入力で何が偶然動いているだけの入力かを切り分けられます。

#### 7. host 属性と内部状態の一致

列挙外値や正規化後の状態は、host 側属性と内部 `data-*` で一致させるべきです。したがって、setter / converter 段階で値を正規化し、外から見える状態と内部状態の二重化を解消します。

### 中優先

#### 8. 空文字 highlight の no-op 化または warning 化

空文字 highlight は安全に扱えても、意味のある成功状態としては昇格させない方がよいです。したがって、長期的には次のいずれかへ寄せます。

- no-op として描画しないこと
- 少なくとも開発時 warning を出すこと

#### 9. Storybook 契約の全面再編

現行 Storybook は `origin` / `current` / `aria-current` / style 注入 ID など現行実装に強く結び付いています。したがって、新契約に沿って Storybook を再編します。

再編後は、少なくとも次を固定対象とします。

- `current-match`
- `text` と fallback の分離
- 狭い入力文法
- component contract と prose contract の分離
- `forced-colors` / `print` / token contract

#### 10. Visual Contract の細部調整

角丸、current-match の視覚差分有無、annotation と search の差分有無など、見た目の細部は最後に詰めます。これらは重要ではありますが、API と責務境界が固まる前に触ると再調整が発生しやすいためです。

### 実行順

実行順は次の 3 段階を推奨します。

#### 第 1 段階

- 公開 API の一本化
- `aria-current` の分離
- `text` と fallback 制御の分離

この段階で、契約の中心にある歪みを取り除きます。

#### 第 2 段階

- グローバル style 注入の分離
- `.prose mark` 契約の分離
- 子ノード入力文法の狭義化
- host 属性と内部状態の一致

この段階で、責務境界と入力境界を整理します。

#### 第 3 段階

- 空文字 highlight の no-op 化または warning 化
- Storybook 契約の全面再編
- Visual Contract の細部調整

この段階で、運用と検証の面を新契約に合わせて仕上げます。

### 最初に着手すべき 3 点

着手順としては、次の 3 点を最初の修正対象とします。

1. `origin` を公開入力から外し、`current` を `current-match` に置き換えること
2. `aria-current` を component から外すこと
3. `text === ''` fallback をやめること

この 3 点で、highlight 契約の中心にある歪みの大半を解消できます。
