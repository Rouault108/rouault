# Highlight

## 概要

本書は、Rouault における highlight コンポーネントの**長期的な公開契約**を定義するものです。現行実装の都合を固定することではなく、**設計のきれいさ、責務分離、保守性**を優先して、どの契約を残し、どの契約を縮退または別文書へ分離するかを明確にします。

本コンポーネントの目的は、本文中の一部文字列を**意味的にマークされた箇所**として表現することです。強い装飾や対話機能を担うのではなく、**ネイティブ **``** を最終 DOM として出力し、本文読解の流れを壊さずに注意を添える**ことを第一目的とします。

また、本コンポーネントは本文フローと自然に統合されることを重視します。したがって、公開契約では次を優先します。

- 公開タグはできる限り 1 つへ絞ること
- タグ名ではなく property を意味源にすること
- 値と制御信号を分離すること
- component contract と document styling policy を分離すること
- 外部が依存してよい公開面を最小化すること

Rouault における highlight は、**「没入して読む」ことのできるデザイン**の一部として、検索ヒットや注目箇所を静かに示すために存在します。したがって、本書では**読書面の一貫性**と**長期保守性**を優先して契約を定義します。

## 適用範囲

本書は、highlight コンポーネントの次の事項を対象とします。

- 公開タグと公開入力
- コンテンツ入力契約
- 状態モデル
- DOM / Accessibility
- Visual Contract
- 環境別の振る舞い
- 関連契約
- 境界条件
- Storybook 契約
- 現行実装で未対応の事項

一方で、本書は次の事項を扱いません。

- 検索語の抽出アルゴリズム
- 検索ヒット集合の管理や current 切替ロジック
- 文書全体の検索 UI、検索移動、スクロール同期
- `.prose mark` を含む本文組版全体の見た目契約
- グローバル style 注入機構そのものの設計
- Markdown パーサや SSR パイプラインの責務
- annotation 機能全体の永続化や編集 UI

これらは上位レイヤまたは別契約の責務です。

## 設計判断

本書では、highlight を**小さな inline semantic component**として定義します。これにより、意味表現と視覚表現の境界を明確にし、本文組版や検索 UI の責務と分離します。

長期的な設計判断は次のとおりです。

- 公開タグは ``** を唯一の正規タグ**とします。
- `ui-search-highlight` は長期契約上の正規タグには含めません。互換上残す場合でも、新規利用の基準にはしません。
- 意味分類はタグ名ではなく ``** property** で表現します。
- `current` という汎用状態名は採らず、`` という検索文脈に限定された状態名を採ります。
- `aria-current` の自動付与はコンポーネント責務に含めません。
- `.prose mark` の見た目契約とグローバル style 注入は本コンポーネントの責務に含めません。

この判断により、highlight は**意味的マークアップの生成**に集中し、検索 UI や文書スタイル全体の policy を抱え込まない形へ整理します。

## 公開契約

### 公開タグ

長期契約上の正規公開タグは `` のみです。

```text
<ui-highlight></ui-highlight>
```

`ui-search-highlight` は長期契約上の正規タグではありません。現行実装に存在する場合でも、互換用途にとどめ、新規設計では依存しません。

### 公開入力

`ui-highlight` は、`kind`、`current-match`、`text` を公開入力として扱います。

| 名前              | 種別                   | 必須  | 内容                           | 契約                                           |
| --------------- | -------------------- | --- | ---------------------------- | -------------------------------------------- |
| `kind`          | property / attribute | いいえ | highlight の意味分類              | `search` / `annotation`。既定値は `annotation` です |
| `currentMatch`  | property             | いいえ | 検索ヒット列の現在位置かどうか              | `kind="search"` のときのみ意味を持ちます                 |
| `current-match` | attribute            | いいえ | `currentMatch` の attribute 形 | boolean attribute として扱います                    |
| `text`          | property / attribute | いいえ | 表示文字列                        | 未指定または `null` の場合のみ初期子テキスト fallback を許可します   |

### 意味分類契約

`kind` は次の 2 値のみを正規入力とします。

| 値            | 意味    | 想定用途                 |
| ------------ | ----- | -------------------- |
| `search`     | 検索ヒット | 本文内検索、全文検索結果、検索移動対象  |
| `annotation` | 注目箇所  | 利用者注釈、手動マーク、文脈上の注意箇所 |

列挙外値は公開契約外です。実装がフォールバックを持つ場合でも、利用者は列挙外値に依存しません。

### `current-match` 契約

`current-match` は、**検索ヒット列の中で現在位置にある要素**を表すための状態です。したがって、`kind="search"` の場合にのみ意味を持ちます。

- `kind="annotation"` に対する `current-match` は公開契約外です。
- `current-match` は意味状態であり、コンポーネント自身がアクセシビリティ属性へ自動変換することは公開契約に含めません。
- `current-match` の視覚差分を必須としません。

### `text` 契約

`text` は表示文字列を表します。長期契約では、**値そのもの**と**fallback 解決のトリガ**を分離します。

- `text` が非空文字列である場合、その値を表示に用います。
- `text` が空文字列 `''` である場合、**明示的な空文字**として扱います。
- `text` が未指定または `null` である場合に限り、初期子テキスト fallback を許可します。

この契約により、空文字と未指定を同一視しません。

### 属性反映契約

`kind` と `current-match` は reflect されます。`text` は attribute 入力を受理しますが、property から attribute への reflect は公開契約に含めません。

| property       | attribute       | reflect | 備考                           |
| -------------- | --------------- | ------- | ---------------------------- |
| `kind`         | `kind`          | あり      | 正規値のみを契約対象とします               |
| `currentMatch` | `current-match` | あり      | `kind="search"` のときのみ意味を持ちます |
| `text`         | `text`          | なし      | 値と fallback 制御を分離します         |

## コンテンツ入力契約

### 入力優先順位

本コンポーネントは、次の順で表示文字列を解決します。

1. `text` が非 `null` かつ非 `undefined` である場合は、その値を使用します。
2. `text` が未指定または `null` である場合に限り、初期子テキストを使用します。
3. それでも解決できない場合は、空文字として扱います。

### 初期子テキスト fallback

初期子テキスト fallback は、**互換入力**としてのみ許可します。長期的な正規入力は `text` です。

fallback を許可する条件は次のとおりです。

- ホスト直下にプレーンテキストが存在すること
- そのテキストが初回接続時に読み取れること
- 接続後の子ノード変更に追従しないこと

### 子ノード文法

長期契約における正規入力文法は、**プレーンテキストのみ**です。

- ホスト直下のプレーンテキストは互換入力として許可します。
- 直下 `<mark>` は長期契約上の正規入力に含めません。
- 任意の inline 要素子の `textContent` を吸収し続けることは公開契約に含めません。
- ネストされた `ui-highlight` を入力文法として認めません。

これにより、何が正式入力で何が互換入力かを明確に分離します。

### テキスト正規化契約

文字列解決では、空白や改行を自動補完しません。初期子テキストを読む場合は、**元の文字列をできる限り保持し、前後 **``** のみを行う** 方針とします。

したがって、次を固定します。

- テキストノード間に区切り空白は自動挿入しません。
- 前後空白は除去します。
- 中間の空白や改行は入力由来のまま保持します。
- component 自身が文意を推測して文字列を再構成しません。

### 更新契約

初期子テキスト fallback は、**初回接続時に 1 回だけ**評価します。接続後は、初期子ノードを継続的な入力面として扱いません。

したがって、次を固定します。

- 接続後にホスト直下の子ノードを書き換えても、表示文字列は自動再解決しません。
- `MutationObserver` 等による Light DOM 監視は行いません。
- 接続後の表示更新は `text` の変更によってのみ行います。

## 状態モデル

`ui-highlight` の状態は、**何の highlight か**、**検索 current かどうか**、**表示文字列がどこから供給されたか**の 3 軸で読みます。

### 基本状態

最小状態は、`kind="annotation"`、`current-match=false`、非空文字列を 1 つ持つ状態です。この状態では、本文フローの中に静かな線状ハイライトとして描画されます。

### `kind` 状態

`kind` は `search` または `annotation` の 2 値のみを受理します。

- `search` は検索ヒットを表します。
- `annotation` は検索以外の注目箇所を表します。

`kind` は**意味状態**であり、コンポーネント自身が必ず視覚差分を持たせることは契約に含めません。

### `current-match` 状態

`current-match=true` は、検索ヒット集合の中で現在位置にある要素を表します。`kind="search"` のときにのみ有効です。

- `kind="annotation"` と組み合わせた `current-match` は公開契約外です。
- `current-match` は意味状態であり、視覚差分や ARIA 属性への自動変換は別責務です。

### 文字列供給状態

表示文字列は、**明示入力**と**初期子テキスト fallback**のいずれかから供給されます。

- 明示入力: `text` による供給
- fallback 入力: 初回接続時のプレーンテキスト供給

この区別は、更新契約に直接関わります。

### 空文字状態

長期契約では、空文字 highlight を積極的な成功状態として扱いません。

- 解決後文字列が空である場合、実装は no-op とするか、少なくとも開発時 warning を出すことが望ましいです。
- 空の `<mark>` を意味ある最終状態として昇格しません。

## DOM / Accessibility

### 最終 DOM 契約

意味表現の主体はホスト直下の `<mark>` です。最終 DOM は概ね次の形をとります。

```text
<ui-highlight kind="search" current-match>
  <mark data-kind="search" data-current-match="true">...</mark>
</ui-highlight>
```

または

```text
<ui-highlight kind="annotation">
  <mark data-kind="annotation" data-current-match="false">...</mark>
</ui-highlight>
```

`mark` には次の属性を安定公開面として許可します。

| 属性                   | 契約                          |
| -------------------- | --------------------------- |
| `data-kind`          | 解決後の `kind` を出力します          |
| `data-current-match` | `true` / `false` の文字列を出力します |

### Accessibility 契約

アクセシビリティ上の重要点は次のとおりです。

- 意味主体はネイティブ `<mark>` です。
- `mark` は本文フローに留まり、ボタンやリンクのような対話主体になりません。
- `role`、`tabindex`、独自キーボード操作は公開契約に含めません。
- `aria-current` の自動付与は公開契約に含めません。
- 必要な ARIA 意味付けは上位レイヤが判断します。

highlight は**検索 UI そのものではなく、本文内の意味マークアップ**です。したがって、検索のアクセシビリティ policy 全体を内包しません。

### レイアウト / Selection 契約

本コンポーネントは、本文中の**インライン文脈**で使用することを前提とします。

したがって、次を固定します。

- ホストは本文フローに自然に挿入されるインライン要素として扱います。
- `mark` 自体は本文の `line-height`、`letter-spacing`、`white-space`、`text-wrap` を変更しません。
- ハイライトは選択可能テキストであり、コピー結果に不可視文字や補助記号を混入させません。
- 文字選択時も元の本文文字列を維持し、選択結果の意味内容を変えません。

## Visual Contract

`ui-highlight` の視覚契約は、背景塗りつぶしではなく、**本文色を維持したまま下方に線状の色面を敷くこと**にあります。これは本文文字のコントラストを保ったまま、静かな強調を与えるためです。

### 情報順位

- 本文文字色が主です。
- ハイライトは本文より前面に出ず、補助的に機能します。
- `kind` や `current-match` は、既定では視覚差分を必須としません。
- 色だけに依存せず、強制カラーおよび印刷では下線へ移行します。

### 視覚仕様

通常モードでは、`mark` に対して次を適用します。

- `background: transparent`
- `color: inherit`
- `padding: 0`
- `text-decoration: none`
- `box-shadow: inset 0 -0.5em 0 color-mix(in oklch, var(--bg-highlight-subtle) 88%, transparent)`
- `box-decoration-break: clone`
- `-webkit-box-decoration-break: clone`
- `border-radius: 0`

これにより、複数行にまたがる場合でも行ごとに切れず、本文の行送りを大きく乱さない線状ハイライトを形成します。

### 状態と見た目の関係

`kind` と `current-match` は**意味状態**です。コンポーネント既定スタイルでは、両者の差を必ずしも見た目へ反映しません。

これは、意味状態と視覚状態をむやみに結び付けず、読書面に不要な強調競合を持ち込まないためです。上位レイヤが必要に応じて差分表示を追加する場合でも、既定コントラクトを壊さない範囲で行います。

### 安定 styling hook

本コンポーネントの安定 styling hook は次に限定します。

- `ui-highlight > mark`
- `data-kind`
- `data-current-match`
- `--bg-highlight-subtle`

`.prose mark` やグローバル selector は、本コンポーネントの安定公開面に含めません。

## 環境別の振る舞い

### Forced Colors

`forced-colors: active` 環境では、色面塗りを維持しません。`background` を透明にし、`text-decoration-line: underline` によって非色シグナルを維持します。`box-shadow` は除去します。

このとき、独自色を固定するのではなく、環境側の色制御を妨げないことを優先します。

### Print

`@media print` では、通常モードの線状ハイライトを維持しません。背景依存を避けるため、`background: transparent`、`color: currentColor`、`text-decoration-line: underline`、`box-shadow: none` へ切り替えます。

### Light / Dark Theme

本コンポーネントはセマンティックトークンに依存するため、Light / Dark いずれでも同一 CSS で動作します。テーマ差は `--bg-highlight-subtle` と上位文字色の差し替えで吸収します。

### Reduced Motion

本コンポーネント自身はアニメーションやトランジションに依存しません。したがって、`prefers-reduced-motion` に対する特別な分岐は不要です。

## 関連契約

### 文書スタイル契約との分離

`.prose mark` を含む本文全体のマークアップ見た目契約は、本コンポーネントの責務に含めません。これは prose / typography / foundations など別契約で定義します。

### style 提供責務との分離

グローバル style 注入機構は、本コンポーネントの公開契約に含めません。必要な style は、design system bootstrap、foundation layer、または別の style registrar が提供する設計を第一候補とします。

### 検索 UI 契約との分離

検索ヒット集合の管理、`current-match` の切替、スクロール同期、キーボード移動、ARIA policy 全体は上位レイヤの責務です。highlight はその結果を受けて意味マークアップを出力するだけです。

### 正規化後の真実

長期契約では、外から見える状態と内部で使う状態を一致させます。列挙外値を許容する場合でも、host 側属性と内部 `data-*` が異なる真実を持つ設計は採りません。

## 境界条件

### 1. `text` のみを与える場合

`text` が非空文字列である場合、その値を `<mark>` に描画します。

### 2. `text` 未指定で初期子テキストがある場合

`text` が未指定または `null` の場合に限り、初回接続時のプレーンテキストを fallback として採用できます。接続後は継続入力として扱いません。

### 3. 要素子を含む場合

任意要素子の `textContent` を吸収し続けることは公開契約に含めません。要素子を用いた入力は契約外です。

### 4. 直下 `<mark>` を含む場合

直下 `<mark>` は長期契約上の正規入力に含めません。互換のために受理する実装があっても、利用者は依存しません。

### 5. `kind` が列挙外値である場合

列挙外値は公開契約外です。実装がフォールバックを持つ場合でも、その値に依存しません。

### 6. `kind="annotation"` と `current-match`

この組み合わせは公開契約外です。`current-match` は検索 current に限定します。

### 7. 解決後文字列が空である場合

長期契約では、空の highlight を意味ある成功状態として扱いません。実装は no-op または開発時 warning を選べますが、空の `<mark>` を正式な最終状態として期待しません。

### 8. 接続後の子ノード変更

初回接続後にホスト直下の子ノードを書き換えても、表示文字列の自動再解決は行いません。再描画入力として保証されるのは `text` です。

### 9. ネストされた highlight

`ui-highlight` の内側に別の `ui-highlight` を入れる構成は公開契約外です。入れ子の統合、平坦化、意味優先順位付けは保証しません。

### 10. 隣接する複数 highlight

隣接する複数の highlight は独立要素として扱います。自動マージや連結表示への正規化は行いません。

## Storybook 契約

各 Story は見本ではなく、**契約確認点**として扱います。将来変更時には、少なくとも次を固定します。

| Story                              | 固定する契約                                                          |
| ---------------------------------- | --------------------------------------------------------------- |
| `Default`                          | `ui-highlight` がネイティブ `<mark>` を出力し、不要な対話属性を持たないこと              |
| `ExplicitTextContract`             | `text` を明示した場合、その値が最優先されること                                     |
| `FallbackTextContract`             | `text` 未指定時のみ初期子テキスト fallback が働くこと                             |
| `KindMatrix`                       | `kind="search"` / `kind="annotation"` で `data-kind` が正しく出力されること |
| `CurrentMatchContract`             | `kind="search"` と `current-match` の関係が正しく表現されること                |
| `WhitespaceNormalizationContract`  | 初期子テキスト解決で前後 `trim()` のみを行い、空白を自動補完しないこと                        |
| `UpdateLifecycleContract`          | 初期子テキスト fallback が初回接続時 1 回のみであり、接続後の Light DOM 変更に追従しないこと      |
| `BoundaryConditions`               | 列挙外 `kind`、空文字、要素子、ネスト、隣接 highlight の境界が明示されること                 |
| `MediaAndTokenContracts`           | `forced-colors` / `print` / トークン参照契約を保持すること                     |
| `DarkModeTokenAndContrastContract` | Light / Dark 両方でセマンティックトークンを追従すること                              |

## 補足

`ui-highlight` の要点は、強い装飾を与えることではありません。**本文の意味論を壊さず、自然言語の流れの中で注意点を静かに示すこと**にあります。

したがって、今後の変更でも次の 4 点は崩さない方がよいです。

1. 最終 DOM は常にネイティブ `<mark>` であること。
2. highlight 自身は小さな inline semantic component にとどまること。
3. `.prose mark` やグローバル style policy を抱え込まないこと。
4. 強制カラーおよび印刷で非色シグナルを失わないこと。

## 現行実装で未対応の事項

本節は、現行の `highlight.ts` および `highlight.stories.ts` を基準として、**本書が定義する長期契約に対して未実装、未強制、または未整合である事項**を整理するものです。

### 1. 公開タグの一本化

現行実装は `ui-highlight` と `ui-search-highlight` の 2 タグを公開しています。長期契約が求める `ui-highlight` への一本化は未対応です。

### 2. `origin` / `current` から `kind` / `current-match` への再設計

現行実装は `origin` と `current` を公開入力とし、`kind` と `current-match` は未実装です。したがって、意味源の整理と状態名の狭義化は未対応です。

### 3. `aria-current` の自動付与

現行実装は `current=true` のとき内部 `<mark>` へ `aria-current="true"` を自動付与します。本書が求める「ARIA policy は上位レイヤ責務」という分離は未対応です。

### 4. `text` の未指定と空文字の分離

現行実装では `text === ''` が fallback 解決トリガとしても機能します。したがって、値と制御信号の分離は未対応です。

### 5. 子ノード入力文法の狭義化

現行実装は、直下 text node、直下 `<mark>`、さらに `textContent` fallback により、要素子を広く吸収し得ます。本書が求める「プレーンテキスト中心の狭い文法」は未対応です。

### 6. 空文字 highlight の扱い

現行実装は空文字を許容し、空の `<mark>` を描画し得ます。本書が求める「空文字は no-op または warning 対象」という方針は未対応です。

### 7. グローバル style 注入の分離

現行実装はコンポーネント自身が文書へ style を注入します。本書が求める「component contract と document styling policy の分離」は未対応です。

### 8. `.prose mark` の責務分離

現行実装の style スコープには `.prose mark` が含まれます。本書が求める「本文組版契約との分離」は未対応です。

### 9. 正規化後状態の一貫性

現行実装では、host 側属性と内部 `data-*` の解決済み状態が一致しないケースを許し得ます。本書が求める「外から見える状態と内部状態の一致」は未対応です。

### 10. Storybook 契約の再編

現行 Storybook は `origin` / `current` / `aria-current` / style 注入 ID など現行実装前提の確認を含みます。本書が求める `kind` / `current-match` / fallback 分離 / style policy 分離を前提とした Storybook 契約への再編は未対応です。

### 11. 複数 document 境界への非対応

現行実装の style 注入はグローバル `document` を直接参照しており、`ownerDocument` 単位での注入一意性を持ちません。したがって、iframe や別 window を含む複数 document 環境に対して、本書が前提とする責務分離や document 境界の明確化は未対応です。

### 12. 初回接続時の直下ノード強制除去

現行実装は初回接続時に `replaceChildren()` を無条件で実行し、Light DOM 直下の既存ノードを一括で除去します。これは重複表示防止としては合理的ですが、長期契約が求める「狭い互換入力だけを許可し、それ以外は契約外として扱う」方針に対して、**移行方針や警告方針が未整備**です。

とくに、コメントノード、装飾用 wrapper、直下 `<mark>`、任意 inline 要素子をどのように非推奨化・排除していくかは未対応です。

### 13. 内部 style helper / 定数 export の縮小

現行実装は `DOCUMENT_CSS`、`DOCUMENT_STYLE_ID`、`HIGHLIGHT_SCOPE_SELECTOR`、`HIGHLIGHT_RULE_TEMPLATE` を export しています。これは Storybook から参照しやすい反面、**本来は内部実装に属する style policy や生成詳細が公開面へ漏れている**状態です。

本書が求める「安定公開面の最小化」に対して、これらの内部 export をどこまで内部化し、どこまでテスト専用の補助面として残すかは未対応です。

### 14. Storybook と Visual Contract の角丸 / トークン不整合

現行実装の通常モード CSS は `border-radius: 0` を与えていますが、現行 Storybook は `--radius-sm` 由来の角丸が適用されることや CSS 文字列に `var(--radius-sm)` が含まれることを要求しています。したがって、**実装、Storybook、契約書の 3 点で角丸ポリシーとトークン依存が一致していません**。

これは単なる Story の書き漏れではなく、Visual Contract の基礎要素が未整合であることを意味します。

### 15. 本節の扱い

本節に記載した事項は、現行公開契約として利用者が依存してよいものではありません。これらを採用する場合は、実装、Storybook、契約書の 3 点を同時に更新し、未対応状態を残したまま公開契約へ昇格させません。

## 新規で追加を検討する価値がある機能

本節は、長期契約と Rouault の読書体験を前提として、**新規で追加を検討する価値がある機能**を整理するものです。ここでいう「価値がある」とは、単に機能が増えるという意味ではなく、**意味の明瞭さ、可観測性、保守性を高めつつ、本文読解の没入を壊さない**ことを指します。

本コンポーネントは、小さな inline semantic component にとどめることが重要です。したがって、追加を検討する機能は、責務を増やすものではなく、**既存の意味状態を少しだけ補強するもの**に限定します。

### 最優先で検討する価値がある機能

#### 1. `current-match` の控えめな視覚差分

もっとも検討価値が高いのは、`current-match` に対して**控えめな視覚差分**を与えることです。

長期契約では `current-match` を意味状態として定義していますが、検索移動を伴う文脈では、現在位置がまったく見分けられないと読書面の補助として弱くなります。したがって、既定の線状ハイライト表現を維持したまま、**現在ヒットだけをわずかに識別しやすくする差分**は導入価値があります。

導入する場合は、次の制約を守ります。

- 差分は最小限にとどめます。
- 本文文字色のコントラストを下げません。
- 常時アニメーションや強い発光を使いません。
- 下線系や外枠を追加するより、既存の線状ハイライト表現の範囲で差を付けます。

### 条件付きで検討する価値がある機能

#### 2. `kind="search"` と `kind="annotation"` の控えめな差別化

annotation を正式に育てる前提がある場合に限り、`search` と `annotation` に**控えめな視覚差**を持たせることは検討価値があります。

ただし、この差は意味分類を補助するためのものであり、強いバリアント化を目的としません。導入する場合は次を守ります。

- 本文色は引き続き `inherit` を維持します。
- 差分は線の色味や濃度の範囲にとどめます。
- `search` と `annotation` を 2 系統以上へ増やしません。
- forced-colors / print では差より可読性を優先します。

annotation 機能自体が未成熟な段階では、この差別化を先に入れる必要はありません。

#### 3. 空文字 highlight の開発時 warning

これは視覚機能ではありませんが、品質管理上は検討価値があります。

長期契約では空文字 highlight を意味ある成功状態として扱いません。したがって、開発時にのみ warning を出し、**上位ロジックで意味のない highlight が生成されていることを可視化する**仕組みは有用です。

これは runtime UX を増やす機能ではなく、保守性を高めるための開発補助機能です。

#### 4. 最小限のテーマ用 style knob

必要性が明確な場合に限り、`current-match` や `annotation` 向けに**最小限の追加トークン**を導入する余地はあります。

ただし、公開する調整面は極小に保つ必要があります。たとえば、次のような追加は許容し得ます。

- current-match 用の補助トークン
- annotation 用の補助トークン

一方で、太さ、角丸、影、オフセットなどを個別に広く公開することは避けます。

### 採用しない方がよい機能

#### 1. クリック可能 annotation / tooltip / popover 化

highlight を対話要素へ拡張することは、本コンポーネントの責務を壊します。注釈の表示、編集、popover、tooltip、context menu は別コンポーネントの責務です。

#### 2. 検索移動 API やスクロール API

next / previous hit、scrollIntoView、検索ヒット総数管理、current index 管理などは上位検索 UI の責務です。highlight はそれらを内包しません。

#### 3. 隣接 highlight の自動マージや重複解消

これは本文変換ロジックまたは検索前処理の責務です。inline component 側で自動マージや優先順位付けを行うべきではありません。

#### 4. 強いアニメーション

点滅、パルス、波打ちなどの強いアニメーションは、Rouault の読書体験と相性が悪く、forced-colors / print 契約とも整合しにくいため採用しません。

### 追加検討の優先順位

新規機能を本当に追加する場合、優先順位は次のとおりです。

1. `current-match` の控えめな視覚差分
2. annotation を正式採用する場合の `kind` 差別化
3. 空文字 highlight の開発時 warning
4. 必要最小限の追加トークン

この順序は、**新しい責務を増やさず、既存の意味状態を補強するものから先に採る**という原則に基づきます。

## 実装修正優先順位

本節は、長期契約に照らして**現行実装で優先的に修正すべき事項**を、設計上の重要度と依存関係に基づいて並べるものです。単に実装量の多少ではなく、**契約の歪みをどれだけ先に減らせるか**を基準に優先順位を付けます。

### 最優先

#### 1. 公開 API の一本化

最優先で着手すべきなのは、公開 API の意味源を 1 つへ揃えることです。

具体的には次を含みます。

- `ui-search-highlight` を正規公開タグから外し、`ui-highlight` に一本化すること
- `origin` を廃止し、`kind="search|annotation"` へ置き換えること
- `current` を廃止し、`current-match` へ置き換えること

この修正が最優先である理由は、現行設計の最大の歪みが**タグ名と属性の二重意味源**にあるためです。ここを残したまま他の修正を進めると、後段の契約整理が再び崩れます。

#### 2. `aria-current` の自動付与廃止

次に着手すべきなのは、highlight 本体から `aria-current` の自動付与を外すことです。

この修正は、**本文内意味マークアップ**と**検索 UI のアクセシビリティ policy** を切り分けるために必要です。highlight は `data-current-match` までを担い、ARIA の current state は上位レイヤが判断して付与する構造へ寄せます。

#### 3. `text` の値と fallback 制御の分離

`text === ''` を fallback 解決トリガとしても使っている設計は、早い段階で解消すべきです。

したがって、次を優先して実装します。

- `text` が未指定または `null` のときだけ fallback を許可すること
- `text === ''` は明示的空文字として扱うこと
- 値そのものと制御信号を別の意味として扱うこと

この修正により、表示値の意図が API 上で明瞭になります。

### 高優先

#### 4. グローバル style 注入の分離

公開 API の一本化が済んだ後は、component contract と document styling policy の分離へ進みます。

具体的には次を対象とします。

- コンポーネント自身が `document.head` へ style を注入する責務を外すこと
- 必要な style を foundation layer、bootstrap、または専用 registrar 側へ移すこと
- highlight 本体は `<mark>` の意味出力と最小限の styling hook の提供に集中すること

この修正は、責務分離の観点で非常に重要です。

#### 5. `.prose mark` 契約の分離

`.prose mark` を含む本文組版の見た目契約は、本コンポーネント契約から分離します。

これにより、次を明確化できます。

- `ui-highlight > mark` は component contract
- `.prose mark` は prose / typography / foundations contract

見た目が似ていても、責務層は同一ではありません。

#### 6. 子ノード入力文法の狭義化

次に、fallback 入力をプレーンテキスト中心の狭い文法へ寄せます。

具体的には次を行います。

- 直下プレーンテキストのみを互換入力として残すこと
- 直下 `<mark>` fallback を廃止または互換扱いへ降格すること
- 任意要素子の `textContent` 吸収をやめること

これにより、何が正式入力で何が偶然動いているだけの入力かを切り分けられます。

#### 7. host 属性と内部状態の一致

列挙外値や正規化後の状態は、host 側属性と内部 `data-*` で一致させるべきです。したがって、setter / converter 段階で値を正規化し、外から見える状態と内部状態の二重化を解消します。

### 中優先

#### 8. 空文字 highlight の no-op 化または warning 化

空文字 highlight は安全に扱えても、意味のある成功状態としては昇格させない方がよいです。したがって、長期的には次のいずれかへ寄せます。

- no-op として描画しないこと
- 少なくとも開発時 warning を出すこと

#### 9. Storybook 契約の全面再編

現行 Storybook は `origin` / `current` / `aria-current` / style 注入 ID など現行実装に強く結び付いています。したがって、新契約に沿って Storybook を再編します。

再編後は、少なくとも次を固定対象とします。

- `kind` / `current-match`
- `text` と fallback の分離
- 狭い入力文法
- component contract と prose contract の分離
- `forced-colors` / `print` / token contract

#### 10. Visual Contract の細部調整

角丸、current-match の視覚差分有無、annotation と search の差分有無など、見た目の細部は最後に詰めます。これらは重要ではありますが、API と責務境界が固まる前に触ると再調整が発生しやすいためです。

### 実行順

実行順は次の 3 段階を推奨します。

#### 第 1 段階

- 公開 API の一本化
- `aria-current` の分離
- `text` と fallback 制御の分離

この段階で、契約の中心にある歪みを取り除きます。

#### 第 2 段階

- グローバル style 注入の分離
- `.prose mark` 契約の分離
- 子ノード入力文法の狭義化
- host 属性と内部状態の一致

この段階で、責務境界と入力境界を整理します。

#### 第 3 段階

- 空文字 highlight の no-op 化または warning 化
- Storybook 契約の全面再編
- Visual Contract の細部調整

この段階で、運用と検証の面を新契約に合わせて仕上げます。

### 最初に着手すべき 3 点

着手順としては、次の 3 点を最初の修正対象とします。

1. `origin` / `current` を `kind` / `current-match` に置き換えること
2. `aria-current` を component から外すこと
3. `text === ''` fallback をやめること

この 3 点で、highlight 契約の中心にある歪みの大半を解消できます。
