# Footer

## 概要

本書は、Rouault における `footer` の**目標契約**を定義するものです。ここでいう目標契約とは、現行実装の細部をそのまま写すものではなく、**長期的な保守性、責務分離、再利用性、アクセシビリティ、一貫した拡張面**を優先して整理した公開契約です。

`footer` は、本文終端に静かなメタ情報と補助導線を置くための部品です。情報量を増やすことや装飾を強めることは目的ではありません。本文から注意を奪わず、ページの終端で必要最小限の情報を安定して提示することを目的とします。

本書は、次の方針を前提とします。

- `footer` は **純粋描画責務**を持つ部品として扱います。
- Rouault 固有の値は **上位設定**が供給します。
- CSS の公開拡張面は **CSS custom properties を中心**とします。
- Storybook は **契約の検証器**であり、契約書そのものではありません。

---

## 適用範囲

本書は、次の事項を対象とします。

- 公開契約
- 入力モデル
- 状態モデル
- DOM / Accessibility
- Visual Contract
- 環境別の振る舞い
- 拡張面
- 非目標
- 現行実装との差分

一方で、本書は次の事項を扱いません。

- 画面全体のレイアウト責務
- ルーター実装そのもの
- `/about` や `/contact` のページ内容
- 著作権表示の法的妥当性そのもの
- ビルドメタデータ配布方式の決定
- 外部アセット配信基盤の可用性保証

これらは上位レイヤまたは別契約の責務です。

## 設計方針

### 責務分離

`footer` は、**描画**、**アクセシビリティ**、**最小限の視覚整列**を責務とします。サイト名、所有者名、ライセンス表現、補助リンク群、ビルド識別子の意味づけは `footer` 自身の責務ではありません。

### 純粋描画

`footer` は import 時に document を変更しません。文書スコープのスタイル注入が必要な場合でも、それは明示的な初期化責務として分離します。描画関数は、入力から DOM 断片を返すことに専念します。

### 上位供給

Rouault 固有の定数は `footer` に埋め込まず、上位設定または呼び出し側が供給します。これにより、内容の再利用性とテスト容易性を確保します。

### 明示的な公開面

利用者が依存してよいものは、**入力モデル、ルート要素、公開 CSS 変数、アクセシビリティ契約**に限定します。内部 class 名、具体 DOM 深さ、装飾アイコンの要素種別は原則として公開面に含めません。

## 公開契約

`footer` の公開契約は、**描画入力を受けてネイティブ \*\***\`\`\***\* を返すこと**です。固定値を暗黙に持つのではなく、必要な値は上位から供給されます。

### 公開 API

```ts
export interface FooterLinkItem {
  href: string;
  label: string;
  external?: boolean;
}

export interface FooterMetaContent {
  siteName: string;
  siteUrl?: string;
  copyrightText: string;
  buildLabel?: string;
}

export interface FooterA11yLabels {
  navLabel: string;
}

export interface FooterRenderOptions {
  id?: string;
  meta: FooterMetaContent;
  links?: readonly FooterLinkItem[];
  a11y?: Partial<FooterA11yLabels>;
}

export declare function renderFooter(options: FooterRenderOptions): TemplateResult;
```

### 契約の要点

- `renderFooter()` は \*\*必須の \*\*\`\` を受け取ります。
- `links` は任意です。未指定の場合、補助ナビゲーション自体を描画しないことを許容します。
- `buildLabel` は任意です。未指定の場合、ビルド識別子領域自体を描画しないことを許容します。
- `id` は任意です。空文字列または空白のみの場合は出力しません。
- `a11y.navLabel` は任意です。未指定時は安定した既定値を用います。

### 固定値を持たない契約

`footer` は次の値を固定しません。

- サイト名
- サイト URL
- 著作権文言
- ライセンス文言
- 所有者名
- ビルド識別子の内容
- 補助リンク群
- UI 文言の言語

これらはすべて上位が供給します。

### 非公開にする実装詳細

次の事項は公開契約に含めません。

- 内部 class 名の完全な一覧
- 装飾アイコンの要素種別
- 文書スタイル注入方式
- buildLabel の内部正規化規則
- 外部画像 URL の具体値

## 入力モデル

### `FooterMetaContent`

`meta` は footer の主要情報を表します。

| 名前            | 必須   | 内容                                         | 契約                                                         |
| --------------- | ------ | -------------------------------------------- | ------------------------------------------------------------ |
| `siteName`      | はい   | サイト名                                     | 可視テキストとして出力します                                 |
| `siteUrl`       | いいえ | サイト名リンク先                             | 指定時のみリンク化します。未指定時はテキストとして出力します |
| `copyrightText` | はい   | 著作権・ライセンス等を含む整形済み文言       | `footer` 側で再解釈しません                                  |
| `buildLabel`    | いいえ | 版・ビルド・リビジョン等を表す整形済み表示値 | 指定時のみ表示します                                         |

ここで重要なのは、`copyrightText` と `buildLabel` を**整形済み表示値**として扱うことです。`footer` は Git hash の妥当性や年範囲計算を責務に含めません。

### `FooterLinkItem`

`links` は補助ナビゲーションを表します。

| 名前       | 必須   | 内容               | 契約                                        |
| ---------- | ------ | ------------------ | ------------------------------------------- |
| `href`     | はい   | 遷移先 URL         | ネイティブ `<a>` の `href` として使用します |
| `label`    | はい   | 表示文言           | 可視テキストとして出力します                |
| `external` | いいえ | 外部リンクかどうか | 外部リンク時の `rel` 付与判定に使用できます |

### `FooterA11yLabels`

`a11y` は補助ラベルを表します。

| 名前       | 必須   | 内容                                 | 契約                       |
| ---------- | ------ | ------------------------------------ | -------------------------- |
| `navLabel` | いいえ | 補助ナビゲーションの accessible name | 未指定時は既定値を用います |

### 無効値の扱い

- `id` は `trim()` 後に空である場合、未指定として扱います。
- `links` は空配列を許容します。この場合、`nav` 自体を描画しないことを許容します。
- `siteUrl` が未指定である場合、サイト名はリンク化しません。
- `buildLabel` が未指定または空文字列相当である場合、build 領域は描画しません。

入力値の妥当性検証は、**描画不能を避けるための最小限**に留めます。業務ルール上の厳密検証は上位で行います。

## 状態モデル

`footer` の状態は、対話状態ではなく、**どの入力群が与えられたか**により決まります。

### 基本状態

`meta.siteName` と `meta.copyrightText` を持つ状態です。`footer` は主要メタ情報のみを描画します。

### サイト名リンク状態

`meta.siteUrl` が与えられた場合、サイト名をリンクとして描画します。未指定時はテキストとして描画します。

### build 表示状態

`meta.buildLabel` が与えられた場合、補助的な build 領域を描画します。未指定時は描画しません。

### 補助ナビゲーション状態

`links` が 1 件以上与えられた場合、`nav` を描画します。空または未指定の場合、`nav` 自体を描画しません。

### 最小状態

`meta.siteName` と `meta.copyrightText` のみを持つ最小状態を正式に許容します。footer は補助リンクや buildLabel に依存しません。

## DOM / Accessibility

ルートは常にネイティブ `<footer>` とします。`role` 属性は手動付与しません。暗黙の `contentinfo` ランドマークを利用します。

```text
<footer id? class="ui-footer">
  <div class="ui-footer__inner">
    <div class="ui-footer__meta">
      <span class="ui-footer__site">siteName</span>
      <span class="ui-footer__copyright">copyrightText</span>
      <span class="ui-footer__build">buildLabel?</span>
    </div>

    <nav class="ui-footer__nav" aria-label="...">
      <a>...</a>
    </nav>
  </div>
</footer>
```

### DOM 契約

- ルートはネイティブ `<footer>` とします。
- 主要メタ情報群と補助ナビゲーション群を別領域として分離します。
- 視覚順序・読み上げ順序・DOM 順序は一致させます。
- `nav` は `links` が 1 件以上ある場合のみ描画します。
- build 領域は `buildLabel` がある場合のみ描画します。

### Accessibility 契約

- ルートは暗黙の `contentinfo` を利用します。
- `nav` には `aria-label` を付与します。
- 区切り記号を用いる場合は `aria-hidden="true"` とします。
- 装飾アイコンや装飾画像を用いる場合、読み上げ対象にしません。
- サイト名がリンクでない場合も、主要情報として読めるテキストを保持します。

### 文言と言語

`footer` 自体は、文言の言語を固定しません。可視文言と補助ラベルの言語は上位入力に従います。ライセンス表現を英語併記するかどうかも上位方針の責務とします。

## Visual Contract

`footer` の視覚契約は、本文終端で**主張しすぎず、しかし読める**ことです。装飾性ではなく、終端情報の静かな整列を重視します。

### 情報順位

- 主要情報は `meta` に集約します。
- 補助リンクは二次情報として扱います。
- buildLabel は最も弱い情報として扱います。

### レイアウト契約

- `footer` は全幅を占有します。
- 内部は中央寄せのコンテナを持ちます。
- 狭幅時は**内容保持を優先し、複数行への折り返しを許容**します。
- 高さは固定値に依存せず、`min-block-size` 的な扱いを基本とします。
- オーバーフローで情報を隠さず、切り詰めより折り返しを優先します。

### 文字とコントラスト

- 本文より一段弱い視覚強度に抑えます。
- ただし、補助リンクは hover / focus-visible で明確に識別可能である必要があります。
- buildLabel は主要情報より弱く、しかし判読可能な強度を維持します。

### 参照トークン

公開トークンは、少なくとも次を含みます。

| 用途             | トークン                   |
| ---------------- | -------------------------- |
| 背景             | `--footer-bg`              |
| 文字色           | `--footer-fg`              |
| 弱い文字色       | `--footer-fg-muted`        |
| 境界線色         | `--footer-border`          |
| 境界線幅         | `--footer-border-width`    |
| 最大幅           | `--footer-max-inline-size` |
| 縦余白           | `--footer-padding-block`   |
| 横余白           | `--footer-padding-inline`  |
| 群間隔           | `--footer-gap`             |
| build 領域の弱度 | `--footer-build-opacity`   |

トークンの正本は契約書とし、実装と Storybook はそれに一致させます。

### 直接値の扱い

- 色、spacing、主要レイアウト寸法は直値に依存しません。
- CSS 変数のフォールバック値は、互換性維持のための最小限に留めます。
- 装飾画像の寸法や余白も、可能な限り class またはトークンで管理します。

## 環境別の振る舞い

### Dark Mode

ダークモード対応はテーマトークン解決に委ねます。`footer` 自体は `prefers-color-scheme` 分岐を前提にしません。

### Forced Colors

高コントラスト環境では、境界線、リンク、主要テキストの判別性を優先します。装飾要素の見栄えより、情報の識別可能性を優先します。

### Print

画面用 footer をそのまま印刷対象にすることは前提にしません。印刷時は、次のどちらかをプロダクト方針として別途定義します。

- 画面用 footer を非表示にします。
- 印刷用の簡略メタ情報を別契約で定義します。

本契約では、画面用 footer と印刷用 footer は**役割が異なるものとして分離可能**であることを許容します。

### オフライン・外部依存劣化

- 外部画像が取得不能でも、主要テキストとリンクは保持します。
- 外部アイコンが利用不能でも、主要情報の意味が失われない構成を維持します。
- 外部依存は装飾または補助に留めます。

## Storybook 契約

Storybook は見本ではなく、**契約検証**を主目的とします。少なくとも次を検証します。

| Story                   | 検証する契約                                                                  |
| ----------------------- | ----------------------------------------------------------------------------- |
| `DefaultContract`       | ネイティブ `<footer>`、主要メタ領域、任意の補助ナビゲーション領域を持つこと   |
| `MinimalState`          | `meta` のみで描画可能であること                                               |
| `LinkAndBuildVariants`  | `siteUrl`、`buildLabel`、`links` の有無に応じて描画有無が切り替わること       |

Storybook は契約書の代替ではありません。契約書を正本とし、Storybook はそれを検証します。

## 新規で追加を検討する価値がある機能

本節は、`footer` に新たな責務を無制限に加えるためのものではありません。`footer` は本文終端の静かなメタ情報であるべきであり、機能追加は**情報量の増加**ではなく、**責務分離、運用柔軟性、媒体別適応**を高める方向に限定するのが望ましいです。

### 最優先で検討する価値がある機能

#### 補助リンク群のデータ化

現行実装では補助リンクが固定値に近く、Rouault 固有ポリシーと `footer` 自身の契約が分離されていません。したがって、`links` を正式な入力として扱い、補助リンク群を上位から供給できるようにする機能は、最優先で検討する価値があります。

これはリンク数を増やすこと自体が目的ではありません。`footer` を「固定 2 リンクの描画器」ではなく、**補助ナビゲーションを静かに描画する部品**として整理するための機能です。

#### build 表示の任意化

版情報や build 情報は有用ですが、常時表示を固定すると、読書体験に対して視覚的な弱ノイズが恒常的に残ります。したがって、`buildLabel` を指定時のみ表示する機能は検討価値が高いです。

この機能は情報を増やすためではなく、**必要な環境だけで build 情報を出し、不要な画面では静かに省略する**ためのものです。とくに、個人用閲覧環境、公開配布環境、印刷環境で表示方針を分けたい場合に有効です。

#### 印刷用簡略 footer モード

画面用 footer と印刷物に残したい情報は一致しません。画面では補助リンクが有効でも、印刷では著作権や版情報だけを残したい場合があります。したがって、画面用 footer とは別に、**印刷用の簡略メタ情報だけを出せる機能**は検討価値があります。

これは画面用 footer を肥大化させる機能ではなく、**媒体ごとに役割を分離する機能**です。長期的には、画面用契約と印刷用契約を分けて扱う方が設計は明快です。

### 条件付きで検討価値がある機能

#### サイト名リンクの任意化

`siteName` を常にリンク化するのではなく、`siteUrl` がある場合のみリンク化し、未指定時はテキストとして表示する方針は、責務境界として自然です。これは `meta` 全体の上位供給化と整合するため、単独機能というより**入力契約の整理に伴って導入する価値がある機能**です。

#### 文言と補助ラベルの上位供給

可視文言と `aria-label` を固定値にせず、上位から供給できるようにすることは、多言語化や表示文言調整の観点で一定の価値があります。ただし、個人開発かつ単一言語運用で十分な間は、最優先ではありません。

この機能は、国際化そのものを目的とするより、**文言所有権を \*\***\`\`\***\* から切り離す**ための整理として位置づけるのが適切です。

#### 外部装飾依存の切替

外部画像や外部アイコンに依存する場合、それらを無効化できる機能、またはローカルアセットへ切り替えやすい構造を用意することには価値があります。ただし、これは公開機能というより、劣化耐性と実装の自己完結性を高めるための整備項目です。

### 原則として追加しない方がよい機能

#### SNS アイコン群

ソーシャル導線は一般的な footer ではよく見られますが、Rouault の `footer` では優先度が低いです。本文終端で視線を散らしやすく、静かなメタ情報という役割を崩しやすいためです。

#### Back to Top

ページ移動補助として一定の利便性はありますが、本文終端メタ情報の責務ではありません。必要であれば別コンポーネント、またはレイアウト機能として定義した方が契約はきれいです。

#### テーマ切替、検索、登録導線

テーマ切替、検索起動、ニュースレター登録、外部サービス誘導などは、いずれもグローバル操作またはサービス導線です。これらを footer に積むと、終端メタ情報ではなく操作パネルに近づいてしまいます。Rouault の `footer` には原則として追加しない方がよいです。

### 判断基準

新規機能を追加する際は、少なくとも次の基準で判断するのが望ましいです。

- 本文終端の静けさを壊さないか
- Rouault 固有値を `footer` 内へ再び埋め込まないか
- 画面用 footer を操作パネル化しないか
- 上位供給へ寄せた方が責務分離として自然ではないか
- 印刷や高コントラストなど媒体別契約として分離した方がよくないか

この基準に照らすと、優先度が高いのは**補助リンク群のデータ化**、**build 表示の任意化**、**印刷用簡略 footer モード**です。これらは `footer` を肥大化させるのではなく、契約境界をきれいにし、運用の柔軟性を上げる方向の機能です。

---

## 非目標

次の事項は `footer` 自身の責務に含めません。

- Git hash の厳密検証
- 年範囲計算
- 著作権文の自動生成
- ライセンス文言の法的妥当性判断
- ルーター固有挙動
- 外部リンク先の正当性確認
- 外部アセットの配信保証

これらは上位ロジックまたは別契約で扱います。

## 現行実装で未だ対応していない契約・機能

本節は、目標契約に対して**現行 **``** がまだ満たしていない項目**を、記述漏れがないように整理するものです。ここでは単に抽象的な差分を書くのではなく、**どの契約または機能が現実装に未反映か**を列挙します。

### 入力契約で未対応の項目

#### 1. `meta` 入力モデル

目標契約では `meta.siteName`、`meta.siteUrl`、`meta.copyrightText`、`meta.buildLabel` を上位から受け取る前提ですが、現行実装は `UiFooterRenderOptions` として `id`、`revision`、`year` しか受け取りません。したがって、主要メタ情報を上位供給する契約は未対応です。

#### 2. `links` 入力モデル

目標契約では補助リンク群を `links` 配列として受け取る前提ですが、現行実装は `/about` と `/contact` を内部固定しています。補助リンク群のデータ化機能は未対応です。

#### 3. `a11y` 入力モデル

目標契約では `a11y.navLabel` を上位から供給できる前提ですが、現行実装は `aria-label="フッターナビゲーション"` を固定しています。補助ラベルの上位供給は未対応です。

#### 4. `siteUrl` の任意化

目標契約では `siteUrl` がある場合のみサイト名をリンク化し、未指定時はテキストとして描画する前提ですが、現行実装はアプリ名を常に固定外部 URL へリンクしています。サイト名リンクの任意化は未対応です。

#### 5. `buildLabel` の整形済み入力

目標契約では build 表示を整形済みの `buildLabel` として受け取る前提ですが、現行実装は `revision` を受けて内部で正規化し、`#` 付き表示へ変換します。build 表示の責務縮小は未対応です。

### 状態モデルで未対応の項目

#### 6. 最小状態

目標契約では `meta.siteName` と `meta.copyrightText` のみで成立する最小状態を正式に許容しますが、現行実装は revision 表示と補助ナビゲーションを常に描画します。最小状態の正式対応は未実装です。

#### 7. build 領域の非表示状態

目標契約では `buildLabel` 未指定時に build 領域自体を描画しないことを許容しますが、現行実装では常に `.revision` を描画し、無効値でも `#dev` へフォールバックします。build 表示の任意化は未実装です。

#### 8. `nav` の省略状態

目標契約では `links` が空または未指定の場合、`nav` 自体を描画しないことを許容しますが、現行実装では常に `nav.footer-nav` と 2 本のリンクを描画します。補助ナビゲーションの省略状態は未実装です。

### 描画責務で未対応の項目

#### 9. 純粋描画化

目標契約では描画責務と文書副作用責務を分離しますが、現行実装は `renderFooter()` 内で `ensureFooterDocumentStyles()` を呼び出し、さらにモジュール末尾でも `ensureFooterDocumentStyles()` を即時実行します。import 時副作用の排除は未対応です。

#### 10. Rouault 固有値の完全な上位移譲

#### 12. `nav` の条件付き描画

### 実装上すでに存在するが文書で明示した方がよい事項

以下は現行実装に存在し、本文中でも概ね触れているものの、差分節で明示しておくと抜けが減る事項です。

- `id` は `trim()` 後に空なら出力しないこと
- `revision` は `#` 接頭辞を正規化すること
- `revision` は 7〜40 桁の 16 進文字列のみ正規値として扱うこと
- `year` は `NaN` や負数で現在年へフォールバックすること
- `ensureFooterDocumentStyles()` は同一 style 要素を 1 回だけ注入すること
- `separator` は `--separator-opacity` により外部上書き可能であること
- forced-colors 時に `CanvasText` 境界線を使うこと
- print 時に `display: none !important` を用いること

これらは目標契約の中核ではありませんが、**現行から移行する際の保持事項なのか、置き換える事項なのか**を判断しやすくするため、差分節でも触れておく価値があります。

## 補足

`footer` の価値は、情報を多く持つことではありません。**責務を絞り、上位から与えられた終端情報を静かに整列させること**にあります。

長期的に保守しやすい `footer` にするため、次の原則は維持します。

1. 描画責務と文書副作用責務を分離します。
2. Rouault 固有値を上位設定へ移します。
3. build や著作権の意味づけを footer 自身へ持ち込まないようにします。
4. 公開拡張面を CSS 変数と入力モデルへ絞ります。
5. Storybook を正本仕様にせず、契約検証器として使います。

この方針により、footer は Rouault 固有の一断片でありながら、責務境界の明確な契約対象として維持できます。
