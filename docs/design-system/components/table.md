# Table

## 概要

本書は、`ui-table` の公開契約、状態モデル、アクセシビリティ、および視覚契約を整理するものです。

`ui-table` は、構造化されたデータを比較・閲覧するためのコンポーネントです。単に `<table>` を囲うラッパーではなく、**ネイティブ table セマンティクスを壊さずに横スクロールを成立させること**、**密度切替をホスト属性で制御すること**、**Shadow DOM の **``** 制限を越えてテーブル内部要素へ一貫したスタイルを適用すること**を公開契約として固定します。

また、`ui-table` は読書体験の中に差し込まれるデータ表示面として、本文の流れを不必要に分断しないことを求めます。Rouault における table は、単に情報量を載せる器ではなく、**比較対象を静かに読み比べられること**、**横線中心の控えめな構造化で視線の走査を助けること**、**長い表でも意味的なまとまりを維持できること**を重視します。

したがって、本コンポーネントの契約は、HTML table の意味論を維持しつつ、**「没入して読む」ことのできるデータ表示**を成立させる方向で定義します。

## 公開契約

`ui-table` は、**ネイティブ **``** の意味論を保持したまま、必要時にだけ横スクロール可能な閲覧面を与えるコンポーネント**として定義します。ここでの責務は、table の再実装ではなく、**意味論保持、最小限のスクロール補助、最小限のアクセシビリティ補助、密度切替**です。

一方で、本文カラムからのブレークアウト、ページ全体の prose レイアウト、数値列の意味付け、複雑表の上位データ設計は、本コンポーネントの中核責務に含めません。これらは上位レイヤまたは別契約として扱います。

`ui-table` 自体は `<table>` を生成しません。利用者は既定スロットへ **単一のネイティブ **``** 1 個**を与えなければなりません（MUST）。`thead`、`tbody`、`tfoot`、`caption`、`th`、`td`、`colspan`、`rowspan` などの意味論は、ホストではなくスロットされたネイティブ table によって成立します。

アクセシブルネームは、`aria-labelledby` または `aria-label` のいずれかで与えなければなりません（MUST）。フォールバック名に依存した運用は正規契約に含めません。

### 入力契約

| 名前               | 種別                                       | 必須     | 内容                | 契約                                 |
| ---------------- | ---------------------------------------- | ------ | ----------------- | ---------------------------------- |
| `density`        | property / attribute                     | いいえ    | 行密度               | `normal` / `compact`。既定値は `normal` |
| `scrollMode`     | property / attribute                     | いいえ    | スクロール領域の公開方針      | `auto` / `always`。既定値は `auto`      |
| `ariaLabel`      | property / attribute (`aria-label`)      | 条件付き必須 | スクロール領域のアクセシブルネーム | `ariaLabelledby` がない場合は必須          |
| `ariaLabelledby` | property / attribute (`aria-labelledby`) | 条件付き必須 | スクロール領域の参照ラベル     | `ariaLabel` がない場合は必須               |

### スロット契約

| 名前     | 種別   | 位置づけ | 内容                         |
| ------ | ---- | ---- | -------------------------- |
| 既定スロット | slot | 正規入力 | 直下に配置された単一のネイティブ `<table>` |

既定スロットには、**直下に配置された単一のネイティブ **``** 1 個だけ**を正規入力として受け取ります。空白テキストノードやコメントノードの混在は許容しますが、複数の `<table>` を並べる構成、`<table>` 以外の主要要素を前後に混在させる構成、または table を伴わない構成は公開契約上の対象外です。

セル内に別の `<table>` をネストする構成も正規サポート対象に含めません。ネスト table を必要とする場合は、別責務での表示戦略を採ります。

### 公開メソッド

`ui-table` は次の公開メソッドを持ちます。

| メソッド      | 内容                    |
| --------- | --------------------- |
| `focus()` | 内部スクロール領域へフォーカスを委譲します |
| `blur()`  | 内部スクロール領域からフォーカスを外します |

利用者は、Shadow DOM 内の特定ノード名や DOM 構造に依存してはなりません（MUST NOT）。フォーカス制御は公開メソッドを通じて行います。

### 属性反映契約

公開入力のうち、`density`、`scrollMode`、`ariaLabel`、`ariaLabelledby` は property と attribute の両面から操作できます。`density` と `scrollMode` はホスト属性へ反映され、スタイルと状態判定の入力となります。

| property         | attribute         | reflect | 備考                                  |
| ---------------- | ----------------- | ------- | ----------------------------------- |
| `density`        | `density`         | あり      | 密度切替に用います                           |
| `scrollMode`     | `scroll-mode`     | あり      | `auto` / `always` の方針を示します          |
| `ariaLabel`      | `aria-label`      | なし      | 内部スクロール領域の `aria-label` に反映します      |
| `ariaLabelledby` | `aria-labelledby` | なし      | 内部スクロール領域の `aria-labelledby` に反映します |

### 列挙外値・無効値の扱い

`density` は `normal` / `compact`、`scrollMode` は `auto` / `always` のみを契約値とします。列挙外文字列を与えた場合の見た目や挙動は未定義であり、利用者はこれに依存してはなりません（MUST NOT）。

アクセシブルネームの優先順位は次のとおりです。

1. `aria-labelledby`
2. `aria-label`

どちらも与えられていない場合は契約違反です。描画継続の有無やフォールバック名の付与は互換措置であり、正規契約には含めません。

### 責務範囲

責務範囲には、横スクロールコンテナの提供、`density` による視覚密度切替、`scrollMode` に基づくスクロール領域公開方針、公開 `focus()` / `blur()`、テーブル内部要素に対する一貫したスタイル適用、および最小限のアクセシビリティ補助を含みます。

一方で、本文レイアウトへのブレークアウト、列幅最適化、データ型別整形、数値列の意味付け、ソート UI、レスポンシブ変形表示、行選択、列固定、仮想スクロール、印刷最適化は責務に含めません。

## 状態モデル

`ui-table` の主要状態は、見た目の変種数ではなく、**密度、スクロール領域の公開方針、アクセシブルネームの有無、表の意味構造**によって読み分けます。

### 1. 基本状態

最小状態は、`density="normal"`、`scrollMode="auto"`、アクセシブルネーム付き、単一のネイティブ `<table>` を 1 つスロットした状態です。この状態では、表が実際に overflow しない限り、追加の focusable region は現れません。

### 2. 密度状態

`density` は `normal` と `compact` の 2 状態を持ちます。

| `density` 値 | 意味   | 想定用途              |
| ----------- | ---- | ----------------- |
| `normal`    | 標準密度 | 通常の本文内表、比較表、注記付き表 |
| `compact`   | 高密度  | 列数や行数が多い一覧、比較表    |

`density` は **視覚密度だけ**を表し、セル内 interactive content の可触領域や UI 密度全般までは規定しません。

### 3. スクロール公開状態

`scrollMode` は `auto` と `always` の 2 状態を持ちます。

| `scrollMode` 値 | 意味                                                            |
| -------------- | ------------------------------------------------------------- |
| `auto`         | 実際に横方向 overflow が発生した場合にだけ、スクロール領域を focusable region として公開します |
| `always`       | overflow の有無にかかわらず、スクロール領域を常に focusable region として公開します       |

既定値は `auto` です。したがって、**不要な tab stop を増やさないこと**を既定方針とします。

`scrollMode="auto"` の overflow 判定は、少なくとも次の契機で再評価されなければなりません。

1. 初回描画時に、スロット内容とスタイル適用が反映された後。
2. ホスト要素または内部スクロール領域の利用可能幅が変化したとき。
3. スロットされた `<table>` の構造、セル内容、または属性変化により、横方向必要幅が変化し得るとき。
4. table の文字幅に影響し得るフォント読み込みが完了したとき。

複数の変化が短時間に連続した場合、再評価は 1 回にまとめてよいです。実装はバッチングしてよいものとしますが、**利用者から観測可能な状態は、変化後の安定した描画に追随して収束**しなければなりません。

一方で、単なる hover、focus ring、色変化など、横方向必要幅に影響しない変化は再評価契機に含めません。

### 4. アクセシブルネーム状態

スクロール領域は `aria-labelledby` または `aria-label` によって名前を持ちます。無名の scroll region は正規状態に含めません。

### 5. 構造状態

`ui-table` 自体が構造状態を持つのではなく、スロットされたネイティブ table が `caption`、`thead`、`tbody`、`tfoot`、複数 `tbody`、`colspan`、`rowspan` を持つことによって意味構造が成立します。

ただし、単純表と複雑表は区別して扱います。

- **単純表**: 各データセルに対して、`scope` により見出しの対応が一意に読める表
- **複雑表**: `scope` だけでは、データセルと見出しの対応が一意に読めない表

複雑表は、少なくとも次のいずれかに該当する場合に成立します。

1. 1 つのデータセルに対して、複数の列見出し候補または行見出し候補が交差し、`scope` だけでは対応関係が一意に定まらない。
2. `colspan` または `rowspan` により、見出しセルが複数の見出し軸にまたがり、見出しの階層関係を明示しなければ意味が伝わらない。
3. 複数の見出し行または見出し列が存在し、あるデータセルがどの見出し群に属するかを `scope` のみで安全に復元できない。

単に `colspan` または `rowspan` を 1 回使っているだけでは、自動的に複雑表とはみなしません。**判定基準は span の有無ではなく、セルと見出しの対応が **``** のみで一意に読めるかどうか**です。

複雑表では、`headers` / `id` による関連付けを要求します。

## DOM / Accessibility

ルートは `:host` です。Shadow DOM 内部に単一のスクロールコンテナを持ち、その中に既定スロットを配置します。利用者がスロットした `<table>` は Light DOM 側に存在します。

```text
<ui-table density="normal" scroll-mode="auto" aria-labelledby="...">
  #shadow-root
    <div ...>
      <slot></slot>
    </div>

  <table>
    ...
  </table>
</ui-table>
```

`ui-table` の重要点は、table 要素を Shadow DOM 内で再構築しないことです。実データの意味論はあくまで Light DOM のネイティブ `<table>` に残し、スクロールとスタイルのみをコンポーネントが補助します。

### Accessibility 契約

アクセシビリティ上の重要点は次のとおりです。

- スクロール対象は内部スクロールコンテナです。
- `scrollMode="auto"` では、実際に横方向 overflow が発生した場合にだけ、内部スクロールコンテナへ `role="region"` と focusability を与えます。
- `scrollMode="always"` では、overflow の有無にかかわらず、内部スクロールコンテナへ `role="region"` と focusability を与えます。
- `scrollMode="auto"` の overflow 判定は、初回描画後、利用可能幅の変化時、スロットされた table の内容変化時、フォント読み込み完了時に再評価します。
- スクロール領域には `aria-labelledby` または `aria-label` によるアクセシブルネームを与えます。
- `caption` は table 本体の説明であり、スクロール領域のアクセシブルネームとは別責務です。両者は代替関係ではありません。
- テーブル自体の意味論はネイティブ `<table>` に依存します。
- 単純表では `scope="col"` / `scope="row"` を標準とします。
- 複雑表では、必要に応じて `headers` / `id` による明示的関連付けを要求します。

また、キーボード操作で横スクロールに到達できることはアクセシビリティ契約に含みますが、**内部ノード名や Shadow DOM 構造自体は公開契約ではありません**。外部利用者は、公開 `focus()` / `blur()` 以外の方法で内部 DOM に依存してはなりません。

### スタイル適用戦略

Shadow DOM の `::slotted()` はスロット直下の要素にしか適用できず、`th` や `td` のような孫要素には適用できません。そのため `ui-table` は、Light DOM 側の table 内部要素にも一貫したスタイルが届く戦略を必要とします。

ただし、**どの方式でスタイルを届かせるか自体は公開契約ではありません**。document への style 注入、constructable stylesheet、その他の方式は、同じ見た目と同じ公開振る舞いを維持する限り内部戦略として差し替え可能です。

したがって、利用者は style タグの ID、内部 class 名、具体的なセレクターへ依存してはなりません。公開拡張面は、原則として CSS Custom Properties とスロットされるネイティブ table の構造だけです。

## Visual Contract

`ui-table` の視覚契約は、比較表や一覧表を**静かに読めること**を優先する点にあります。強いグリッド線や箱型セルではなく、**横線中心の軽い構造**、**必要時のみ現れる行強調**、**キャプション・ヘッダー・本文セルの階層差**によって、表内の走査を助けます。

### 情報順位

- `caption` は表全体のタイトルとして最上位の説明を担います。
- `th` は構造軸の説明として、本文セルより控えめだが識別可能な強度を持ちます。
- `td` は本文情報の主役です。
- 行区切りは視線誘導の補助であり、主張しすぎません。
- Active Ruler は現在読んでいる行を一時的に示しますが、常時強調にはしません。

### レイアウト

ホストは `display: block` で、既定では **親コンテナ幅に収まる inline layout** を採ります。本文カラムからのブレークアウトは本コンポーネントの中核契約に含めません。必要な場合は、上位の prose レイヤまたは専用ラッパーで制御します。

内部スクロールコンテナは横方向のみスクロールし、縦方向は visible を維持します。内部の `table` は `width: max-content` と `min-width: 100%` を併用し、収まるときは幅いっぱい、収まらないときは必要幅まで広がる構成を取ります。

### 視覚仕様

- `table` は `border-collapse: collapse`、`border-spacing: 0` を持ちます。
- `caption` は上側配置かつ左寄せです。
- `th` は小さめのサイズ、やや広い字間、控えめな色で構造見出しとして振る舞います。
- `td` は本文色を用い、内容の主役として描画します。
- `tr` は下線のみを持ち、縦線は用いません。
- `tfoot tr:first-child` と `tbody + tbody` には太めの境界線を与え、意味の切れ目を強調します。

セル内容のオーバーフロー方針は、**個々のセルを強制的に省略するのではなく、必要に応じて表全体を横スクロールさせる**ことを基本とします。したがって、標準契約にはセル単位の `ellipsis` を含めません。本文セルは原則として折り返し可能とし、長い識別子、URL、コード片のように自然折り返ししにくい内容は、必要に応じて表全体の横スクロールで受けます。

### 密度ごとの差分

- `normal` は標準パディング、標準データセルフォントサイズです。
- `compact` はヘッダー、本文セルの縦パディングを縮小し、本文セルフォントも一段小さくします。

密度差は、視覚強調の差ではなく**情報密度の差**として扱います。`compact` にしても見出し階層や意味構造は変えません。

### 配置契約

新規コードに対する**正式な配置契約**は、`th` / `td` 上の `data-align="start|center|end"` とします。

- `data-align="start"` は論理先頭揃え
- `data-align="center"` は中央揃え
- `data-align="end"` は論理末尾揃え

`align="left|center|right"` は、Markdown 由来 HTML との互換のためにのみ許容する**凍結された歴史的互換入力**です。新規コードの正式 API には含めません。

`data-align` と `align` が同時に存在する場合は、常に `data-align` を優先します。`align` 互換は `left` / `center` / `right` の 3 値に限定し、将来この入力に対して新しい意味や派生値を追加しません。

### 数値列契約

数値列のタイポグラフィは配置契約から分離します。`data-type="number"` を持つセルまたは列は、tabular numerals を適用し、既定配置を `end` とします。明示的な `data-align` が指定されている場合は、配置についてはそちらを優先します。

### フォーカス表示

内部スクロール領域が `:focus-visible` になった場合、`outline`、`outline-offset`、`border-radius`、および `--animation-focus` によるフォーカスアニメーションを適用します。これは「表の中身」に対するフォーカスではなく、**横スクロール可能領域としての focus** を可視化する契約です。

## 環境別の振る舞い

### Reduced Motion

`prefers-reduced-motion: reduce` 環境では、行ホバー時のトランジション時間を `0.01ms` に極小化します。スクロールコンテナのフォーカス時アニメーションも停止します。

### Touch / Coarse Pointer

`@media (hover: none) and (pointer: coarse)` 環境では、tbody 行の hover 背景を無効化します。また、セル内容の省略を強制せず、`white-space: normal`、`overflow: visible`、`text-overflow: clip` を適用します。

### Forced Colors

`forced-colors: active` 環境では、行境界線を `CanvasText` で描画します。`tfoot` の先頭境界線および `tbody + tbody` の境界線も `CanvasText` にフォールバックします。色指定によるニュアンス差よりも、構造の視認性を優先します。

### Dark Mode

現行実装は `prefers-color-scheme` を直接分岐していません。ダークテーマ対応は、主としてトークン側の色差し替えに委ねます。したがって、`ui-table` は**専用ダークモード実装を持つのではなく、トークン適用先として振る舞う**コンポーネントです。

### Print

印刷最適化は本コンポーネントの中核契約に含めません。したがって、print 専用再整形は標準契約外です。印刷や PDF 化を正式に扱う場合は、上位レイヤで別途最適化契約を持ちます。

## 関連契約

### table セマンティクス契約

`ui-table` は table の意味論を提供するコンポーネントではなく、**既存のネイティブ table セマンティクスを保持したまま表示補助を加えるコンポーネント**です。

- 表の構造は利用者が `<table>` とその子要素で定義します。
- `caption`、`thead`、`tbody`、`tfoot`、`th`、`td`、`scope`、`colspan`、`rowspan` の意味は HTML 標準に従います。
- `ui-table` はこれらを再定義しません。

### Long Table Strategy 契約

現行 Storybook は、行数が多い表に対して意味のまとまりごとに複数の `tbody` を用いる運用を示しています。これを本契約では Long Table Strategy と呼びます。

この方針では、`tbody + tbody` に太めの境界線を与え、視覚的にも意味的にもチャンク分割を明示します。大量行を 1 つの `tbody` に平坦に並べるのではなく、**意味単位ごとに chunking すること**を推奨します。

### Markdown 互換契約

`align` 属性サポートは、Markdown 由来のテーブル HTML と互換を保つための**後方互換契約**です。新規コードの正式 API は `data-align="start|center|end"` とし、`align` 属性は歴史的互換入力としてのみ受理します。

この互換入力の寿命は、**Markdown / CMS / 既存コンテンツから生成された HTML を受け入れるための恒久互換**として固定します。ただし、これは一般利用向けの公開 API を意味しません。次の規則を適用します。

- 新規に手書きするコンポーネント利用コードでは、`align` を使ってはなりません（MUST NOT）。
- `align` は、コンテンツ起源の HTML を受け入れるためにのみ許容します。
- `align` の許容値は `left` / `center` / `right` の 3 値に凍結します。
- `data-align` が同時に存在する場合は、常に `data-align` を優先します。
- 上流で正規化可能な場合は、`align` を `data-align` へ変換してから流し込むことを推奨します。

したがって、`align` は**削除予定の暫定 API ではなく、対象を限定した凍結互換**として扱います。

### 複雑表アクセシビリティ契約

単純表と複雑表は分けて扱います。

- 単純表では `scope` ベースの見出し関連付けを標準とします。
- 複雑表では `headers` / `id` による明示的関連付けを要求します。

ここでいう複雑表とは、次のいずれかに該当する表を指します。

1. 1 つのデータセルに対して複数の見出し候補が交差し、`scope` だけでは見出し対応が一意に読めない。
2. `colspan` / `rowspan` により見出しの階層関係を明示しなければ意味が伝わらない。
3. 複数の見出し行または見出し列を持ち、データセルが属する見出し群を `scope` のみで安全に復元できない。

逆に、単に `colspan` または `rowspan` を含むだけで、`scope` により対応関係が一意に読める場合は単純表として扱います。

### セル内容モデル契約

`ui-table` は読書主体の表を対象とするため、セル内容は原則として **phrasing content と軽量な埋め込み内容**を正規範囲とします。正規範囲には、少なくとも次を含みます。

- プレーンテキスト
- 強調、注釈、短い引用などの inline テキスト装飾
- 単一リンクまたは少数の短いリンク
- 短いコード片、キーボード表記、短い数式断片
- 小さなインライン画像、アイコン、状態表示
- 単一段落、または意味的に一続きとして読める短い複合 inline 内容

一方で、次の内容は標準契約に含めません。

- フォーム群、編集 UI、複合操作 UI
- セル内スクロール領域
- 複数の interactive widget が並ぶ複合内容
- 複数段落から成る長文本文
- ネストされたリスト、カード、パネル、サブレイアウト
- code block 相当の複数行コード
- 表の中にさらに独立した閲覧面を形成する内容

画像、箇条書き、複数段落、複数行コードなどは、必要性が高い場合でも**標準契約ではなく拡張的利用**として扱います。これらを正式サポートへ昇格させる場合は、セル内余白、行高、focus 表示、レスポンシブ時の読みやすさまで含めて別途契約化します。

したがって、`ui-table` のセルは、**読むための軽量な情報断片を置く場所**として設計し、ミニレイアウトコンテナとしては扱いません。

### スタイル拡張契約

`ui-table` は `::part(...)` を公開していません。主な拡張面は CSS Custom Properties と、スロットされるネイティブ table 自体の属性・構造です。

利用者は、次のレイヤで調整を行います。

- ホスト側カスタムプロパティによる色、余白、フォーカス調整
- スロットする table 側の構造変更
- 必要に応じた上位コンテナでのレイアウト制御

一方で、Shadow DOM 内の内部スクロールコンテナ、注入 style タグ、style タグの ID、注入 CSS の具体的セレクターへ直接依存する拡張は公開契約に含みません。利用者は、**公開拡張面と非公開内部面を混同してはなりません**。

### 開発時警告契約

`ui-table` は、**安価・高確度・構造的に判定できる契約違反だけ**を開発時 warning の対象とします。これは描画停止ではなく、契約違反またはアクセシビリティ品質低下を知らせる補助契約です。

開発時 warning の対象に含めてよいのは、少なくとも次のような条件です。

- `aria-labelledby` と `aria-label` のどちらも与えられていない。
- 既定スロット直下にネイティブ `<table>` が存在しない。
- 既定スロット直下に複数のネイティブ `<table>` が存在する。
- セル内にネストされた `<table>` が存在する。
- `density` や `scrollMode` に列挙外値が与えられている。

一方で、次のような条件は**実装時の自動検知対象に含めません**。

- 複雑表で `headers` / `id` が本当に必要かどうかの意味論判定
- セル内容が「軽量範囲」を超えるかどうかの意味解釈
- 印刷最適化の必要性
- コンテンツ起源か手書きコードかといった入力由来の判定

したがって、runtime validation の責務は、**意味解釈を要しない構造違反の通知**に限定します。深い意味論や設計方針の逸脱は、文書契約、レビュー、Storybook の negative case によって担保します。

warning の発火単位は、**同一 document 内で、違反種別ごとに 1 回**とします。すなわち、同じ document の中で同種の違反が複数インスタンスにまたがって繰り返されても、console への warning は 1 回だけ出せば足ります。別種の違反は、それぞれ独立して 1 回ずつ通知してよいです。

この単位を採る理由は次のとおりです。

- **1 インスタンス単位**では、同一原因の違反が多数の table に波及したときに console が過度に汚れやすい。
- **1 セッション単位**では、document 境界や iframe 境界と一致せず、局所的なデバッグ単位として粗すぎる。
- **1 document 単位**であれば、現在観測している描画面に対する問題を 1 度は確実に通知しつつ、重複警告も抑制できる。

また、開発時 warning は本番動作契約ではありません。正規入力違反であっても、可能な限り描画継続を優先し、**production では throw や描画停止の理由にしません**。ただし、何が warning 対象で、何を runtime では検知しないか、さらに warning をどの単位で抑制するかという分類自体は公開契約に含めます.

## 境界条件

### 1. アクセシブルネーム未指定

`aria-labelledby` と `aria-label` のどちらも未指定の状態は契約違反です。互換のために描画が継続されたとしても、正規サポート入力ではありません。

### 2. 単一行テーブル

`thead + tbody` で、`tbody` に 1 行だけを持つ最小限の table は有効です。最小行数であっても構造が崩れてはなりません。

### 3. ヘッダーのみ

`tbody` が空で、`thead` のみを持つ table も許容します。検索結果 0 件や、データ未投入状態の表示で起こり得る構成です。ただし、空状態メッセージの生成は `ui-table` の責務ではありません。

### 4. `caption` 付き

`caption` は左寄せかつ上側配置されます。テーブル内容の説明として推奨します。

### 5. `tfoot` 付き

`tfoot` の先頭行には太めの上境界線を与えます。合計、サマリー、注記行など、本文行から切り離したい情報の表示に用います。

### 6. 複数 `tbody`

複数の `tbody` を持つ table は正規サポート対象です。各 `tbody` の境界に強調線を入れ、長い表の意味的区切りとして扱います。

### 7. `colspan` / `rowspan`

ネイティブ table モデルに従って受理します。ただし、`scope` によりセルと見出しの対応が一意に読めない場合は複雑表とみなし、`headers` / `id` による関連付けを要求します。単に `colspan` または `rowspan` を含むだけで自動的に複雑表とはみなしません。

### 8. 数値セル

`data-type="number"` を持つセルは tabular numerals を適用し、既定配置を `end` とします。数値列であることは、右揃え属性そのものではなく、内容型によって表します。

### 9. セル内容が軽量範囲に収まる場合

プレーンテキスト、短いリンク、短いコード片、インライン画像、短い注記など、読書主体の軽量内容は正規サポート対象です。

### 10. セル内容が軽量範囲を超える場合

複数段落の長文、ネストリスト、複数行コード、フォーム群、複合操作 UI、セル内スクロール領域は標準契約外です。描画されたとしても、正規サポート入力ではありません。

### 11. 列数が多いワイド表

表がコンテナ幅を超える場合、内部スクロール領域の横スクロールで閲覧可能とします。`scrollMode="auto"` では overflow 発生時にのみ focusable region となり、`scrollMode="always"` では常に focusable region となります。

### 12. `<table>` をスロットしない場合

実装上は任意ノードをスロットできたとしても、本契約の対象外です。`ui-table` は table セマンティクスを代替しないため、`<table>` を伴わない利用はサポート対象外とします。

### 13. ネスト table

セル内に別の `<table>` をネストする構成は正規サポート対象外です。

## 補足

`ui-table` の要点は、多機能な表コンポーネントであることではありません。**ネイティブ table の意味論を壊さずに、読むための器として整えること**にあります。

したがって、今後の変更でも次の 5 点は崩さない方がよいです。

1. 実データの意味論は常にネイティブ `<table>` 側に残すこと。
2. 横スクロール主体は内部スクロール領域であり、table 自体を疑似構造へ変換しないこと。
3. `density` は視覚密度だけを表すこと。
4. アクセシブルネームは `aria-labelledby` または `aria-label` によって明示すること。
5. ページレイアウト責務と table 表示責務を混同しないこと。

## 将来拡張の原則

本節は現行実装の公開契約ではなく、将来追加を検討する場合の設計指針です。追加機能は、table を高機能データグリッド化するためではなく、**読書文脈での比較・参照体験を壊さずに補強する場合に限って**採用します。

### 最優先で検討する価値がある拡張

#### 1. `aria-describedby` と説明補助の受け口

現行の目標契約ではスクロール領域名として `aria-labelledby` / `aria-label` を扱いますが、表の読み方や補足説明まで含めた関連付けはまだ弱いです。将来拡張では、`aria-describedby` や注記・補足文との橋渡しを追加する価値があります。

この拡張を採用する場合、次を満たします。

- `aria-labelledby` / `aria-label` / `aria-describedby` の役割分担と優先順位を明確に固定します。
- スクロール領域の名前と table 本体の意味論を混同しません。
- 既存の `caption` 契約と競合しないよう整理します。

#### 2. 注入 CSS のスコープ戦略の再設計

現行は `ui-table table` などのグローバルセレクターでスタイルを注入しています。これは実装上妥当ですが、複数テーマや埋め込みコンテキストでの制御性をさらに高めるには、将来より厳密なスコープ戦略を検討する価値があります。

この拡張を採用する場合、次を満たします。

- Light DOM table の意味論は維持します。
- スタイル注入回数は引き続き 1 回に抑えます。
- 既存テーマや prose 文脈との互換性を壊しません。

### 条件付きで価値がある拡張

#### 3. sticky header / sticky first column

比較表や長い一覧では有用ですが、table を読む体験を静かに保てる場合に限り検討対象です。データグリッド的操作性を優先し始めると責務が膨らむため、通常の読書文脈では標準契約にしません。

#### 4. `dense` 以上の追加密度やサイズ展開

現行の `normal` / `compact` は十分に単純です。将来さらに密度段階を追加する場合は、可読性を犠牲にしてはなりません。少なくとも本文文脈で読める下限を下回る密度は採用しません。

### 採用しない方針

次の方向は、読書体験を損ないやすく、table の責務も汚しやすいため採りません。

- 独自セル編集、選択、ドラッグなどのデータグリッド機能を内蔵すること
- `<table>` を廃して div / grid ベースへ置き換えること
- ソートやフィルターのアプリケーション責務を本コンポーネントへ持ち込むこと
- 空状態、エラー状態、ローディング状態を table ラッパー自身が生成すること

## 新規で追加を検討する価値がある機能

本節は、現行実装の不足を埋めるためではなく、``** の設計思想を壊さずに、読むための table として価値を上げる新規機能**を整理するものです。

ここで追加を検討する価値がある機能とは、データグリッド化や操作機能の増強ではなく、**発見しやすさ、比較しやすさ、意味の伝わりやすさ**を改善するものを指します。

### 最優先で検討する価値がある機能

#### 1. 横スクロール可能性の視覚ヒント

読書文脈では、表が横方向に読めること自体に気づきにくい場合があります。したがって、横スクロール可能性を静かに示す補助は、追加価値が高いです。

候補は次のようなものです。

- 左右端の fade / shadow
- 末端未到達時のみ現れる edge affordance
- 初回のみ表示する scroll hint
- キーボード focus 時のみ現れる scrollability cue

これらは、table の意味論を壊さず、責務も大きく広げません。**操作を増やすのではなく、発見しやすくする**補助として適合度が高いです。

#### 2. sticky header

比較表や長い一覧では、列見出しを見失うこと自体が読解コストになります。そのため、sticky header は追加価値が高い機能です。

ただし、sticky first column まで同時に標準化すると責務が膨らみやすいため、優先順位としては **header のみ先行**が望ましいです。

導入する場合は、既定有効ではなく opt-in とし、読書文脈に対して過度に主張しないことを条件とします。

#### 3. `aria-describedby` を含む説明補助

現行契約では `aria-labelledby` / `aria-label` による命名を扱っていますが、表の読み方や補足説明まで含めた関連付けは弱いです。したがって、`aria-describedby` の受け口を追加する価値があります。

これは視覚機能ではなく、**アクセシビリティと読解支援を接続する機能**です。caption、注記、補足文、スクロール説明との関係を自然に扱えるようになります。

### 優先度が高いが、条件付きで検討する機能

#### 4. 数値列の列単位指定

現行の目標契約では `data-type="number"` をセルまたは列へ付与する方針を採っていますが、実運用では数値列は列単位で一括指定したい場面が多くあります。

したがって、たとえば `<col data-type="number">` のように、**列定義から数値列契約を一括適用する機能**は追加価値があります。

これは新しい責務を増やすというより、既存の数値列契約を実務上扱いやすくする方向の改善です。

#### 5. 比較読解のための軽量な強調 API

比較読解では、特定の行や列を静かに目立たせたい場面があります。そのため、状態管理や選択機能ではなく、**比較対象の視覚階層を少しだけ上げる API**は検討価値があります。

たとえば、次のような方向です。

- 行単位または列単位の軽い強調
- 比較対象を示す静的な emphasis 指定
- hover 依存ではない読み比べ補助

ただし、選択状態、チェック状態、アクティブ状態のような interaction state を持ち込んではなりません。追加する場合は、**状態 API ではなく視覚階層 API**として限定する必要があります。

#### 6. caption を補助する注記・出典の受け口

読書アプリでは、表の前後に短い導入、注記、出典、読み方の補足が付くことがあります。これをすべて外側 prose に任せると、利用側の構造がぶれやすくなります。

そのため、caption を置き換えるのではなく、**caption を補助する弱い受け口**として、注記や出典を関連付ける仕組みを検討する価値があります。

ただし、figure 的責務まで広げると table wrapper の純度が下がるため、あくまで補助的な機能として扱うべきです。

### 条件付きで価値がある機能

#### 7. print / PDF 向けの軽量最適化

現行契約では印刷最適化を中核責務から外していますが、読書アプリ文脈では print や PDF 化の需要が将来的に発生し得ます。そのため、完全な print engine ではなく、**軽量な印刷補助**には検討価値があります。

候補は次のようなものです。

- 印刷時の breakout 無効化
- 不要な affordance の非表示
- 必要最小限のヘッダー繰り返し支援

ただし、これは中核責務へ戻すべき機能ではありません。実需要が確認できた場合に限って、薄い最適化として検討するのが妥当です。

### 採用優先度が低い、または採らない方がよい機能

次の方向は、読書体験を損ないやすく、table の責務も汚しやすいため、現時点では追加価値が低いと判断します。

- ソート
- フィルター
- ページネーション
- セル編集
- 行選択
- ドラッグ操作
- 仮想スクロール
- カード化レスポンシブ変形
- 空状態、エラー状態、ローディング状態の内蔵

これらは、`ui-table` を「読むための table」から、application widget や data grid に変質させやすい機能です。

### 本節のまとめ

本コンポーネントで追加を検討する価値が高いのは、**操作を増やす機能ではなく、読解コストを下げる機能**です。方向性としては、次の 3 系統に整理できます。

1. 発見しやすくする
2. 比較しやすくする
3. 意味を伝わりやすくする

優先順位を 3 つに絞るなら、特に価値が高いのは次の機能です。

1. 横スクロール可能性の視覚ヒント
2. sticky header
3. `aria-describedby` を含む説明補助

## 現行実装で未対応の事項

本節は、**本書で再固定した目標契約**に対して、現行の `table.ts` および `table.stories.ts` がまだ追従していない事項を整理するものです。

### 1. `scrollMode` の未実装

現行実装は `auto` / `always` の公開入力を持たず、内部スクロール領域を常に focusable region として公開します。したがって、不要な tab stop を増やさない `auto` 既定方針は未実装です。

### 2. `focus()` / `blur()` の未実装

現行実装には公開 `focus()` / `blur()` がなく、外部からのフォーカス制御は内部 DOM 探索に依存し得ます。公開 API による委譲契約は未実装です。

### 3. `aria-labelledby` の pass-through 未実装

現行実装が内部スクロール領域へ反映するアクセシビリティ関連入力は `aria-label` のみです。したがって、`aria-labelledby` を用いた正規命名契約は未実装です。

### 4. 無名状態の互換継続

本書ではアクセシブルネームを必須契約としましたが、現行実装は未指定時にも描画を継続し、`Data table` をフォールバック適用します。これは目標契約と一致しません。

### 5. 構造違反に対する開発時 warning の未実装

本書では、単一のネイティブ `<table>` 直下 1 個という入力契約違反や、ネスト table のような**安価かつ高確度に検知できる構造違反**は、開発時 warning の対象に含める方針としました。現行実装はこれらを体系的には検知しません。

### 6. runtime validation の分類未実装

本書では、構造違反だけを runtime warning 対象とし、複雑表の意味論判定やセル内容モデルの深い解釈は runtime で自動検知しない方針を採りました。現行実装および Storybook には、この分類方針を明示的に実装へ反映した仕組みがありません。

### 7. 開発時 warning の発火単位未実装

本書では、開発時 warning の発火単位を**同一 document 内で、違反種別ごとに 1 回**としました。しかし現行実装が持つ `_hasWarnedMissingAriaLabel` は各インスタンスに紐付く単一フラグであり、少なくとも無名アクセシブルネームに関しては**インスタンスごとに 1 回**の warning になります。document 単位・違反種別単位の抑制契約は未実装です。

### 8. レイアウト責務の分離

本書では breakout を中核契約から外し、上位レイヤ責務としましたが、現行実装はホストに既定のブレークアウト幅と負マージンを持ちます。したがって、責務分離方針は未実装です。

### 9. `data-align` / `data-type` 契約の未実装

本書では `data-align="start|center|end"` を正式 API、`data-type="number"` を数値列契約としましたが、現行実装は `align="left|center|right"` と `align="right"` に紐づく `tnum` で動作しています。配置とタイポグラフィの分離は未実装です。

### 10. Storybook 契約マトリクスの未追従

現行 Storybook の docs 説明、argTypes、使用例、play 関数は、再固定後の目標契約ではなく、旧来の実装前提をまだ多く保持しています。たとえば、次のような前提が残っています。

- `aria-label` のみをアクセシブルネーム入力とみなす。
- `aria-labelledby`、`scrollMode`、`data-align`、`data-type` に対応した controls / docs が存在しない。
- `.table-container` という内部 class 名に依存する。
- `Default` や `Compact` で、常時 `role="region"` / `tabindex="0"` を期待する。
- `Default` で document style tag の ID を直接検証する。
- `NumericData` と `AlignmentSupport` が `align` 属性中心の旧契約を前提にする。

したがって、Storybook は現行実装の説明としては整合していても、**目標契約の確認点としては未追従**です。

### 11. 実装ソース内 JSDoc / 使用例の未追従

`table.ts` の冒頭 JSDoc、使用例、`@property` 説明は、再固定後の目標契約ではなく旧来の実装前提を保持しています。たとえば、次のような内容が残っています。

- `aria-label` のみを公開アクセシブルネーム入力として説明する。
- 使用例が `align="right"` 中心の旧配置契約を前提にする。
- breakout レイアウトを暗黙の既定として含む実装説明を残す。
- グローバル style 注入を内部戦略ではなく、実質的に前提仕様のように記述する。

したがって、**実装ファイル内コメントと目標契約が未整合**です。ソース内ドキュメントも、Storybook や契約書と同時に更新する必要があります。

### 12. 内部戦略用エクスポートの公開面化

現行実装は `DOCUMENT_STYLE_ID` と `DOCUMENT_CSS` をモジュール外へ `export` しています。これは実装上は便利ですが、目標契約では style 注入方式そのものを公開契約から外しているため、**内部戦略が accidental public API 化している**状態です。

これらを本当に公開面として維持するのか、内部定数へ戻すのかは未整理であり、目標契約に照らすと未対応事項として明示すべきです。

### 13. 複雑表アクセシビリティ要件の未強制

本書では複雑表に対して `headers` / `id` 連携を要求し得る契約としましたが、現行実装および Storybook はこれを検証・強制しません。

### 14. セル内容モデルの未検証

本書では読書主体の軽量内容を正規範囲としましたが、現行実装はセル内内容を検証しません。複雑な interactive widget を排除する仕組みはありません。

### 15. 印刷最適化の非対応明文化

本書では印刷最適化を中核契約外としましたが、現行 Storybook や実装ではその非対応方針を明示的に検証していません。

### 16. 本節の扱い

本節に記載した事項は、目標契約に向けた未追従項目です。これらを解消する場合は、実装、Storybook、契約書の 3 点を同時に更新し、互換措置と目標契約を混在させたまま放置しません。

特に開発時 warning については、構造違反の検知対象、runtime で自動検知しない対象、違反種別ごとの 1 document 1 回という発火単位を揃えて更新します。
