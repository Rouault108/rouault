# Article Header

## 概要

本書は、`ui-article-header` の公開契約、状態モデル、DOM / アクセシビリティ契約、表示契約、イベント契約、および Storybook 契約を定義します。

`ui-article-header` は、記事冒頭における **識別情報**、**時間情報**、**分類情報**、**帰属情報** を提示するヘッダーコンポーネントです。本コンポーネントでは、見出しを主情報、日付と読了時間を主要メタデータ、タグを分類情報、出典とライセンスを補助メタデータとして段階化して扱います。

本コンポーネントの中核契約は次のとおりです。

- 記事タイトルは常に主情報として扱います。
- 代表日付は `updatedDate > published` の優先順位で決定します。
- `created` は可視テキストとしては表示せず、日付の補助文脈としてのみ扱います。
- タグは独立行で表示し、`ui-tag` によるリンクとして扱います。
- 出典は安全な URL のみを表示し、ライセンスは補助文字列として表示します。

配色、モーション、高コントラスト対応は、コンポーネント固有のモード分岐ではなく、トークン契約およびメディアクエリにより成立させます。

## 適用範囲

本書は、`ui-article-header` の次の事項を対象とします。

- 公開契約を対象とします。
- 状態モデルを対象とします。
- DOM / アクセシビリティ契約を対象とします。
- 表示契約を対象とします。
- イベント契約を対象とします。
- Storybook 契約を対象とします。
- 関連契約を対象とします。
- 契約が不明瞭な点を対象とします。
- 新規で追加を検討する価値がある機能を対象とします。
- 現行実装で未対応の事項を対象とします。

本書は、次の事項を対象外とします。

- ルーティング実装は対象外とします。
- タグ一覧ページの存在保証は対象外とします。
- CMS ごとの入力差分吸収は対象外とします。
- 著者情報、パンくず、目次、ページネーション等との上位統合は対象外とします。
- テーマ切替ロジックそのものは対象外とします。

これらは上位レイヤまたは別契約の責務です。

## 1. 公開契約

本章では、`ui-article-header` が受理する入力、公開面の責務、および属性反映規則を定義します。

### 1.1 入力面

`heading` は必須入力です。`published`、`created`、`updatedDate`、`tags`、`tagsJson`、`readingTime`、`status`、`source`、`license` は任意入力です。

`updatedDate` は property 名です。対応する HTML 属性名は `updated` です。これは LitElement のライフサイクルメソッド `updated()` との衝突を回避するためです。

`tags` は正規入力です。`tagsJson` は補助入力です。実装は `tags` が空でない場合に `tags` を優先し、`tags` が空である場合に限り `tagsJson` からタグ配列を復元します。

| 名前       | 種別            | 必須  | 内容 | 契約        |
| ------- | ------- | --- | --------- | -------- |
| `heading`| property / attribute   | はい  | 記事タイトル  | 公開契約上は必須です。実装上は空文字既定値を持ちますが、空文字運用は行いません。 |
| `published`   | property / attribute     | いいえ | 公開日   | 代表日付の候補です。                                          |
| `created`     | property / attribute                  | いいえ | 作成日            | 可視表示には用いず、日付の補助文脈にのみ用います。                           |
| `updatedDate` | property                              | いいえ | 更新日            | HTML 属性名は `updated` です。代表日付の最優先候補です。                |
| `tags`        | property                              | いいえ | タグ配列           | 正規入力です。空白除去と空要素除外のみを行います。                           |
| `tagsJson`    | property / attribute (`tags-json`)    | いいえ | タグ配列の JSON 文字列 | 補助入力です。`tags` が空である場合にのみ採用します。                      |
| `readingTime` | property / attribute (`reading-time`) | いいえ | 読了時間（分）        | 四捨五入後に 1 以上の整数値のみ表示します。                             |
| `status`      | property / attribute                  | いいえ | 記事状態           | `draft` / `archived` / `wip` / `deprecated` のみ有効です。 |
| `source`      | property / attribute                  | いいえ | 出典 URL         | `http:` / `https:` のみ表示対象です。                        |
| `license`     | property / attribute                  | いいえ | ライセンス表示名       | 妥当性検証は行わず、そのまま表示します。                                |

### 1.2 受理値と非受理値

- `heading` が空文字または空白のみ文字列である場合は、契約上の正常入力とはみなしません。
- `published`、`created`、`updatedDate` は `YYYY-MM-DD` 形式を第一想定とします。
- 先頭の ISO 日付部分を抽出できる場合は、その日付部分を表示します。
- 先頭の ISO 日付部分を抽出できない場合は、入力文字列をそのまま表示します。
- `readingTime` が `null`、`NaN`、または四捨五入後に 0 以下となる場合は、無効値として扱います。
- `status` が未知値である場合は、非表示とします。
- `source` が `http:` / `https:` 以外である場合は、無効値として扱います。
- `tagsJson` が JSON 配列であり、かつ各要素が文字列である場合は、採用します。

### 1.3 責務境界

本コンポーネントは次を責務に含みます。

- 見出しを表示します。
- 代表日付を決定します。
- 読了時間を正規化して表示します。
- ステータスを表示します。
- タグを正規化します。
- タグ遷移先 URL を派生します。
- 出典 URL を安全化します。
- ライセンス文字列を表示します。
- 必要なアクセシビリティ属性を付与します。
- `tag-click` イベントを発火します。

本コンポーネントは次を責務に含みません。

- タグ一覧ページの実在を保証しません。
- 出典先の妥当性を保証しません。
- ライセンス文字列の意味を検証しません。
- URL ルーティングを制御しません。
- 記事全体レイアウトを統括しません。

### 1.4 属性反映契約

公開入力のうち、attribute 経路と property 経路の対応は固定します。

| 入力名           | HTML 属性名       | property      | 契約                                   |
| ------------- | -------------- | ------------- | ------------------------------------ |
| `heading`     | `heading`      | `heading`     | attribute / property の双方を受理します。      |
| `published`   | `published`    | `published`   | attribute / property の双方を受理します。      |
| `created`     | `created`      | `created`     | attribute / property の双方を受理します。      |
| `updatedDate` | `updated`      | `updatedDate` | HTML 属性名は `updated` に固定します。          |
| `readingTime` | `reading-time` | `readingTime` | number 変換後に評価します。                    |
| `status`      | `status`       | `status`      | attribute / property の双方を受理します。      |
| `source`      | `source`       | `source`      | attribute / property の双方を受理します。      |
| `license`     | `license`      | `license`     | attribute / property の双方を受理します。      |
| `tags`        | なし             | `tags`        | property 専用の正規入力です。                  |
| `tagsJson`    | `tags-json`    | `tagsJson`    | property / attribute の双方を受理する補助入力です。 |

`tags` と `tagsJson` は同等入力ではありません。`tags` は正規入力です。`tagsJson` は補助入力です。

## 2. 状態モデル

本章では、入力から表示状態へ変換する規則、および表示有無を決定する条件を定義します。

### 2.1 代表日付

代表日付は `updatedDate > published` の優先順位で決定します。

1. `updatedDate` が空でない場合は、`updatedDate` を採用します。
2. `updatedDate` が空であり、`published` が空でない場合は、`published` を採用します。
3. 両方が空である場合は、日付項目を表示しません。

採用された日付のラベルは次のとおりです。

| 条件                    | 表示ラベル   |
| --------------------- | ------- |
| `updatedDate` を採用した場合 | `最終更新日` |
| `published` を採用した場合   | `公開日`   |

`created` は独立した可視項目ではありません。`created` が存在する場合は、`time` 要素の `aria-label` に `作成日: ...` を補助文脈として付加します。

### 2.2 日付表示文字列

日付表示は `formatArticleDate()` により整形します。整形規則は次のとおりです。

- 前後空白は除去します。
- 先頭に `YYYY-MM-DD` が存在する場合は、その日付部分を表示値として採用します。
- 先頭に `YYYY-MM-DD` が存在しない場合は、正規化後の文字列をそのまま表示します。

したがって、本コンポーネントは **厳密な日付妥当性検証** を責務に含みません。

### 2.3 読了時間

`readingTime` は四捨五入した整数分として表示します。表示条件は次のとおりです。

- `readingTime === null` である場合は、非表示とします。
- `Number.isNaN(readingTime)` である場合は、非表示とします。
- `Math.round(readingTime) <= 0` である場合は、非表示とします。
- それ以外の場合は、`読了目安 N分` として表示します。

### 2.4 タグ

タグは描画前に正規化します。正規化規則は次のとおりです。

- `tags` が 1 件以上存在する場合は、`tags` を採用します。
- `tags` が空である場合は、`tagsJson` を JSON 配列として解釈し、文字列要素のみを採用します。
- 各タグ文字列の前後空白は除去します。
- 空文字列は除外します。
- 入力順は保持します。
- 重複は保持します。

正規化後の配列が空である場合は、タグ行を表示しません。

### 2.5 出典とライセンス

`source` は安全化した上でのみ表示します。

- 前後空白は除去します。
- `new URL()` により解釈可能である場合は、評価対象とします。
- `protocol` が `http:` または `https:` である場合は、表示します。
- `protocol` が `http:` または `https:` 以外である場合は、存在しないものとして扱います。

`license` は前処理を行いません。可視表示では入力値をそのまま用います。`source` と `license` の両方が空である場合は、補助メタデータ行を表示しません。

### 2.6 ステータス

`status` は列挙値として扱います。対応関係は次のとおりです。

| `status` 値   | 表示ラベル | アイコン                    | トーンクラス              |
| ------------ | ----- | ----------------------- | ------------------- |
| `draft`      | 下書き   | `lucide:file-dashed`    | `status-draft`      |
| `archived`   | アーカイブ | `lucide:archive`        | `status-archived`   |
| `wip`        | 作業中   | `lucide:construction`   | `status-wip`        |
| `deprecated` | 非推奨   | `lucide:alert-triangle` | `status-deprecated` |

未知の値は描画しません。

### 2.7 最小状態

最小状態は `heading` のみが与えられた状態です。この場合は、見出しのみを表示し、主要メタデータ行、タグ行、補助メタデータ行、ステータスバッジは表示しません。

### 2.8 無効値・空白値の正規化

公開入力に対する空白値と無効値の扱いは次のとおりです。

- `heading` は契約上の必須入力として扱います。
- `heading` が空文字または空白のみ文字列である場合は、正常入力として扱いません。
- `published`、`created`、`updatedDate` は前後空白を除去して評価します。
- `time[datetime]` に設定する値は、採用された入力値そのものを使用します。
- `datetime` 属性値は ISO 妥当値へ再正規化しません。
- `source` は前後空白を除去した上で URL 解釈します。
- `license` は trim せず、そのまま表示します。
- `license` に空白のみ文字列を与えた場合は、可視文字列として残します。
- `status` は列挙値一致である場合にのみ表示します。
- `status` の前後空白は吸収しません。
- `tags` および `tagsJson` 由来の各タグ文字列は trim した上で評価します。
- `tags` および `tagsJson` 由来の各タグ文字列が空文字列である場合は、除外します。

この契約は、可視表示の正規化と入力値保存を切り分けるためのものです。入力値の意味妥当性までは保証しません。

## 3. DOM / アクセシビリティ契約

本章では、`ui-article-header` が生成する DOM 構造、およびアクセシビリティ上の成立条件と非責務を定義します。

### 3.1 構造

ルート要素は `<header>` です。記事タイトルは `<h1>` です。主要メタデータ群および補助メタデータ群は `<ul>` と `<li>` により表現します。採用された日付は `<time datetime="..."></time>` で表現します。タグは `ui-tag` により表現します。出典は `<a>` により表現します。

```text
<header class="article-header">
  [div.status.status-badge]
  <h1 class="heading">...</h1>
  [ul.metadata-list.metadata-list--primary]
  [div.tags-row > span.tag-links > ui-tag*]
  [ul.metadata-list.metadata-list--secondary]
</header>
```

### 3.2 日付のアクセシビリティ契約

日付項目の `aria-label` は、採用された日付の意味文脈を含みます。

- `updatedDate` を採用した場合は `最終更新日: ...` を含みます。
- `published` を採用した場合は `公開日: ...` を含みます。
- `created` が存在する場合は `、作成日: ...` を後続付加します。

### 3.3 出典リンクのアクセシビリティ契約

出典リンクは次の属性を持ちます。

- `target="_blank"` を付与します。
- `rel="noopener noreferrer"` を付与します。
- `aria-label="出典（外部リンク）"` を付与します。

### 3.4 タグのアクセシビリティ契約

各タグは `ui-tag` として描画し、`href="/tags/${encodeURIComponent(tag)}"` を持ちます。`aria-label` は `タグ: {tag}` です。

### 3.5 非責務

本コンポーネントは、見出し自体をアンカーリンク化しません。タグ行に対して追加のリストセマンティクスも付与しません。現行実装の構造は `div.tags-row > span.tag-links` です。

### 3.6 見出しレベルおよび利用文脈

本コンポーネントは記事ページの主題見出しを表すため、見出し要素として常に `<h1>` を描画します。したがって、利用文脈は次に限定します。

- 記事詳細ページで使用します。
- 単一ノートページで使用します。
- 文書本文の主題ヘッダーとして使用します。

次の文脈では本コンポーネントをそのまま使用しません。

- 一覧カード内の見出しには使用しません。
- ダイアログやサイドバー内の部分見出しには使用しません。
- 1 ページ内に複数回出現する主題ヘッダーには使用しません。

再利用が必要である場合は、見出しレベルを切り替える派生コンポーネントまたは別コンポーネントとして分離します。

### 3.7 装飾アイコンとランドマーク責務

本コンポーネント内のアイコンは装飾専用です。意味情報はテキストにより担保し、アイコン単体に可読名を持たせません。

ルートの `<header>` は文書上のセクション見出しを包含しますが、固有の landmark 名は持ちません。ページ全体のランドマーク構成および補助ラベル付与は親レイヤの責務です。

## 4. 表示契約

本章では、情報順序、レイアウト、タイポグラフィ、トークン参照、およびリンク表示の規則を定義します。

### 4.1 情報順序

正規の情報順序は次のとおりです。

1. ステータスバッジ
2. 記事タイトル
3. 主要メタデータ行
4. タグ行
5. 補助メタデータ行

この順序は、**信頼性シグナル → 主情報 → 時間情報 → 分類情報 → 帰属情報** という読み順を固定するためのものです。

### 4.2 レイアウト契約

- `:host` は `display: block` とします。
- 最大幅は `var(--width-reading, 72ch)` とします。
- ルート下端には本文との境界として `border-block-end` を設けます。
- 主要メタデータ行と補助メタデータ行では `flex-wrap: wrap` を許容します。
- メタデータ項目間の区切り文字には `・` を使用します。
- タグ行は独立段として扱います。
- タグ行では `inline-flex` + `wrap` により複数タグを並べます。

### 4.3 タイポグラフィ契約

- 見出しには `clamp()` による流体サイズを適用します。
- 見出しの行高には `var(--line-height-tight)` を使用します。
- 見出しの字間には `var(--tracking-tight)` を使用します。
- `font-feature-settings: 'palt'` を適用します。
- `word-break: auto-phrase` を適用します。
- `overflow-wrap: break-word` を適用します。

### 4.4 セマンティックトークン契約

主な参照トークンは次のとおりです。

| 用途                | トークン                                   |
| ----------------- | -------------------------------------- |
| 見出し色              | `--fg-default`                         |
| 主要メタデータ色          | `--fg-muted`                           |
| 補助メタデータ色 / セパレータ色 | `--fg-subtle`                          |
| 作業中ステータス          | `--fg-warning`                         |
| 非推奨ステータス          | `--fg-danger`                          |
| 読書幅               | `--width-reading`                      |
| 余白                | `--space-*`                            |
| フォントサイズ           | `--text-*`                             |
| 行高                | `--line-height-tight`                  |
| トラッキング            | `--tracking-tight`                     |
| フォーカスリング色         | `--focus-ring-color`                   |
| フォーカスリング幅         | `--focus-ring-width`                   |
| フォーカスリングオフセット     | `--focus-ring-offset`                  |
| 遷移時間              | `--duration-fast`, `--duration-normal` |
| イージング             | `--ease-out`                           |

### 4.5 リンク表示契約

出典リンクのクラスは `.link-text.source-link` です。リンクは既定状態で下線を持ちます。`hover` および `focus-visible` では、文字色とフォーカスリングにより可視性を補強します。

## 5. イベント契約

本章では、`tag-click` の発火条件、通知内容、および親側による介入可能性を定義します。

### 5.1 `tag-click` 発火条件

`tag-click` はタグリンクに対する click activation を契機として発火します。発火条件は次のとおりです。

- タグ要素が描画されている場合にのみ発火します。
- クリック対象が当該タグリンクである場合にのみ発火します。
- 1 回の click activation に対して 1 回のみ発火します。

本イベントは hover、focus、pointerenter 等では発火しません。

### 5.2 `tag-click` イベント契約

タグクリック時には `tag-click` イベントを発火します。これは単なる通知ではなく、**ネイティブリンク遷移へ介入可能なキャンセル可能イベント**です。

| 項目            | 契約                                 |
| ------------- | ---------------------------------- |
| イベント名         | `tag-click`                        |
| `detail.tag`  | クリックされたタグ文字列                       |
| `detail.href` | `/tags/${encodeURIComponent(tag)}` |
| `bubbles`     | `true`                             |
| `composed`    | `true`                             |
| `cancelable`  | `true`                             |

親側が `preventDefault()` を呼び出した場合は、内部の click handler が元のクリックイベントに対して `event.preventDefault()` を実行し、ネイティブ遷移を中止します。

`detail.href` の生成規則は公開契約に含みます。タグ遷移先は `/tags/${encodeURIComponent(tag)}` を標準形とし、親側で独自ルーティングへ置き換える場合でも、この値を基準情報として受け取ります。

## 6. 境界条件

本章では、入力が欠落または無効である場合の最終表示結果を定義します。

- `heading` のみが与えられた場合は、見出しのみを表示します。
- 正規化後のタグ配列が空である場合は、タグ行を描画しません。
- `readingTime` が無効値である場合は、読了時間項目を描画しません。
- `source` が安全でない場合は、描画しません。
- `source` と `license` の双方が空である場合は、補助メタデータ行を描画しません。
- `status` が未知値である場合は、描画しません。

## 7. Storybook 契約

本章では、各 Story が固定する確認観点と、変更時に維持すべき契約を定義します。

各 Story は単なる表示例ではなく、将来変更時の契約確認点です。

| Story                         | 固定する契約                                                    |
| ----------------------------- | --------------------------------------------------------- |

## 9. 関連契約

## 10. 契約が不明瞭な点

本章では、現行の公開契約において意味論または責務境界がまだ十分に固定されていない事項を列挙し、長期的な視点でどのように明確化すべきかを整理します。

### 10.1 `heading` の必須性

現行文書では `heading` を必須入力として扱っていますが、実装上は空文字既定値を持ち、空の `<h1>` も構成可能です。このため、公開契約上の必須性と実装上の成立条件が一致していません。

長期的には、`heading` は **厳密必須** として固定するのが適切です。空文字および空白のみ文字列は invalid input と定義し、正常系には含めません。`ui-article-header` は記事主題ヘッダーであり、見出しなし状態を正常契約に含めない方が設計が明快です。

### 10.2 日付モデルの意味論

`created`、`published`、`updatedDate` の三つの日付は存在しますが、それぞれが何を意味するかはまだ十分に固定されていません。特に、`created` を内部制作日とみなすのか、初版日とみなすのかが曖昧です。

長期的には、日付モデルを次のように分離して定義するのが適切です。

- `created` は内部制作メタデータです。
- `published` は公開版の初回公開日です。
- `updatedDate` は公開版の最終的な substantive update です。
- 公開 UI の代表日付は `updatedDate > published` の優先順位で決定します。
- `created` 単独では公開 UI の日付項目を成立させません。

これにより、内部制作時系列と公開時系列を明確に分離できます。

### 10.3 日付入力値と `time[datetime]`

現行契約では日付入力に緩い文字列受理を許しつつ、`time[datetime]` には採用された入力値そのものを用います。このため、可視表示は成立しても HTML セマンティクスが壊れる余地があります。

長期的には、日付入力を ISO 8601 の正規値に限定するのが適切です。`time[datetime]` には常に正規化済み値を用い、正規化不能値は非表示または開発時警告の対象とします。表示のための緩いパースは UI コンポーネントではなく adapter 層へ分離します。

### 10.4 `tags` と `tagsJson` の二重入力

現行契約は `tags` を正規入力、`tagsJson` を補助入力として扱いますが、公開 API としては二重入力です。UI コンポーネントの入力面としては責務がやや広く、長期的な保守では曖昧さの原因になります。

長期的には、公開契約上の正規入力は `tags` のみに固定するのが適切です。`tagsJson` は Markdown bridge または adapter 層へ退避し、`ui-article-header` 自体は純粋 UI コンポーネントとして保ちます。

### 10.5 タグの識別子と表示名

現行契約ではタグを単なる文字列として扱い、表示文字列から URL を直接派生します。このため、表示名変更、大小文字差、末尾空白差、同名異義などの扱いが固定されていません。

長期的には、タグは少なくとも論理的に `key` と `label` を分離して扱うのが適切です。

- `key` は安定識別子です。
- `label` は表示名です。
- URL は `key` から派生します。
- 重複判定は `key` 単位で行います。

これにより、表示文字列と識別子を切り分けられます。

### 10.6 タグ URL 生成責務

現行契約では `/tags/${encodeURIComponent(tag)}` を `ui-article-header` 自体が生成します。これは UI コンポーネントがアプリケーションの URL 規則を直接抱える設計です。

長期的には、タグ URL 規則は親レイヤまたはルーティング層の責務とするのが適切です。`ui-article-header` はタグリンクを表示する責務に限定し、URL は `href` を含む入力モデルまたは外部ビルダで供給します。

### 10.7 `tag-click` の意味論

現行契約では `tag-click` を click activation に結び付けていますが、長期的に必要なのは click そのものではなく tag activation の意味論です。キーボード活性化をどのように扱うかも明示されていません。

長期的には、`tag-click` を `tag-activate` 相当の意味論へ整理するのが適切です。

- 発火契機は pointer と keyboard を含む activation とします。
- `preventDefault()` は既定ナビゲーション抑止を意味します。
- `detail` には識別子、表示名、遷移先を含めます。

これにより、入力デバイス非依存のイベント契約になります。

### 10.8 `source` の情報モデル

現行契約の `source` は URL 文字列 1 件のみです。表示ラベルは常に「出典」であり、表示名と URL は分離されていません。複数出典や出典名の表示にも対応する契約ではありません。

長期的には、`source` は単なる文字列ではなく、表示ラベルと URL を分離した帰属情報モデルとして定義するのが適切です。必要に応じて複数件も許容し、単一 URL 文字列に意味論を詰め込みすぎない方が保守しやすくなります。

### 10.9 `license` の意味論

現行契約の `license` は自由文字列として表示するだけであり、SPDX 互換識別子なのか、表示ラベルなのか、リンク可能なライセンス情報なのかが固定されていません。

長期的には、次のどちらかに明確化するのが適切です。

- `license` を完全に表示専用の自由文字列として固定します。
- `licenseId`、`licenseLabel`、`licenseHref` を持つ構造化モデルへ移行します。

設計のきれいさを優先するなら、後者の構造化モデルが望ましいです。

### 10.10 `status` の軸

`draft`、`wip`、`archived`、`deprecated` は一つの `status` に収まっていますが、制作状態と読者向け注意状態が混在しています。何の軸を表す状態なのかがまだ十分に固定されていません。

長期的には、次のいずれかに固定するのが適切です。

- `status` を単一軸の列挙値として厳密に定義します。
- `editorialState` と `readerAdvisory` に分離します。

設計の明快さでは、後者の分離が優位です。

### 10.11 タグ群のセマンティクス

現行契約ではタグ群を独立段として表示しますが、セマンティクスは `div` と `span` に留まっています。これはメタデータ列なのか、ナビゲーションなのかがまだ固定されていません。

長期的には、次のどちらかに固定するのが適切です。

- タグ群を周辺ナビゲーションとして扱い、`nav` と list semantics を採用します。
- タグ群を純粋なメタデータとして扱い、metadata list の一部へ統合します。

Rouault の文脈では、タグは周辺ナビゲーションとして扱う方が自然です。

### 10.12 閉じた primitive としての境界

現行の `ui-article-header` は slot や任意拡張点を持たず、固定順の閉じた構造です。しかし、今後 subtitle、author、breadcrumb 等を含めるべきかどうかが契約として明示されていません。

長期的には、`ui-article-header` は **閉じた primitive** として固定するのが適切です。新しい情報群を追加したくなった場合は props を増やさず、上位の compound component または別コンポーネントへ分離します。これにより、責務境界を小さく保てます。

### 10.13 環境別契約の強度

Storybook では coarse pointer 向け契約を期待していますが、現行実装には対応がありません。このため、touch discoverability を MUST とするのか、SHOULD とするのかがまだ固定されていません。

長期的には、環境別契約の強度を分けて定義するのが適切です。

- `prefers-reduced-motion` は MUST とします。
- `forced-colors` は MUST とします。
- coarse pointer discoverability は SHOULD とします。

このように強度を明示すると、Storybook と実装の差分を評価しやすくなります。

### 10.14 公開トークンと内部トークンの境界

現行契約はセマンティックトークンを列挙していますが、どのトークンが公開契約で、どれが内部実装都合なのかはまだ十分に固定されていません。誤記修正だけではなく、公開面の境界を明示する必要があります。

長期的には、トークンを次の二層に分離して定義するのが適切です。

- public semantic tokens
- internal implementation tokens

文書契約には public semantic tokens のみを記載し、内部トークンは実装詳細として扱います。

## 11. 新規で追加を検討する価値がある機能

本章では、`ui-article-header` の primitive 性を維持したまま、長期的な設計のきれいさと保守性を高める観点から、追加を検討する価値がある機能を整理します。

### 11.1 最優先で検討する価値がある機能

#### 11.1.1 構造化された帰属情報

現行契約では `source` は単一 URL 文字列、`license` は単一の自由文字列です。この形は単純ですが、複数出典、表示ラベル付き出典、ライセンス URL、帰属種別の分離には対応しにくく、将来の拡張で文字列契約が肥大化しやすくなります。

長期的には、出典とライセンスを単純文字列の増築で維持するのではなく、構造化された帰属情報モデルへ移行する価値があります。たとえば、表示ラベル、遷移先、種別、外部リンク扱いの有無を持つ単位を定義し、必要に応じて複数件を保持できるようにします。これにより、現在の `source` と `license` に分散している責務を一つの情報モデルへ統合できます。

#### 11.1.2 タグの構造化入力

現行契約のタグは文字列配列であり、表示文字列から URL を直接派生します。この方式は小規模では簡潔ですが、表示名変更、大小文字差、同名異義、安定 URL の維持といった論点に弱く、UI コンポーネントが識別子と表示名を兼務する状態になります。

長期的には、タグを `key` と `label` を持つ構造化入力へ移行する価値があります。必要であれば `href` も入力側から与え、`ui-article-header` 自体はタグの描画と活性化通知に責務を限定します。これにより、タグの表示面とアプリケーション側の識別・ルーティング責務を切り分けられます。

#### 11.1.3 パーマリンク導線

記事ヘッダーは、利用者が当該ノートを参照、再訪、共有する際の自然な起点です。しかし、現行契約には記事自体の恒久リンクを提示する導線がありません。出典リンクは存在しても、記事自身の参照導線は欠けています。

長期的には、控えめな permalink 導線を追加する価値があります。これは派手な共有ボタン群ではなく、恒久 URL の提示または copy link 操作のような静かな導線が適切です。Rouault の閲覧体験を壊さず、参照性だけを補強できます。

### 11.2 本コンポーネントに追加しない方がよい機能

次の機能は `ui-article-header` の primitive 性を崩しやすく、長期的には別コンポーネントまたは上位レイヤの責務とする方が適切です。

- 任意 slot による拡張
- SNS シェアボタン群
- Hero image
- Breadcrumb
- TOC
- 検索導線

これらを `ui-article-header` 自体へ取り込むと、記事主題ヘッダーとしての責務境界が曖昧になります。

## 12. 現行実装で未対応の事項

本章では、文書契約に対して現行実装がまだ満たしていない事項を列挙します。

### 12.1 タッチ環境向けメディアクエリ

`AccessibilityMediaContracts` Story は `@media (hover: none) and (pointer: coarse)` の存在を期待していますが、現行の `article-header.ts` には当該メディアクエリが存在しません。したがって、**Storybook 側の期待契約と実装契約は一致していません**。

未対応なのはメディアクエリ文字面だけではありません。現行実装には、タッチ環境で hover に依存しない discoverability を補強する専用スタイルも存在しません。したがって、touch 向け契約としては **メディアクエリ定義** と **その内部での discoverability 調整** の両方が未対応です。

### 12.2 トークン名の実装修正

主要メタデータのアイコン色に対する CSS に `var(--fg-sabtle, ...)` という綴りが存在します。これは `--fg-subtle` の誤記です。文書契約上の正規値は `--fg-subtle` です。現行実装側では修正対象です。

### 12.3 `tagsJson` 補助入力の確認面

現行実装は `tags-json` 属性および `tagsJson` property を補助入力として受理しますが、Storybook の `argTypes` には `tagsJson` が存在せず、専用 Story もありません。そのため、**実装は存在するが、公開入力面としての確認導線と検証面が不足しています**。

現段階で `tagsJson` を公開契約に残すのであれば、少なくとも次のいずれかが必要です。

- `argTypes` に `tagsJson` を追加します。
- `tags` が空であるときに `tagsJson` へフォールバックする Story を追加します。

逆に、長期方針として `tagsJson` を adapter 層へ退避するのであれば、公開契約から外し、未対応項目ではなく削除候補として扱うのが適切です.
