# Ol

## 概要

本書は、`ui-ol` の長期保守向け公開契約を定義します。

`ui-ol` は、**1 つの順序付きリストを、読書文脈に適した静かな番号表現として提示するコンポーネント**です。責務は、**ordered list の意味を保ったまま、番号の視覚表現、本文開始位置の整列、番号属性との整合を安定して提供すること**に限定します。

本書では、現行実装の都合よりも、設計の一貫性、責務分離、保守性、将来拡張時の破壊的変更回避を優先します。したがって、現行実装が持つ救済挙動、ドキュメント全体へのスタイル注入、内部属性による同期は、必要に応じて **互換層** または **未整理事項** として切り分けます。

---

## 目的

`ui-ol` の目的は、次の 4 点に限定します。

1. **番号の意味を native ordered list semantics と一致させること**
2. **番号桁数や番号進行規則が変化しても、同一 list 内で本文開始位置を安定させること**
3. **本文を主、マーカーを従とする視覚階層を維持すること**
4. **ordered list の視覚整形契約を、prose policy や他種 list の契約から分離すること**

本書において「読書文脈に適する」「静かである」などの表現は、設計意図を説明する補助語であり、単独では合否判定基準を意味しません。合否判定は、公開契約、Visual Contract、境界条件、Storybook 契約に定義した観測可能条件によって行います。

---

## 適用範囲

本書は、次を対象とします。

- `ui-ol` の公開契約
- 入力モデル
- 状態モデル
- DOM / Accessibility
- Visual Contract
- 環境別の振る舞い
- Storybook 契約
- 現行実装との差分と未整合

本書は、次を対象外とします。

- Markdown から ordered list を生成する上位パーサ
- `.prose` 全体に対する既定 list policy
- unordered list の表現契約
- checklist、link list、accordion list など別種 list の仕様
- 記事全体の見出し・TOC・sidebar 設計
- 印刷専用の最適化および独立した print 契約
- DOM 正規化や構造救済を前提とした authoring 体験の設計
- マーカー書式の追加公開契約（例: `decimal-dot`、`decimal-paren`、`decimal-plain`）
- nested ordered list に対する深度別の弱い表現差分
- `steps` 以外の追加 `variant` 定義

本書は、現時点の `ui-ol` を **単一 ordered list の視覚整形契約** として固定することを目的とします。したがって、screen 向け ordered list 契約を強くする事項は本文へ含めますが、新しい公開表現体系、用途別バリアント、print 専用契約は本書の対象に含めません。

## 設計原則

### 原則 1. `ui-ol` は 1 ホスト = 1 ordered list です

`ui-ol` は、**単一の root **``** を包むためのコンポーネント**です。複数 root `<ol>` を持つコンテナではありません。

### 原則 2. 番号の真実源はネイティブ HTML です

番号の意味論は `ol`、`li`、`start`、`reversed`、`value` によって決定します。`ui-ol` は独自の番号モデルを導入しません。

### 原則 3. ordered list 以外を巻き込みません

`ui-ol` が責務として扱うのは ordered list だけです。unordered list、definition list、任意の prose block を同じ契約へ含めません。

### 原則 4. コンポーネント契約と prose policy を分離します

`ui-ol` の契約は `ui-ol` 自体の公開面に限定します。`.prose ol` などのドキュメント全体スタイルは、本来別契約です。

### 原則 5. 内部同期の表現は公開 API にしません

内部 `data-*` 属性、内部 CSS 変数、内部スタイル注入方式は、公開 API として固定しません。

## 公開契約

### 規範語

本書では、規範語を次の意味で用います。

- **MUST**: 実装が満たさなければならない必須要件
- **MUST NOT**: 実装または利用者が依存してはならない禁止要件
- **SHOULD**: 強く推奨される要件。ただし、明示的な理由がある場合に限り逸脱できます
- **MAY**: 許容される任意要件
- **非保証**: 実装がたまたまそう振る舞っても、将来を含めて保証しない領域
- **未定義**: 入力または状態に対して外部観測結果を固定しない領域
- **将来検討**: 現時点では正式契約に含めず、将来の独立検討対象とする領域

### コンポーネントの役割

`ui-ol` は、root ordered list の **視覚整形レイヤ** です。内部描画は `<slot>` に留め、ordered list の意味論はライト DOM 側の native `<ol>` / `<li>` が担います。

`ui-ol` の責務は、次に限定します。

- native ordered list semantics と整合する視覚マーカーを与えること
- 同一 list 内で本文開始位置を安定させること
- `start`、`reversed`、`li[value]` に起因する番号進行と視覚表示を整合させること
- `variant` が許可する範囲に限って視覚差分を与えること

`ui-ol` は、次を責務に含めません。

- 文書全体の list styling
- DOM 構造の自由な正規化
- unordered list、checklist、accordion list など別種 list の整形
- authoring 用の救済入力を常設仕様として保証すること
- ソート、選択、展開、ドラッグなどの状態管理

### 公開入力

| 名前           | 種別             | 必須   | 内容               | 契約                                                                 |
| -------------- | ---------------- | ------ | ------------------ | -------------------------------------------------------------------- |
| root `<ol>`    | child node       | はい   | 順序付きリスト本体 | 正規入力ではホスト直下に root `<ol>` を 1 つだけ持ちます             |
| `variant`      | host attribute   | いいえ | 表現バリアント     | 現時点の正式値は `steps` のみです。未指定時が既定状態です            |
| `ol[start]`    | native attribute | いいえ | 開始番号           | native semantics と視覚マーカーを整合させます                        |
| `ol[reversed]` | native attribute | いいえ | 降順番号           | native semantics と視覚マーカーを整合させます                        |
| `li[value]`    | native attribute | いいえ | 明示番号           | 当該項目の番号を native semantics に従って再設定し、視覚表示へ反映します |

### 正規入力契約

`ui-ol` の正規入力は、次に固定します。

```text
<ui-ol>
  <ol>
    <li>...</li>
    <li>...</li>
  </ol>
</ui-ol>
```

正規入力における制約は、次のとおりです。

* ホスト直下の root list は `<ol>` 1 個のみでなければなりません（MUST）
* root `<ol>` の正規子は `<li>` のみでなければなりません（MUST）
* nested `<ol>` は `<li>` の子としてのみ許可します（MAY）
* nested `<ul>` は存在してもよいですが、`ui-ol` の公開契約対象外です
* `<ol>` 以外の一般ノードをホスト直下へ置く構成は正規入力ではありません

### 救済入力契約

`<ui-ol><li>...</li></ui-ol>` のような入力は、正規入力に含めません。これは **移行互換または authoring 救済** であり、公開契約の中心ではありません。

実装がこの種の入力を吸収しても構いません（MAY）。ただし、利用者はその挙動に依存してはなりません（MUST NOT）。

### 属性契約

`variant` は **ホスト属性** のみを正規の指定位置とします。host 以外への指定解釈は公開契約に含めません。

`variant` の公開値として正式に意味を持つのは `steps` のみです。列挙外値は **未定義** とします。利用者は列挙外値の見た目や挙動に依存してはなりません（MUST NOT）。

`start` および `value` は、**前後空白を除去した結果が符号付き十進整数として解釈可能な値**を有効入力とします。有効域には 0、負数、3 桁超、4 桁超を含みます。空文字列、空白のみ、整数解釈不能な値は無効です。

有効な `start` / `value` が与えられた場合、実装は native ordered list semantics と整合する視覚マーカーを与えなければなりません（MUST）。

`reversed` は boolean attribute として扱います。属性が存在する場合、番号進行は降順です。

### 非公開内部表現

内部同期のために `data-*` 属性、内部クラス、`--ui-ol-*` 形式の CSS カスタムプロパティ、内部 style 注入を用いても構いません（MAY）。ただし、これらは公開 API ではありません。利用者は依存してはなりません（MUST NOT）。

## 入力モデル

### ルート構造

`ui-ol` は、単一 root ordered list のみを扱います。複数 root `<ol>` を 1 ホストで扱う設計は採りません。

### 項目構造

root `<ol>` の子は `<li>` のみです。`template`、`div`、`p`、テキストノード、コメント、別の block 要素を混在させる構成は契約違反です。

### ネスト構造

nested `<ol>` は `<li>` の子として許可します。これは ordered list の自然な入れ子です。

一方、nested `<ul>` は `ui-ol` の責務ではありません。ordered list 内に unordered list が現れること自体は妨げませんが、その見た目や spacing は `ui-ol` の公開契約に含めません。

### 構造違反時の扱い

構造違反時は、次の保証を行いません。

- 番号の視覚同期
- 本文開始位置の整列
- spacing の一貫性
- アクセシビリティ補強の一貫性

構造違反入力は、契約上 **非保証** とします。実装が best-effort で表示しても構いませんが、利用者は正規入力と同等の安定動作を期待してはなりません（MUST NOT）。

また、長期的な入力純化のため、development 環境では次の構造違反に対して警告または validation を追加しても構いません（MAY）。

- root `<ol>` 不在
- 複数 root `<ol>`
- `ol` 直下の非 `li` 混在
- ホスト以外への `variant` 指定
- ordered / unordered の責務境界を壊す構造

ただし、これらの警告や validation の**存在、文言、発火契機、出力形式**は公開契約に含めません。これは表示仕様ではなく、正規入力への収束を補助する開発支援です。

## 状態モデル

`ui-ol` の公開状態は、**番号進行規則**、**列幅状態**、**表現バリアント** によって決まります。内部同期方式や再計算契機は公開状態に含めません。

### 基本状態

既定状態は、昇順、開始番号 1、既定マーカー表現、既定トークン適用です。

### 開始番号状態

`start` が有効な整数である場合、先頭番号はその値から始まります。0 および負数も有効です。

### 降順状態

`reversed` が存在する場合、番号は降順です。`start` がない場合の開始番号は native ordered list semantics に従います。

### 明示値状態

`li[value]` が有効な整数である場合、その項目の番号はその値に再設定されます。以後の項目の番号進行は native ordered list semantics に従います。

### 列幅状態

マーカー列幅は、その list で表示される最大 marker 長に対して十分な幅を持たなければなりません（MUST）。公開契約の本質は、内部計算式ではなく、**本文開始位置の安定性** にあります。

### バリアント状態

未指定時が既定状態です。`variant="steps"` は、**マーカー側に限った軽い表現差分** を与えます。

`variant="steps"` は、次を変更してはなりません（MUST NOT）。

- 番号意味
- root / nested list の構造意味
- 本文色
- 本文開始位置
- 項目間余白
- ordered list と unordered list の責務境界

### 動的同期

接続後の DOM 追加、DOM 削除、属性変更、`slotchange`、`MutationObserver` による追従は、**現時点では公開状態に含めません**。

実装が再同期を行っても構いません（MAY）。ただし、利用者は次に依存してはなりません（MUST NOT）。

- 追従の有無
- 追従完了までのタイミング
- 監視対象属性の範囲
- 再計算回数
- 再同期方式

公開契約として保証するのは、**正規入力が安定状態で与えられたとき、その状態に対して描画結果が整合すること** のみです。

## DOM / Accessibility

### DOM 境界

`ui-ol` の Shadow DOM は表示境界です。ordered list の意味論は、ライト DOM 側の native `<ol>` / `<li>` が担います。

ホスト要素はレイアウト境界として存在しますが、list semantics の所有者ではありません。したがって、`ui-ol` 自身が list semantics を新設することはありません。

### アクセシビリティ方針

本コンポーネントの真実源は native ordered list semantics です。したがって、`ol` / `li` がすでに提供している意味論を優先し、ARIA による再定義は互換補助に留めます。

### 契約

- ordered list の意味は native `ol` / `li` に依存します
- `ui-ol` は、意味論と整合する視覚表現を与えなければなりません（MUST）
- 既存の `role`、`aria-*`、アクセシブルネーム計算を勝手に破壊してはなりません（MUST NOT）
- ホスト要素を list owner として扱う `role="list"` の再定義は、公開契約の中心に置きません
- `li` 内の interactive descendant の意味論と操作性を阻害してはなりません（MUST NOT）

### 視覚マーカーと読み上げの関係

視覚マーカーを native marker とは別要素で補助する場合、その補助要素は **読み上げ上の重複を生まない装飾要素** として扱わなければなりません（MUST）。

したがって、装飾マーカーを別要素で表現する場合は、少なくとも次を満たす必要があります。

- 補助マーカーはアクセシブルネーム計算へ混入しないこと
- native ordered list semantics による番号読み上げと二重化しないこと
- list item の本文テキストを分断しないこと

### wrapper と補助要素

本文ラッパや marker ラッパを導入しても構いません（MAY）。ただし、それらは意味論上の所有者ではなく、表示補助に留まらなければなりません。

### インタラクティブ要素共存

`li` 内に `a`、`button`、`input`、`details` などの interactive 要素を含めても構いません。`ui-ol` の責務は ordered list の視覚整列であり、各 interactive 要素固有のキーボード操作、フォーカス、名前付け契約は各要素側が担います。

補助 hit area を導入する場合でも、list semantics、名前付け、フォーカス順序を変えてはなりません（MUST NOT）。

## Visual Contract

### 設計意図

本節の目的は、本文を主、マーカーを従とする読書向け ordered list を定義することです。ただし、ここでの合否判定は観測可能条件によって行い、印象語のみに依存しません。

### 情報順位

- 本文はマーカーより高い視覚優先度を持たなければなりません（MUST）
- `variant="steps"` を含め、強調差分はマーカー側に限定しなければなりません（MUST）
- 本文色は既定状態と `steps` の間で不変でなければなりません（MUST）

### レイアウト契約

各 list item は、**マーカー列** と **本文列** からなる 2 列構成として観測されなければなりません。

同一 root `<ol>` 内では、各項目の本文開始位置は揃っていなければなりません。合格条件は次のとおりです。

- 同一 list 内の各項目について、本文コンテンツ開始要素の左端 `x` 座標差が **1 CSS px 以下** であること
- `9 → 10`、`99 → 100`、`-1 → 0`、`0 → 1`、`999 → 1000` の境界をまたいでも上記条件を満たすこと
- `li[value]` による途中ジャンプがあっても上記条件を満たすこと

項目間余白は、同一 list 内で一定でなければなりません。合格条件は、連続する兄弟 `li` 間の block direction gap の差が **1 CSS px 以下** であることです。

nested ordered list は、親項目本文の後に接続してよいですが、親 list と子 list の本文開始位置は**それぞれの list 単位で独立に整列**していなければなりません。

### マーカー契約

- マーカーは、native ordered list semantics と整合する番号表現を視覚提示しなければなりません（MUST）
- マーカー列の右端は、同一 list 内で **1 CSS px 以下** の誤差で揃っていなければなりません（MUST）
- 数字は `tabular-nums` 相当の整列性を持つ書体設定を用いるべきです（SHOULD）
- 既定状態のマーカー色は本文色より弱い視覚重量でなければなりません（MUST）
- `variant="steps"` ではマーカー色のみ差分を持ってよく、本文色は変えてはなりません（MUST NOT）

### 列幅契約

公開契約は、列幅計算式ではなく結果にあります。したがって、実装が固定閾値分岐、最大 marker 長推定、実測ベースのいずれを採用しても構いません（MAY）。

ただし、次は必須です。

- 同一 list 内で表示される最大 marker 長に対して、本文開始位置が崩れないこと
- `start`、`reversed`、`li[value]` による番号進行変化を含めても整列が維持されること
- 0、負数、3 桁超、4 桁超、および途中ジャンプを含めても整列が維持されること
- `variant="steps"` の有無で本文列の位置が変わらないこと

ここで固定するのは、**内部の列幅算出方式**ではなく、**外部から観測可能な本文開始位置の安定性**です。したがって、実装詳細として `3ch` / `4ch` のような局所分岐を使っても構いませんが、それ自体は契約ではありません。

### トークン契約

`ui-ol` は、少なくとも次の概念トークンに依存します。

| 用途                 | トークン              |
| -------------------- | --------------------- |
| 項目間余白           | `--space-2`           |
| マーカー色           | `--fg-muted`          |
| 手順マーカー色       | `--primary`           |
| 数字書体             | `--font-mono`         |
| 数字太さ             | `--font-medium`       |
| 補助 hit area        | `--control-min-touch` |
| 小型操作要素の最低高 | `--control-height-sm` |

ここで固定するのは個別値ではなく、**spacing / color / type / support token によって結果が供給されること**です。

## 環境別の振る舞い

### Forced Colors

forced colors 環境では、マーカー色はシステム色に追従します。色による意味依存は避けます。

### Dark Mode

ダークモードでは、セマンティックトークン差し替えによって視覚差を吸収します。コンポーネント固有の別配色契約は持ちません。

### Reduced Motion

本コンポーネントは常時アニメーションを持ちません。reduced motion 専用分岐は不要です。

### 非ブラウザ環境

非ブラウザ環境では、例外を出さずに描画可能であることを優先します。ただし、live sync や style injection は環境依存機能です。

### Print

print は現時点で正式契約に含めません。印刷時の見た目は best-effort です。

## 関連契約

### prose policy との分離

`.prose ol` のような文書全体に対する list styling は、`ui-ol` のコンポーネント契約と分離します。必要であれば、別文書で prose list policy を定義します。

### unordered list との分離

`ui-ol` は unordered list の契約を持ちません。ordered / unordered を 1 コンポーネントで統合しません。

### variant 所有者の分離

`variant` の所有者は `ui-ol` ホストです。子 `ol` やグローバル prose selector を variant 所有者にしません。

## 境界条件

### 1. 通常の昇順リスト

先頭番号は `1` から始まり、同一 list 内で本文開始位置が揃います。

### 2. `start` による開始番号変更

`start` は有効な符号付き整数を受理します。`1`、`0`、`-1`、`9`、`99`、`999`、`1000` の各開始値でも、native semantics と視覚表示が整合しなければなりません。

### 3. `reversed`

`reversed` 指定時は、降順の意味と視覚表示が整合しなければなりません。`start` あり / なしの両方を境界条件に含めます。

### 4. `li[value]` による途中再設定

`li[value]` は有効な符号付き整数を受理します。途中で `10`、`0`、`-3`、`1000` などへ再設定しても、その項目の番号と以後の番号進行は native semantics と整合しなければなりません。

### 5. 桁境界

少なくとも次の遷移を境界条件に含めます。

- `9 → 10`
- `99 → 100`
- `999 → 1000`
- `-1 → 0`
- `0 → 1`

これらの遷移でも、本文開始位置とマーカー右端整列は維持されなければなりません。

### 6. `reversed` と `start` / `value` の複合

`reversed` と `start`、`reversed` と `li[value]` の複合は正式な境界条件に含めます。複合時も native semantics と視覚表示の不整合を生じてはなりません。

### 7. nested ordered list

nested ordered list は、親本文の後に接続してよいですが、親 list と子 list の整列契約は相互に独立でなければなりません。

### 8. nested unordered list

nested unordered list は存在してもよいですが、`ui-ol` の ordered list 用 marker 契約、列幅契約、整列契約を継承しません。

### 9. 構造違反

次は非保証です。

- root `<ol>` 不在
- 複数 root `<ol>`
- `ol` 直下の非 `li` 混在
- host 以外への `variant` 指定
- ordered / unordered の責務境界を壊す構造

実装が best-effort で表示しても構いませんが、利用者は正規入力と同格に扱ってはなりません。

## Storybook 契約

Storybook は見本ではなく、**公開契約の検証面** です。各 Story は 1 つの主要契約を検証し、入力条件、観測点、失敗条件、確認方法を固定します。

### Storybook の役割

Storybook は、次を担います。

- 正規入力に対する公開契約の可視化
- 破壊的変更を検知しやすい観測点の固定
- 外部から観測可能な結果の検証

Storybook は、次を担いません。

- 内部 `data-*` 属性や内部 CSS 変数名の存在確認
- `MutationObserver` や style injection の方式確認
- 非正規入力の常設保証
- 実装都合の一時的挙動を公開契約へ昇格させること

### 観測方法

確認方法は次の 3 種に限定します。

| 確認方法            | 用途                                                                 |
| ------------------- | -------------------------------------------------------------------- |
| DOM 観測            | 構造、native 属性意味、正規入力 / 非正規入力の区別、list 境界の確認  |
| computed style 観測 | 本文開始位置、マーカー整列、色差、spacing、トークン反映の確認        |
| visual diff         | 総合的な見た目崩れの補助確認                                         |

visual diff は補助手段です。意味契約の主要確認には用いません。

### Story 一覧

| Story                          | 主要契約                           | 第一確認手段        | 補助確認手段        |
| ------------------------------ | ---------------------------------- | ------------------- | ------------------- |
| `Default`                      | 正規入力の基本構造と既定番号       | DOM 観測            | computed style 観測 |
| `StartZeroAndNegative`         | `start` の 0 / 負数受理            | DOM 観測            | computed style 観測 |
| `StartAndValueJump`            | `start` と `li[value]` の番号再設定 | DOM 観測            | computed style 観測 |
| `Reversed`                     | `reversed` の意味整合              | DOM 観測            | computed style 観測 |
| `ReversedWithStartAndValue`    | `reversed` と `start` / `value` の複合 | DOM 観測         | computed style 観測 |
| `MarkerAlignment`              | 本文開始位置とマーカー右端整列     | computed style 観測 | visual diff         |
| `VariantSteps`                 | `steps` がマーカー差分に限定されること | computed style 観測 | visual diff      |
| `NestedOrderedList`            | 親子 ordered list の独立整列       | DOM 観測            | computed style 観測 |
| `NestedUnorderedListIsolation` | unordered list への非干渉          | DOM 観測            | computed style 観測 |
| `StructureViolation`           | 非正規入力が非保証であること       | DOM 観測            | visual diff         |
| `EnvironmentContracts`         | トークン差し替え・forced colors 耐性 | computed style 観測 | visual diff       |

### 各 Story の固定条件

#### `Default`

- 正規入力のみを用います
- root `<ol>` は 1 個のみです
- nested list、`variant`、`reversed`、`value` は持ち込みません
- DOM 観測では root `<ol>` の一意性と既定番号意味を確認します
- computed style 観測では本文開始位置と基本 spacing を確認します

#### `StartZeroAndNegative`

- `start="0"` および `start="-1"` を含めます
- DOM 観測では開始番号意味を確認します
- computed style 観測では 0 および負数でも本文開始位置が崩れないことを確認します

#### `StartAndValueJump`

- `start` と `li[value]` の両方を含めます
- 少なくとも `9 → 10` と `99 → 100` をまたぐ番号進行を含めます
- `li[value]="0"` または `li[value]="-3"` のいずれかを含めます
- DOM 観測では番号再設定と以後の進行を確認します
- computed style 観測では途中ジャンプ後も本文開始位置が崩れないことを確認します

#### `Reversed`

- `reversed` のみを主要変数とします
- `start` を持たない降順を確認します
- DOM 観測では降順意味を確認します
- computed style 観測では降順でも本文開始位置が維持されることを確認します

#### `ReversedWithStartAndValue`

- `reversed` と `start` または `li[value]` の複合を扱います
- DOM 観測では複合時の番号進行を確認します
- computed style 観測では複合でも整列が崩れないことを確認します

#### `MarkerAlignment`

- 少なくとも `9 → 10`、`99 → 100`、`999 → 1000`、`-1 → 0`、`0 → 1` を含めます
- 観測点は本文開始位置とマーカー右端整列です
- computed style 観測では、本文左端 `x` 座標差およびマーカー右端 `x` 座標差が 1 CSS px 以下であることを確認します
- visual diff は補助確認に留めます

#### `VariantSteps`

- 比較対象として既定状態を並置します
- 観測点はマーカー色差分に限定します
- 本文色、本文位置、spacing、番号意味が不変であることを確認します
- `steps` によって本文が強調されないことを確認します

#### `NestedOrderedList`

- 親子とも ordered list とします
- DOM 観測では親 list と子 list の境界が独立していることを確認します
- computed style 観測では親 list と子 list がそれぞれ独立に整列していることを確認します

#### `NestedUnorderedListIsolation`

- 親を ordered list、子を unordered list とします
- DOM 観測では ordered / unordered の構造境界を確認します
- computed style 観測では ordered list 用の marker 契約や整列規則が unordered list 側へ漏れていないことを確認します

#### `StructureViolation`

- root `<ol>` 不在、複数 root `<ol>`、`ol` 直下の非 `li` 混在の少なくとも 1 つを含めます
- 正常系の見本として扱ってはなりません
- DOM 観測では非正規入力であることを確認します
- visual diff は best-effort 表示の参考確認に留め、主要判定には使いません

#### `EnvironmentContracts`

- forced colors 相当、トークン差し替え、ダークモード相当を扱ってよいですが、論点は環境耐性に限定します
- computed style 観測では、本文開始位置、spacing、本文色不変、マーカー色切替、システム色追従を確認します
- visual diff は総合的な見た目崩れの補助確認に留めます

### 失敗の扱い

Storybook で失敗を検知した場合は、次のいずれかを必ず行います。

- 実装を契約へ戻す
- 契約変更として本文書と Story を同時更新する

Story だけを実装都合で緩めることは認めません。

## 採用しない方針

次の方向は採りません。

- `ui-ol` を `.prose ol` の汎用スタイル政策と一体化すること
- 複数 root `<ol>` を 1 ホストで管理すること
- ordered list と unordered list を 1 契約へ統合すること
- DOM 正規化を常設の主機能にすること
- 内部 `data-*` や内部 CSS 変数を外部 API に昇格させること
- ordered list に選択、展開、ドラッグなど別責務の状態を持ち込むこと

## 現行実装との差分と未整合

本節は、**望ましい長期契約** と **現行 **`** / **` の差分を、次の 2 類型に分けて整理するものです。

- **実装にあるが長期契約へ採らないもの**
- **将来契約へ昇格し得るが未固定なもの**

この区分により、現行挙動のうち何を縮退対象とし、何を将来の正式契約候補として扱うかを明確にします。

### 実装にあるが長期契約へ採らないもの

#### 1. `.prose ol` へのスタイル注入

現行実装は `ui-ol` だけでなく `.prose ol` まで対象にしたドキュメントスタイル注入を行います。これは現行動作として存在しますが、長期契約では prose policy の責務であり、`ui-ol` の公開契約には採りません。

#### 2. 救済入力の自動正規化

現行実装は直下 `li` を新規 `<ol>` へ再配置できます。これは互換上の救済としては有効ですが、長期契約では正規入力に含めません。したがって、**実装に存在しても、常設仕様としては採りません**。

#### 3. 複数 root `<ol>` の処理

現行実装は複数 root `<ol>` を処理できますが、長期契約では 1 ホスト = 1 root `<ol>` に固定します。複数 root 処理は互換的挙動に留め、正式契約には採りません。

#### 4. nested unordered list への副作用余地

現行セレクタ設計では `ui-ol li` が広く当たり得るため、nested unordered list の `li` まで巻き込む余地があります。これは現行実装上の副作用可能性であり、長期契約では採りません。むしろ排除対象です。

#### 5. ARIA 補強の中心化

現行実装は `role="list"` / `role="listitem"` を補強します。長期契約では、これは native semantics を補助する互換実装に留め、契約の中心には採りません。

#### 6. `variant` 指定位置の互換解釈

現行実装には host 以外への互換的解釈余地がありますが、長期契約では host のみを正規指定位置に固定します。host 以外への指定解釈は、存在しても正式契約に採りません。

#### 7. Structure violation の best-effort 吸収

現行実装は構造違反入力を一部 best-effort で吸収します。長期契約では、こうした吸収は非保証入力に対する互換挙動として扱い、正式契約には採りません。

#### 8. Storybook の内部実装依存

現行 `MediaAndTokenContracts` は style tag の ID、CSS text、セレクタ文字列の存在を直接検査します。これは現行実装確認には有効ですが、長期契約では実装詳細観測であり、採りません。

#### 9. Dark mode 検証の独立 Story 前提

現行 Storybook には `DarkModeTokenContract` が独立に存在します。これは現行構成として存在しますが、長期契約では環境契約へ統合可能であり、独立 Story 前提そのものは採りません。

### 将来契約へ昇格し得るが未固定なもの

#### 10. 列幅推定の一般化

現行実装は 3 桁閾値の簡易推定に留まります。長期契約では、最大 marker 長に基づく一般化された列幅契約へ昇格し得ますが、まだ実装・Storybook と一体で固定し切れていません。

#### 11. 動的同期仕様の独立契約化

現行実装は `connectedCallback()`、`slotchange`、および `MutationObserver` により再同期します。監視対象属性も `start` / `reversed` / `value` に限定されています。これは現行機能として有用であり、将来的に **live sync の境界** を正式契約として切り出す余地がありますが、現時点では未固定です。

#### 12. タッチターゲット補助契約の整理

現行 Storybook コメントには 44 px 相当の表現が残りますが、実装と検証は `--control-min-touch` および `--control-height-sm` を前提とした 24 px 以上の補助 hit area に寄っています。これは現状不整合ですが、将来的には **固定 px 値ではなくトークン駆動の補助契約** として昇格し得ます。

#### 13. トークン依存の厳密化

現行実装は `--control-min-touch` だけでなく `--control-height-sm` にも依存します。長期契約では概念トークンへ整理していますが、将来的には **必須トークン / 任意トークン / fallback を持つトークン** を分離した厳密契約へ昇格し得ます。

#### 14. Print 契約の独立化

print は現時点で正式契約外ですが、要件が増えるなら screen 契約とは別に独立した print 契約へ昇格し得ます。現時点では未固定です。

#### 15. 開発時の構造違反警告

現行実装には正式な development warning 契約はありません。ただし、正規入力への収束を促すため、将来的には development 限定の構造違反警告を正式機能として昇格させる余地があります。

### 本節の読み方

- 本節前半にある項目は、現行実装に存在しても **長期契約へ寄せる際には縮退または分離する対象** です。
- 本節後半にある項目は、現行実装や現行運用の延長として **将来的に正式契約へ昇格する可能性がある対象** です。

この区分により、現行挙動の棚卸しと将来契約の候補整理を混同しません。
