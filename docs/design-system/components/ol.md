# Ol

## 概要

本書は、`ui-ol` の長期保守向け公開契約を定義します。

`ui-ol` は、**1 つの順序付きリストを、読書文脈に適した静かな番号表現として提示するコンポーネント**です。責務は、**ordered list の意味を保ったまま、番号の視覚表現、本文開始位置の整列、番号属性との整合を安定して提供すること**に限定します。

本書では、現行実装の都合よりも、設計の一貫性、責務分離、保守性、将来拡張時の破壊的変更回避を優先します。したがって、現行実装が持つ救済挙動、ドキュメント全体へのスタイル注入、内部属性による同期は、必要に応じて **互換層** または **未整理事項** として切り分けます。

---

## 目的

`ui-ol` の目的は、次の 4 点です。

1. **番号の意味をネイティブ ordered list に一致させること**
2. **1 桁・2 桁・3 桁以上でも本文開始位置を安定させること**
3. **読書の主役を本文に置き、番号は補助情報として静かに提示すること**
4. **ordered list の責務を、それ以外の prose policy や list policy から分離すること**

---

## 適用範囲

本書は、次を対象とします。

- `ui-ol` の公開契約
- 入力モデル
- 状態モデル
- DOM / Accessibility
- Visual Contract
- 環境別の振る舞い
- Storybook 契約
- 現行実装との差分と未整合

本書は、次を対象外とします。

- Markdown から ordered list を生成する上位パーサ
- `.prose` 全体に対する既定 list policy
- unordered list の表現契約
- checklist、link list、accordion list など別種 list の仕様
- 記事全体の見出し・TOC・sidebar 設計
- 印刷専用の最適化
- DOM 正規化や構造救済を前提とした authoring 体験の設計

## 設計原則

### 原則 1. `ui-ol` は 1 ホスト = 1 ordered list です

`ui-ol` は、**単一の root **``** を包むためのコンポーネント**です。複数 root `<ol>` を持つコンテナではありません。

### 原則 2. 番号の真実源はネイティブ HTML です

番号の意味論は `ol`、`li`、`start`、`reversed`、`value` によって決定します。`ui-ol` は独自の番号モデルを導入しません。

### 原則 3. ordered list 以外を巻き込みません

`ui-ol` が責務として扱うのは ordered list だけです。unordered list、definition list、任意の prose block を同じ契約へ含めません。

### 原則 4. コンポーネント契約と prose policy を分離します

`ui-ol` の契約は `ui-ol` 自体の公開面に限定します。`.prose ol` などのドキュメント全体スタイルは、本来別契約です。

### 原則 5. 内部同期の表現は公開 API にしません

内部 `data-*` 属性、内部 CSS 変数、内部スタイル注入方式は、公開 API として固定しません。

## 公開契約

### コンポーネントの役割

`ui-ol` は、root ordered list の **視覚整形レイヤ** です。内部描画は `<slot>` に留め、実データはライト DOM 側で与えます。

`ui-ol` の責務は、次に限定します。

- ordered list の番号表現を視覚的に整えること
- 番号列幅を調整し、本文開始位置を揃えること
- ネイティブ番号属性と視覚マーカーを整合させること
- 読書文脈に適した弱い視覚階層を与えること

`ui-ol` の責務に含めません。

- 文書全体の list styling
- DOM 構造の自由な正規化
- list type の自動判別
- authoring 用の入力救済を常設仕様にすること
- ソート、展開、選択、ドラッグ並べ替えなどの状態管理

### 公開入力

| 名前             | 種別               | 必須  | 内容        | 契約                              |
| -------------- | ---------------- | --- | --------- | ------------------------------- |
| root `<ol>`    | child node       | はい  | 順序付きリスト本体 | 正規入力ではホスト直下に `<ol>` を 1 つだけ持ちます |
| `variant`      | host attribute   | いいえ | 表現バリアント   | 現時点の正式値は `steps` のみです           |
| `ol[start]`    | native attribute | いいえ | 開始番号      | 視覚マーカーと整合します                    |
| `ol[reversed]` | native attribute | いいえ | 降順番号      | 視覚マーカーと整合します                    |
| `li[value]`    | native attribute | いいえ | 明示番号      | 当該項目の番号を上書きします                  |

### 正規入力契約

`ui-ol` の正規入力は、次に固定します。

```text
<ui-ol>
  <ol>
    <li>...</li>
    <li>...</li>
  </ol>
</ui-ol>
```

正規入力における制約は、次のとおりです。

- ホスト直下の root list は `<ol>` 1 個のみです
- root `<ol>` の正規子は `<li>` のみです
- nested `<ol>` は `<li>` の子としてのみ許可します
- nested `<ul>` は `ui-ol` の契約対象外です
- `<ol>` 以外の一般ノードをホスト直下へ置く構成は正規入力ではありません

### 救済入力契約

`<ui-ol><li>...</li></ui-ol>` のような入力は、長期的には正規入力へ含めません。これは **移行互換または authoring 救済** としてのみ扱います。

設計上の原則として、利用者は救済入力に依存しません。契約書、Storybook、上位変換は、正規入力のみを中心に構成します。

### 属性契約

`variant` は **ホスト属性** のみを正規の指定位置とします。直下 `<ol>` などホスト以外への指定は、公開契約に含めません。

`variant` の公開値として正式に意味を持つのは `steps` のみです。列挙外値は未定義であり、利用者は依存してはなりません（MUST NOT）。

`start` と `value` は整数として解釈します。設計上は、**すべての整数を受理可能な番号入力**として扱います。空文字列、空白のみ、整数変換不能な文字列は無効値です。

`reversed` は boolean attribute として扱います。属性が存在する場合に降順です。

### 非公開内部表現

内部同期のために `data-*` 属性や `--ui-ol-*` 形式の CSS カスタムプロパティを用いても構いません。ただし、これらは公開 API ではありません。利用者は依存してはなりません（MUST NOT）。

## 入力モデル

### ルート構造

`ui-ol` は、単一 root ordered list のみを扱います。複数 root `<ol>` を 1 ホストで扱う設計は採りません。

### 項目構造

root `<ol>` の子は `<li>` のみです。`template`、`div`、`p`、テキストノード、コメント、別の block 要素を混在させる構成は契約違反です。

### ネスト構造

nested `<ol>` は `<li>` の子として許可します。これは ordered list の自然な入れ子です。

一方、nested `<ul>` は `ui-ol` の責務ではありません。ordered list 内に unordered list が現れること自体は妨げませんが、その見た目や spacing は `ui-ol` の公開契約に含めません。

### 構造違反時の扱い

構造違反時は、次の保証を行いません。

- 番号の視覚同期
- 本文開始位置の整列
- spacing の一貫性
- アクセシビリティ補強の一貫性

将来的に警告や validation を導入する余地はありますが、少なくとも契約書上は **違反入力は非保証** とします。

## 状態モデル

`ui-ol` の状態は、見た目の派手さではなく、**番号進行規則** と **表現バリアント** によって決まります。

### 基本状態

既定状態は、昇順、開始番号 1、既定マーカー色です。

### 開始番号状態

`start` がある場合、先頭番号はその値から始まります。

### 降順状態

`reversed` がある場合、番号は降順です。`start` がない場合の開始番号は、ordered list のネイティブ意味論に従います。

### 明示値状態

`li[value]` がある場合、その項目の番号は明示値で再設定されます。以後の項目は、その値を起点に進みます。

### バリアント状態

`variant="steps"` は、**手順性の示唆** を与える軽い表現差分です。本文の主従を変えるほどの強調は行いません。

### 列幅状態

マーカー列幅は、**その list で表示される最大 marker 文字列長**に応じて決定します。設計上の本質は、`3ch` / `4ch` のような固定分岐ではなく、**本文開始位置を安定させること**です。

### 動的同期状態

現行実装は、接続時、`slotchange` 発生時、およびライト DOM 変更時に再同期します。再同期対象は、主として次の項目です。

- root `<ol>` の有無
- nested ordered list を含む list 群
- `start` / `reversed` / `li[value]` に基づく番号同期
- `role` 補強が必要な `ol` / `li`

これは互換実装上の live sync であり、長期契約の中心ではありません。ただし、現行実装を前提にした利用では、**後追加ノードや属性変更に一定の追従があること**を前提にできます。

## DOM / Accessibility

### DOM 境界

`ui-ol` の Shadow DOM は表示境界であり、ordered list の意味論はライト DOM 側の `<ol>` / `<li>` が担います。

ホスト要素自体は block-level wrapper として振る舞います。したがって、`ui-ol` はレイアウト境界として存在しますが、番号意味と list semantics の担い手ではありません。

### アクセシビリティ方針

長期的な設計としては、**native ordered list semantics を真実源** とします。したがって、`ol` / `li` 自体が持つ意味論を優先し、ARIA による過剰な再定義を基本方針にしません。

### 契約

- ordered list の意味は native `ol` / `li` に依存します
- `ui-ol` は番号を見た目だけで再現するのではなく、意味論と整合した視覚表現を与えます
- 既存の `role` や ARIA 属性を勝手に上書きしません
- 必要な補強を行う場合でも、それは **互換実装上の補助** であり、契約の中心ではありません

### インタラクティブ要素共存

`li` 内に `a`、`button`、`[role="button"]` などの操作要素を含めても構いません。ただし、`ui-ol` の責務は ordered list の視覚整列であり、操作コンポーネント固有のアクセシビリティ要件は各要素側の契約です。

補助 hit area を与える場合も、それは **ordered list の責務を超えない弱い補助** に留めます。

## Visual Contract

### 目的

視覚契約の目的は、**番号を読ませることではなく、本文の読書を妨げないこと**です。

### 情報順位

- 主役は本文です
- マーカーは本文より弱い視覚重量を持ちます
- `steps` でも、強調はマーカーに限定します
- 番号は意味の手がかりであり、視線の主目的にはしません

### レイアウト契約

- 各項目は、**マーカー列** と **本文列** からなる 2 列構成です
- 本文開始位置は、番号桁数が変わっても揃います
- 項目間余白は一定です
- nested ordered list は親項目本文の後に自然な垂直リズムで接続します

### マーカー契約

- マーカーは視覚的には番号 + 区切り記号として提示します
- 右寄せで整列します
- `tabular-nums` 相当の数字整列を用います
- 既定色は抑制された補助色です
- `steps` では主色系へ寄せても、本文色は変えません

### 列幅契約

マーカー列幅は、**表示対象の最大 marker 長に対して十分な幅**を持ちます。実装が 3 桁境界の簡易推定を採るか、一般式を採るかは内部実装です。公開契約は、本文開始位置の安定性にあります。

### トークン契約

`ui-ol` は、少なくとも次の概念トークンに依存します。

| 用途          | トークン                  |
| ----------- | --------------------- |
| 項目間余白       | `--space-2`           |
| マーカー色       | `--fg-muted`          |
| 手順マーカー色     | `--primary`           |
| 数字書体        | `--font-mono`         |
| 数字太さ        | `--font-medium`       |
| 補助 hit area | `--control-min-touch` |
| 小型操作要素の最低高  | `--control-height-sm` |

ここで重要なのは個々の値ではなく、**spacing / color / type / touch support が foundation token で供給されること**です。

## 環境別の振る舞い

### Forced Colors

forced colors 環境では、マーカー色はシステム色に追従します。色による意味依存は避けます。

### Dark Mode

ダークモードでは、セマンティックトークン差し替えによって視覚差を吸収します。コンポーネント固有の別配色契約は持ちません。

### Reduced Motion

本コンポーネントは常時アニメーションを持ちません。reduced motion 専用分岐は不要です。

### 非ブラウザ環境

非ブラウザ環境では、例外を出さずに描画可能であることを優先します。ただし、live sync や style injection は環境依存機能です。

### Print

print は現時点で正式契約に含めません。印刷時の見た目は best-effort です。

---

## 関連契約

### prose policy との分離

`.prose ol` のような文書全体に対する list styling は、`ui-ol` のコンポーネント契約と分離します。必要であれば、別文書で prose list policy を定義します。

### unordered list との分離

`ui-ol` は unordered list の契約を持ちません。ordered / unordered を 1 コンポーネントで統合しません。

### variant 所有者の分離

`variant` の所有者は `ui-ol` ホストです。子 `ol` やグローバル prose selector を variant 所有者にしません。

---

## 境界条件

### 1. 通常の昇順リスト

先頭は `1` から始まり、本文開始位置が揃います。

### 2. `start` 指定

任意の整数開始値から始められます。`9` から `10` へ遷移しても本文開始位置は揃います。

### 3. `reversed` 指定

降順でも番号意味と視覚表示が整合します。

### 4. `li[value]` 指定

途中項目で番号を飛ばしても、以後の番号進行は整合します。

### 5. 3 桁以上

3 桁以上でも本文開始位置は破綻しません。4 桁以上の扱いは、将来的には一般化した列幅推定へ寄せます。

### 6. nested ordered list

nested ordered list は、親本文から自然に接続し、別の ordered list として整列します。

### 7. nested unordered list

nested unordered list は存在してもよいですが、`ui-ol` の視覚契約対象外です。

### 8. 構造違反

root `<ol>` 不在、複数 root `<ol>`、`ol` 直下の非 `li` 混在は非保証です。

## Storybook 契約

Storybook は見本ではなく、**公開契約の検証面**です。したがって Story は「見え方の例」ではなく、**何を固定し、何を固定しないか**を明示した契約単位として構成します。

### Storybook の役割

Storybook の役割は、次に限定します。

- 正規入力に対する公開契約を可視化すること
- 破壊的変更を検知しやすい観測点を固定すること
- 実装詳細ではなく、外部から観測可能な結果を確認すること

Storybook の役割に含めません。

- 内部 `data-*` 属性や内部 CSS 変数の存在確認
- DOM 正規化の内部手順確認
- `.prose ol` のような別責務の確認
- 実装都合の一時的な回避策を公開契約へ昇格させること

### Storybook で観測する対象

各 Story では、少なくとも次の観測対象を明示します。

| 観測対象 | 内容                                              |
| ---- | ----------------------------------------------- |
| 構造   | 正規入力が描画されること                                    |
| 番号意味 | `start` / `reversed` / `li[value]` が視覚表現と整合すること |
| 整列   | 番号桁数が変わっても本文開始位置が揃うこと                           |
| 変種   | `variant` が許可された差分だけを生むこと                       |
| 境界   | nested ordered list や構造違反時の扱いが契約どおりであること        |
| 環境   | forced colors、トークン差し替え時に公開契約が崩れないこと             |

### Storybook で観測しない対象

次は Storybook の契約対象に含めません。

- 内部同期に用いる属性名や CSS 変数名
- 何回再計算したかといった内部更新回数
- MutationObserver や style injection の実装方式そのもの
- 非正規入力を常設仕様として保証すること

### Story 設計原則

各 Story は 1 つの主要契約を検証します。複数の論点を 1 Story に混在させません。

各 Story は、次の 3 点を持ちます。

- **入力条件**
- **観測点**
- **失敗条件**

確認方法は Story ごとに固定します。各 Story は、**第一確認手段** と **補助確認手段** を持ちます。実装者の裁量で確認方法を毎回選び直しません。

確認方法の優先順位は、次のとおりです。

1. **意味契約** は DOM 観測で確認します
2. **レイアウト契約** は computed style 観測と寸法観測で確認します
3. **色や tone の差分** は computed style 観測で確認します
4. **環境差の総合確認** は visual diff を補助的に用います

visual diff は補助手段です。番号意味、属性意味、構造違反の扱いなど、意味論契約の主要確認手段にはしません。

### Story 一覧

| Story                          | 入力条件                                              | 観測点                                                       | 失敗条件                                                         | 第一確認手段            | 補助確認手段            |
| ------------------------------ | ------------------------------------------------- | --------------------------------------------------------- | ------------------------------------------------------------ | ----------------- | ----------------- |
| `Default`                      | 正規入力の最小構成                                         | ordered list が描画され、先頭番号が既定開始値と整合し、本文開始位置が安定していること         | root `<ol>` を前提とする基本構造が崩れること、既定番号が不整合になること                   | DOM 観測            | computed style 観測 |
| `StartAndValue`                | `start` と `li[value]` を含む構成                       | 開始番号、途中番号飛び、以後の番号進行が視覚的に整合すること                            | 途中番号変更後の進行が崩れること、視覚番号がネイティブ意味とずれること                          | DOM 観測            | computed style 観測 |
| `Reversed`                     | `reversed` を含む構成                                  | 降順の意味と視覚番号が一致すること                                         | 降順時に視覚番号だけが昇順になること、または開始値解釈が破綻すること                           | DOM 観測            | computed style 観測 |
| `MarkerAlignment`              | 1 桁・2 桁・3 桁以上が混在する構成                              | 番号桁数が変わっても本文開始位置が揃うこと                                     | `9` と `10`、`99` と `100` などで本文開始位置がずれること                      | computed style 観測 | visual diff       |
| `VariantSteps`                 | `variant="steps"` の構成                             | 許可された差分がマーカーの tone に限定されること                               | 本文色、本文位置、spacing、番号意味まで変化すること                                | computed style 観測 | visual diff       |
| `NestedOrderedList`            | `<li>` 配下に nested `<ol>` を持つ構成                    | nested ordered list が独立した ordered list として整列すること          | 親 list の marker 契約が子 list に破壊的に漏れること、または子 list の本文開始位置が崩れること | DOM 観測            | computed style 観測 |
| `NestedUnorderedListIsolation` | `<li>` 配下に nested `<ul>` を持つ構成                    | nested unordered list が `ui-ol` の ordered list 契約対象外であること | ordered list 用 marker や整列規則が nested unordered list に漏れること    | DOM 観測            | computed style 観測 |
| `StructureViolation`           | root `<ol>` 不在、複数 root `<ol>`、`ol` 直下の非 `li` 混在など | 非正規入力が非保証であること、または互換救済としてのみ扱うことが明示されること                   | 非正規入力を正規入力と同格に見せること                                          | DOM 観測            | visual diff       |
| `EnvironmentContracts`         | forced colors 相当およびトークン差し替え構成                     | 環境差があっても公開契約が崩れないこと                                       | 色依存の意味破綻、トークン差し替えで整列や可読性が崩れること                               | computed style 観測 | visual diff       |

### 確認方法の固定契約

確認方法は、次のように固定します。

| 確認方法              | 用途                                        | 主要に使う Story                                                                                                                                     | 採らない用途         |
| ----------------- | ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | -------------- |
| DOM 観測            | 構造、属性意味、正規入力 / 非正規入力の区別、nested list の境界確認 | `Default`、`StartAndValue`、`Reversed`、`NestedOrderedList`、`NestedUnorderedListIsolation`、`StructureViolation`                                    | 色差や本文位置の主要確認   |
| computed style 観測 | 本文開始位置、色差、spacing、tone、環境トークン反映の確認        | `Default`、`StartAndValue`、`Reversed`、`MarkerAlignment`、`VariantSteps`、`NestedOrderedList`、`NestedUnorderedListIsolation`、`EnvironmentContracts` | 構造違反の意味判定      |
| visual diff       | 総合的な見た目崩れの補助確認                            | `MarkerAlignment`、`VariantSteps`、`StructureViolation`、`EnvironmentContracts`                                                                    | 番号意味や構造意味の主要確認 |

各 Story は、表に定めた **第一確認手段** を必須とします。補助確認手段だけで合格としません。

### Story ごとの厳密条件

#### `Default`

- 正規入力のみを用います
- root `<ol>` は 1 個のみです
- nested list や variant は持ち込みません
- 確認対象は、基本番号意味、本文開始位置、基本 spacing に限定します
- **第一確認手段は DOM 観測**です
- 先頭項目の意味、root `<ol>` の一意性、正規入力構造を DOM で確認します
- **補助確認手段は computed style 観測**です
- 本文開始位置と基本 spacing の安定性を computed style で確認します

#### `StartAndValue`

- `start` により先頭番号が変化することを確認します
- `li[value]` により途中番号が明示変更されることを確認します
- 明示変更後の次項目が、その値を起点に自然に進むことを確認します
- `reversed` との複合条件は別 Story に分離します
- **第一確認手段は DOM 観測**です
- `start` と `value` の入力意味、および番号進行の意味整合を DOM で確認します
- **補助確認手段は computed style 観測**です
- 番号飛び後も本文開始位置が崩れないことを確認します

#### `Reversed`

- `reversed` のみを主要変数とします
- `start` あり / なしの両方を確認してもよいですが、観測点は降順契約に限定します
- 降順時に本文整列契約も維持されることを確認します
- **第一確認手段は DOM 観測**です
- `reversed` の意味と開始番号解釈を DOM で確認します
- **補助確認手段は computed style 観測**です
- 降順でも本文開始位置が安定することを確認します

#### `MarkerAlignment`

- 少なくとも `9 → 10` と `99 → 100` を含めます
- 観測点は本文開始位置であり、内部列幅計算方法ではありません
- 数字書体や色差分は主要観測点に含めません
- **第一確認手段は computed style 観測**です
- 各項目の本文開始位置、marker 列幅、整列結果を寸法として確認します
- **補助確認手段は visual diff** です
- 全体の見た目崩れを補助的に確認します

#### `VariantSteps`

- 比較対象として既定 variant を並置します
- 観測点はマーカーの tone 差分に限定します
- 本文色、本文位置、番号意味、構造、spacing が不変であることを重視します
- **第一確認手段は computed style 観測**です
- マーカー色差分と本文側の不変条件を確認します
- **補助確認手段は visual diff** です
- tone 差分が全体崩れを伴わないことを補助的に確認します

#### `NestedOrderedList`

- 親 list と子 list の両方が ordered list であることを明示します
- 子 list は親本文の後に自然に接続する必要があります
- 親 list の状態が子 list の番号意味を壊さないことを確認します
- **第一確認手段は DOM 観測**です
- 親子の list 境界が ordered list として正しく分かれることを確認します
- **補助確認手段は computed style 観測**です
- 子 list の本文開始位置と親子間の接続 spacing を確認します

#### `NestedUnorderedListIsolation`

- 親は ordered list、子は unordered list とします
- `ui-ol` の marker 契約が unordered list 側へ漏れないことを確認します
- この Story は「対応する」ことではなく「巻き込まない」ことを確認する Story です
- **第一確認手段は DOM 観測**です
- ordered / unordered の境界が構造上分離されていることを確認します
- **補助確認手段は computed style 観測**です
- unordered list 側へ ordered list 用 marker や整列規則が漏れていないことを確認します

#### `StructureViolation`

- この Story は正常系の見本ではありません
- 非正規入力を正式サポートへ見せない記述にします
- best-effort 救済を示す場合も、それが長期契約の中心ではないことを明記します
- **第一確認手段は DOM 観測**です
- 入力が非正規であることと、正規入力と同格に扱っていないことを確認します
- **補助確認手段は visual diff** です
- 救済時の見た目を補助的に観測しても構いませんが、主要判定には使いません

#### `EnvironmentContracts`

- forced colors では色名ではなく意味保持を確認します
- トークン差し替えでは個別値ではなく、spacing / type / tone / touch support の概念が維持されることを確認します
- dark mode は別 Story に分けてもよいですが、`EnvironmentContracts` に含める場合は論点を environment に限定します
- **第一確認手段は computed style 観測**です
- システム色追従、トークン反映、整列維持を確認します
- **補助確認手段は visual diff** です
- 環境差による総合的な見た目崩れを補助的に確認します

### 命名契約

Story 名は、見た目ではなく検証対象を表します。したがって、`PrettyList` のような主観名は用いません。`StartAndValue`、`NestedUnorderedListIsolation` のように、**どの契約を固定する Story なのか**が名前から分かるようにします。

### 失敗の扱い

Storybook で失敗を検知した場合、それは単なる回帰ではなく、公開契約変更の候補として扱います。したがって、次のいずれかを必ず行います。

- 実装を契約に戻す
- 契約変更として文書と Story を同時更新する

Story だけを実装都合で緩めることはしません。

### 現行 Storybook との関係

現行 `ol.stories.ts` にある Story は、契約検証の素材として有用です。ただし、長期契約に合わせて見ると、次の再編成が望まれます。

- `.prose ol` 全体の媒介確認は `ui-ol` 契約から切り離します
- nested unordered list への非干渉確認を独立 Story として追加します
- `StructureViolation` は正常系一覧の一部ではなく、非正規入力の扱いを示す独立カテゴリへ寄せます
- 各 Story の観測点を 1 つの主要契約へ絞ります
- `MediaAndTokenContracts` のような内部 style tag や CSS text の直接検査は、長期契約では実装詳細観測として縮退させます
- `DarkModeTokenContract` のような個別 Story は、長期契約では `EnvironmentContracts` に統合するか、環境 Story 群として再編します

## 採用しない方針

次の方向は採りません。

- `ui-ol` を `.prose ol` の汎用スタイル政策と一体化すること
- 複数 root `<ol>` を 1 ホストで管理すること
- ordered list と unordered list を 1 契約へ統合すること
- DOM 正規化を常設の主機能にすること
- 内部 `data-*` や内部 CSS 変数を外部 API に昇格させること
- ordered list に選択、展開、ドラッグなど別責務の状態を持ち込むこと

## 将来拡張の原則

将来拡張は、機能数を増やすためではなく、**ordered list としての完成度を高めるため**にのみ採用します。したがって、追加候補は次の基準で評価します。

- ネイティブ ordered list の意味論を強めるか
- 本文開始位置の安定性を高めるか
- 読書の没入を壊さないか
- prose policy や interaction component の責務を持ち込まないか

### 最優先で検討する価値がある拡張

#### 1. マーカー書式の明示的契約化

最優先候補は、**マーカー書式を公開契約として明示すること**です。現状の `1.` 固定表現だけでは、手順列挙、規約列挙、参照列挙といった文書上の差分を表し切れません。

ただし、ここで追加するのは自由入力ではなく、**列挙型の公開値**に限定します。たとえば `decimal-dot`、`decimal-paren`、`decimal-plain` のように、十進番号を前提とした区切り記号差分に留めます。

この拡張で固定すべき原則は、次のとおりです。

- 番号の真実源は引き続き native `ol` / `li` / `start` / `reversed` / `value` とします
- マーカー書式は装飾ではなく、文書体系上の契約として扱います
- 初期段階ではローマ数字やアルファベットなど、意味体系まで変わる表記は含めません
- 書式追加時も本文開始位置の安定性を崩しません

#### 2. 列幅推定の一般化

次に優先度が高いのは、**列幅推定の一般化**です。設計の本質は `3ch` / `4ch` という局所分岐ではなく、**最大 marker 長に対して本文開始位置を安定させること**にあります。

この拡張で目指すのは、次のような一般化です。

- 3 桁境界専用の二値分岐から離れること
- 4 桁以上、負数、将来のマーカー書式差分にも耐えること
- 列幅計算の内部方式は自由でも、外部契約は本文開始位置の安定性に固定すること

#### 3. 開発時の構造違反警告

長期的な入力純化のために、**development 限定の構造違反警告**を追加する価値があります。これは表示機能ではなく、正規入力へ収束させるための補助機能です。

対象とする警告候補は、次のとおりです。

- root `<ol>` 不在
- 複数 root `<ol>`
- `ol` 直下の非 `li` 混在
- ホスト以外への `variant` 指定
- ordered / unordered の責務境界を壊す構造

この警告は authoring 救済を恒久化するためではなく、**救済入力依存を減らすため**に導入します。

### 条件付きで検討する価値がある拡張

#### 4. Print 契約の独立化

print は現時点で正式契約外ですが、印刷、PDF 保存、共有文書化の要件が増えるなら、独立した契約として起こす価値があります。

その場合、screen 契約へ混在させるのではなく、少なくとも次を独立して定義します。

- 印刷時も番号意味を保持すること
- 本文開始位置の整列を極力維持すること
- 色に依存しない最低限の可読性を確保すること

#### 5. ネスト深度別の弱い差分

nested ordered list の可読性をさらに高めるために、深度別の spacing や marker tone をわずかに調整する価値はあります。

ただし、この拡張は本文主従を壊しやすいため、次を条件とします。

- 深度差分は弱い表現に留めること
- 深度に意味差を持ち込まないこと
- parent / child の ordered list 境界を曖昧にしないこと

#### 6. 第 2 バリアントの追加

`variant` を増やす価値があるとしても、見た目都合のバリアントではなく、**文書用途に意味を持つ差分**に限ります。

ただし、これはマーカー書式契約と重なりやすいため、優先順位は高くありません。`variant` を追加する場合も、先にマーカー書式の公開契約を固めます。

### 採らない方針

次の方向は、ordered list の純度を下げるため採りません。

- checklist 化
- 展開 / 折りたたみ
- ステップ移動 UI
- 並べ替えやドラッグ操作
- 装飾的な番号バッジ化
- unordered list や interaction component の責務統合

これらは便利に見えても、`ui-ol` を ordered list の視覚整形レイヤから外してしまいます。

### 拡張採用時の順序

拡張を採用する場合の推奨順序は、次のとおりです。

1. マーカー書式の明示的契約化
2. 列幅推定の一般化
3. 開発時の構造違反警告
4. Print 契約の独立化
5. ネスト深度別の弱い差分

この順序は、**見た目の遊びを増やす前に、ordered list としての完成度を上げる**ことを意味します。

## 現行実装との差分と未整合

本節は、**望ましい長期契約** と **現行 **``** / **`` の差分を、次の 2 類型に分けて整理するものです。

- **実装にあるが長期契約へ採らないもの**
- **将来契約へ昇格し得るが未固定なもの**

この区分により、現行挙動のうち何を縮退対象とし、何を将来の正式契約候補として扱うかを明確にします。

### 実装にあるが長期契約へ採らないもの

#### 1. `.prose ol` へのスタイル注入

現行実装は `ui-ol` だけでなく `.prose ol` まで対象にしたドキュメントスタイル注入を行います。これは現行動作として存在しますが、長期契約では prose policy の責務であり、`ui-ol` の公開契約には採りません。

#### 2. 救済入力の自動正規化

現行実装は直下 `li` を新規 `<ol>` へ再配置できます。これは互換上の救済としては有効ですが、長期契約では正規入力に含めません。したがって、**実装に存在しても、常設仕様としては採りません**。

#### 3. 複数 root `<ol>` の処理

現行実装は複数 root `<ol>` を処理できますが、長期契約では 1 ホスト = 1 root `<ol>` に固定します。複数 root 処理は互換的挙動に留め、正式契約には採りません。

#### 4. nested unordered list への副作用余地

現行セレクタ設計では `ui-ol li` が広く当たり得るため、nested unordered list の `li` まで巻き込む余地があります。これは現行実装上の副作用可能性であり、長期契約では採りません。むしろ排除対象です。

#### 5. ARIA 補強の中心化

現行実装は `role="list"` / `role="listitem"` を補強します。長期契約では、これは native semantics を補助する互換実装に留め、契約の中心には採りません。

#### 6. `variant` 指定位置の互換解釈

現行実装には host 以外への互換的解釈余地がありますが、長期契約では host のみを正規指定位置に固定します。host 以外への指定解釈は、存在しても正式契約に採りません。

#### 7. Structure violation の best-effort 吸収

現行実装は構造違反入力を一部 best-effort で吸収します。長期契約では、こうした吸収は非保証入力に対する互換挙動として扱い、正式契約には採りません。

#### 8. Storybook の内部実装依存

現行 `MediaAndTokenContracts` は style tag の ID、CSS text、セレクタ文字列の存在を直接検査します。これは現行実装確認には有効ですが、長期契約では実装詳細観測であり、採りません。

#### 9. Dark mode 検証の独立 Story 前提

現行 Storybook には `DarkModeTokenContract` が独立に存在します。これは現行構成として存在しますが、長期契約では環境契約へ統合可能であり、独立 Story 前提そのものは採りません。

### 将来契約へ昇格し得るが未固定なもの

#### 10. 列幅推定の一般化

現行実装は 3 桁閾値の簡易推定に留まります。長期契約では、最大 marker 長に基づく一般化された列幅契約へ昇格し得ますが、まだ実装・Storybook と一体で固定し切れていません。

#### 11. 動的同期仕様の独立契約化

現行実装は `connectedCallback()`、`slotchange`、および `MutationObserver` により再同期します。監視対象属性も `start` / `reversed` / `value` に限定されています。これは現行機能として有用であり、将来的に **live sync の境界** を正式契約として切り出す余地がありますが、現時点では未固定です。

#### 12. タッチターゲット補助契約の整理

現行 Storybook コメントには 44 px 相当の表現が残りますが、実装と検証は `--control-min-touch` および `--control-height-sm` を前提とした 24 px 以上の補助 hit area に寄っています。これは現状不整合ですが、将来的には **固定 px 値ではなくトークン駆動の補助契約** として昇格し得ます。

#### 13. トークン依存の厳密化

現行実装は `--control-min-touch` だけでなく `--control-height-sm` にも依存します。長期契約では概念トークンへ整理していますが、将来的には **必須トークン / 任意トークン / fallback を持つトークン** を分離した厳密契約へ昇格し得ます。

#### 14. Print 契約の独立化

print は現時点で正式契約外ですが、要件が増えるなら screen 契約とは別に独立した print 契約へ昇格し得ます。現時点では未固定です。

#### 15. 開発時の構造違反警告

現行実装には正式な development warning 契約はありません。ただし、正規入力への収束を促すため、将来的には development 限定の構造違反警告を正式機能として昇格させる余地があります。

### 本節の読み方

- 本節前半にある項目は、現行実装に存在しても **長期契約へ寄せる際には縮退または分離する対象** です。
- 本節後半にある項目は、現行実装や現行運用の延長として **将来的に正式契約へ昇格する可能性がある対象** です。

この区分により、現行挙動の棚卸しと将来契約の候補整理を混同しません。

## まとめ

`ui-ol` の長期契約を一文で要約すると、次のとおりです。

``** は、単一の ordered list を、ネイティブ番号意味と整合したまま静かに整列表示するためのコンポーネントです。**``** は prose policy でも DOM 正規化器でもありません。**
