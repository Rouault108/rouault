# Ul

## 文書の目的

本書は、`ui-ul` の**長期的に固定すべき公開契約**を定義するものです。ここで定義する契約は、現行実装の挙動をそのまま追認するためのものではなく、**設計の一貫性、責務分離、保守性、予見可能性**を優先して整理した目標契約です。

`ui-ul` は、順序なしリストの見た目を派手に変える装飾部品ではありません。**単一の順序なしリストを、読書文脈に適した静かな視覚秩序で提示し、`list-style: none` を採用しても意味論を失わせないための構造コンポーネント**です。

したがって、`ui-ul` の責務は次に限定します。

- 単一の root `ul` の受理
- 最小限の入力救済
- 意味論補強
- 読書向けの局所的な視覚整形

一方で、`.prose ul` のような**ページ全体へのグローバルなタイポグラフィ初期化**は、本コンポーネントの主責務に含めません。

## 適用範囲

本書は、`ui-ul` の次の事項を対象とします。

- 公開契約
- 受理する Light DOM 構造
- 入力の正規化方針
- DOM / Accessibility
- Visual Contract
- 環境別の振る舞い
- 境界条件
- Storybook 契約
- 長期固定契約に対する現行実装との差分

一方で、本書は次の事項を扱いません。

- 順序付きリスト（`ol`）の契約
- `.prose` 文脈全体のタイポグラフィ設計
- リスト項目内のリンク先、ボタン動作、ルーティング
- マーカーの任意差し替えやテーマ別装飾拡張
- サイズや密度の見た目バリアント
- `ui-ul` 単体による強いインタラクティブ target 保証
- 救済入力を strict に無効化する運用モード
- 高頻度 DOM 編集やエディタ用途の更新保証
- 多機能な公開設定面や公開再同期 API
- 複合 `li` 内容を第一級ユースケースとして扱う契約拡張
- ページ全体へのグローバル CSS 初期化

これらは、上位レイヤ、別コンポーネント、開発運用、または typography system の責務です。

## 長期固定方針

本コンポーネントの契約は、次の方針を優先して固定します。

1. **ローカル責務を優先する**\
   `ui-ul` は局所コンポーネントであり、ページ全体の prose スタイル初期化子ではありません。

2. **正規入力と救済入力を分離する**\
   正規入力は単一の root `ul` とし、それ以外は救済入力または契約違反入力として区別します。

3. **構造正規化と視覚整形を分離して考える**\
   DOM 補正は最小限に抑え、任意要素の自動意味昇格は行いません。

4. **HTML-native-first を採る**\
   `ui-ul` は `ul` / `li` を前提とし、ARIA は意味論の補助に限定します。

5. **インタラクティブ要素への配慮は副次責務に留める**\
   リンクやボタンの十分なヒット領域保証は、それらの本体契約に委ねます。

6. **動的同期は軽微変更に対する補助機構として扱う**\
   高頻度編集や強い同期保証を前提にしません。

7. **契約違反入力には fail-soft を採る**\
   契約違反入力に対しては、追加の構造補正や意味昇格を行わず、入力 DOM をできるだけ保持します。

8. **公開再同期 API は持たない**\
   `refresh()` のような明示 API は現契約では採用しません。再同期は接続時と軽微変更への追随に限定します。

## 公開契約

`ui-ul` は、property や attribute による多機能な設定面を持ちません。公開入力は、**Light DOM として与えるリスト構造そのもの**です。利用者は `ui-ul` を「設定型 UI 部品」ではなく、**単一の順序なしリストを整える構造コンポーネント**として扱います。

### 入力分類契約

入力は、次の 3 類型に分けて扱います。

| 類型         | 位置づけ               | 契約                                                     |
| ------------ | ---------------------- | -------------------------------------------------------- |
| 正規入力     | 第一級で保証する入力   | 単一の root `ul` を持つ入力                              |
| 救済入力     | 互換目的で受理する入力 | 直下 `li`、または root `ul` と stray `li` の混在         |
| 契約違反入力 | 補正も保証もしない入力 | 複数の root `ul`、一般要素の自動箇条書き化を期待する入力 |

### 正規入力

`ui-ul` が将来にわたり第一級で保証する正規入力は、次の形です。

| 入力形                                             | 内容                          | 契約     |
| -------------------------------------------------- | ----------------------------- | -------- |
| `<ui-ul><ul>...</ul></ui-ul>`                      | 直下に単一の root `ul` を置く | 正規入力 |
| `<ui-ul><ul><li>...<ul>...</ul></li></ul></ui-ul>` | ネストした `ul` を含む        | 正規入力 |

`ui-ul` は `ul` と `li` を前提とします。`ol`、`menu`、独自の `role` を持つ疑似リストを `ul` と同等には扱いません。

### 救済入力

次の入力は、互換目的で救済します。

| 入力形                                    | 内容                           | 契約                                    |
| ----------------------------------------- | ------------------------------ | --------------------------------------- |
| `<ui-ul><li>...</li></ui-ul>`             | 直下 `li` のみ                 | 救済用 `ul` を自動補完します            |
| `<ui-ul><ul>...</ul><li>...</li></ui-ul>` | root `ul` と stray `li` の混在 | stray `li` を救済用 `ul` へ再配置します |

救済入力は **正規入力と同格ではありません**。長期固定契約では、救済入力を**後方互換のための限定的な受理経路**として位置づけます。したがって、新規実装は救済入力に依存しないことを推奨します（SHOULD NOT）。

### 契約違反入力

次の入力は、本コンポーネントの契約対象外です。

- 直下に複数の root `ul` を置く入力
- `div`、`p`、カスタム要素などの一般要素を自動的に箇条書き化することを期待する入力
- `ul` / `li` 以外の要素へ list semantics の自動昇格を期待する入力

契約違反入力に対して、`ui-ul` は **fail-soft** に振る舞います。すなわち、**追加の構造補正、一般要素の包み替え、意味論の自動昇格を行いません**。また、視覚契約および意味論補強も保証しません。利用者は契約違反入力の結果に依存してはなりません（MUST NOT）。

### 入力正規化契約

`ui-ul` は、受理した Light DOM をそのまま透過するのではなく、**順序なしリストとして意味が成立する最小限の正規化**を行います。

- 正規化対象は stray `li` のみです。
- 直下の `ul` は root list として扱います。
- 直下の一般要素は自動的に `ul` へ包み替えません。
- テキストノードやコメントノードは list semantics の補強対象外です。
- 一般要素の意味昇格は行いません。
- 救済用 `ul` を生成する場合、救済対象 `li` の**相対順序は保持**します。
- 救済用 `ul` の挿入位置は、**最初の救済対象 `li` が存在した位置**を基準とします。
- 正規化は、**構造成立のために必要な最小差分**に限定します。

したがって、`ui-ul` は「任意の子要素をよしなに箇条書き化するコンテナ」ではありません。

### 公開 property / attribute

現行契約において、利用者向けの公開 property / attribute は定義しません。

| 名前 | 種別 | 契約                                                 |
| ---- | ---- | ---------------------------------------------------- |
| なし | -    | 公開設定面は Light DOM 構造と CSS トークンが中心です |

未定義の属性、内部状態 class、内部 style 実装に依存してはなりません（MUST NOT）。

### スロット契約

| 名前         | 種別 | 内容                                                     |
| ------------ | ---- | -------------------------------------------------------- |
| 既定スロット | slot | `ul`、`li`、およびその配下の通常コンテンツを受け取ります |

名前付きスロットは公開しません。

### 構造補正契約

#### 1. root `ul` の自動補完

直下に `li` が存在し、かつ root `ul` が存在しない場合、`ui-ul` は救済用 `<ul>` を生成し、直下 `li` をそこへ移動します。

#### 2. stray `li` の救済

既存の root `ul` があり、直下に stray `li` が混在する場合、stray `li` 群は新たに生成した救済用 `<ul>` に再配置されます。既存の `ul` は維持されます。救済用 `<ul>` は、**最初の stray `li` が存在した位置**へ挿入し、救済対象 `li` の相対順序を保持します。

#### 3. 複数の root `ul` の不採用

直下に複数の root `ul` が存在する構造は、長期固定契約では採用しません。単一の論理リストを表す部品として、`ui-ul` は単一の root `ul` を前提とします。

#### 4. ネスト構造の意味論補強

root `ul` と、その配下にあるネスト `ul` に対して、`role` 属性が未指定であれば `role="list"` を付与します。各 `li` に対しても、`role` 属性が未指定であれば `role="listitem"` を付与します。

#### 5. 利用者指定 role の尊重

`ui-ul` は `role` を無条件に上書きしません。既に `role` を持つ `ul` / `li` に対しては、その値を尊重します。

### Light DOM 変異契約

`ui-ul` は構造補正の過程で、**利用者が渡した既存ノードを移動する**ことがあります。この変異は公開契約として固定します。

- stray `li` は、新規生成した `ul` の子へ**再配置**されます。
- `li` ノードは複製しません。
- ノード同一性は維持されます。
- 既存の属性、`dataset`、イベントリスナー、参照保持は維持されます。
- `parentNode` / `parentElement` は変化し得ます。
- stray `li` 群の相対順序は保持されます。
- 契約違反入力に対しては、追加の DOM 正規化を行いません。
- 正規化は**冪等**であることを必須契約とします。

### 更新タイミング契約

意味論補強は、次の契機で同期されます。

- `connectedCallback()` 実行時
- 既定スロットで `slotchange` が発火した時
- `MutationObserver` が Light DOM の**構造変化**を検知した時

本契約が強く保証するのは、**初期接続時の同期**です。動的更新に対する再同期は補助機構であり、利用者が DOM 変化を加えた直後に同一タスク内で結果を観測できることまでは保証しません。動的更新後の確認は、少なくとも次フレーム以降で行うものとします。

ここでいう構造変化とは、`ul` / `li` の追加、削除、再親子付けのような **childList 中心の変化** を指します。テキストノード内容の変更、スタイル変更、意味論に無関係な属性変更は、再同期の第一級対象に含めません。

また、長期固定契約では `refresh()` などの**公開再同期 API は提供しません**。強い同期要求を持つ利用形態は、本コンポーネントの対象外です。

### 公開メソッド

現行契約では、利用者向けの公開メソッドを定義しません。

| 名前 | 種別 | 契約                               |
| ---- | ---- | ---------------------------------- |
| なし | -    | ホストは構造コンテナとして扱います |

### 責務範囲

責務範囲には、次を含みます。

- 単一の root `ul` の受理
- 救済入力に対する最小限の構造補正
- ネスト `ul` を含む意味論補強
- 読書向けの局所的なマーカー階層と行間リズムの統一

一方で、次は責務に含めません。

- `.prose ul` のようなグローバル typography 初期化
- `ol` との共通抽象化
- 一般要素の自動箇条書き化
- 高頻度編集用途の強い同期保証
- リンクやボタンの十分なヒット領域保証
- リスト項目内インタラクティブ要素のイベント制御

## 状態モデル

`ui-ul` の状態は、内部状態遷移ではなく、**入力がどのように正規化され、意味論補強され、局所的な視覚契約が適用されるか**によって読みます。

### 1. 基本状態

最小状態は、`<ui-ul><ul><li>...</li></ul></ui-ul>` です。この状態では、root `ul` に `role="list"`、各 `li` に `role="listitem"` が補強され、Level 1 のマーカーとして `•` を使用します。

### 2. 救済状態

直下に `li` のみが存在する場合、`ui-ul` は救済用 `ul` を生成し、意味的に妥当なリスト構造へ補正します。

### 3. ネスト状態

ネストした `ul` は階層に応じてマーカーを切り替えます。

| 階層         | マーカー |
| ------------ | -------- |
| Level 1      | `•`      |
| Level 2      | `◦`      |
| Level 3      | `▪`      |
| Level 4 以降 | `▪`      |

3 階層目以降は差分を増やさず、読書ノイズの抑制を優先します。

### 4. 動的更新状態

Light DOM が後から更新された場合、軽微な変更に対しては `MutationObserver` により再同期を試みます。ただし、これは補助機構であり、高頻度編集や厳密な同期保証を意味しません。

## DOM / Accessibility

ルートは `:host` です。Shadow DOM 内部にはスロットのみを持ち、実際のリスト構造は Light DOM 側に存在します。

```text
<ui-ul>
  #shadow-root
    <slot></slot>
  <ul role="list">
    <li role="listitem">...</li>
  </ul>
</ui-ul>
```

### DOM 契約

- `:host` は `display: block` です。
- root list は Light DOM に存在します。
- ネストした `ul` も Light DOM に存在します。
- Shadow DOM は、構造透過と `slotchange` 監視のためにのみ用います。
- 局所スタイルは `ui-ul` 自身のリスト構造を対象とします。

### Accessibility 契約

- `list-style: none` を採用しても、`role="list"` / `role="listitem"` を補強して意味を維持します。
- `role` は未指定時のみ補強し、利用者が明示した role は尊重します。
- ネストした `ul` に対しても同じ契約を適用します。
- `ui-ul` は semantic HTML を前提とし、ARIA をネイティブ意味論の代替として拡張しません。

本コンポーネントで重要なのは、**見た目だけのマーカー表現ではなく、箇条書きとしての意味論を失わないこと**です。

## Visual Contract

`ui-ul` の視覚契約は、マーカーを強調して目立たせることではなく、**本文の読書リズムを壊さずに、箇条書きの階層だけを静かに読ませること**にあります。

### 情報順位

- 主役は常に各 `li` の本文です。
- マーカーは構造信号であり、本文より強く主張しません。
- ネストは、インデントと最小限のマーカー差分で示します。

### 内容モデル

`li` は、**本文を担う内容塊**を中心に、その後続として必要に応じて nested `ul` を持てるものとします。

本文を担う内容塊には、たとえば次を含みます。

- 単一のテキストフロー
- インライン主体の内容
- 1 つ以上の段落やブロック要素
- リンクやボタンを含む内容

長期固定契約として第一級で想定するのは、**本文が明確で、箇条書きとして自然に読める構成**です。`li` 内に複数の段落、補足、補助要素が含まれること自体は契約違反ではありません。ただし、そのような複合内容は、単純な一行項目よりもレイアウト差が出やすいため、視覚整形上の最適化対象としては優先度を下げます。

そのうえで、複合内容を含む場合でも、**マーカーと本文の上端整列、複数行本文の縦リズム、nested `ul` を含む際の段間整合**は、読書文脈を損なわない範囲で維持することを優先します。

複合内容で安定した見た目が必要な場合は、`li` 内にラッパー要素を置き、その中へ内容を集約する構成を推奨します（SHOULD）。

### レイアウト

root `ul` は、長期固定契約でも**ネイティブのインデントと上下余白をリセットした読書向けの素体**として扱います。したがって、`list-style` だけでなく、root `ul` 自体の `padding` / `margin` も 0 を基本とします。

各 `li` は `grid` で構成し、マーカー列と本文列を分離します。ここで重要なのは、**マーカーを独立した構造信号として扱い、本文を常に主役に保つこと**です。

| 要素        | 契約                                                       |
| ----------- | ---------------------------------------------------------- |
| root `ul`   | `list-style: none; padding: 0; margin: 0`                  |
| `li`        | `display: grid`                                            |
| 列構成      | `grid-template-columns: var(--space-4) 1fr`                |
| 列間隔      | `gap: var(--space-2)`                                      |
| 垂直整列    | `align-items: start`                                       |
| 項目間隔    | 隣接する `li` の `margin-block-start: var(--space-2)`      |
| nested `ul` | `grid-column: 2` かつ `margin-block-start: var(--space-2)` |

複数行本文、補足要素、nested `ul` を含む場合でも、**本文先頭位置の視覚整列、項目間の縦リズム、ネスト開始位置の自然さ**を優先します。これらは公開 API の追加対象ではなく、既存レイアウト契約の内部品質として扱います。

### マーカー体系

- Level 1 は `•`
- Level 2 は `◦`
- Level 3 以降は `▪`
- マーカー色は `--fg-muted` を参照します

マーカーは、**情報量を増やす符号ではなく、深さの存在を静かに示す補助記号**です。3 階層目以降で差分を増やさないのは、階層識別よりも読書ノイズの抑制を優先するためです。

### インタラクティブ要素

`ui-ul` は、リンクやボタンの usability を主責務として保証しません。必要に応じて補助ヒット領域を付与しても、それは**副次的な補助**であり、本コンポーネント単体で十分なタッチターゲットを完結保証するものではありません。

したがって、インタラクティブ要素の十分なヒット領域、フォーカス設計、操作性保証は、それぞれの要素自身の契約で担うものとします。

### トークン依存契約

本コンポーネントは、次のトークン群に依存します。

| 種別                   | 用途                   | トークン              | 契約                                           |
| ---------------------- | ---------------------- | --------------------- | ---------------------------------------------- |
| Required               | マーカー列幅           | `--space-4`           | 未定義時は列幅が設計意図どおりに成立しません   |
| Required               | 項目間隔               | `--space-2`           | 未定義時は縦リズムとネスト間隔が不定になります |
| Required               | マーカー色             | `--fg-muted`          | 未定義時は情報順位が崩れ得ます                 |
| Optional with fallback | 補助ヒット領域最小寸法 | `--control-min-touch` | 未定義時は既定フォールバックを用います         |
| Optional with fallback | 補助対象要素の最小高さ | `--control-height-sm` | 未定義時は既定フォールバックを用います         |

したがって、`--space-2`、`--space-4`、`--fg-muted` は、テーマ側で供給することを推奨します（SHOULD）。

長期固定契約では、**`ui-ul` 固有のトークン名前空間は導入しません**。必要な調整は共通トークンで吸収し、固有トークンの追加は別途の破壊的契約変更として扱います。

## 環境別の振る舞い

### Forced Colors

`@media (forced-colors: active)` では、マーカー色を `CanvasText` に切り替え、`forced-color-adjust: auto` を指定します。高コントラスト環境での可視性維持を優先します。

### Dark Mode

ダークモード専用の分岐は持ちません。色は `--fg-muted` のようなセマンティックトークンを通じて追従します。

### Print

印刷時には、**箇条書きとしての可読性が崩れないこと**を優先します。少なくとも次を満たすことを長期固定契約に含めます。

- マーカーが印刷時にも視認可能であること
- インデントと項目間隔が崩れないこと
- nested `ul` を含む場合でも階層が読めること
- 画面向けの補助的なインタラクティブ表現が印刷可読性を妨げないこと

印刷時契約は、画面契約とは別の見た目バリアントを導入することではなく、**読書文脈の延長として破綻を防ぐ**ことを目的とします。

### SSR / 非ブラウザ環境

長期固定契約では、次のように分離して扱います。

- **SSR 時点で保証するもの**: `ul` / `li` を前提とした構造契約
- **クライアント接続後に成立するもの**: 意味論補強、軽微変更への再同期、局所視覚整形
- **非保証事項**: `MutationObserver` 非存在環境での動的更新追随

構造意味論は SSR 時点でも壊さず、クライアント側はそれを補強する位置づけとします。

## 関連契約

### スコープ契約

本コンポーネントの視覚契約は、`ui-ul` 自身が受理した root `ul` とその descendants に限定します。`.prose ul` のような外部文脈全体へのグローバル適用は、長期固定契約には含めません。

### 監視契約

`ui-ul` は接続時に `MutationObserver` を開始し、切断時に停止できます。監視対象はホスト要素自身の `childList` および `subtree` です。

ただし、この監視は**軽微な変更への追随補助**であり、編集系用途や高頻度更新の正式基盤ではありません。

### 開発時診断契約

`ui-ul` は fail-soft を採るため、契約違反入力でも致命的に破綻しない一方、誤用が静かに残る可能性があります。そのため、**開発時に限って**、契約違反または救済入力への依存を警告してよいものとします。

診断対象の例は次のとおりです。

- 複数の root `ul`
- 直下の一般要素混在
- 救済入力の使用
- 契約違反入力への依存が疑われる構造

これは公開設定面を増やすための契約ではありません。警告の有無、文言、通知手段は実装判断に委ね、**本番時の公開 API や既定動作の分岐には持ち込みません**。

### スタイル拡張契約

`ui-ul` は `::part(...)` を公開しません。外部拡張面は CSS Custom Properties と Light DOM 構造に限定します。

## 境界条件

### 1. 正規入力

`<ui-ul><ul>...</ul></ui-ul>` は、もっとも標準的な入力です。構造補正は不要で、意味論補強と局所視覚契約のみが入ります。

### 2. 直下に `li` のみが存在する場合

`<ui-ul><li>...</li></ui-ul>` は救済入力です。`ui-ul` は救済用 `ul` を生成し、直下 `li` を移送します。

### 3. root `ul` と stray `li` が混在する場合

既存の root `ul` と stray `li` が混在する場合、stray `li` のための新しい `ul` を生成します。既存の `ul` を壊して統合しません。

### 4. 直下に一般要素が存在する場合

`div`、`p`、カスタム要素など、直下の一般要素は自動包み替えの対象外です。これらはホスト直下の兄弟ノードとして残り、list semantics およびリスト向け視覚契約の対象外です。

### 5. 複数の root `ul`

直下に複数の root `ul` を置く構造は契約違反入力です。長期固定契約では採用しません。

### 6. 深いネスト

4 階層目以降も描画は継続しますが、マーカーは `▪` で固定されます。階層ごとに無限に異なるマーカーを増やしません。

### 7. 動的追加

初期描画後に `li` や nested `ul` が追加された場合も、軽微変更であれば次フレーム以降の同期で `role` 補強が入り得ます。ただし、追加直後の同一タスク内で補強済みであることまでは保証しません。

### 8. 利用者指定 role

利用者が `role` を明示した場合、`ui-ul` はそれを上書きしません。不適切な role を自動修正する契約も持ちません。

## Storybook 契約

Storybook は見本集ではなく、**公開契約の確認手段**として扱います。長期固定契約に対して継続的に確認すべき観点は、少なくとも次のとおりです。

- 単一の root `ul` に対して `role="list"`、各 `li` に対して `role="listitem"` が補強されること
- ネスト階層に応じてマーカー体系が維持されること
- 直下 `li` 入力で救済用 `ul` の自動補完が成立すること
- stray `li` が複製ではなく再配置として救済されること
- 一般要素は自動箇条書き化されないこと
- 契約違反入力では fail-soft に振る舞い、追加の正規化を行わないこと
- forced-colors と共通トークン依存が定義どおりに機能すること
- マーカー色がセマンティックトークンを通じて追従すること
- 印刷時にマーカー、インデント、項目間隔、ネスト階層の可読性が維持されること

個別の Story 名や Story 構成は固定契約ではありません。Storybook 側の整理や再編があっても、上記の検証観点が維持されていれば契約整合は保たれます。

なお、現行 Storybook に含まれる実装固有の確認点は、公開契約そのものとは区別して扱います。実装依存の確認点は、将来の実装変更に応じて見直し得ます。

### 現行 Storybook で検証済みだが長期固定契約には採っていない項目

現行 Storybook には、長期固定契約には採っていないものの、現実装固有の挙動として検証されている項目があります。

- `ScopeIsolation`: `.prose ul` に適用され、通常の `ul` には漏れないこと
- `MediaAndTokenContracts`: ドキュメント style 注入と単一 style tag ID に依存すること

これらは**現実装の確認点**ではありますが、長期固定契約として将来も維持することを意味しません。

## 補足

`ui-ul` の要点は、`ul` を別の見た目へ置き換えることではありません。**順序なしリストの意味を維持したまま、読書面での箇条書きの視覚秩序を静かに整えること**にあります。

今後の変更でも、次の 4 点は崩さない方がよいです。

1. 単一の root `ul` を正規入力とすること。
2. `list-style: none` と意味論補強を対にすること。
3. 一般要素の自動箇条書き化を行わないこと。
4. 深いネストで装飾を増やしすぎず、本文優先を維持すること。

## 長期固定契約に対する現行実装との差分

本節は、**本書で定義した長期固定契約**と現行実装との差分を整理するものです。ここに挙げる項目は、現時点では実装または Storybook 側に残っている差分であり、将来的には契約と整合するよう見直されることを想定します。

### 1. `.prose ul` へのグローバル適用

現行実装は `ui-ul > ul` だけでなく `.prose ul` にもスタイルを適用します。長期固定契約では、これは `ui-ul` の主責務から外しています。

### 2. 複数の root `ul` の受理

現行実装は直下の複数 `ul` を処理できますが、長期固定契約では複数の root `ul` を正規入力として採用しません。

### 3. インタラクティブ要素への配慮の扱い

現行実装はリンクやボタンへの補助ヒット領域を比較的強く持ちますが、長期固定契約ではこれを副次責務へ下げています。

### 4. style 注入の責務

現行実装はドキュメント単位の style 注入を行いますが、長期固定契約ではページ全体へのグローバル初期化を `ui-ul` の責務から外しています。

### 5. style 注入ライフサイクル

現行実装は固定 ID `ui-ul-document-styles` を用いて style を一度だけ注入し、以後は再注入しません。また、最後の `ui-ul` が破棄されても style を回収しません。長期固定契約では、このような**グローバル singleton style の寿命管理**を `ui-ul` の責務として採っていません。

### 6. `li` の垂直整列

現行実装の CSS は `align-items: center` を採っていますが、長期固定契約では読書文脈と複数行本文への整合を優先して `align-items: start` を採っています。したがって、現実装は長期固定契約ほどには上端整列へ寄っていません。

### 7. セレクタ適用範囲の広さ

現行実装のセレクタは `ui-ul li` や `ui-ul li ul` を用いるため、`ui-ul` 配下であれば、長期固定契約が第一級対象としない構造にもスタイルが及ぶ可能性があります。特に、`li` 配下の `ol` や契約違反入力由来の構造に対しても、視覚契約が部分的に作用し得ます。長期固定契約では、こうした**広めのセレクタによる副作用**を前提にしません。

### 8. Storybook の契約分類

現行 Storybook は主要契約を広くカバーしていますが、正規入力、救済入力、契約違反入力、副次責務を分けた構成にはまだなっていません。

### 9. 44 px 表現との整合

インタラクティブ要素に関する Storybook 文言と実測条件には差があります。長期固定契約では、`ui-ul` 単体による十分なヒット領域保証を採りません。したがって、Storybook の説明文は「副次的補助」に整合する表現へ修正する必要があります。

### 10. 印刷契約の未実装・未検証

長期固定契約では Print を正式に採用し、印刷時にもマーカー、インデント、項目間隔、ネスト階層の可読性維持を求めています。しかし現行実装には `@media print` の明示的な調整がなく、現行 Storybook にも印刷契約を直接検証する確認点がありません。したがって、印刷契約は現時点では長期固定契約に対して未実装または未実証です。

### 11. 契約違反入力に対する補正の残存

長期固定契約では、契約違反入力に対して追加の構造補正を行わず fail-soft に留めます。しかし現行実装の `_ensureRootList()` は、既に root `ul` が存在する場合や複数の root `ul` が存在する場合でも、直下 `li` があれば救済用 `ul` を生成して移送します。したがって、現行実装は一部の契約違反入力に対しても構造補正を行っており、fail-soft 原則より強い正規化が残っています。

### 12. 実装追随の優先順位

実装を長期固定契約へ寄せる場合、優先順位は次の順が望ましいです。

1. `.prose ul` へのグローバル責務の分離
2. セレクタ適用範囲の縮小と `align-items` の整合
3. 複数の root `ul` の扱い整理
4. Storybook の契約分類再編
5. インタラクティブ要素への配慮の責務縮退
6. style 注入戦略の再設計

### 13. 本節の扱い

本節に記載した差分は、利用者が現行実装へ依存してよい公開契約ではありません。実装、Storybook、契約書の 3 点を同時に更新することで、初めて長期固定契約として確定します。
