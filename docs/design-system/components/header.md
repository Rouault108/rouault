# Header

## 概要

本書は、`ui-header` の公開契約、状態モデル、アクセシビリティ、および視覚契約を整理するものです。

`ui-header` は、アプリケーションシェル上部に配置するヘッダーコンポーネントです。単にヘッダーらしい見た目を描画するのではなく、**アプリ全体のナビゲーション開始点をどこに置くか**、**文脈表示をどの位置に固定するか**、**`sidebarExpanded` という現名称の layout 同期入力を start 幅予約へどう反映するか**、**その状態変化をどのイベント面で通知するか**を公開契約として固定します。

また、`ui-header` は `display: contents` により外側のアプリシェルレイアウトへ透過的に参加します。そのため、本コンポーネントの契約は、単体の箱として完結することよりも、**アプリシェル内での位置づけを崩さないこと**を優先します。

Rouault における header は、本文を主役とする読書体験を妨げずに、**移動、文脈把握、補助操作**だけを静かに支える必要があります。したがって、本コンポーネントの契約は、存在感を過剰に高めることではなく、**「没入して読む」ことのできるデザイン**を保ちながらアプリシェルの秩序を維持する方向で定義します。

### 本書における強度表現

本書では、強度表現を次の意味で統一します。

- **MUST / MUST NOT**: 互換性、成立条件、責務境界の維持に必須の規則です。
- **SHOULD / SHOULD NOT**: 推奨構成または優先度の高い運用規則です。正当な理由がある場合に限り逸脱し得ますが、既定の判断としては採りません。

## 公開契約

`ui-header` は、`sidebarExpanded` を唯一の公開状態入力として扱います。あわせて、`start`、`center`、`end` の 3 スロットを公開入力面として持ちます。内部実装はネイティブ `<header>` を持つ Shadow DOM 構造ですが、利用者は `ui-header` を**アプリシェルの上部レイアウト単位**として扱います。

`sidebarExpanded` の既定値は `true` です。`true` の場合、start ゾーンは `--sidebar-width` 分の幅を予約します。`false` の場合、start ゾーンは内容幅まで縮退します。ここで変化するのは**ヘッダー内のレイアウト予約**であり、サイドバー本体の開閉そのものではありません。

本書では、`sidebarExpanded` を**互換のために維持されている現名称**として扱います。意味上は「サイドバー本体状態」ではなく、**start ゾーンを sidebar 列へ同期させる layout 入力**です。利用者は、この入力をサイドバー状態機械の代表値として扱ってはなりません（MUST NOT）。

`ui-header` は `sidebarExpanded` の変化時に `ui-header-sidebar-toggle` イベントを発火します。ただし、このイベントは**利用者による変更要求イベントではなく、反映済み状態の通知イベント**です。コンポーネント内部にトグル UI は含まず、状態のソースオブトゥルースは外部にあります。

### 入力契約

| 名前              | 種別                                      | 必須   | 内容                                              | 契約                                                                                                 |
| ----------------- | ----------------------------------------- | ------ | ------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `sidebarExpanded` | property / attribute (`sidebar-expanded`) | いいえ | start ゾーンを sidebar 列へ同期させる layout 入力 | `true` の場合は `--sidebar-width` を予約し、`false` の場合は内容幅へ縮退します。既定値は `true` です |

### `sidebarExpanded` の解釈契約

`sidebarExpanded` は現名称としては sidebar 状態を連想させますが、公開契約上の意味は **layout 同期入力**です。したがって、次を固定します。

- `sidebarExpanded` はサイドバー本体の source of truth ではありません。
- `sidebarExpanded` は start ゾーンの予約幅を切り替える入力です。
- `sidebarExpanded=true` は「sidebar が開いている」ことを一般化して表しません。
- sidebar 側に overlay、rail、collapsed、hidden など複数モードが存在しても、header はそれらを解釈しません。

利用者は、sidebar 側の複数状態を `sidebarExpanded` へ安易に射影して意味を増やしてはなりません（MUST NOT）。必要であれば、上位レイヤで別の layout 状態へ正規化してから header へ渡さなければなりません（MUST）。

### スロット契約

| 名前     | 種別       | 位置づけ             | 内容                                                     |
| -------- | ---------- | -------------------- | -------------------------------------------------------- |
| `start`  | named slot | ナビゲーション開始点 | サイドバートグル、セクション切替、ロゴなどを受け取ります |
| `center` | named slot | 文脈表示             | パンくずリスト、ページ文脈、現在地表示などを受け取ります |
| `end`    | named slot | 補助操作             | 検索、テーマ切替、補助アクションなどを受け取ります       |

3 スロットはいずれも任意です。空であってもコンポーネントは描画を継続します。

`start` と `end` は、単一要素の直接 slot assignment に限定しません。複数要素を束ねる wrapper を slot root として与えてかまいません。現行 Story もこの構成を用います。一方で、header は wrapper 内部の意味論やアクセシビリティを正規化しません。

header は単一行・固定高さのレイアウトとして扱います。`block-size` は `--header-height` に固定され、スロット内容に応じて自動伸長しません。したがって、利用者は start / center / end のいずれについても、多行化、縦方向拡張、固定高さを前提にしない内容を持ち込むべきではありません（SHOULD NOT）。内容の折り返し、切り詰め、省略はスロット内容側で制御しなければなりません（MUST）。

`center` スロットは視覚的中央に固定するため、内部では絶対配置されます。したがって、**start / end の内容量に応じて自動的に衝突回避する契約は持ちません**。必要な場合は、`--ui-header-center-start-inset` および `--ui-header-center-end-inset` によって利用側が調整しなければなりません（MUST）。

### start / center / end の禁止事項

各スロットは、単に左右中央へ内容を置くための空き領域ではありません。`ui-header` は 3 スロットの意味秩序を公開契約として持ちます。利用者は、次の禁止事項を守らなければなりません（MUST）。

- `start` に primary CTA、常設入力フォーム、大きな検索入力、長文説明を置いてはなりません。
- `center` に主操作群、複数ボタン列、編集可能入力、複数行前提の内容を置いてはなりません。
- `end` に主要ナビゲーションの主系列、長大な文脈表示、ページ本文の要約を置いてはなりません。
- いずれのスロットにも、固定高さと単一行前提を壊す縦長コンテンツを常設してはなりません。
- header 全体を「何でも置ける横一列」として利用してはなりません。

推奨配置は次のとおりです。

- `start`: ナビゲーション開始点、サイドバートリガー、ロゴ、文脈切替
- `center`: パンくず、現在地、軽い文脈ラベル
- `end`: 検索トリガー、テーマ切替、補助アクション

### center スロット内容契約

`center` は、文脈表示を静かに載せるためのスロットです。本文理解を補助する情報を置く場所であり、主操作群を常設する場所としては設計しません。

利用者は、次の制約を前提に `center` を使用します。

- `center` には、直接 slot assignment される単一の根要素を置くことを基本とするべきです（SHOULD）。
- `center` の内容は 1 行で収まる密度に保たなければなりません（MUST）。
- 長大なタイトル列、複数ボタン列、複数行折り返しを前提とした内容は置いてはなりません（MUST NOT）。
- 狭幅で非表示になっては困る重要操作は置いてはなりません（MUST NOT）。
- 内容が長い場合の省略、truncate、短縮表示はスロット内容側で解決しなければなりません（MUST）。

現行契約では、`center` の幅上限、折り返し制御、左右内容との衝突解決を header 自身は肩代わりしません。`center` は**密度を抑えた文脈表示領域**として扱います。

### 公開イベント

| 名前                       | 型                                   | 発火条件                                              | 契約                                                                               |
| -------------------------- | ------------------------------------ | ----------------------------------------------------- | ---------------------------------------------------------------------------------- |
| `ui-header-sidebar-toggle` | `CustomEvent<{ expanded: boolean }>` | 初回レンダリング後に `sidebarExpanded` が変化したとき | `detail.expanded` に反映後の状態を含みます。`bubbles=false`、`composed=false` です |

このイベントは、内部ユーザー操作を起点とするトグル要求ではありません。利用側が `sidebarExpanded` を変更した結果として発火する**状態通知**です。したがって、利用者はこのイベントを「開閉ボタンが押された通知」として扱ってはなりません（MUST NOT）。

同一値への再設定では、状態変化が起こらない限りイベントは発火しません。初期値の適用時にもイベントは発火しません。

### イベント時序契約

`ui-header-sidebar-toggle` は、`sidebarExpanded` の反映後に発火する通知イベントです。要求イベントではありません。

利用者は、次の時序を前提に扱います。

- `sidebarExpanded` の新しい値がコンポーネント状態へ反映された後に発火します。
- `detail.expanded` は、発火時点での反映済み状態を表します。
- 初回描画では発火しません。
- 同一値の再設定では発火しません。
- property 経由の変更と attribute 経由の変更は、いずれも同じ意味の通知として扱います。

したがって、利用者はこのイベントを状態更新の入力契機として使うよりも、**反映結果の観測**として扱うべきです（SHOULD）。

また、利用者はこのイベントの受信を前提に `sidebarExpanded` の source of truth を header 内へ置いてはなりません（MUST NOT）。状態管理は外部が保持します。

### 公開トークン

`ui-header` は、外部から上書き可能な CSS Custom Properties として次を公開します。

| 名前                             | 既定値 | 用途                                   |
| -------------------------------- | ------ | -------------------------------------- |
| `--ui-header-backdrop-saturate`  | `0.5`  | Glassmorphism 背景の `saturate()` 強度 |
| `--ui-header-center-start-inset` | `0px`  | center ゾーンの開始側インセット        |
| `--ui-header-center-end-inset`   | `0px`  | center ゾーンの終了側インセット        |

これらは公開拡張面です。一方で、`--ui-header-edge-highlight` はコンポーネントローカルトークンであり、公開契約には含めません。

### 公開トークンの値域と無効値

公開トークンは次の値域で扱います。

| 名前                             | 想定する値型                                     | 既定動作                         | 無効値の扱い                                                           |
| -------------------------------- | ------------------------------------------------ | -------------------------------- | ---------------------------------------------------------------------- |
| `--ui-header-backdrop-saturate`  | CSS の `<number>`                                | `saturate(0.5)` として評価します | 無効値は当該宣言が無効になり、UA の CSS 評価結果に従います             |
| `--ui-header-center-start-inset` | CSS の `<length-percentage>` を含む inset 相当値 | `0px`                            | 無効値は当該宣言が無効になり、既定値または他宣言へフォールバックします |
| `--ui-header-center-end-inset`   | CSS の `<length-percentage>` を含む inset 相当値 | `0px`                            | 無効値は当該宣言が無効になり、既定値または他宣言へフォールバックします |

利用者は、`--ui-header-center-start-inset` および `--ui-header-center-end-inset` に `calc(...)` を与えてかまいません。負値も CSS としては与えられますが、header 契約としては与えるべきではありません（SHOULD NOT）。

また、無効値を与えた場合に header が独自に補正して安全値へ丸める契約は持ちません。値の妥当性は利用側が担保しなければなりません（MUST）。

### 属性反映契約

| property          | attribute          | reflect | 備考                             |
| ----------------- | ------------------ | ------- | -------------------------------- |
| `sidebarExpanded` | `sidebar-expanded` | あり    | boolean attribute として扱います |

### 公開しないもの

`ui-header` は、公開メソッドを持ちません。また、`part` 属性を公開しません。したがって、Shadow DOM 内部要素への `::part(...)` によるスタイル拡張には対応しません。

内部 class 名、Shadow DOM 内部構造の細部、zone ごとの class 名、`header` 直下の配置順序などは公開契約に含みません。利用者はこれらに依存してはなりません（MUST NOT）。

### 責務範囲

責務範囲には、sticky header の描画、3 ゾーンへのスロット配置、`sidebarExpanded` の属性反映、背景表現、レスポンシブ時の center ゾーン切替、および状態変化通知を含みます。

一方で、次の事項は責務に含めません。

- サイドバー開閉ロジックそのもの
- center と start / end の衝突自動解消
- 各スロット内容のアクセシブル名生成
- トグルボタンや検索ボタンなど個別操作の意味付け
- グローバルナビゲーション設計そのもの

## 状態モデル

`ui-header` の主要状態は、インタラクティブ状態ではなく、**レイアウト予約状態**、**表示可否状態**、**スロット充足状態**によって読み分けます。

### 1. 基本状態

最小状態は、`sidebarExpanded=true` で、必要に応じて各スロットへ内容を差し込んだ状態です。このとき、start ゾーンは `--sidebar-width` を予約し、center は視覚的中央に、end は右端に寄ります。

### 2. 展開状態

`sidebarExpanded=true` の場合、start ゾーンの `inline-size` は `var(--sidebar-width, 240px)` になります。これはサイドバー列に視覚的に揃えるための予約であり、start スロット内容そのものの幅ではありません。

### 3. 縮退状態

`sidebarExpanded=false` の場合、start ゾーンは固定幅を持たず、内容幅に縮退します。Zen Mode のように左側余白を抑えたい場面ではこの状態を用います。

### 4. center 表示状態

`center` ゾーンは、ビューポート幅が `640px` 以下のとき非表示になります。これは center スロットに要素が存在していても同様です。つまり、**center スロットの有無と center ゾーンの可視性は独立**しています。

### 5. スロット充足状態

3 スロットはいずれも空を許容します。`center` が空であっても、`start` と `end` のみでヘッダーは成立します。すべて空であっても、ヘッダー構造自体は描画されます。

### 6. 状態同期

`sidebarExpanded` は property と attribute の両面から操作できます。いずれかの面で変更された場合、他方へ反映されます。初回レンダリング時の既定値適用ではイベントを発火しません。

### 7. イベント状態

`ui-header-sidebar-toggle` は、`sidebarExpanded` が実際に変化したときにのみ発火します。連続変更時は、**有効な変化 1 回につき 1 回**発火します。同一値の再設定では発火しません。

## DOM / Accessibility

ルートは `:host` です。ホストは `display: contents` を採用し、自身のボックスを持ちません。Shadow DOM 内部には単一のネイティブ `<header>` を持ち、その内部に `.inner` と 3 つの zone を配置します。

```text
<ui-header sidebar-expanded?>
  #shadow-root
    <header>
      <div class="inner">
        <div class="zone-start">
          <slot name="start"></slot>
        </div>
        <div class="zone-center">
          <slot name="center"></slot>
        </div>
        <div class="zone-end">
          <slot name="end"></slot>
        </div>
      </div>
    </header>
</ui-header>
```

### Accessibility 契約

アクセシビリティ上の重要点は次のとおりです。

- 内部ルートはネイティブ `<header>` です。
- `ui-header` 自体はフォーカス対象ではありません。
- `ui-header` 自体はキーボード操作を持ちません。
- スクリーンリーダー上の意味付けの大半は、スロットへ渡す子要素側の責務です。
- `start`、`center`、`end` に置くインタラクティブ要素は、それぞれ自前でアクセシブル名と役割を満たさなければなりません（MUST）。

`center` ゾーンは内部コンテナに `pointer-events: none` を持ち、`slot[name='center']::slotted(*)` に対して `pointer-events: auto` を戻します。したがって、`center` スロットには**直接割り当てられる根要素**を置く前提で扱います。利用者は、`center` のインタラクティブ性を成立させる要素を direct slot assignment で与えるべきです（SHOULD）。

一方で、`start` と `end` には wrapper を介した構成を許容します。これらの zone では、header 自体が wrapper 内部のボタン群やドロップダウン群に追加の役割補正を行う契約は持ちません。

### DOM 契約

- `:host` は `display: contents` です。
- 内部の `header` が sticky 表示と背景表現の主体です。
- `part` は公開しません。
- Shadow DOM 内部 class は公開面ではありません。

したがって、利用者は `ui-header` を通常の箱モデル要素として扱って margin、background、border をホスト側へ付与する前提には依存しません。箱としての見た目は内部 `header` に存在します。

## Visual Contract

`ui-header` の視覚契約は、上部ナビゲーションを**画面上部へ静かに固定しつつ、本文より強く主張しないこと**にあります。

### レイアウト

- 内部 `header` は `position: sticky`、`top: 0` です。
- `grid-column: 1 / -1` により、アプリシェル Grid 全幅へ参加します。
- `block-size` は `var(--header-height, 48px)` です。
- `.inner` は `max-inline-size: var(--bp-xl, 1280px)` を持ち、中央寄せされます。
- `.inner` の左右パディングは `var(--space-4, 1rem)` です。
- `start` は左寄せ、`center` は視覚的中央、`end` は右寄せです。
- header は単一行レイアウトであり、内容に応じて自動で高さを増やしません。
- sticky の基準は CSS の通常規則に従い、もっとも近いスクロールコンテナまたはビューポートに対して成立します。header 自身はスクロールコンテナを所有しません。

### start / center / end の秩序

- `start` はナビゲーション開始点として左側に置きます。
- `center` はヘッダー全体に対する視覚的中央に固定します。
- `end` は補助操作群として右端に寄せます。

ここで重要なのは、`center` が **start / end の残余空間に対して中央寄せされるのではなく、ヘッダー全体に対して中央寄せされる**ことです。したがって、左右内容が大きい場合の衝突回避は自動ではありません。

### 背景表現

非対応環境では `var(--glass-panel, var(--bg-default))` を背景として使用します。`backdrop-filter` 対応環境では、`var(--bg-default)` に 0.85 の透過を与えた背景と blur / saturate を組み合わせ、Glassmorphism として描画します。

### ダークモード時のエッジ

ダークモードでは境界線色を `--ui-header-edge-highlight` へ寄せ、`backdrop-filter` 対応環境では inset shadow を強めます。これは暗背景でヘッダー境界が沈み込みすぎないようにするためです。

### モバイル時の簡素化

`640px` 以下では `center` ゾーンを非表示にします。これにより、狭幅環境では start / end の操作性を優先し、文脈表示を省略します。

### 視覚仕様上の注意

`ui-header` は強い塗り分けや大きな影で注意を奪う設計にはしません。読書面に対しては、**存在は認識できるが視線を奪いすぎない**ことを優先します。したがって、過度な装飾、常時強い発光、派手なモーションには依存しません。

## 環境別の振る舞い

### Backdrop Filter 非対応環境

`backdrop-filter` 非対応環境では blur / saturate を使わず、通常背景と境界線のみで描画します。Glassmorphism は Progressive Enhancement です。

### Dark Mode

`prefers-color-scheme: dark` 環境では、境界線と inset shadow を強め、背景境界を読み取りやすくします。色差の主調整はトークン差し替えに委ねます。

### Forced Colors

`forced-colors: active` 環境では、背景を `Canvas`、境界線を `CanvasText` に切り替え、`backdrop-filter` と box-shadow を無効化します。見た目の特殊効果より、システム色との整合を優先します。

現行実装では、補助的な境界補正は direct-slotted の `button` および `[role='button']` に対してのみ与えます。wrapper 配下の子孫要素や、他の child component 内部までは header が救済しません。

### Reduced Motion

`prefers-reduced-motion: reduce` 環境では、`header`、`.zone-start`、`.zone-end` の transition duration を極小化します。現行実装に本質的なアニメーションはほぼありませんが、将来のモーション追加に対して抑制面を先に確保しています。

### Print

印刷時は内部 `header` を非表示にします。`ui-header` は画面操作導線であり、印刷対象に含めません。

## 関連契約

### アプリシェル契約

`ui-header` は、外側のアプリシェルレイアウトへ透過的に参加するコンポーネントです。`display: contents` と `grid-column: 1 / -1` を前提としているため、**単体カードや独立パネルの汎用ヘッダー**としては設計していません。

外側に Grid がない環境でも描画自体は可能ですが、全幅参加や列整列の意味は薄れます。したがって、利用者は `ui-header` をアプリシェル文脈で使うべきです（SHOULD）。

### サイドバー契約

`sidebarExpanded` は、サイドバー状態の**反映先**ではあっても**起点**ではありません。サイドバー本体、トグルボタン、永続化、URL 同期などは別契約です。

`ui-header-sidebar-toggle` も同様に、サイドバー操作要求イベントではなく、反映済み状態の通知です。状態管理は外部が持たなければなりません（MUST）。

### center 配置契約

`center` は視覚的中央へ固定する契約です。その代わり、左右内容との衝突解決は持ち込みません。左右幅が大きいレイアウトでは、利用側が次のいずれかで調整しなければなりません（MUST）。

- center 内容の幅を抑える
- `--ui-header-center-start-inset` を与える
- `--ui-header-center-end-inset` を与える
- center 内容を狭幅時に省略または簡略化する

### スタイル拡張契約

スタイル拡張は CSS Custom Properties に限定します。`part` は公開しません。内部 class 名に依存するスタイル上書きは公開契約外です。

### 重なり順序 / オーバーレイ契約

`ui-header` は `--z-fixed` によって通常本文より前面に表示される固定ヘッダーです。ただし、本コンポーネントはアプリケーション全体の最前面レイヤを占有するためのものではありません。

したがって、次を契約とします。

- `ui-header` は通常の本文、背景、サイドバー本文より前面に表示されてよいです。
- modal、dialog、global overlay、popover layer など、明確に一時前景として設計されたレイヤより前面に出ることを前提にしません。
- `ui-header` 自身は overlay の stacking policy を管理しません。
- `--z-fixed` の上書きは可能ですが、アプリ全体のレイヤ秩序を壊さない範囲で行わなければなりません（MUST）。

利用者は、header を常に最上位へ固定するために局所的な `z-index` 競争へ参加させる方針を採るべきではありません（SHOULD NOT）。header は固定ナビゲーション層であり、全局オーバーレイ層ではありません。

### スロット内容契約

`ui-header` は slot host であり、slot content の意味論や操作は内蔵しません。したがって、パンくず、検索トリガー、テーマボタン、ドロップダウンなどは、それぞれのコンポーネント契約に従います。

## 境界条件

### 1. `center` スロットが空

`center` が空でもヘッダーは成立します。ルートページや最上位画面ではこの構成を許容します。

### 2. 3 スロットがすべて空

すべて空でも内部 `header` と 3 zone は描画されます。これは構造上は有効ですが、実際の利用価値は限定的です。

### 3. `sidebarExpanded` の属性除去

`sidebar-expanded` 属性を除去すると `sidebarExpanded=false` へ反映され、状態通知イベントが発火します。逆に property を `true` へ戻すと属性が復活します。

### 4. 同一値の再設定

`sidebarExpanded` を同じ値へ再設定しても、イベントは重複発火しません。

### 5. 高速連続変更

`false -> true -> false` のような高速連続変更では、**有効な状態変化ごとに 1 回**イベントが発火します。

### 6. スロット内容の動的差し替え

スロット内容は動的に差し替え可能です。差し替え後も zone 構造は維持されます。

### 7. 狭幅ビューポート

`640px` 以下では `center` は非表示になります。`center` に重要操作を置く構成には依存してはなりません（MUST NOT）。

### 8. スロット内容が固定高さを超える場合

header は固定高さであり、自動伸長しません。start / center / end の内容が 1 行を超える場合や、縦方向に大きい要素を入れた場合の見え方は未定義です。利用者は、固定高さ内に収まる内容を渡さなければなりません（MUST）。

### 9. 左右内容が大きい場合

`center` は視覚的中央へ固定されるため、左右内容が大きい場合は重なり得ます。現行契約では自動解消しません。

### 10. 印刷時

どの状態であっても、印刷時は非表示です。

## 契約が不明瞭な箇所

本節は、現行の `header.ts` および `header.stories.ts` を踏まえて、**公開契約として読むと意味が揺れやすい箇所**を整理するものです。ここで挙げる項目は、単なる実装上の気付きではなく、長期運用時に利用側の依存先がぶれやすい論点を対象とします。

### 1. `sidebarExpanded` の意味

現行実装では、`sidebarExpanded` はサイドバー本体の開閉を制御しません。実際に変化するのは start ゾーンの幅予約です。したがって、名前から連想される「サイドバー状態」と、実際の「header レイアウト同期状態」の間にずれがあります。

本書では、このずれを軽微な命名差としては扱いません。`sidebarExpanded` は**意味が誤読されやすい入力名**であり、長期的には layout 意味へ寄せた命名へ移行すべき候補です。少なくとも、現名称を維持する間も、利用者が sidebar 本体状態として読まないよう強く拘束する必要があります。

### 2. `ui-header-sidebar-toggle` の意味

現行実装のイベントは、ユーザー操作要求ではなく、`sidebarExpanded` 反映後の通知です。しかし、イベント名には `toggle` が含まれており、操作起点イベントにも読めます。

このままでは、利用者が「header 内部のトグル操作通知」と誤読しやすく、状態管理責務の位置が曖昧になります。

### 3. イベントの公開範囲

現行イベントは `bubbles=false`、`composed=false` です。つまり、host を直接参照する利用者には観測しやすい一方で、アプリ全体へ自然伝播する境界イベントではありません。

この局所性が意図された契約なのか、実装上たまたまそうなっているだけなのかは、現行文書だけでは十分に強く固定されていません。

### 4. `ui-header` の適用文脈

`display: contents` と `grid-column: 1 / -1` を採用しているため、実体は app-shell 参加用の header です。しかし、コンポーネント名だけを見ると汎用 header のようにも読めます。

このままでは、カード、セクション、記事内 header としての流用を誘発し、意図しない layout 依存を持ち込みやすくなります。

### 5. `center` の幾何契約

`center` は start / end の残余空間中央ではなく、header 全体に対する視覚的中央へ固定されます。この方針自体は明確ですが、左右内容との衝突を誰が解消するのかが、なお利用者にとって自明とはいえません。

`--ui-header-center-start-inset` と `--ui-header-center-end-inset` は存在しますが、どの場面で誰が算出するかまでは現行契約で固定していません。

### 6. `center` に置ける内容の密度

現行文書では `center` を文脈表示領域としていますが、どこまでの長さ、複雑さ、操作密度を許容するかはまだ抽象的です。

このままでは、パンくず、長いタイトル、検索入力、ボタン列、タブなどが段階的に流入し、`center` の役割が肥大化しやすくなります。

### 7. `start` / `center` / `end` の禁止事項

各スロットの意味はおおむね定義されていますが、置いてはならないものの境界はまだ弱いです。

特に、header を「なんでも置ける横一列」として扱い始めると、意味秩序が崩れ、読書体験に対する静かな補助面という性質を失いやすくなります。

### 8. slot root と wrapper の扱い

実利用では `div slot="start"` のような wrapper を使う構成と、`center` へ直接要素を割り当てる構成が混在し得ます。しかし、forced-colors の補正は direct-slotted `button` / `[role='button']` を前提にしています。

このため、slot 入力形と環境対応単位の整合が完全には取れていません。

### 9. ランドマーク契約

内部はネイティブ `<header>` ですが、これをアプリ全体で 1 個の top-level header として扱うのか、複数配置も許容するのかは明示度がまだ不足しています。

アクセシビリティ上は、この点を曖昧にすると landmark 秩序が崩れやすくなります。

### 10. breakpoint の所有者

`center` 非表示は `640px` 固定値で定義されています。これは現行実装としては十分に動作しますが、アプリ全体の responsive policy と header 個別ルールの境界はまだ曖昧です。

将来 breakpoint を再編した場合、header のみが独自値で残ると整合を崩しやすくなります。

### 11. 公開トークン境界

header 固有の公開トークンは限定的ですが、実際には foundation token へ広く依存します。どこまでを header 固有契約として安定保証し、どこからをアプリ全体の基盤依存とみなすかは、今後さらに明確化する余地があります。

### 12. Reduced Motion の意味

Reduced Motion への配慮はありますが、header 自体は本質的なモーションをほとんど持ちません。このため、現行の reduced-motion 契約は「将来追加への予防線」としての意味が強く、現在の実質的差分は限定的です。

### 13. Forced Colors の責務範囲

header 自身が forced-colors 環境でどこまで child content を救済するかは、まだ厳密には固定していません。container レベルまでを見るのか、子コンポーネント側契約へ委ねるのかの責務境界が曖昧です。

### 14. z-index / overlay の序列

`ui-header` は固定ヘッダーとして前面に出ますが、dialog、popover、scrim、global overlay などとの厳密な序列は、header 単独の契約としてはまだ不十分です。

これは header だけで閉じず、アプリ全体の layer policy と接続して定義する必要があります。

### 15. 空の header を有効入力として許すか

実装上は 3 スロットすべて空でも成立します。しかし、構造上 valid であることと、設計上 meaningful であることは別です。

空のまま正式に許すか、最低限どこか 1 ゾーンの存在を期待するかは、設計規律としてまだ固定し切っていません。

### 16. Story の位置づけ

現行 Story は契約確認にかなり寄っていますが、すべてが同じ強度の公開契約試験であるわけではありません。契約試験、視覚回帰、参考使用例が混在しています。

この区別を曖昧なままにすると、どこまでが公開契約として守るべきものかが読み取りにくくなります。

## 長期方針

本節は、前節で列挙した曖昧点を、**設計のきれいさと保守性を優先してどの方向へ固定するか**を示すものです。現行実装の都合に引きずられず、長期的に責務境界が明確になる方針を優先します。

本節では、各方針を **MUST / MUST NOT / SHOULD / SHOULD NOT** の強度付きで記述します。

### 最優先で固定する方針

#### 1. `sidebarExpanded` を layout 同期契約として扱う

- **MUST**: `sidebarExpanded` は、サイドバー本体状態の代理ではなく、header 側の幅予約状態として扱わなければなりません。
- **SHOULD**: 長期的には、`startReserved`、`alignStartToSidebar`、`startReserveMode` のような layout 指向名へ改めるべきです。
- **MUST NOT**: 移行期間中であっても、`sidebarExpanded` を sidebar 本体状態として読んではなりません。
- **MUST NOT**: header は sidebar の状態機械を内包してはなりません。

#### 2. イベントを通知イベントへ限定する

- **MUST**: `ui-header-sidebar-toggle` は、操作要求イベントではなく反映後通知として扱わなければなりません。
- **SHOULD**: 可能であれば、header 自体のイベント責務をさらに薄くし、操作要求は start スロット内の個別トリガー部品へ分離するべきです。
- **SHOULD**: header は layout host に留まるべきです。

#### 3. `ui-header` を app-shell 専用部品として固定する

- **MUST**: `ui-header` は、app-shell 上端に置く専用部品として扱わなければなりません。
- **MUST NOT**: `ui-header` を汎用 header として広く流用してはなりません。
- **SHOULD**: カードや記事内セクションに局所 header が必要な場合は、別コンポーネントとして定義するべきです。

#### 4. `center` は視覚的中央固定、衝突解決は利用側責務に固定する

- **MUST**: `center` は、残余空間中央ではなく、header 全体に対する視覚的中央として扱わなければなりません。
- **MUST NOT**: 衝突自動解消を header の責務へ取り込んではなりません。
- **MUST**: 利用側は、`center` 内容の短縮、inset 付与、狭幅時の簡略化または非表示によって調整しなければなりません。
- **SHOULD**: header 自体を過度に賢くしない責務分離を優先するべきです。

#### 5. landmark を top-level header 専用として固定する

- **MUST**: `ui-header` は、アプリ全体で 1 個の top-level header を構成する前提で扱わなければなりません。
- **SHOULD NOT**: 複数配置を一般化するべきではありません。
- **SHOULD**: landmark 秩序の安定を優先するべきです。

### 次に固定する方針

#### 6. `center` は低密度な文脈表示専用とする

- **SHOULD**: `center` には、パンくず、現在地、軽い文脈ラベルなど、受動的かつ低密度な情報のみを置くべきです。
- **SHOULD NOT**: 長大タイトルの常設、多数の操作ボタン列、検索入力本体、複数行前提の内容を置くべきではありません。
- **MUST NOT**: 狭幅で失われては困る主操作を置いてはなりません。

#### 7. `start` / `center` / `end` の禁止事項を規範として固定する

- **MUST**: `start` はナビゲーション開始点と文脈切替に限定しなければなりません。
- **MUST NOT**: `start` に primary CTA、常設入力フォーム、長文説明を置いてはなりません。
- **MUST**: `center` は文脈表示に限定しなければなりません。
- **MUST NOT**: `center` に主操作群、複数ボタン列、編集可能入力、複数行前提の内容を置いてはなりません。
- **MUST**: `end` は補助操作に限定しなければなりません。
- **MUST NOT**: `end` に主要ナビゲーションの主系列や長大な文脈表示を置いてはなりません。
- **MUST NOT**: header 全体として、primary CTA や大きな入力フォームを常設してはなりません。

#### 8. slot wrapper を許容するなら、環境対応も wrapper 前提へ寄せる

- **MUST**: slot 入力として wrapper を現実的に許容する場合は、forced-colors 補正の責務単位もそれに合わせて整理しなければなりません。
- **SHOULD**: zone 単位または子コンポーネント契約へ責務を移すべきです。
- **MUST NOT**: wrapper 許容と direct slot 前提の環境対応を中途半端に併存させてはなりません。

#### 9. breakpoint は app-shell 側 policy に従属させる

- **SHOULD**: `640px` を header 私有の固定値として扱い続けるより、アプリ全体の responsive policy に接続して定義するべきです。
- **SHOULD NOT**: header 単独の breakpoint を増やすべきではありません。
- **SHOULD**: foundation または layout 契約側から与えられる形に寄せるべきです。

#### 10. token を二層に分けて整理する

- **SHOULD**: トークンは、`header public token` と `foundation dependency token` の二層に分けて記述するべきです。
- **SHOULD**: header 自身が長期安定を約束する範囲と、全体デザインシステムに従属する範囲を分離するべきです。

### 補助的に整理する方針

#### 11. Reduced Motion は「本質的 motion を持たない」ことを主軸に書く

- **SHOULD**: reduced-motion 契約は「動きを抑える」よりも、「本質的 motion を持たない」ことを主軸に書くべきです。
- **SHOULD NOT**: header をアニメーション表現の主体として扱うべきではありません。

#### 12. Forced Colors は container 責務に留める

- **SHOULD**: header は container としての背景・境界・レイアウト成立を担保するべきです。
- **SHOULD**: child content の forced-colors 最適化は、原則として各子コンポーネント契約へ委ねるべきです。
- **SHOULD NOT**: header が child content の見え方まで包括的に救済するべきではありません。

#### 13. z-index は app 全体の layer contract へ移す

- **SHOULD**: overlay 序列は、header 単独ではなく app 全体の layer policy 文書で定義するべきです。
- **MUST**: header.md では、その外部方針へ従うことだけを明記しなければなりません。
- **MUST NOT**: header 単独で overlay 序列を語り切ってはなりません。

#### 14. 空の header の扱いを設計ルールとして定める

- **SHOULD**: 実装として空を許容しても、設計ルールとしては `start` または `center` の少なくとも一方を持つことを原則にするべきです。
- **SHOULD**: これを公開契約にするか、利用ガイドに留めるかを別途定めるべきです。

#### 15. Story を 3 種に分類して維持する

- **MUST**: Story は、公開契約試験、視覚回帰確認、参考使用例の 3 種に分類して扱わなければなりません。
- **MUST**: Story を追加または削除する場合は、まずどの種別に属するかを決めたうえで配置しなければなりません。
- **SHOULD**: 公開契約試験は、property、attribute、slot、event、状態遷移などの公開面を固定するために維持するべきです。
- **SHOULD**: 視覚回帰確認は、環境差や見え方の破綻検知のために維持するべきです。
- **MUST NOT**: 参考使用例を契約試験の代替として扱ってはなりません。

### 採らない方針

- **MUST NOT**: header 内で sidebar 状態を自律管理してはなりません。
- **MUST NOT**: header 自体へ検索、テーマ、ユーザーメニュー等の具体機能を内蔵してはなりません。
- **SHOULD NOT**: `center` の自動衝突回避のために複雑な計測ロジックを安易に抱え込むべきではありません。
- **MUST NOT**: slot content の意味論やアクセシビリティを header が肩代わりしてはなりません。
- **MUST NOT**: overlay や layer policy を header 単独で支配してはなりません。

## 最優先で検討する価値がある機能

本節は、`ui-header` に新規で追加を検討する価値がある機能のうち、**責務境界を濁さず、app-shell 契約をより安定させるもの**を整理するものです。検索、メニュー、ユーザー機能などを header 本体へ抱え込む方向ではなく、既存契約の弱い部分を補強する方向だけを対象とします。

### 1. 狭幅専用の文脈表示スロット

現行契約では、`center` は狭幅で非表示になります。このため、狭幅時には文脈表示を完全に失うか、`start` / `end` へ無理に押し込むしかありません。

長期的に最も追加価値が高いのは、`center` の本契約を壊さず、狭幅時だけ簡略な文脈表示へ置き換える入力面です。たとえば、`compact-center`、`mobile-center`、`collapsed-center` のような専用スロットが候補になります。

この機能を採用する場合は、次を固定します。

- `center` は通常幅での文脈表示に限定します。
- 狭幅時は `compact-center` 系スロットで代替表示できるようにします。
- `center` と狭幅専用スロットを同時表示してはなりません（MUST NOT）。
- 狭幅専用スロットにも主操作を置いてはなりません（MUST NOT）。

この機能は、`center` を文脈表示専用に保ったまま、モバイル時の情報喪失だけを抑制できるため、設計との相性がよいです。

### 2. start 予約幅を sidebar 意味から切り離す入力

現行の `sidebarExpanded` は、実質的には start ゾーンを sidebar 幅へ揃えるかどうかの入力です。しかし、名前は sidebar 本体状態のように読めます。

このずれを長期的に解消するためには、header 側の layout 意味を直接表す入力面を検討する価値があります。たとえば、`startReserved`、`startReserveMode`、`startReservedWidth`、`alignStartToSidebar` のような入力が候補になります。

この機能を採用する場合は、次を固定します。

- header は sidebar 本体状態の代理をしてはなりません（MUST NOT）。
- start ゾーンの予約は、header 自身の layout モードとして表現しなければなりません（MUST）。
- sidebar を持たない画面でも意味が通る API にしなければなりません（MUST）。

これは新規機能というより、責務境界のきれいさを上げるための API 再編候補です。

### 3. slot 単位の表示ポリシー指定

現行では `center` の可視性が固定 breakpoint に結び付いています。これを完全自動化や計測ロジックへ進めるのではなく、単純な表示ポリシー入力として扱えると、利用側の構成自由度が上がります。

たとえば、`centerVisibility="auto | always | never"` や、狭幅時の代替表示を切り替えるポリシー入力が候補になります。

この機能を採用する場合は、次を固定します。

- 表示ポリシーは slot 可視性の切り替えに限定しなければなりません（MUST）。
- 自動衝突回避や複雑なレイアウト計測までは持ち込むべきではありません（SHOULD NOT）。
- foundation または app-shell の responsive policy と矛盾しない範囲で運用しなければなりません（MUST）。

この機能は有用ですが、`compact-center` 系スロットの追加より優先度は一段下です。

## 条件付きで検討する価値がある機能

本節は、用途拡大や周辺契約の成熟が前提になる場合にのみ検討価値がある機能を整理するものです。現時点で必須ではありませんが、将来の設計判断に備えて論点を残します。

### 1. landmark の明示ラベル入力

将来的に `ui-header` を app-shell 専用以外にも使う可能性があるなら、内部 `<header>` に対するアクセシブル名入力を検討する価値があります。たとえば、`aria-label` や `aria-labelledby` を host 側から受け取る形です。

ただし、top-level header 専用で固定するなら、この機能は不要です。したがって、適用範囲を広げる場合に限って検討します。

### 2. 外部入力型の scroll-state 反映

スクロール開始後に境界や背景の見え方を少しだけ変えたい場合、`scrolled` や `elevated` のような状態入力を受け取る案はあります。

ただし、header 自身が scroll 監視を始めると責務が重くなります。したがって、検討する場合でも次を守ります。

- scroll source は外部が管理しなければなりません（MUST）。
- header は反映先として property を受け取るだけに留めるべきです（SHOULD）。
- hide-on-scroll や reveal-on-scroll のような振る舞いまでは抱え込むべきではありません（SHOULD NOT）。

### 3. slot presence 状態の公開

`data-has-start`、`data-has-center`、`data-has-end` のような状態を内部または公開属性として持つ案はあります。これは、slot が空のときの余白調整や見え方安定化に寄与し得ます。

ただし、`part` を公開しない方針のままでは外部拡張価値は限定的です。そのため、公開機能としては優先度が高くありません。必要であれば、まず内部実装改善として扱う方がよいです。

### 4. 狭幅時の代替表示モード切り替え

`compact-center` 系スロットを導入した後であれば、`replace`、`hide` のような狭幅時代替ポリシーを簡潔に切り替える入力面を追加する余地があります。

ただし、これは slot 可視性制御と重なりやすいため、最初から詰め込みません。まずは専用スロットか表示ポリシーのどちらを主軸にするかを先に固定します。

### 5. wrapper 前提の環境対応補助

slot wrapper を正式に許容する方針を強めるなら、forced-colors などの環境対応を direct-slotted 要素前提から切り離す補助機能を検討できます。

ただし、これは header 単体の新機能というより、環境対応責務を zone 単位へ寄せる設計整理です。優先度は高くありません。

## 現行実装を踏まえて契約や機能で未だ対応していないもの

本節は、現行の `header.ts` と `header.stories.ts` を基準として、**文書上で方向性や検討価値に触れているが、実装としてはまだ提供していないもの**、および**公開契約としては定義したいが、実装で自動保証していないもの**を整理するものです。

### 1. 狭幅専用の文脈表示スロット

`compact-center`、`mobile-center`、`collapsed-center` のような狭幅専用スロットは現時点では存在しません。狭幅では `center` を単純に非表示にするのみです。

### 2. `sidebarExpanded` に代わる layout 指向 API

start 予約幅を sidebar 意味から切り離した API は現時点ではありません。公開入力は `sidebarExpanded` のみであり、layout 専用モードや予約幅そのものを表す入力は未提供です。

### 3. slot 単位の表示ポリシー入力

`centerVisibility` のような可視性ポリシー入力は存在しません。`center` の表示可否は `640px` の固定 breakpoint によってのみ切り替わります。

### 4. landmark の明示ラベル入力

内部 `<header>` に対して `aria-label` や `aria-labelledby` を host から受け取る公開入力はありません。top-level header 専用という運用前提で成立していますが、用途拡大に備えた入力面は未提供です。

### 5. 外部入力型の scroll-state 反映

`scrolled` や `elevated` のような、スクロール状態を外部から反映する property はありません。背景表現や境界強度は、テーマと環境メディアクエリによってのみ変化します。

### 6. slot presence 状態の公開

`data-has-start`、`data-has-center`、`data-has-end` のような状態は公開していません。slot の充足有無に応じた外部スタイル分岐は、現行契約ではサポートしません。

### 7. wrapper 前提の forced-colors 補助

forced-colors 時の補助境界は direct-slotted の `button` / `[role='button']` のみを対象とします。wrapper 配下まで一貫して補助する機構はありません。

### 8. `ui-header` の適用文脈の機械的制約

文書上は app-shell 文脈での使用を前提としていますが、実装がそれを機械的に強制するわけではありません。card 内や section 内に配置すること自体は技術的には可能であり、契約違反を実装が検出する機能はありません。

### 9. top-level header 一意性の保証

文書上は top-level header 専用とする方針を示していますが、ページ内の `ui-header` 個数を制約する実装はありません。複数配置を自動検出または拒否する機能は未提供です。

### 10. 高さ超過や多行内容の自動救済

header は固定高さ・単一行レイアウトですが、内容超過時の自動折り返し防止、切り詰め、再配置などを header 自身は行いません。これらはスロット内容側で解決する前提であり、header 側の救済機構は未提供です。

### 11. Story に対応する公開面のうち、視覚確認のみで止まっている項目

Forced Colors、Reduced Motion、Print、Dark Mode、Backdrop Saturation は Story 上で確認できますが、公開 API というより視覚回帰確認に留まります。環境別の差分を host property や属性で制御する入力面は現時点ではありません。

この節に記載した事項は、いずれも現時点での公開契約には含めません。採用する場合は、実装、Storybook、契約書を同時に更新します。

## 補足

`ui-header` の核は、多機能な操作バーを作ることではありません。**app-shell 上で start / center / end の意味秩序を固定し、状態は外部管理のまま、読書体験を乱さずに支えること**にあります。

したがって、今後の修正でも次の点は維持します。

1. app-shell 文脈で使うこと
2. `center` を視覚的中央へ固定すること
3. sidebar 状態機械を header へ持ち込まないこと
4. header を layout host として保つこと
5. child content の意味論を肩代わりしないこと
