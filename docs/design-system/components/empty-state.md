# Empty State

## 文書の位置づけ

本書は、`ui-empty-state` の公開契約、状態モデル、アクセシビリティ、視覚契約、および現行実装との差分を定義する契約文書です。

`ui-empty-state` は、一覧・検索結果・コンテンツ領域が空であること、または読み込み失敗などにより継続表示できないことを、**静かに、しかし明確に伝えるための状態提示コンポーネント**です。単に文言を中央寄せするだけではなく、**見出し・補足説明・行動導線・象徴表現**をどのような優先順位で配置するかを公開契約として固定します。

Rouault における empty state は、単に「何もない」ことを伝える要素ではありません。**次に何をすればよいかを過不足なく示しつつ、本文やナビゲーションの読書リズムを不必要に乱さないこと**を求めます。したがって、本コンポーネントの契約は、状況説明の明確さと、**「没入して読む」ことのできるデザイン**の維持を両立する方向で定義します。

また、`variant`、スロット構成、ライブリージョンとしての意味付け、アイコンとイラストレーションの優先規則、モーション抑制、高コントラスト対応は、都度の画面実装に委ねるのではなく、**状態契約と視覚契約**として定義します。

## 適用範囲

本書は、`ui-empty-state` の次の事項を対象とします。

- 公開契約
- 状態モデル
- DOM / Accessibility
- Visual Contract
- 環境別の振る舞い
- 関連契約
- 境界条件
- Storybook 契約
- 将来拡張の原則
- 現行実装で未対応の事項

一方で、本書は次の事項を扱いません。

- 各画面で empty state をいつ表示するかという画面遷移条件
- 検索失敗・権限不足・ネットワーク失敗などの業務的分類そのもの
- アクション押下後の処理内容
- 画像アセット自体の供給
- 国際化文言の管理方式
- ローディング状態や skeleton 表示の設計
- 画面全体のレイアウト責務

これらは上位レイヤまたは別コンポーネントの責務です。

## 公開契約

`ui-empty-state` は、`variant` を公開入力として扱います。スロットは `heading`、`description`、`action`、`icon`、`illustration` を持ちます。内部実装は Shadow DOM 内の構造を持ちますが、利用者は `ui-empty-state` を契約単位として扱います。

本書において `variant` は、**視覚トーンではなく状態種別を表す semantic kind** として扱います。`default`、`search`、`error` は単なる見た目の違いではなく、利用者へ伝えるべき空状態の意味分類です。したがって、色だけを変えるために `variant` を使うことには依存しません。

`variant` の既定値は `default` です。受理する正規値は `default`、`search`、`error` です。列挙外値は公開契約上の入力ではありません。無効値が与えられた場合、公開状態は正規値へ正規化されなければなりません（MUST）。

`heading` スロットは公開契約上の必須入力です。実装は見出し欠落時に描画を停止しないことがありますが、アクセシブルで意味のある empty state とするため、`heading` は必ず与えなければなりません（MUST）。

`description`、`action`、`icon`、`illustration` は任意です。`description` がない場合は見出しの下余白を調整し、`action` がない場合はアクション領域を描画に参加させません。`illustration` が与えられた場合は `icon` より優先され、アイコン領域は非表示となります。

ライブリージョンとして扱う対象は、**状態メッセージ領域**に限定します。通知対象は `heading` と `description` であり、`action` は状態通知の一部として扱いません。`aria-label` は自動生成しません。読み上げ内容は `heading` および `description` に含まれる可視テキストから構成されることを前提とします。

また、状態の意味そのものは `variant` だけで成立しません。`variant` は状態種別を表しますが、支援技術に伝えるべき状態の主内容は `heading` と、必要に応じた `description` に置かなければなりません（MUST）。

`ui-empty-state` は対話主体コンポーネントではありません。独自の公開メソッドは持たず、独自イベントも発火しません。利用者はホスト要素に対して imperative な制御 API や専用イベントを期待してはなりません（MUST NOT）。

### 入力契約

| 名前      | 種別                 | 必須   | 内容     | 契約                                                                                      |
| --------- | -------------------- | ------ | -------- | ----------------------------------------------------------------------------------------- |
| `variant` | property / attribute | いいえ | 状態種別 | semantic kind として `default` / `search` / `error` を受理します。既定値は `default` です |

### スロット契約

| 名前           | 種別       | 位置づけ | 個数契約      | 内容                                                             |
| -------------- | ---------- | -------- | ------------- | ---------------------------------------------------------------- |
| `heading`      | named slot | 必須入力 | 1 個          | 状態の主文言です。アクセシブルな状態通知の主たる入力です         |
| `description`  | named slot | 任意入力 | 0 または 1 個 | 状態の補足説明です。空または空白のみの場合は非表示として扱います |
| `action`       | named slot | 任意入力 | 0 個以上      | 次に取る行動を提示する操作要素です。複数配置を許可します         |
| `icon`         | named slot | 任意入力 | 0 または 1 個 | 状態を象徴する簡潔な視覚要素です                                 |
| `illustration` | named slot | 任意入力 | 0 または 1 個 | 状態をより広い文脈で示す視覚要素です。`icon` より優先します      |

`heading` スロットは、`h2`、`h3`、`h4` など、画面文脈に応じた見出し要素を受け取ることができます。見出しレベルはコンポーネント側で固定しません。利用側は文書アウトラインに整合する見出しレベルを選択しなければなりません（MUST）。また、`heading` は**単一の意味ブロック**として扱います。正規入力は 1 個の見出し要素、または 1 個の意味的に等価な単一ノードです。見出し内部での強調、インラインコード、ルビ等のインライン表現は許可しますが、複数の見出し、複数の兄弟ノード、複数段落、対話要素を同一 `heading` に並列配置する構成は正規入力ではありません。

`description` はテキストまたは段落要素を受け取りますが、意味のない空白文字のみを与える構成には依存しません。空白のみの場合は、内容なしとして扱います。`description` も**単一の意味ブロック**として扱い、正規入力は 1 個の短い説明文または 1 個の説明段落です。インライン強調、インラインコードは許可します。インラインリンクは**補助参照に限って**許可しますが、0 個または 1 個までとし、複数のリンクを並べる構成、リンクのみで説明の主意味を成立させる構成、主要導線や主要操作を `description` 内リンクへ委ねる構成は正規入力ではありません。複数の段落、複数の兄弟ブロック、リスト、表、主要操作ボタンを `description` に含める構成も正規入力ではありません。

`action` は単一要素に限定しません。複数の操作要素を並べることができ、狭い横幅では折り返しを許可します。ただし、正規入力は `button`、`a`、またはそれに準ずる対話要素です。プレーンテキストのみを `action` スロットへ与える構成は描画され得ますが、公開契約上の正規入力ではありません。

複数の `action` を与える場合、**DOM 順序を情報順位として扱います**。先頭要素が最上位アクションであり、後続要素は同順位または下位アクションです。視覚順序、フォーカス順序、読み上げ順序は DOM 順序を保たなければなりません（MUST）。折り返しが発生しても、順序意味は DOM 順序を基準に解釈します。

複数アクション時であっても、主要アクションは 1 個までに抑えるべきです。2 個以上の強い主要操作を同列に並べる構成は、empty state の情報順位を曖昧にするため推奨しません。`ui-empty-state` 自体はアクションの優先度を自動判定しないため、どの操作が第一候補かは利用側が DOM 順序と個別コンポーネントの見た目で明示しなければなりません（MUST）。

`icon` は単独の象徴表現を想定します。`illustration` が存在する場合、`icon` の内容は描画上抑止されます。利用者は、`illustration` と `icon` を同時に常時見せる構成に依存してはなりません（MUST NOT）。また、`icon` は補助的かつ非対話の視覚表現として扱います。主要操作や状態理解に必須の文言を `icon` のみに載せてはなりません（MUST NOT）。

`illustration` は `icon` より上位の補助表現ですが、こちらも非対話の視覚表現として扱います。主要操作や状態理解に必須の情報を `illustration` のみに依存してはなりません（MUST NOT）。

### 属性反映契約

公開入力のうち `variant` は property と attribute の両面から操作できます。

| property  | attribute | reflect | 備考                                                                                |
| --------- | --------- | ------- | ----------------------------------------------------------------------------------- |
| `variant` | `variant` | あり    | 列挙外値は公開契約上の入力ではありません。無効値は canonical な正規値へ正規化します |

### 列挙外値・無効値の扱い

`variant` は公開上 `default`、`search`、`error` の 3 値を契約とします。列挙外値が入力された場合、コンポーネントは公開状態を `default` へ正規化します。公開上の source of truth は常に正規値でなければなりません（MUST）。利用者は、無効値が内部だけで吸収され、属性や property に残存する構成に依存してはなりません（MUST NOT）。

### 責務範囲

責務範囲には、空状態の中心配置、見出し・補足説明・操作導線の構造化、ライブリージョンとしての意味付け、象徴要素の優先順位制御、バリアントに応じた色差、モーション抑制、および高コントラスト・印刷環境での表示調整を含みます。

一方で、どの画面で空状態へ遷移するか、どの失敗を `error` と定義するか、アクション押下後に何を実行するか、再試行回数や権限回復導線をどう設計するかは責務に含めません。また、画面全体の高さ確保やビューポート中央配置の責務も含めません。本コンポーネントは**割り当てられた領域の中で**中央寄せを行いますが、その領域の大きさを決めるのは上位レイアウトの責務です。

## 状態モデル

`ui-empty-state` の主要状態は、**どの状況を伝えるか、補助情報を持つか、操作導線を持つか、象徴要素をどの層で見せるか**によって読み分けます。

### 基本状態

最小状態は、`variant="default"` で、`heading` のみを持つ状態です。この状態では、余計な説明や操作を伴わず、空であることだけを簡潔に伝えます。

### 状態種別

`variant` は視覚差分の指定子ではなく、**empty state の状態種別**です。意味は次表のとおりです。

| `variant` 値 | 意味           | 想定用途                                   |
| ------------ | -------------- | ------------------------------------------ |
| `default`    | 中立的な空状態 | 初期状態、未作成、未配置                   |
| `search`     | 検索結果なし   | 検索語に一致する結果が存在しない状態       |
| `error`      | 失敗状態       | 読み込み失敗、取得失敗、再試行が必要な状態 |

`variant` は状態意味を表す契約であり、業務上の厳密分類そのものは担いません。たとえば `error` は「失敗である」という意味種別を示しますが、失敗原因の分類や復旧戦略は別契約です。

### 通知領域状態

通知対象は `heading` と `description` から成る状態メッセージ領域です。`action` は通知領域に含めません。したがって、状態変化として支援技術へ伝えるべき内容は、操作ラベルではなくメッセージ本文に載せます。

### 説明有無状態

`description` に可視テキストが存在する場合、内部的に説明あり状態として扱われます。説明が存在しない場合、説明領域は非表示となり、見出し直後の余白は説明なし前提の値へ切り替わります。

空白文字のみの `description` は説明ありとは見なしません。

### アクション有無状態

`action` に要素または可視テキストが存在する場合、アクション領域は表示されます。要素が存在しない場合、アクション領域は非表示となります。

複数の `action` を与えた場合、アクション領域は `flex-wrap: wrap` により折り返し可能な配置を取ります。正規入力として扱う操作数は 0 個から 2 個までです。3 個以上は描画され得ますが、公開契約上の正規入力ではありません。

### 象徴要素状態

象徴要素は `illustration` と `icon` の 2 層を持ちます。優先順位は次のとおりです。

1. `illustration` が存在する場合は `illustration` を表示します。
2. `illustration` が存在しない場合は `icon` を表示します。
3. `icon` も存在しない場合は中立的なフォールバックアイコンを表示します。

フォールバックアイコンは状態意味を担う本体ではなく、象徴要素が未指定であることを埋める中立的な placeholder です。

### 見出し欠落状態

`heading` に可視テキストが存在しない場合でも描画は継続することがありますが、これは契約違反状態です。長期的には開発時エラー相当として扱うべき入力であり、互換性を保証しません。

### スロット同期状態

本コンポーネントは、初回描画後および各スロットの再割当に応じて、`heading`、`description`、`action`、`illustration` の内容を再評価します。したがって、スロット内容の動的追加・削除に追従し、説明領域やアクション領域の表示有無、象徴要素の優先関係は再同期されます。

一方で、割り当て済みノード内部の任意の深い変更すべてに対する追従までは公開契約に含めません。追従保証はスロット再割当を基準とします。

## DOM / Accessibility

ルートは `:host` です。Shadow DOM 内部に単一の `<section class="container">` を持ち、その内部を**通知領域**と**操作領域**へ分離します。`illustration`、`icon`、`heading`、`description` は通知領域に属し、`actions` は通知領域の外に置きます。

```text
<ui-empty-state>
  #shadow-root
    <section class="container" data-variant="...">
      <div class="message" role="status" aria-atomic="true">
        <div class="illustration" aria-hidden="true">
          <slot name="illustration"></slot>
        </div>
        <div class="icon" aria-hidden="true">
          <slot name="icon">
            <iconify-icon class="fallback-icon"></iconify-icon>
          </slot>
        </div>
        <div class="heading" id="empty-state-heading">
          <slot name="heading"></slot>
        </div>
        <div class="description" id="empty-state-description">
          <slot name="description"></slot>
        </div>
      </div>
      <div class="actions" aria-labelledby="empty-state-heading">
        <slot name="action"></slot>
      </div>
    </section>
</ui-empty-state>
```

### Accessibility 契約

アクセシビリティ上の重要点は次のとおりです。

- `role="status"` と `aria-atomic="true"` は通知領域にのみ適用します。
- `action` はライブリージョンの本文に含めません。
- `aria-label` は自動生成しません。
- 読み上げ内容は `heading` と `description` の可視テキストに依存します。
- 状態理解に必須の意味は `heading` と、必要に応じた `description` に置き、`icon` や `illustration` のみに依存しません。
- `icon` 領域は `aria-hidden="true"` であり、象徴表現はアクセシブル名の主入力として扱いません。
- `illustration` も既定では装飾的な補助表現として扱い、`aria-hidden="true"` 相当の扱いとします。
- `variant` は状態種別を表しますが、それ単独で支援技術向けの意味変化を保証しません。
- `heading` は必須です。文書アウトラインに適した見出しレベルは利用側が選択します。
- `action` に配置する操作要素は、利用側で個別にキーボード操作可能でなければなりません（MUST）。

本コンポーネントで重要なのは、**空状態を視覚的に中央へ置くこと**ではなく、**状態変化を支援技術でも一貫して伝えられること**です。したがって、見出し欠落や `aria-label` 自動補完に依存した設計は採りません。

### 内部派生状態

説明有無、アクション有無、イラスト有無などの派生状態は内部描画制御のための内部状態です。これらは公開入力ではなく、ホスト属性として外部へ観測可能な API にしません。利用者は派生状態へ依存して外部ロジックや CSS を組んではなりません（MUST NOT）。

## Visual Contract

`ui-empty-state` の視覚契約は、空状態を**中央寄せされた静かな状態提示**として成立させることにあります。強いプロモーションや警告バナーではなく、**読む流れの中断を最小限に抑えつつ、必要な意味差だけを見せること**を目的とします。

### 情報順位

- 見出しは主情報です。
- 説明文は見出しの補足です。
- アクションは必要な場合にのみ表示される導線です。
- イラストレーションは文脈説明が必要なときの上位象徴表現です。
- アイコンは簡潔な象徴表現です。

したがって、視覚的主役は常に `heading` です。`illustration` や `icon` は状態理解を補助しますが、本文や見出しの可読性を奪うほど強調してはなりません。

### レイアウト

ホストは縦方向の flex コンテナとして振る舞い、内容は中央揃え・中央寄せとします。内部 `.container` は全幅を取りつつ、各領域を縦方向に積み上げます。ただし、この中央寄せはコンポーネントに割り当てられた領域の中でのみ成立します。画面全体の中央に見せるために必要な高さ確保は上位レイアウトが担います。

`illustration` は上部に配置し、最大幅は `--empty-state-illustration-max-width` で制御できます。`description` は `40ch` を上限とし、長文が広がり過ぎないように制御します。`actions` は中央揃えの横並びを基本とし、必要に応じて折り返します。

### 視覚仕様

- `default` は中立的な文字色・補助色で構成します。
- `search` は `icon` に控えめな色差を与えます。
- `error` は `icon` と `heading` を警告系の色へ切り替えます。
- `description` は見出しより一段弱い文字色で補助情報として見せます。
- `icon` は本文より弱く、補助情報として視認できる強度に保ちます。

`error` であっても、警告バナーのような過度な圧迫感には寄せません。Rouault の文脈では、失敗状態も**読書面のノイズを抑えた形で伝えること**を優先します。

### モーション

ホスト要素は登場時に `empty-state-enter` アニメーションを持ちます。これは `opacity` と `translateY(var(--space-2, 8px))` による軽い出現です。ただし、動きは状況理解を補助する最小限にとどめ、注意喚起そのものをアニメーションへ依存させません。

### スタイル拡張面

公開されたスタイル拡張面は限定します。コンポーネント固有の公開 CSS Custom Property は `--empty-state-illustration-max-width` です。利用者は、コンポーネント単位で意味を持つ上書きは、このような専用プロパティを通じて行います。

一方で、`--fg-*`、`--space-*`、`--text-*`、`--icon-*` などは基盤トークン参照です。これらはデザインシステム全体の値として解決されるものであり、`ui-empty-state` 固有 API としては扱いません。

### 参照トークン

本コンポーネントは、主として次のトークンに依存します。

| 用途                     | トークン                                              |
| ------------------------ | ----------------------------------------------------- |
| 見出し色                 | `--fg-default`                                        |
| 説明文色                 | `--fg-muted`                                          |
| search アイコン色        | `--fg-subtle`                                         |
| error 見出し・アイコン色 | `--fg-danger`                                         |
| 余白                     | `--space-2` / `--space-3` / `--space-4` / `--space-6` |
| 文字サイズ               | `--text-lg` / `--text-sm`                             |
| フォント太さ             | `--font-semibold` / `--font-normal`                   |
| 行間                     | `--line-height-tight` / `--line-height-normal`        |
| アイコン寸法             | `--icon-xl` / `--icon-lg`                             |
| 動き                     | `--duration-normal` / `--ease-out`                    |
| イラスト最大幅           | `--empty-state-illustration-max-width`                |

## 環境別の振る舞い

### Reduced Motion

`prefers-reduced-motion: reduce` 環境では、登場アニメーション時間を極小化し、反復回数を 1 回に固定します。状態認識を動きに依存させません。

### Forced Colors

`forced-colors: active` 環境では、`icon` に `GrayText` を使用し、`error` の `icon` および `heading` は `CanvasText` へフォールバックします。独自色の意味差よりも、システム配色下での可読性を優先します。

### Print

`@media print` では `icon` と `actions` を非表示にします。印刷物では操作導線と象徴アイコンの優先度が低く、見出しと説明文のみが残ればよいという判断です。

したがって、印刷後も `heading` 単独、または `heading` と `description` によって状態の主意味が成立しなければなりません。復旧手順や補助説明を紙面に残す必要がある場合は、`action` ではなく `description` 側に置きます。

### Dark Surface

暗色背景上でも、見出しと説明文のコントラストは WCAG AA 相当の可読性を満たすことを前提とします。色そのものはトークン差し替えで吸収します。

## 関連契約

### アクション要素契約

`ui-empty-state` 自身はアクションの意味や挙動を定義しません。`action` スロットに何を置くかは利用側責務です。ただし、次を満たします。

- アクション要素はキーボード操作可能でなければなりません（MUST）。
- 主要操作が存在する場合でも、本文や見出しの読書リズムを奪う過剰な装飾に依存しません。
- 正規入力として扱うアクション数は 0 個から 2 個までです。
- 複数アクションを置く場合、情報順位は DOM 順序で明示しなければなりません（MUST）。
- 先頭アクションが第一候補です。後続アクションは補助または代替の位置づけとして扱います。
- 主要アクションは 1 個までです。2 個目を置く場合は secondary action として扱います。
- 3 個以上のアクションは描画され得ますが、公開契約上の正規入力ではありません。
- 折り返し後の見た目が複数行になっても、優先順位は表示行ではなく DOM 順序で解釈します。

### 見出し・説明文契約

`heading` と `description` は、どちらも**単一の意味ブロック**として扱います。これは「ノード数」ではなく、「利用者が 1 つの文または 1 つの短い説明として読めるか」を基準にします。

- `heading` は 1 個の主見出しです。
- `heading` はインライン表現を含められますが、複数の見出し、複数の兄弟ノード、対話要素を含みません。
- `description` は 1 個の短い説明ブロックです。
- `description` は 0 個または 1 個の補助的なインラインリンクを含められます。
- `description` 内リンクは参照、詳細説明、補助ヘルプへの導線に限定します。
- `description` 内リンクは主要導線、主要操作、唯一の復旧手段を担いません。
- `description` は複数段落、リスト、表、主要操作群、複数リンク群を含みません。
- 実装上描画できることと、公開契約上保証することは同一ではありません。複数兄弟ノードや複数ブロックが描画されても、それは互換性を保証する入力ではありません。

この制約は、empty state を「小さな状態提示ユニット」として保つためのものです。説明責務が大きくなる場合は、上位コンポーネントへ分離します。

### 説明文内リンク契約

`description` 内のリンクは、empty state の意味を補助する**補助参照導線**としてのみ扱います。これは `action` スロットの代替ではありません。

- `description` に含められるインラインリンクは 0 個または 1 個です。
- リンクは短く、単独でも意味が取れるテキストでなければなりません（MUST）。
- リンクは詳細説明、ヘルプ、設定説明、関連文書などの補助参照先を指します。
- リンク先へ進まなくても、empty state の主意味と第一行動は理解できなければなりません（MUST）。
- 主要な復旧導線、再試行導線、作成導線は `action` に置きます。
- `action` が存在する場合、`description` 内リンクはそれより上位の導線として扱いません。
- 複数リンク、リンクだけが意味の中心になる文、リンクをボタン代わりに見せる構成には依存しません。
- 新しいタブを開くこと自体を禁止しませんが、リンク挙動の特殊性に empty state の理解を依存させません。

この制約は、説明文が操作群へ変質することを防ぎ、読書面に近い静かな状態提示を維持するためのものです。

### アイコン契約

`icon` スロットは簡潔な象徴表現を受け取ります。内容は通常、装飾的かつ補助的なものとして扱い、読み上げ名の主入力にはしません。

フォールバックアイコンは中立的な placeholder です。これは empty state の主意味を担うものではなく、象徴要素が未指定であることを補う補助表現にすぎません。利用側は必要に応じて `icon` または `illustration` を明示します。

### イラストレーション契約

`illustration` は `icon` より上位の視覚表現ですが、既定では装飾的な補助表現として扱います。イラストレーション自体に状態理解の必須情報を担わせません。イラストレーションが存在する場合、`icon` は表示されません。

### スタイル拡張契約

`ui-empty-state` は `::part` を公開しません。外部からの主な拡張面は、公開した CSS Custom Properties とスロット内容そのものです。

利用者は、内部 class 名、`data-variant`、内部派生状態、Shadow DOM 構造などの内部識別子に依存してはなりません（MUST NOT）。将来変更時に互換性を保証しません。

### 公開イベント・公開メソッド契約

`ui-empty-state` は独自の公開イベントを発火しません。また、公開メソッドも持ちません。利用側が監視すべきイベントや imperative API は、`action` スロットへ与えた要素側の契約に属します。

### 開発時警告契約

`heading` に可視テキストが存在しない場合、実装は開発時に警告を出し得ます。これは利用側へ契約違反を知らせる補助手段であり、描画停止や例外送出を意味しません。

## 境界条件

### 見出しのみ

`heading` のみを与えた場合、最小構成の empty state として描画します。説明文とアクションは表示されません。

### 説明文あり

`description` に可視テキストがある場合、見出しの下に補足説明を表示します。説明文は最大 `40ch` で折り返します。

### 空白のみの説明文

`description` が空白文字のみで構成される場合、内容なしとして扱います。説明領域は表示されず、`description` があることを前提とした余白にも依存しません。

### アクションなし

`action` が存在しない場合、アクション領域は表示されません。

### 複数アクション

複数の `action` を与えた場合でも表示を継続します。狭い幅では折り返しを許可します。ただし、優先順位は DOM 順序で解釈します。先頭要素が第一候補であり、後続要素は補助または代替導線です。正規入力は 2 個までとし、3 個以上は非正規入力です。

### `illustration` と `icon` の併存

両方を与えた場合、`illustration` を優先し、`icon` は非表示となります。両者同時表示には依存しません。

### `icon` 未指定

`icon` が指定されない場合でも、中立的なフォールバックアイコンを描画します。ただし、`illustration` が存在する場合はこのフォールバックも表示されません。フォールバックは主意味を担いません。

### 見出し欠落

`heading` が欠落した場合でも描画は継続しますが、アクセシブルな empty state としては契約違反です。実装は警告を出し得ます。

### 複数の `heading` ノード

複数の見出しノードまたは複数の兄弟ノードを `heading` に与えた場合、描画が継続することはあり得ますが、公開契約上は非正規入力です。単一の主見出しとしての意味保証は行いません。

### 複数の `description` ブロック

複数段落、複数の兄弟ブロック、リスト、表などを `description` に与えた場合、描画が継続することはあり得ますが、公開契約上は非正規入力です。単一の短い説明ブロックとしての意味保証は行いません。

### 複数の主要アクション

複数の `action` を配置すること自体は許可しますが、複数の主要アクションを同列に置く場合、`ui-empty-state` はどれが第一候補かを自動判定しません。先頭要素を第一候補とみなす以外の意味保証は行いません。

### 補助リンクを含む説明文

`description` に補助的なインラインリンクを含めることはできますが、0 個または 1 個までとします。そのリンクを主要導線として扱う構成には依存しません。主要導線は `action` に置きます。

### 複数の説明文内リンク

`description` に複数のインラインリンクを含めた場合、描画が継続することはあり得ますが、公開契約上は非正規入力です。補助参照としての静かな説明文という性質を保証しません。

### リンクのみで成立する説明文

`description` が実質的にリンクのみ、またはリンク先へ遷移しなければ意味が成立しない文で構成される場合、公開契約上は非正規入力です。empty state の主意味はリンク先に依存しません。

### 無効な `variant`

無効な `variant` が与えられた場合、公開状態は `default` へ正規化されます。利用者は、無効値が内部だけで吸収され、属性や property に残る構成に依存してはなりません（MUST NOT）。

### 3 個以上のアクション

3 個以上の `action` を与えた場合、描画が継続することはあり得ますが、公開契約上は非正規入力です。小さな状態提示ユニットとしての情報順位を保証しません。

## 補足

`ui-empty-state` の要点は、単なる「空です」という表示ではありません。**状態の意味を短い構造へ圧縮し、必要なら次の行動へつなぎ、それでも本文の読書リズムを壊し過ぎないこと**にあります。

したがって、今後の変更でも次の 6 点は崩さない方がよいです。

1. `heading` を主情報とすること。
2. ライブリージョンの対象を状態メッセージ領域に限定すること。
3. `variant` を視覚トーンではなく状態種別として扱うこと。
4. `illustration` が `icon` より優先され、かつ既定では装飾的補助表現に留まること。
5. `description` や `action` の有無をスロット再割当に追従して同期すること。
6. 内部派生状態を公開 API にしないこと。

## 将来拡張の原則

本節は現行実装の公開契約ではなく、将来追加を検討する場合の設計指針です。追加機能は、empty state を多機能化するためではなく、**空状態の意味伝達をより明確にしつつ、読書面の静けさを保つ場合に限って**採用します。

### 最優先で検討する価値がある拡張

#### ライブリージョン強度の公開制御

通知強度を画面側で厳密制御したい場合、状態メッセージ領域に対して `aria-live` 相当の公開制御を追加検討する価値があります。

この拡張を採用する場合、次を満たします。

- 既定値は現行と同等の穏やかな通知強度を保ちます。
- 通知対象はあくまで状態メッセージ領域に限定します。
- 画面単位で不要な再通知を増やしません。
- エラー時のみ過剰に通知強度を上げる設計には慎重であるべきです。

#### 状態種別ごとの既定アイコン規則

現行のフォールバックアイコンは中立的な placeholder ですが、`search` や `error` では状態種別に応じた既定アイコン規則を持たせる拡張に価値があります。これは主意味を補う補助表現としてのみ扱います。

この拡張を採用する場合、次を満たします。

- 利用者が明示した `icon` は常に優先します。
- `illustration` 優先規則は維持します。
- 既定アイコンは主意味を担わず、`heading` と `description` の代替になりません。
- 状態差が視覚ノイズではなく意味差として機能する場合に限定します。

### 条件付きで価値がある拡張

#### `sm` サイズバリアント

サイドバー、カード内、小さな補助領域などで empty state を使う必要がある場合に限り、`sm` のみのサイズバリアントには価値があります。ただし、通常の読書面ではレイアウト側で吸収する方がきれいです。

この拡張を採用する場合、次を満たします。

- `md` を既定サイズとし、追加は `sm` に限定します。
- `lg` など強い拡大型は追加しません。
- 情報順位、アクセシビリティ、DOM 構造は既定サイズと同一に保ちます。
- 単なる装飾差ではなく、コンテナ密度の差を吸収するためにのみ使います。

#### `action-group-label` 相当の補助契約

複数アクションを持つ場合、操作群の意味付けを補助する契約は条件付きで価値があります。ただし、通常の empty state では過剰設計になり得ます。

この拡張を採用する場合、次を満たします。

- 単一アクション時の簡潔さを損ないません。
- アクション群の情報順位は上位レイヤで管理します。
- empty state 自体にボタン群の複雑な制御責務を持ち込みません。
- 支援技術向けの補助意味付けに用途を限定し、視覚構造の複雑化に使いません。

### 採用しない方針

次の方向は、状態提示コンポーネントの責務を汚しやすいため採りません。

- empty state 自体に非同期取得や再試行ロジックを内蔵すること
- `variant` を無制限に増やし、画面固有の業務分類をすべて受け持たせること
- `subtitle`、`footer`、`meta` などの補助スロットを増やすこと
- `alignment`、`fullHeight` などレイアウト責務を持ち込むこと
- 内部 class や派生属性を公開 API として扱うこと
- アイコンとイラストレーションを同時表示する複雑な装飾モードを標準化すること

## 現行実装で未対応の事項

本節は、現行の `empty-state.ts` および `empty-state.stories.ts` を基準として、**契約書内で将来拡張または厳密化対象として触れているが、現時点では未実装、未強制、または未整合である事項**を整理するものです。

### 見出し必須の実行時強制

契約上 `heading` は必須ですが、現行実装は欠落時に警告を出すのみで、描画停止や例外送出は行いません。したがって、**見出し必須は公開契約としては強いが、実行時強制は未実装**です。

### ライブリージョンの領域分離

現行実装はホスト全体へ `role="status"` と `aria-atomic="true"` を付与しており、通知領域と操作領域を DOM 上で明確に分離していません。したがって、**通知対象を状態メッセージ領域へ限定する契約は、現時点では未実装**です。

### `aria-live` の明示制御

現行実装は `role="status"` と `aria-atomic="true"` を付与しますが、`aria-live` の明示制御は公開していません。通知強度は暗黙的な `status` に委ねています。

### `variant` の canonicalization

本書では無効 `variant` を canonical な正規値へ正規化する契約を置きますが、現行実装は内部解決値と公開状態が分離し得ます。したがって、**公開状態を常に正規値へ戻す canonicalization は未実装**です。

### 派生状態の非公開化

現行実装は `has-description`、`has-action`、`has-illustration` をホストへ付与し得ます。本書では内部派生状態を公開 API にしない方針としますが、**ホストから内部派生状態を隠す構造は未実装**です。

### イラストレーションの装飾専用化

本書では `illustration` を既定で装飾的補助表現として扱いますが、現行実装はそのアクセシビリティモードを強制していません。したがって、**装飾専用としての実行時保証は未実装**です。

### 公開イベント・公開メソッドなしの明文化対応

本書では独自イベントと公開メソッドを持たない契約を明文化しますが、現行 Storybook やテストはこの非存在契約を明示的には固定していません。

### アクションスロットの対話要素限定

本書では `action` の正規入力を `button`、`a`、またはそれに準ずる対話要素に限定します。しかし、現行実装は `slot="action"` に対して要素の種別を検証せず、プレーンテキストのみであっても `has-action` を立てて表示対象として扱い得ます。したがって、**アクションスロットを対話要素に限定する実行時強制は未実装**です。

### 複数アクション時の優先順位と最大数の実行時強制

現行実装は複数 `action` を受理できますが、先頭要素を第一候補として扱うという契約や、正規入力を 2 個までとする契約を、見た目や属性として実行時強制する仕組みは持ちません。**複数アクション時の意味秩序と最大数制約は文書契約としては定義できても、実装側の強制は未対応**です。

### 見出し・説明文の単一意味ブロック強制

本書では `heading` と `description` を単一意味ブロックとして定義しますが、現行実装は複数兄弟ノードや複数ブロック入力を実行時に拒否しません。したがって、**単一意味ブロック制約は契約としては定義できても、実行時強制は未対応**です。

### `icon` / `illustration` の個数制約

本書では `icon` と `illustration` をそれぞれ 0 または 1 個の入力として扱います。しかし、現行実装は `slot="icon"` および `slot="illustration"` の割当数を検証せず、複数ノードが割り当てられた場合もそのまま描画し得ます。したがって、**象徴要素の個数制約は契約として定義できても、実行時強制は未対応**です。

### 説明文内リンク規則の実行時強制

本書では `description` 内リンクを 0 個または 1 個の補助参照導線に限定しますが、現行実装はリンク数、リンクの役割、主要導線との優先順位を実行時に検証しません。したがって、**説明文内リンク規則は契約としては定義できても、実行時強制は未対応**です。

### スロット同期の追従範囲の固定

本書では追従保証をスロット再割当基準に限定しますが、現行 Storybook や実装説明ではその境界が明示的に固定されていません。

### Storybook / Autodocs の旧契約残存

現行 Storybook には、ライブリージョンの領域分離、`variant` の canonicalization、内部派生状態の非公開化、イラストレーションの装飾専用化、複数アクションの最大数規則、見出し・説明文の単一意味ブロック規則、説明文内リンクの件数・役割・優先順位規則、公開イベント・公開メソッドなしの契約などを確認する Story は存在しません。

それだけでなく、現行 Storybook / Autodocs には**本書の現行契約と逆向きの前提**が残っています。`variant` はなお "Visual variant" と説明され、Docs 説明も host 全体の `role="status"` / `aria-atomic="true"` を前提にしています。また、`Default` や `DynamicSlotStateSync` などの play test は host 上の `role`、`aria-atomic`、`has-description`、`has-action`、`has-illustration` を検証しており、`BoundaryConditions` では 3 個のアクション折り返しを正常系として扱っています。したがって、**Storybook / Autodocs は未対応であるだけでなく、一部で旧契約を固定している状態**です。
